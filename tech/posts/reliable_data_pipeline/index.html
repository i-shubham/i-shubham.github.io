What actually makes a data pipeline reliable?

A green Airflow run is not the same thing as correct data. This is the checklist I wish someone had handed me after the third “pipeline succeeded, dashboard is wrong” incident.

Shubham Mallick Data Engineering ~12 min read

The first pipeline I thought was “done” finished every night at 02:14, wrote Parquet to S3, and updated a dashboard by morning. Ops loved it. Finance did not. On the third consecutive Monday, revenue was off by roughly 8%. The job had succeeded. The data had not.

That gap — between ran and can be trusted — is where most reliability work actually lives. Retries, bigger clusters, and prettier DAGs help. They are not the core.

The pipeline people draw vs the one that breaks

On a whiteboard, every pipeline looks like this:

In production, the interesting questions sit on the edges: What if yesterday’s file arrives at 10am today? What if the same event is published twice? What if a column changes type without warning? What if Tuesday’s job overwrites Monday’s partition with a partial run?

1. Idempotency beats “retry until green”

If a task can run twice and leave the warehouse wrong, retries are a liability. I treat every write path as something that must survive an accidental re-run on the same day.

A pattern that has held up for me:

  • Stage into a dated run folder / temp table first.
  • Validate row counts, key uniqueness, and null rates.
  • Only then swap / merge into the published partition.

Natural keys matter here. If your only unique key is “whatever Spark generated this run,” you will invent duplicates the first time a task retries after a partial write.

2. Late data is normal. Pretending otherwise is not.

Batch windows lie. Mobile apps go offline. Partner SFTP drops land late. CDC lags. If your job assumes “all of yesterday is present at 01:00,” you will eventually publish a confident wrong number.

Two practical habits:

  • Watermarks, not vibes. Decide how late you wait (say 6 hours), then explicitly reopen / correct earlier partitions when stragglers arrive.
  • Separate freshness from completeness. A dashboard can show “data through 06:00, 97% complete” instead of silently looking finished.

3. Schema drift fails quietly before it fails loudly

The worst schema changes are not the ones that crash the job. Those are annoying and obvious. The dangerous ones cast amount to string, drop a nested field, or start sending null for a previously required attribute while every task still exits 0.

I keep a cheap contract check at the boundary:

expected:
  order_id: string, required
  amount:   decimal, required, > 0
  currency: enum[USD, EUR, INR]

reject or quarantine when:
  - required field missing
  - type no longer parses
  - new field appears in a critical path without an owner

You do not need a perfect governance platform on day one. You need a gate that stops bad shape from becoming “truth” in curated tables.

4. Backfills are part of the product

If fixing last month means manually editing five notebooks and praying about partition order, the pipeline is not reliable. It is fragile with good intentions.

Design for recomputation early:

  • Partition by a stable business date, not “whatever day the job ran.”
  • Keep transforms pure enough that re-running dt=2026-07-01..2026-07-31 produces the same curated result.
  • Record which code version / job run produced each published partition.

5. Watch the data, not only the DAG

Airflow saying success answers one question: did the scheduler believe the operators finished? Useful. Insufficient.

The signals that have caught real issues for me:

  • Row count vs 7-day baseline for each critical table
  • Distinct primary keys vs total rows (duplicate detector)
  • Null rate on money / status / foreign-key columns
  • Freshness: max event time or max load time
  • Downstream reconcile: warehouse total vs source-system control total

When those stay green, I sleep better than when the DAG UI is merely decorative and green.

A boring reliability checklist

Before calling a pipeline production-ready, I want honest answers to:

  1. Can I re-run yesterday without creating duplicates?
  2. Do I know what “complete for date D” means in writing?
  3. What happens when 5% of events arrive tomorrow?
  4. Who gets paged when volume drops 40% but the job succeeds?
  5. Can a new engineer backfill one week without a Slack archaeology session?

If those answers are fuzzy, the architecture diagram does not matter yet.

Closing

Reliable pipelines are less about clever frameworks and more about unglamorous guarantees: idempotent writes, explicit lateness rules, schema gates, recomputable history, and checks on the data itself.

Get those right and the stack choice becomes a detail. Skip them and every new tool just fails with better branding.
