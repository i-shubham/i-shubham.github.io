Design a schema for multi-tenant SaaS

Tenancy is a product and ops decision dressed as a schema choice — isolation, cost, and migrations all pull different directions.

60-minute agenda

How I'd open the discussion

I'd open by asking how many tenants we expect and how much variance in size they'll have. A B2B SaaS with 50 enterprise clients is a completely different animal from a platform with 200,000 SMBs. The former can tolerate DB-per-tenant; the latter cannot.

Then I'd ask about compliance — do any tenants require data residency in a specific region, or SOC-2 isolation guarantees? That single question can eliminate shared-table as an option for some cohorts. I've seen teams build a shared model and then retrofit isolation for one whale customer, which is painful.

Finally I'd discuss the migration story. Schema-per-tenant sounds clean until you need to ALTER TABLE across 2,000 schemas and some of them are on Postgres 12 replicas that lag 30 seconds behind.

Open questions worth asking

  • How many tenants day-one and at steady state (hundreds vs hundreds of thousands)?
  • What is the size distribution — are 5% of tenants 90% of data?
  • Do any tenants require dedicated infrastructure for compliance?
  • Are there cross-tenant queries (analytics, admin dashboards)?
  • How frequently do we run DDL migrations?
  • What is the target onboarding latency for a new tenant?
  • Do tenants need independent backup and restore?
  • Is there a free tier that should have minimal operational cost?
  • Will we support tenant-specific feature flags at the DB level?
  • What database engine are we on — Postgres, MySQL, managed cloud?

Scope I'd lock first

  • In: schema layout, tenant isolation, index strategy, migration workflow.
  • Out: application-layer auth, billing, UI multi-tenancy.
  • Out: full sharding strategy (separate problem).

Isolation

Performance

Migration safety

Data model

sql
CREATE TABLE tenants (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    plan        TEXT NOT NULL DEFAULT 'free',
    region      TEXT NOT NULL DEFAULT 'us-east-1',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    tenant_id   UUID NOT NULL REFERENCES tenants(id),
    id          UUID NOT NULL DEFAULT gen_random_uuid(),
    customer_id UUID NOT NULL,
    status      TEXT NOT NULL DEFAULT 'pending',
    total_cents BIGINT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, id)
);

-- Row-Level Security
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.current_tenant')::UUID);

CREATE INDEX idx_orders_tenant_status ON orders (tenant_id, status, created_at DESC);

Approach / design notes

There are three classic models. Shared table: all tenants in one table, discriminated by a tenant_id column. Schema-per-tenant: each tenant gets its own Postgres schema inside a shared database. DB-per-tenant: each tenant gets a dedicated database or cluster. The right answer is almost always a hybrid.

For the shared-table path, the tenant_id must be the leading column in every composite primary key and every index. Postgres RLS enforces isolation at the engine level — even a buggy application query cannot leak data. The cost is that every query plan includes a tenant_id filter, and the planner must have accurate per-tenant statistics.

Schema-per-tenant gives stronger isolation without the operational cost of separate databases. Each schema has identical DDL, so migrations run in a loop. The downside is connection management: PgBouncer or pgpool must set search_path per connection, and schema count above 10,000 starts hurting catalog performance.

DB-per-tenant is the nuclear option — full isolation, independent backups, per-tenant scaling. But operational cost scales linearly with tenant count. I've used this for regulated enterprises (healthcare, finance) where a shared-anything model fails an audit.

The hybrid I prefer: shared table for free and standard tiers, schema-per-tenant for premium, DB-per-tenant for enterprise. A routing layer resolves tenant_id to the correct connection pool. This lets you optimize cost for the long tail and isolation for the whales.

Deep dive (spend 15–25 minutes here)

Let's walk through shared-table RLS in Postgres. When a request arrives, the app sets a session variable: SET app.current_tenant = 'uuid-here'. The RLS policy on each table says USING (tenant_id = current_setting('app.current_tenant')::UUID). Every SELECT, UPDATE, and DELETE is automatically filtered — even a rogue SELECT * FROM orders returns only that tenant's rows.

The gotcha is superuser and table owner bypass RLS by default. You must create a restricted application role and GRANT it only the needed privileges. SET ROW SECURITY FOR the role, or use FORCE ROW LEVEL SECURITY on the policy. Miss this, and your admin dashboard leaks all tenants.

Index design matters more than people think. A naive index on (status) means the planner scans 500M rows for one tenant's 'active' orders. The composite index (tenant_id, status, created_at DESC) turns that into an index-only scan over ~2,500 rows. I've seen 400× speedups just from fixing index prefix order.

Migration strategy: for shared tables, standard ALTER TABLE applies to everyone at once — good for adding nullable columns. For schema-per-tenant, you loop over schemas and run the DDL inside a transaction per schema. If schema 1,247 fails, you roll back that one and continue. A migration status table tracks which schemas have been upgraded, enabling idempotent retries. For DB-per-tenant, you treat it like a fleet deployment: rolling upgrades with canary tenants first.

Noisy-neighbor mitigation in shared tables: set statement_timeout per tenant plan (free: 5s, pro: 30s). Use pg_stat_statements to identify tenants generating disproportionate load. In extreme cases, move the offending tenant to its own schema or database — your hybrid routing layer makes this a config change, not a code change.

Request path / sequence

Trade-offs I'd say out loud

Shared table vs schema-per-tenant

Lower cost and simpler ops vs stronger isolation and easier per-tenant backup.

RLS vs application-level filtering

RLS is defense-in-depth but adds ~2-5% overhead per query; app filtering is faster but one bug leaks data.

Composite PK (tenant_id, id) vs surrogate PK

Composite enables partition pruning and co-located indexes; surrogate simplifies ORM mapping.

Connection pooling

PgBouncer in transaction mode is mandatory at scale but breaks SET commands — use SET LOCAL inside transactions.

Where it usually breaks

  • Forgetting to set tenant context before a query — RLS returns empty set or wrong tenant's data.
  • Superuser bypassing RLS by default; must use a restricted app role.
  • Index missing tenant_id as leading column — full table scan on 500M rows.
  • Schema-per-tenant with 50,000 schemas — catalog bloat crashes pg_dump.
  • Migrations that lock a shared table for ALTER — blocks all tenants.
  • Not testing RLS with the actual app role during development.

Follow-ups if time remains

  • How would you implement per-tenant rate limiting at the database level?
  • What monitoring would you add to detect noisy neighbors early?
