Build an audit trail without killing write throughput

Audit logs that share the OLTP transaction look correct until they double write latency — or get rolled back with the business row.

60-minute agenda

How I'd open the discussion

I've built audit trails two ways and learned the hard way that the first instinct — a trigger that inserts into an audit table inside the same transaction — is correct for consistency but murders write throughput. Every business INSERT becomes two INSERTs, and the audit table becomes the largest table in the database within months.

The better approach for most systems is CDC: capture changes from the WAL (Postgres) or binlog (MySQL) asynchronously and write them to an append-only store. You get eventual consistency — the audit log lags by milliseconds to seconds — but your OLTP writes stay fast. For regulatory scenarios where the audit must be in the same transaction (SOX, PCI), use the outbox pattern: write audit events to an outbox table in the same transaction, and a separate process ships them to the audit store.

I'd ask about retention and query patterns before choosing. If compliance requires 7-year retention and point-in-time queries, we need a different storage strategy than if we just need 'who changed this row last week.'

Open questions worth asking

  • What entities need auditing — all tables or specific ones?
  • What is the retention requirement — 90 days, 1 year, 7 years?
  • Do we need to reconstruct the state of a row at any point in time?
  • Is the audit log for internal debugging or regulatory compliance?
  • What is the current write throughput on the audited tables?
  • Do we need tamper-proof audit (hash chains, WORM storage)?
  • Who queries the audit log — developers, compliance, customers?
  • What is the acceptable lag between a change and its appearance in audit?
  • Are we on Postgres (WAL), MySQL (binlog), or something else?
  • Do we need to audit DDL changes as well (schema migrations)?

Scope I'd lock first

  • In: audit capture (sync and async), storage design, query API, retention.
  • Out: full SIEM integration, real-time alerting on audit events.
  • Out: application-level authorization (who can view audit logs).

Functional requirements

Capture changes

Record every INSERT, UPDATE, DELETE with before/after state.

Actor attribution

Point-in-time query

Search

Non-functional / rough numbers

Throughput impact

< 5% write latency increase on OLTP tables.

Lag

Audit events available within 5 seconds of the change (CDC path).

Retention

7-year retention for compliance; 90-day hot, remainder cold.

Tamper resistance

Append-only; no UPDATE or DELETE on audit records.

Capacity estimate (do this on the board)

OLTP writes

10,000 writes/s across audited tables.

Audit rows

10K changes/s × 86,400s = 864M audit rows/day.

Row size

~1 KB per audit row (entity_id, before, after, actor, timestamp).

Daily storage

864M × 1 KB = 864 GB/day raw; compressed ~200 GB/day.

7-year retention

200 GB/day × 2,555 days ≈ 500 TB; needs tiered storage (S3 + Parquet).

API / interface sketch

http
-- Trigger-based audit (synchronous)
CREATE OR REPLACE FUNCTION audit_trigger()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO audit_log (table_name, row_id, action, old_data, new_data, actor, ts)
    VALUES (TG_TABLE_NAME, COALESCE(NEW.id, OLD.id), TG_OP,
            row_to_json(OLD), row_to_json(NEW),
            current_setting('app.current_user', true), now());
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Query: who changed order 42?
SELECT * FROM audit_log
WHERE table_name = 'orders' AND row_id = 42
ORDER BY ts DESC;

Data model

sql
CREATE TABLE audit_log (
    id          BIGSERIAL,
    table_name  TEXT NOT NULL,
    row_id      BIGINT NOT NULL,
    action      TEXT NOT NULL,
    old_data    JSONB,
    new_data    JSONB,
    actor       TEXT,
    ts          TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (ts, id)
) PARTITION BY RANGE (ts);

CREATE TABLE audit_log_2026_08 PARTITION OF audit_log
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE INDEX idx_audit_entity ON audit_log (table_name, row_id, ts DESC);

-- Outbox table for CDC-based audit
CREATE TABLE audit_outbox (
    id          BIGSERIAL PRIMARY KEY,
    payload     JSONB NOT NULL,
    published   BOOLEAN NOT NULL DEFAULT false,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

Approach / design notes

Approach 1: Synchronous triggers. Create an AFTER INSERT OR UPDATE OR DELETE trigger on each audited table. The trigger function writes to audit_log in the same transaction. Pros: strong consistency — if the business row commits, the audit row commits. Cons: doubles write I/O, increases transaction duration, audit_log becomes a write bottleneck.

Approach 2: CDC from the WAL. Use Debezium (or pg_logical / wal2json) to stream changes from the Postgres WAL to Kafka, then sink to an audit store (Postgres partition, S3 + Parquet, or Elasticsearch). Pros: zero overhead on OLTP writes. Cons: eventual consistency — a few seconds of lag; if the CDC pipeline fails, you lose audit events unless the WAL is retained.

Approach 3: Outbox pattern. The application writes audit events to an outbox table in the same transaction as the business row. A separate poller or CDC process reads the outbox and ships events to the audit store. This gives transactional consistency (the event is committed with the business row) without the overhead of a trigger (the app controls what data goes in the outbox). The outbox table stays small because processed rows are deleted.

For storage, partition the audit table by month. Hot partitions (last 90 days) live on fast SSD storage. Cold partitions are exported to S3 as Parquet files and queried via Athena or Trino. This keeps the OLTP database lean while meeting 7-year retention requirements.

Tamper-proofing: for SOX/PCI, each audit row includes a SHA-256 hash of the previous row's hash + current row's data, forming a hash chain. Any modification breaks the chain. Store the chain head in an immutable external ledger (AWS QLDB or a simple S3 object with versioning).

Deep dive (spend 15–25 minutes here)

Let's quantify the trigger approach. Our OLTP table handles 10,000 writes/s. Each write is ~0.5 ms. Adding a trigger that INSERTs into audit_log adds another ~0.5 ms (JSONB serialization + index update). Transaction time doubles from 0.5 ms to 1 ms. Throughput drops from 10K to ~5K at the same connection count. You can recover by adding connections, but that increases lock contention and memory usage.

The audit_log table grows at 864M rows/day. Even with monthly partitions, each partition holds ~26B rows after 30 days. The BRIN index on ts helps for time-range queries, but the (table_name, row_id, ts) B-tree index is massive. After 90 days, you're looking at 78B rows in hot storage — that's untenable on the OLTP instance.

CDC sidesteps all of this. Debezium reads the WAL and produces JSON events to Kafka. A Kafka Connect sink writes to S3 in Parquet format, partitioned by date. The OLTP database knows nothing about audit — its write latency is unchanged. The lag is typically 1-3 seconds under normal load, acceptable for most audit use cases.

The outbox pattern is a middle ground. The app does INSERT INTO audit_outbox (payload) VALUES (jsonb_build_object(...)) in the same transaction. A separate cron or Debezium on the outbox table picks up new rows every second and ships them to the audit store. The outbox stays tiny because we DELETE processed rows. If the shipper fails, rows accumulate but aren't lost — it's a durable queue inside the database.

Point-in-time reconstruction: to find the state of order 42 at 2026-01-15 14:30:00, query audit_log for all events where table_name='orders' AND row_id=42 AND ts <= '2026-01-15 14:30:00' ORDER BY ts. Replay the events: start with the INSERT's new_data, apply each UPDATE's new_data in order. The last state is the answer. This is effectively event sourcing over the audit log.

Request path / sequence

Trade-offs I'd say out loud

Trigger vs CDC

Trigger is strongly consistent but doubles write cost; CDC is async with near-zero overhead but allows brief lag.

Outbox vs direct CDC

Outbox gives transactional consistency without trigger overhead; adds a small table to manage.

JSONB vs normalized columns

JSONB is schema-flexible but harder to query; normalized columns are faster but require migrations.

Hot/cold partitioning

Hot 90-day data on SSD for fast queries; cold data on S3 Parquet for cheap retention.

Where it usually breaks

  • Trigger on high-write table — doubles latency and the audit table becomes the bottleneck.
  • Not partitioning audit_log — 864M rows/day fills the disk in weeks.
  • CDC pipeline failure without WAL retention — audit events lost permanently.
  • Storing sensitive data (passwords, PII) in audit JSONB — compliance violation.
  • No actor attribution — audit says 'row changed' but not by whom.
