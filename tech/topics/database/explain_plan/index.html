Explain a bad EXPLAIN plan

Reading EXPLAIN is a skill: estimates vs actuals tell you whether stats, indexes, or the query shape is lying.

60-minute agenda

How I'd open the discussion

I read EXPLAIN plans almost daily, and the single most important skill is comparing estimated rows to actual rows. When the planner estimates 100 rows but the actual is 500,000, something is wrong — usually stale statistics or a correlated predicate the planner can't model. That mismatch cascades: the wrong join strategy, the wrong join order, the wrong scan type.

I'd walk through a concrete bad plan, point out the red flags, and then show how to fix it. The fix is usually one of three things: add or fix an index, update statistics with ANALYZE, or rewrite the query to help the planner (e.g., materializing a CTE, or replacing a correlated subquery with a JOIN).

Open questions worth asking

  • What database engine — Postgres, MySQL, SQL Server?
  • Is this a single-table query or a join?
  • How many rows in each table involved?
  • When was ANALYZE last run on these tables?
  • Is the query parameterized (prepared statement) or literal values?
  • Are there CTEs or subqueries?
  • What is the expected vs actual execution time?
  • Are there any partial indexes or expression indexes?

Scope I'd lock first

  • In: reading EXPLAIN output, identifying problems, common fixes.
  • Out: query optimizer internals (cost model math).
  • Out: database tuning parameters beyond basic stats.

Approach / design notes

Start with EXPLAIN (ANALYZE, BUFFERS) to get both estimated and actual row counts plus buffer access stats. Read the plan bottom-up: the deepest nodes execute first. Look for three red flags: (1) Seq Scan where you expected an index scan, (2) estimated rows wildly different from actual rows, (3) 'Rows Removed by Filter' orders of magnitude larger than 'Rows' returned.

If you see a Seq Scan, check whether an index exists on the filtered column. If it does but the planner ignores it, the selectivity is too low (returning > 10-15% of the table), or statistics are stale. Run ANALYZE and re-check. If the planner still prefers Seq Scan, it's probably correct — for low selectivity, sequential I/O beats random index lookups.

If estimates are off by 100x+, the planner is making bad decisions downstream. Common causes: stale statistics (run ANALYZE), correlated columns (the planner assumes independence), or parameterized queries where the generic plan has wrong estimates. For correlated columns, Postgres 14+ extended statistics (CREATE STATISTICS) can help.

For joins, check the join type: Nested Loop is good for small outer + indexed inner, Hash Join is good for large tables without useful indexes, Merge Join is good when both sides are already sorted. If you see a Nested Loop with a Seq Scan on the inner side, it's almost always wrong — add an index on the join column.

Deep dive (spend 15–25 minutes here)

Let's read a real EXPLAIN ANALYZE output. Here's a bad plan:

Limit (cost=245000..245001 rows=20 actual rows=20 time=2340ms) -> Sort (cost=245000..252500 rows=3000000 actual rows=20 time=2340ms) Sort Key: created_at DESC Sort Method: external merge Disk: 147MB -> Seq Scan on orders (cost=0..200000 rows=3000000 actual rows=3012456 time=890ms) Filter: (status = 'active') Rows Removed by Filter: 6987544

Red flags: (1) Seq Scan on 10M rows, filtering to 3M — no index on status. (2) Sort spills to disk: 147 MB, because work_mem is only 4 MB. (3) Total time 2.3 seconds for 20 rows.

The estimate (rows=3000000) is close to actual (3012456), so stats are fine. The problem is pure index absence. The planner has no choice but to scan the entire table and sort. After adding CREATE INDEX ON orders (status, created_at DESC), the plan becomes:

Limit (cost=0.56..12.34 rows=20 actual rows=20 time=0.4ms) -> Index Scan using idx_orders_status_created on orders Index Cond: (status = 'active') Buffers: shared hit=23

2340 ms → 0.4 ms. No sort node at all — the index provides the order. 23 buffer hits means 23 pages read from shared_buffers, all cached. This is the ideal outcome.

Now consider a more subtle case: the plan shows an Index Scan but the estimated rows are 100 while actual rows are 500,000. The planner chose Nested Loop (expecting 100 iterations) when Hash Join would have been correct. Root cause: stale statistics. The table was bulk-loaded yesterday and ANALYZE hasn't run. After ANALYZE, the planner sees 500K rows and correctly picks Hash Join. Time drops from 30 seconds to 200 ms.

Another pattern: a correlated subquery that forces a Nested Loop. SELECT * FROM orders WHERE total_cents > (SELECT AVG(total_cents) FROM orders WHERE customer_id = orders.customer_id). For each of 10M rows in the outer query, the subquery runs — 10M executions. Rewrite as a JOIN: SELECT o.* FROM orders o JOIN (SELECT customer_id, AVG(total_cents) as avg_total FROM orders GROUP BY customer_id) a ON o.customer_id = a.customer_id WHERE o.total_cents > a.avg_total. One scan + one hash join — 200 ms instead of 10 minutes.

Request path / sequence

Trade-offs I'd say out loud

EXPLAIN vs EXPLAIN ANALYZE

EXPLAIN is planning-only (safe for production); ANALYZE executes the query (shows actuals but takes time).

Index scan vs bitmap scan

Index scan is best for few rows; bitmap scan batches I/O for moderate selectivity, avoiding random reads.

Generic vs custom plan

Prepared statements use generic plans after 5 executions; if parameter distribution varies, generic plans can be wrong.

Where it usually breaks

  • Reading only estimated rows and ignoring actuals — the estimate may be wildly wrong.
  • Assuming Seq Scan is always bad — for low selectivity queries, it's correct.
  • Not running ANALYZE after bulk loads — statistics are stale, planner makes bad choices.
  • Adding an index without checking selectivity — if 90% of rows match, the index won't help.
  • Ignoring 'Rows Removed by Filter' — a high number means the scan is doing wasted work.
