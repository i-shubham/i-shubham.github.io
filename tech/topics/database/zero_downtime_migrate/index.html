Migrate a live table with zero downtime

Locking ALTER on a 200M-row table is an outage wearing a maintenance window badge.

60-minute agenda

How I'd open the discussion

I learned this lesson the hard way: ALTER TABLE orders ADD COLUMN total_usd NUMERIC NOT NULL DEFAULT 0 on a 200M-row table took an ACCESS EXCLUSIVE lock for 45 minutes while it rewrote every row. The entire application was down. Since then, I use the expand/contract pattern for every non-trivial migration.

The pattern has four phases. Expand: add the new column as nullable with no default (instant in Postgres 11+). Dual-write: update the app to write to both old and new columns. Backfill: batch-update existing rows to populate the new column. Contract: make the new column NOT NULL, drop the old column or code path.

Each phase is a separate deployment. If anything goes wrong, you roll back to the previous phase. The key insight is that at no point does the database hold a long lock, and at no point is the application in an inconsistent state.

Open questions worth asking

  • What is the specific DDL change — add column, rename, change type, split table?
  • How many rows in the table?
  • What is the current write throughput?
  • Is this Postgres, MySQL, or another engine?
  • Can we use online DDL tools (gh-ost, pt-osc, pg_repack)?
  • Is there a read replica that needs to stay in sync?
  • What is the acceptable backfill duration (hours, days)?
  • Are there triggers or foreign keys on this table?
  • What is the rollback plan if the migration fails mid-backfill?
  • Do we have a staging environment with production-scale data?

Rollback

Approach / design notes

Phase 1 — Expand: run ALTER TABLE orders ADD COLUMN total_usd NUMERIC. In Postgres 11+, adding a nullable column with no default is a metadata-only operation — it completes in milliseconds regardless of table size. No rows are rewritten. Deploy this in a normal release.

Phase 2 — Dual-write: update the application to write to both total_cents and total_usd on every INSERT and UPDATE. New rows get both values; existing rows still have total_usd = NULL. This is a code-only change, no DDL. Deploy it and verify in production for at least one release cycle.

Phase 3 — Backfill: run a batched UPDATE that sets total_usd = total_cents / 100.0 for rows where total_usd IS NULL. Process 1,000 rows per batch with a 20 ms sleep between batches to throttle WAL generation and avoid overwhelming replicas. Track progress in a migration_status table. If backfill is interrupted, resume from the last completed batch.

Phase 4 — Verify: run a count query to confirm zero rows with total_usd IS NULL. Run a sampling query to verify total_usd = total_cents / 100.0 for a random 1% of rows. If verification passes, switch reads: update the application to read from total_usd instead of total_cents.

Phase 5 — Contract: once all reads use total_usd, run ALTER TABLE orders ALTER COLUMN total_usd SET NOT NULL. In Postgres 12+, this is a metadata check if a CHECK constraint already validated all rows. Then drop the old column: ALTER TABLE orders DROP COLUMN total_cents. This rewrites the table in Postgres, so use a pg_repack or schedule during low traffic.

Each phase is a separate deploy with its own rollback. If phase 3 fails, total_usd stays NULL for some rows but the app still reads total_cents. If phase 4 reveals mismatches, fix the backfill logic and re-run.

Deep dive (spend 15–25 minutes here)

Let's dig into the backfill mechanics. We need to update 200M rows without locking the table or overwhelming the WAL. The naive approach — UPDATE orders SET total_usd = total_cents / 100.0 WHERE total_usd IS NULL — acquires a row-level lock on every row and generates a WAL entry for each. On a 200M-row table, this takes ~45 minutes and generates 100+ GB of WAL, which replicas must replay. If a replica falls behind, you get replication lag alerts and possibly a full re-sync.

Batched approach: UPDATE orders SET total_usd = total_cents / 100.0 WHERE id BETWEEN :start AND :end AND total_usd IS NULL. Process 1,000 rows per batch. Between batches, sleep for 20 ms. This throttles WAL generation to ~50,000 rows/s, which generates ~25 MB/s of WAL — well within most replicas' capacity. Total time: 200M / 50K = 4,000 seconds ≈ 67 minutes.

Progress tracking: maintain a migration_status table with columns (migration_id, last_processed_id, rows_updated, started_at, updated_at). After each batch, update last_processed_id. If the backfill process crashes, restart from last_processed_id + 1. The WHERE total_usd IS NULL clause makes the backfill idempotent — re-processing a batch is harmless.

Dual-write race condition: during backfill, the app might INSERT a row with total_usd set, then the backfill tries to UPDATE it. The WHERE total_usd IS NULL clause skips it — no conflict. But what about an UPDATE to total_cents that happens after the backfill sets total_usd? The app's dual-write ensures it sets both columns on every UPDATE, so the backfill value is overwritten with the correct one. This is why dual-write must be deployed before backfill starts.

Verification is non-negotiable. After backfill completes, run: SELECT COUNT(*) FROM orders WHERE total_usd IS NULL. Must be 0. Then: SELECT COUNT(*) FROM orders WHERE total_usd != total_cents / 100.0. Must be 0 (accounting for rounding). Only then proceed to the contract phase. I've seen teams skip verification and discover 0.1% of rows had wrong values — that's 200K incorrect orders.

Request path / sequence

Trade-offs I'd say out loud

Expand/contract vs big-bang ALTER

Expand/contract is multi-deploy but zero downtime; big-bang is one step but locks the table.

Batched backfill vs pg_repack

Batched is simpler and controllable; pg_repack handles table rewrites but uses more disk and has edge cases with triggers.

Dual-write vs trigger-based sync

Dual-write is explicit and testable; trigger is transparent but harder to debug and adds overhead.

Sleep between batches vs adaptive throttling

Fixed sleep is simple; adaptive (watch replica lag) is better for production.

Where it usually breaks

  • Running ALTER TABLE ADD COLUMN with NOT NULL DEFAULT on a large table — rewrites all rows (pre-Postgres 11).
  • Starting backfill before dual-write is deployed — new rows written during backfill get correct value overwritten.
  • No progress tracking — if backfill crashes, you restart from zero.
  • Backfill generating too much WAL — replicas lag behind and may disconnect.
  • Skipping verification — 0.1% mismatch rate on 200M rows = 200K wrong values.
  • Dropping the old column before confirming all reads use the new one.
