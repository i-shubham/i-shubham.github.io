Choose isolation level for a booking system

Two users booking the last seat is an isolation problem — SERIALIZABLE is not the only hammer, and often not the best.

60-minute agenda

How I'd open the discussion

I've seen double-booking bugs in production — they always come from the same pattern: two transactions read available_seats = 1, both decrement to 0, both commit. READ COMMITTED allows this because each transaction sees the committed state at statement time, not transaction time.

There are three fixes. First, bump to SERIALIZABLE — the database will abort one transaction on conflict. Clean, but the abort rate under contention can be high, and you need retry logic anyway. Second, use SELECT FOR UPDATE to lock the seat row before reading — pessimistic but predictable. Third, add a version column and do an optimistic compare-and-swap: UPDATE seats SET booked = true WHERE id = :id AND version = :v.

I'd pick based on contention level. Low contention (conference rooms): optimistic is great. High contention (concert tickets): pessimistic lock on the row or even a separate booking_locks table to avoid hot-row contention on the seat itself.

Open questions worth asking

  • What is the contention level — how many users compete for the same seat?
  • Is this a reserved-seat system (specific seat) or general admission (any seat)?
  • What database engine — Postgres, MySQL InnoDB, Aurora?
  • Do we need to hold the seat temporarily (cart reservation) before confirming?
  • What is the acceptable failure mode — retry or waitlist?
  • How many seats per event and how many events concurrently?
  • Is there a payment step between reservation and confirmation?
  • Do we need to support bulk booking (10 seats at once)?
  • What is the SLA for booking latency?
  • Are there VIP or priority queues that change the fairness model?

-- Pessimistic: SELECT FOR UPDATE
BEGIN;
SELECT * FROM seats WHERE event_id = 42 AND seat_id = 'A1' FOR UPDATE;
-- check if available
UPDATE seats SET status = 'reserved', user_id = 123 WHERE seat_id = 'A1' AND event_id = 42;
COMMIT;

-- Optimistic: CAS with version
UPDATE seats
SET status = 'reserved', user_id = 123, version = version + 1
WHERE event_id = 42 AND seat_id = 'A1' AND status = 'available' AND version = 7;
-- rows_affected == 0 means conflict, retry

    id          BIGSERIAL PRIMARY KEY,
    name        TEXT NOT NULL,
    venue       TEXT NOT NULL,
    event_date  TIMESTAMPTZ NOT NULL,
    total_seats INT NOT NULL
);

CREATE TABLE seats (
    event_id    BIGINT NOT NULL REFERENCES events(id),
    seat_id     TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'available',
    user_id     BIGINT,
    version     INT NOT NULL DEFAULT 0,
    reserved_at TIMESTAMPTZ,
    PRIMARY KEY (event_id, seat_id)
);

CREATE INDEX idx_seats_available ON seats (event_id, status)
    WHERE status = 'available';

Approach / design notes

Let's compare the three approaches for the hot-ticket scenario where 5,000 users click 'book seat A1' simultaneously.

SERIALIZABLE isolation: each transaction reads the seat row, checks availability, and updates. Postgres SSI (Serializable Snapshot Isolation) detects the rw-conflict and aborts all but one transaction. Clean semantics, but under high contention the abort rate approaches 100% and you need client-side retry with backoff. For a concert, this means 4,999 retries hitting the same row — a thundering herd.

SELECT FOR UPDATE: the first transaction locks the row. All others block on the lock. When the first commits, the next transaction wakes up, sees the seat is now 'reserved', and returns 'seat taken'. No retries, no aborts — just serialized access. The trade-off is that lock hold time determines throughput: if the transaction takes 10 ms, peak throughput for that single seat is 100 TPS. But that's fine — you only need one winner.

Optimistic concurrency (CAS): UPDATE seats SET status='reserved' WHERE seat_id = 'A1' AND version = :v. Only one UPDATE wins; all others get rows_affected = 0. No explicit locks, so the database isn't serializing access — but 4,999 wasted round trips is expensive if the client retries.

My recommendation: for reserved-seat (specific seat), use SELECT FOR UPDATE. The contention is per-seat, and you want exactly-once semantics. For general admission (any seat), use an optimistic approach with a pool: UPDATE seats SET status='reserved' WHERE event_id = 42 AND status = 'available' LIMIT 1. Each user grabs a different row, so contention is low and optimistic works well.

Deep dive (spend 15–25 minutes here)

Let's walk through the double-booking bug step by step under READ COMMITTED. T1 begins, reads seat A1: status='available', version=0. T2 begins, reads seat A1: status='available', version=0. T1 runs UPDATE seats SET status='reserved' WHERE seat_id='A1': succeeds, 1 row. T2 runs the same UPDATE: also succeeds, 1 row, because READ COMMITTED re-reads the latest committed value at statement time — but T1 hasn't committed yet when T2 starts its UPDATE. Actually, in Postgres with READ COMMITTED, T2's UPDATE will block until T1 commits or rolls back, then re-evaluate the WHERE clause. So Postgres doesn't have the naive double-update bug for single-row updates — but it does for more complex predicates.

Where READ COMMITTED fails is the check-then-act pattern: T1 does SELECT available_count FROM events WHERE id=42 (returns 1). T2 does the same (returns 1). T1 does UPDATE events SET available_count = 0. T2 does the same — available_count is now -1. This is a lost update on a counter, not a single-row lock scenario.

SELECT FOR UPDATE prevents this: T1 locks the event row, T2 blocks. When T1 commits (available_count = 0), T2 wakes up, re-reads (sees 0), and returns 'sold out'. No race, no negative count. The lock hold time is the critical metric — keep the transaction as short as possible. Do not make an HTTP call to a payment processor while holding the lock.

In MySQL InnoDB, the behavior is different. InnoDB uses gap locks under REPEATABLE READ to prevent phantom reads. If you SELECT FOR UPDATE with a range predicate, InnoDB locks the gap between index entries, which can cause surprising deadlocks when two transactions lock adjacent gaps. Postgres doesn't use gap locks; it relies on SSI for phantom prevention at SERIALIZABLE level.

Practical pattern for high-contention events: use a 'reservation queue' table. Instead of locking the seat directly, INSERT INTO reservation_queue (event_id, seat_id, user_id, requested_at). A background worker processes the queue in order and assigns seats. This converts lock contention into queue contention, which is much easier to scale.

Request path / sequence

Trade-offs I'd say out loud

SELECT FOR UPDATE vs optimistic CAS

Pessimistic serializes access (lower throughput, no retries); optimistic allows parallel attempts (higher throughput, needs retries).

SERIALIZABLE vs explicit locks

SERIALIZABLE is cleaner but abort rate is high under contention; explicit locks give more control.

Reservation timeout

Short timeout (2 min) frees seats faster but may frustrate slow payers; long timeout (15 min) holds inventory.

Queue-based booking

Converts lock contention to queue processing; adds latency but eliminates deadlocks.

Where it usually breaks

  • Using READ COMMITTED without explicit locks — lost updates on counters.
  • Holding the lock while calling an external payment API — lock timeout, deadlock risk.
  • Optimistic retry storm when 5,000 users compete for 1 seat.
  • Not setting a lock_timeout — one stuck transaction blocks all bookings.
  • MySQL gap locks causing deadlocks on range queries under REPEATABLE READ.
  • Forgetting to release reserved seats on payment timeout.
