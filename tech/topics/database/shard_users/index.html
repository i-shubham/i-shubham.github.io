Shard a growing user table

Sharding users is easy until you pick email as the key and then need lookup by user_id, or vice versa.

60-minute agenda

How I'd open the discussion

I'd start by asking whether we've exhausted vertical scaling options. Sharding is an operational tax you pay on every query, every migration, and every debugging session for the rest of the system's life. A 1 TB user table on a modern Postgres instance with proper indexing handles 50,000 reads/s and 5,000 writes/s. If we're beyond that, then yes, we shard.

The key question is the shard key. user_id is the obvious choice because most queries are per-user: 'get user by id', 'get user's orders'. But login is by email. If we shard by user_id, email lookup becomes a scatter-gather across all shards — or we maintain a global email→user_id lookup table. Neither is free.

I've seen teams pick email as the shard key to optimize login, and then struggle when every other query needs user_id. The pragmatic answer is shard by user_id and maintain a small, highly-cached global lookup for email→shard. That table is tiny (email + shard_id, ~100 bytes per user) and fits in Redis easily.

Open questions worth asking

  • How many users now and projected growth rate?
  • What are the primary access patterns — by user_id, email, phone?
  • Are there cross-user queries (admin search, leaderboard, friends)?
  • What database engine — Postgres, MySQL, Vitess, CockroachDB?
  • How many shards initially and what is the resharding plan?
  • Is the application already shard-aware, or do we need a proxy layer?
  • What is the write/read ratio on the user table?
  • Are there regulatory constraints on data residency (geo-sharding)?
  • Do we need global uniqueness for email and username?
  • What is the acceptable latency for login (email-based lookup)?

Scope I'd lock first

  • In: shard key design, routing, secondary lookups, resharding strategy.
  • Out: full database proxy implementation (Vitess internals).
  • Out: sharding non-user tables (orders, messages) — related but separate.

Functional requirements

Lookup by user_id

Route directly to the correct shard.

Lookup by email

Resolve email to shard, then fetch user.

Create user

Assign shard, insert, update global lookup atomically.

Cross-shard search

Admin search by name returns results from all shards.

Non-functional / rough numbers

Latency

Single-shard read p99 < 5 ms; email lookup p99 < 10 ms (cache hit).

Throughput

100,000 reads/s across all shards; 10,000 writes/s.

Balance

No shard holds more than 120% of the average row count.

Resharding

Add shards with zero downtime and < 1% performance degradation during migration.

API / interface sketch

shard_id = hash(user_id) % num_shards
conn = shard_pool[shard_id]

-- Read user by ID (single shard)
SELECT * FROM users WHERE id = :user_id;  -- on shard N

-- Email lookup (global table + shard hop)
SELECT shard_id FROM global_email_lookup WHERE email = :email;
-- then: SELECT * FROM users WHERE id = :user_id;  -- on resolved shard

-- Create user
BEGIN;  -- on global DB
INSERT INTO global_email_lookup (email, user_id, shard_id) VALUES (:email, :uid, :sid);
COMMIT;
BEGIN;  -- on shard N
INSERT INTO users (id, email, name, ...) VALUES (:uid, :email, :name, ...);
COMMIT;

    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Global lookup table (separate DB or Redis)
CREATE TABLE global_email_lookup (
    email       TEXT PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    shard_id    SMALLINT NOT NULL
);

CREATE INDEX idx_global_lookup_uid ON global_email_lookup (user_id);

Approach / design notes

Shard key selection is the most consequential decision. Hash(user_id) % num_shards gives uniform distribution and makes per-user queries trivial: compute the shard, route the connection, run the query. The alternative — range-based sharding (users 1-10M on shard 0, 10M-20M on shard 1) — is simpler to reason about but creates hotspots as new users concentrate on the latest shard.

The email lookup problem is the classic secondary-index challenge in sharded systems. Three options: (1) scatter-gather every email query across all shards — O(num_shards) latency, unacceptable at 16+ shards. (2) Maintain a global email→(user_id, shard_id) table in a separate store. (3) Use a consistent hash on email for a separate 'login shard', duplicating minimal data. Option 2 is the most practical.

The global lookup table is small: 500M rows × ~100 bytes = 50 GB. Put it in a dedicated Postgres instance with hot standby, or in a Redis cluster for sub-millisecond reads. Writes happen only on user creation and email change — both rare. Cache hit rate should exceed 99.9%.

Resharding is the hard part. When you need to go from 16 to 32 shards, you can't just change the modulus — that rehashes half the users. Use consistent hashing (or virtual shards mapped to physical nodes) so adding a shard only moves ~1/N of the data. During migration, dual-write to both old and new shard, backfill historical data, then cut over reads.

An alternative is to over-provision virtual shards from day one: create 256 virtual shards mapped to 16 physical nodes. When you scale, move virtual shards between nodes without rehashing. Vitess and Citus both use this pattern.

Deep dive (spend 15–25 minutes here)

Let's work through a concrete example. We have 500M users across 16 shards. Shard key is hash(user_id) % 16. User alice@example.com has user_id = 7890. hash(7890) % 16 = 6, so Alice lives on shard 6.

Login flow: the client sends email=alice@example.com. We query the global lookup: SELECT user_id, shard_id FROM global_email_lookup WHERE email = 'alice@example.com'. Returns (7890, 6). We connect to shard 6 and run SELECT * FROM users WHERE id = 7890. Two queries, but the first is cached in Redis 99.9% of the time, so effective latency is ~5 ms.

Now consider the hotspot problem. Suppose a celebrity user generates 10x the read traffic. That user's shard handles disproportionate load. Solutions: read replicas per shard (scale reads), application-level caching (CDN for profiles), or shard-splitting (move hot users to dedicated shards). The virtual-shard model helps: move the virtual shard containing the hot user to a beefier node.

Cross-shard queries are the tax. Admin wants to search users by name containing 'alice'. Without a global search index, we scatter the query to all 16 shards, gather results, merge and sort client-side. For admin tools this is tolerable; for user-facing search, you need Elasticsearch or a dedicated search service fed by CDC from all shards.

Resharding from 16 to 32 shards with consistent hashing: each new shard takes ownership of half the hash range from one existing shard. We backfill by streaming rows from the old shard to the new one via logical replication. During backfill, dual-write: new writes go to both old and new shard. Once backfill completes and both shards are in sync, update the shard map and cut reads over. Total migration time for 31M users per shard split: ~2 hours at 5,000 rows/s with batched inserts.

Request path / sequence

Trade-offs I'd say out loud

Hash vs range sharding

Hash gives even distribution but makes range queries impossible; range supports time-based queries but creates write hotspots.

Global lookup table vs scatter-gather

Lookup adds a hop but is O(1); scatter-gather is O(shards) and gets worse as you add shards.

Virtual shards vs physical shards

Virtual shards (256 mapped to 16 nodes) make resharding a metadata change; physical shards require rehashing.

Shard-local joins vs denormalization

Joins within a shard are fast; cross-shard joins require scatter-gather. Denormalize to avoid them.

Where it usually breaks

  • Picking email as shard key — every user_id query becomes scatter-gather.
  • Modulus-based routing without virtual shards — resharding rehashes half your data.
  • Not handling the global lookup table as a SPOF — replicate and cache it.
  • Cross-shard transactions for user creation (global lookup + shard insert) — use saga pattern.
  • Celebrity hotspot on a single shard — read replicas or shard splitting needed.
  • Schema migrations on 16 shards simultaneously — one failure leaves shards inconsistent.
  • Connection pool exhaustion: 16 shards × 100 connections per app server × 50 servers = 80,000 connections.

What "good enough" looks like in 60 minutes

Explain the shard key trade-off between user_id and email. Show the two-hop email lookup pattern with caching. Discuss resharding with virtual shards. Address cross-shard queries honestly — don't pretend they're free. That's the senior answer. The staff-level add is the virtual shard model and the dual-write migration strategy.
