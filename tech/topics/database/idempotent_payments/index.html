Database · Hard · ~60 min

Implement idempotent payment writes

Networks retry. Clients retry. Your payment insert must not become two captures at the processor.

60-minute agenda

How I'd open the discussion

I've dealt with duplicate charges in production, and it's the kind of bug that costs real money and real trust. The root cause is always the same: the client didn't get an ACK, so it retried, and the server treated the retry as a new request. Two captures at the payment processor, two charges on the customer's card.

The fix has two layers. First, the client sends an idempotency key — a UUID generated before the first attempt. The server stores this key with a UNIQUE constraint and uses INSERT ON CONFLICT to detect retries. Second, we pass the same key to the payment processor, so even if our code calls capture twice, Stripe or Adyen returns the original result.

The hard part is the gap between 'we wrote the row' and 'the processor confirmed'. If the server crashes in that window, we have a database record but no capture — or a capture but no record. That's where reconciliation comes in.

Open questions worth asking

  • What payment processor — Stripe, Adyen, Braintree?
  • Does the client or the server generate the idempotency key?
  • What is the retry window — how long can a client retry with the same key?
  • Do we separate authorize and capture, or single-step charge?
  • What happens if the same key arrives with different amounts?
  • How do we handle partial failures (DB writes, processor fails)?
  • Is there a reconciliation job that runs periodically?
  • What is the SLA for charge correctness — zero duplicates or within-SLA dedup?
  • Do we support refund idempotency as well?
  • What database engine are we using?

Scope I'd lock first

  • In: idempotency key storage, upsert mechanics, processor interaction, recovery.
  • Out: full payment gateway design, PCI compliance, multi-currency.
  • Out: refund flow (mention but don't implement).

Data model

sql
CREATE TABLE payments (
    id              BIGSERIAL PRIMARY KEY,
    idempotency_key UUID NOT NULL,
    customer_id     TEXT NOT NULL,
    amount_cents    BIGINT NOT NULL,
    currency        TEXT NOT NULL DEFAULT 'USD',
    status          TEXT NOT NULL DEFAULT 'pending',
    processor_ref   TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_idempotency_key UNIQUE (idempotency_key)
);

CREATE TABLE payment_events (
    id          BIGSERIAL PRIMARY KEY,
    payment_id  BIGINT NOT NULL REFERENCES payments(id),
    event_type  TEXT NOT NULL,
    detail      JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_payments_status ON payments (status)
    WHERE status IN ('pending', 'processing');

Approach / design notes

The core mechanism is INSERT ON CONFLICT. When a payment request arrives, we try to INSERT a row with the idempotency_key. If the key already exists (UNIQUE violation), we check whether the parameters match: same amount, same currency, same customer. If they match, we return the existing payment — the client is retrying. If they differ, we return 409 Conflict — the client reused a key, which is a bug.

The payment lifecycle is a state machine: pending → processing → captured | failed. We INSERT with status='pending', then call the processor. If the processor succeeds, we UPDATE to 'captured' and store the processor reference. If it fails, we UPDATE to 'failed'. Every transition is recorded in payment_events for auditability.

The dangerous window is between our INSERT and the processor response. If the server crashes here, the row is stuck in 'pending' or 'processing'. A reconciliation job runs every 60 seconds, finds payments older than 5 minutes in 'processing' state, and checks the processor API for their status. If the processor has no record, we retry the capture. If the processor says 'captured', we update our row.

We also pass the idempotency key to the processor itself. Stripe accepts an Idempotency-Key header and deduplicates on their end. This means even if our reconciliation job retries a capture that actually succeeded, Stripe returns the original result. Belt and suspenders.

Key expiration: we don't keep idempotency keys forever. A background job deletes keys older than 24 hours. The client contract states that retries after 24 hours are treated as new payments.

Deep dive (spend 15–25 minutes here)

Let's trace the happy path first. Client generates UUID 'aaaa-bbbb-cccc-dddd' and sends POST /v1/payments with amount=4999. Server runs INSERT INTO payments (idempotency_key, customer_id, amount_cents, status) VALUES ('aaaa-...', 'cust_123', 4999, 'pending'). Row inserted, id=42. Server calls Stripe with Idempotency-Key: 'aaaa-bbbb-cccc-dddd'. Stripe returns charge_id='ch_xyz'. Server runs UPDATE payments SET status='captured', processor_ref='ch_xyz' WHERE id=42. Returns 201 to client.

Retry path: client didn't get the 201 (network timeout) and retries with the same key and same amount. Server runs INSERT ON CONFLICT (idempotency_key) DO NOTHING. Zero rows affected. Server SELECTs the existing row: status='captured', amount=4999, matches the request. Returns 200 with the existing payment. No second charge.

Crash path: server crashes after INSERT but before calling Stripe. Row is stuck as 'pending'. The reconciliation job picks it up after 5 minutes: queries Stripe for this idempotency key — Stripe has no record. Job calls Stripe capture with the same key. Stripe processes it and returns charge_id. Job updates the row to 'captured'. When the client retries (maybe minutes later), it finds the completed payment and gets a 200.

Conflict path: client reuses the key 'aaaa-bbbb-cccc-dddd' but with amount=9999 instead of 4999. Server finds the existing row, compares parameters: amount mismatch. Returns 409 Conflict with an error message. This prevents the client from accidentally overwriting a payment.

Processor-double-charge prevention: even if our code somehow calls Stripe twice with the same Idempotency-Key, Stripe's server returns the cached result from the first call for 24 hours. This is the second layer of defense — our UNIQUE constraint is the first.

Request path / sequence

Trade-offs I'd say out loud

Client vs server idempotency key

Client key covers network retries; server key only covers app-level retries.

ON CONFLICT DO NOTHING vs DO UPDATE

DO NOTHING is safer — no accidental overwrites; DO UPDATE risks masking parameter changes.

Inline processor call vs async queue

Inline is simpler but blocks the HTTP request; async decouples but adds eventual consistency.

24h key TTL vs forever

Short TTL keeps the lookup table small; long TTL prevents late retries from creating duplicates.

Where it usually breaks

  • Not passing idempotency key to the processor — our DB is safe but Stripe gets two charges.
  • Checking parameters after ON CONFLICT DO UPDATE — the update already overwrote them.
  • Transaction wrapping the processor call — if Stripe times out, the DB row is rolled back but the charge exists.
  • No reconciliation job — 'processing' rows stay stuck forever after a crash.
  • Key collision with UUIDv4 — astronomically unlikely but worth asserting in tests.
  • Client generating a new key on retry — defeats the entire mechanism.
  • Race condition if two threads INSERT the same key simultaneously — ON CONFLICT handles it.
