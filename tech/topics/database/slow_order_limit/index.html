Fix a slow ORDER BY + LIMIT query

ORDER BY … LIMIT 20 looks cheap until the planner sorts two million rows to throw away 1,999,980 of them.

60-minute agenda

How I'd open the discussion

I've debugged this exact issue in production more times than I can count. The pattern is always the same: SELECT * FROM orders WHERE status = 'active' ORDER BY created_at DESC LIMIT 20. It looks innocent — 20 rows, how hard can it be? But without the right index, the database fetches every active row, sorts them all, and then discards all but 20.

The fix is usually a composite index that matches the WHERE clause and the ORDER BY direction: (status, created_at DESC). With that index, the planner walks the B-tree in order and stops after 20 rows — no sort needed. But there are subtleties: NULL handling, covering index width, and cases where the optimizer legitimately prefers a filesort.

I'd walk through the EXPLAIN output first to show the candidate where the time is going, then build the solution step by step.

Open questions worth asking

  • What database engine — Postgres, MySQL, SQL Server?
  • How many rows in the table and what percentage match the WHERE filter?
  • Is the ORDER BY column always the same, or does the app support multiple sort orders?
  • Are NULLs present in the ORDER BY column?
  • Is this a paginated query — do we need OFFSET or keyset pagination?
  • How wide are the rows (number of columns, average row size)?
  • Is the table partitioned?
  • What is the current index set on this table?
  • Is this an OLTP query or a reporting query?

Scope I'd lock first

  • In: diagnosing the slow query, index design, covering index, keyset pagination.
  • Out: full query optimizer internals, partitioning strategy.
  • Out: application-level caching (separate concern).

Approach / design notes

Start with EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) on the slow query. Look for 'Sort Method: external merge' or 'Sort Method: top-N heapsort' with a high 'Rows Removed by Filter'. If you see a Seq Scan followed by a Sort node, the database is doing exactly what we fear: scanning millions of rows, sorting them, and returning 20.

The fix is a composite index where the equality columns come first and the ORDER BY column comes last, with the sort direction baked in. For WHERE status = 'active' ORDER BY created_at DESC LIMIT 20, the ideal index is (status, created_at DESC). The planner walks the B-tree to the first leaf matching status='active' and reads 20 entries in order — no sort node at all.

A covering index adds frequently selected columns via INCLUDE, turning the plan into an Index Only Scan. This avoids heap fetches entirely, which matters when the table is larger than shared_buffers and heap pages are on disk. The trade-off is index size: each INCLUDEd column widens the leaf pages.

For pagination, replace OFFSET with keyset (cursor) pagination. Instead of OFFSET 1000, the app sends the last created_at from the previous page: WHERE status = 'active' AND created_at < :last_seen ORDER BY created_at DESC LIMIT 20. This uses the same index and costs O(LIMIT) regardless of page depth, whereas OFFSET N costs O(N + LIMIT).

When does filesort win? If the WHERE clause is very selective (returns < 1% of rows) and the ORDER BY column has no useful index, the planner may correctly choose an index scan on the filter column plus an in-memory top-N heapsort. For 200 rows, sorting is trivial. Don't add an index you'll never need.

Deep dive (spend 15–25 minutes here)

Let's trace through the planner's decision on a 10M-row orders table with 30% active rows. Without the composite index, Postgres has two choices: a Seq Scan with filter (visit all 10M rows, keep 3M, sort, limit) or use the primary key index (useless here since we're not filtering on id). It picks Seq Scan. The Sort node allocates work_mem (default 4 MB in Postgres); if the sort exceeds work_mem, it spills to disk via external merge sort. Sorting 3M rows typically needs ~150 MB, so with default settings you get multiple merge passes — that's your 2-second query.

Now add CREATE INDEX idx_orders_status_created ON orders (status, created_at DESC). The B-tree stores entries in (status, created_at) order. For status = 'active', the planner seeks to the first matching leaf and reads forward (which is backward in created_at, i.e., newest first) — exactly what we want. After 20 entries, it stops. Total I/O: ~3 leaf pages + 20 heap fetches = sub-millisecond.

The DESC in the index definition matters on Postgres. Without it, the index stores created_at ascending. The planner can do a Backward Index Scan, but this prevents using the index for an Index Only Scan with visibility-map optimization. Explicit DESC avoids this edge case.

Covering index deep dive: INCLUDE (id, customer_id, total_cents) stores those values in the leaf pages but not in the B-tree's internal nodes. This means the index doesn't grow as fast as a full composite index, but the planner can serve the query without touching the heap at all. The trade-off: each INSERT now updates both the heap and the wider index leaf — expect ~8-12% write overhead.

NULL behavior: by default Postgres sorts NULLs last in ASC and first in DESC. If created_at can be NULL (bad schema, but it happens), the index should specify NULLS LAST to match the query's expected order. Otherwise the planner cannot use the index to satisfy ORDER BY.

Request path / sequence

Trade-offs I'd say out loud

Composite index vs single-column indexes

Composite eliminates sort; single-column may need a merge or sort step.

Covering index vs standard index

Covering avoids heap I/O but widens leaf pages and slows writes.

Keyset vs OFFSET pagination

Keyset is O(LIMIT) at any depth; OFFSET is O(N+LIMIT) and gets worse.

Index on every sort order vs runtime sort

Each additional index costs write throughput; filesort is fine for rare queries.

Where it usually breaks

  • Index column order wrong — (created_at, status) cannot seek by status first.
  • Forgetting DESC in the index — Postgres cannot do Index Only Scan with backward scan.
  • Using OFFSET for deep pagination — page 5,000 scans 100,000 rows.
  • Covering index too wide — exceeds maximum index tuple size (8 KB on Postgres).
  • Not using CONCURRENTLY for CREATE INDEX — locks the table during build.
  • Assuming the planner always uses the index — low selectivity may prefer Seq Scan.

Follow-ups if time remains

  • How would you handle multiple sort orders (created_at, total, name)?
  • What if the table is partitioned by date — does the index strategy change?
  • How do you monitor index usage and drop unused indexes?
  • What about partial indexes for queries that always filter on status='active'?

What "good enough" looks like in 60 minutes

Show you can read an EXPLAIN plan, identify the sort as the bottleneck, and design a composite index that eliminates it. Discuss covering indexes and keyset pagination as follow-ups. Mention when filesort is acceptable. That's the full picture — most candidates stop at 'add an index' without explaining why the column order matters.
