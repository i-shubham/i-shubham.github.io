Multi-account strategy for prod/stage/dev

Separate accounts beat IAM spaghetti — blast radius and billing clarity show up immediately.

60-minute agenda

How I'd open the discussion

A single AWS account for everything — dev, staging, and production — works until it does not. The problems are predictable: an engineer accidentally deletes a production resource from a dev session, billing is impossible to attribute per team or environment, and IAM policies become an unmaintainable web of conditions trying to isolate resources within a flat namespace.

Separate accounts solve these problems structurally. A dev account has no access to production resources — not because of IAM policy, but because the resources physically do not exist in that account. Billing is automatic: each account's cost is its own line item. Blast radius is limited: a misconfigured security group in dev cannot expose a production database.

AWS Organizations provides the structure: an organization with organizational units (OUs) for prod, staging, dev, shared-services, and security. Service control policies (SCPs) on each OU enforce guardrails that no IAM policy can override. Shared services (networking, CI/CD, logging) live in a dedicated account that all environments access via cross-account roles.

Open questions worth asking

  • How many environments: dev, staging, prod? Any others (sandbox, QA)?
  • How many teams and do they need separate dev accounts?
  • Existing account structure or greenfield?
  • Shared services needed: networking hub, CI/CD, centralized logging?
  • Compliance requirements — are there services that must be denied in certain OUs?
  • DNS and domain management — Route 53 in one account or distributed?
  • SSO provider for cross-account access?
  • Budget — is per-account billing attribution needed?

Scope I'd lock first

  • In scope — Organization structure, OUs, SCPs, cross-account access, shared networking
  • In scope — Account vending (automated new account creation), centralized logging
  • Out of scope — Per-application architecture within each account
  • Defer — AWS Control Tower adoption, automated compliance remediation

Approach / design notes

The multi-account strategy has five components: structure, guardrails, networking, logging, and automation.

Structure: the organization has five OU categories. Workload OUs (prod, staging, dev) hold application accounts. Shared-services holds networking and CI/CD. Security holds log archive and audit tools. Each production service gets its own account for maximum isolation. Staging is one shared account (lower blast radius concern). Dev has per-team accounts for independence.

Guardrails (SCPs): SCPs are deny-only policies on OUs that no IAM policy can override. On the dev OU: deny large instance types (only t3, t4g, m5.large allowed), deny public S3 bucket creation, deny CloudTrail deletion. On the prod OU: deny resource creation outside approved regions (us-east-1, us-west-2), deny S3 public access, require encryption on all EBS volumes and S3 objects. SCPs are the first line of defense against misconfiguration.

Networking: Transit Gateway in the shared-services account acts as a hub. Each environment account creates a VPC and attaches it to the Transit Gateway. Route tables control traffic: prod VPCs cannot route to dev VPCs. Shared services (ECR, internal APIs) are accessible from all environments via the Transit Gateway. DNS is centralized in Route 53 in the networking account with cross-account hosted zone associations.

Logging: an organization-level CloudTrail sends all API events from all accounts to an S3 bucket in the log-archive account. VPC flow logs from all accounts go to the same bucket with a different prefix. GuardDuty runs as an organization feature with the security account as the delegated administrator. Security Hub aggregates findings across all accounts.

Automation (account vending): when a new team needs a dev account, a Terraform pipeline creates the account, moves it to the correct OU, deploys the baseline VPC, attaches it to Transit Gateway, configures SSO roles, enables CloudTrail and GuardDuty, and sets budget alerts. The new account is ready in under 1 hour.

Deep dive (spend 15–25 minutes here)

SCP design principles: SCPs should be deny-lists, not allow-lists. An allow-list SCP that only permits specific services breaks every time AWS launches a new service your team needs. A deny-list approach: deny specific dangerous actions (delete CloudTrail, create IAM users, launch expensive instances) and allow everything else. This is easier to maintain and does not block engineers from using new services.

Cross-account database access: production databases should not be accessible from dev accounts. For debugging, engineers query a read replica in staging (which has anonymized data) or use a secure bastion in the prod account with break-glass access. Direct VPC peering between dev and prod is explicitly blocked via Transit Gateway route tables.

Consolidated billing with Savings Plans: Savings Plans purchased at the organization level apply across all member accounts. This means: if the prod account commits to $10K/month Compute Savings Plan, unused capacity in prod flows to staging, then dev. This maximizes utilization of the commitment. RIs, however, are account-specific unless sharing is enabled.

Account vending automation: I use Terraform with the AWS provider's aws_organizations_account resource. The pipeline: (1) create account, (2) move to target OU, (3) assume a bootstrap role in the new account, (4) deploy baseline stack (VPC, SSO roles, CloudTrail, GuardDuty membership, budget alarm), (5) attach VPC to Transit Gateway. The bootstrap role is created automatically by AWS Organizations (OrganizationAccountAccessRole) and can be assumed from the management account.

Account sprawl management: with automated vending, it is easy to create too many accounts. Guardrails: (1) require Jira ticket for account creation, (2) quarterly review of account utilization — accounts with < $100/month spend are candidates for consolidation, (3) naming convention enforcement (env-team-purpose), (4) auto-tag with creation date and owner.

Account vending with organization and baseline setup

import boto3

def create_member_account(name: str, email: str, ou_id: str):
    org = boto3.client('organizations')
    result = org.create_account(
        Email=email,
        AccountName=name,
        RoleName='OrganizationAccountAccessRole',
        IamUserAccessToBilling='DENY'
    )
    account_id = result['CreateAccountStatus']['AccountId']

    # Wait for account creation
    waiter = org.get_waiter('account_created')
    # Move to target OU
    roots = org.list_roots()['Roots']
    org.move_account(
        AccountId=account_id,
        SourceParentId=roots[0]['Id'],
        DestinationParentId=ou_id
    )

    # Apply baseline via cross-account assume role
    sts = boto3.client('sts')
    creds = sts.assume_role(
        RoleArn=f'arn:aws:iam::{account_id}:role/OrganizationAccountAccessRole',
        RoleSessionName='baseline-setup'
    )['Credentials']

    # Use creds to deploy baseline resources in new account
    deploy_baseline(creds, account_id, name)
    return account_id
use aws_sdk_organizations as org;
use aws_sdk_sts as sts;

pub async fn create_member_account(
    name: &str, email: &str, ou_id: &str,
) -> String {
    let config = aws_config::load_defaults(aws_config::BehaviorVersion::latest()).await;
    let org_client = org::Client::new(&config);
    let sts_client = sts::Client::new(&config);

    let result = org_client
        .create_account()
        .email(email)
        .account_name(name)
        .role_name("OrganizationAccountAccessRole")
        .iam_user_access_to_billing(org::types::IamUserAccessToBilling::Deny)
        .send()
        .await
        .unwrap();

    let account_id = result
        .create_account_status()
        .unwrap()
        .account_id()
        .unwrap()
        .to_string();

    // Move to target OU
    let roots = org_client.list_roots().send().await.unwrap();
    let root_id = roots.roots().first().unwrap().id().unwrap();

    org_client
        .move_account()
        .account_id(&account_id)
        .source_parent_id(root_id)
        .destination_parent_id(ou_id)
        .send()
        .await
        .unwrap();

    // Cross-account assume role for baseline setup
    let role_arn = format!(
        "arn:aws:iam::{account_id}:role/OrganizationAccountAccessRole"
    );
    let creds = sts_client
        .assume_role()
        .role_arn(&role_arn)
        .role_session_name("baseline-setup")
        .send()
        .await
        .unwrap();

    deploy_baseline(&creds, &account_id, name).await;
    account_id
}
#import <Foundation/Foundation.h>
#include <string>

@protocol AWSOrganizations <NSObject>
- (NSString *)createAccountWithName:(NSString *)name
                              email:(NSString *)email
                           roleName:(NSString *)role;
- (NSString *)rootId;
- (void)moveAccount:(NSString *)accountId from:(NSString *)src to:(NSString *)dst;
@end

@protocol AWSSTS <NSObject>
- (NSDictionary *)assumeRole:(NSString *)roleArn session:(NSString *)session;
@end

static NSString *createMemberAccount(id<AWSOrganizations> org,
                                     id<AWSSTS> sts,
                                     NSString *name,
                                     NSString *email,
                                     NSString *ouId) {
    // Create account in the organization
    NSString *accountId = [org createAccountWithName:name
                                               email:email
                                            roleName:@"OrganizationAccountAccessRole"];

    // Move from root OU to target OU
    NSString *rootId = [org rootId];
    [org moveAccount:accountId from:rootId to:ouId];

    // Cross-account assume role to deploy baseline
    NSString *roleArn = [NSString stringWithFormat:
        @"arn:aws:iam::%@:role/OrganizationAccountAccessRole", accountId];
    NSDictionary *creds = [sts assumeRole:roleArn session:@"baseline-setup"];

    // deployBaseline(creds, accountId, name) — application-specific setup
    NSLog(@"Baseline deployed for account %@", accountId);
    return accountId;
}

Request path / sequence

Trade-offs I'd say out loud

Per-service prod accounts vs shared prod

Per-service gives maximum isolation but multiplies accounts. Shared prod is simpler but increases blast radius

Transit Gateway vs VPC peering

TGW scales to 50+ VPCs with centralized routing. Peering is free but creates N² relationships; unmanageable past 5 VPCs

SCP deny-list vs allow-list

Deny-list is easier to maintain and does not block new services. Allow-list is more secure but requires constant updates

Shared staging vs per-team staging

Shared is cheaper and simpler. Per-team gives isolation but doubles account count and networking complexity

Org-level Savings Plan vs per-account

Org-level maximizes utilization across accounts. Per-account gives clearer cost attribution but wastes unused commitment

Where it usually breaks

  • SCP blocks a legitimate action in production — emergency fix: temporarily move the account out of the OU (requires org admin); post-fix: update the SCP
  • Transit Gateway route allows dev-to-prod traffic — quarterly route table audit; use network firewall for inspection between environments
  • New account has no VPC — account vending automation failed silently; add verification step that checks baseline resources
  • Consolidated billing obscures per-team costs — enforce tagging; use Cost Allocation Tags for team-level attribution within each account
  • Account sprawl: 50 accounts after 2 years, 20 are barely used — quarterly utilization review; consolidate or close unused accounts

What "good enough" looks like in 60 minutes

A strong answer covers: OU structure with environment separation, SCPs as guardrails (with specific examples), Transit Gateway for shared networking, centralized logging in a security account, and automated account vending. Explain why per-account isolation beats IAM-policy isolation.

You do not need to design the full Control Tower setup or automated compliance remediation. The interviewer wants to see: understanding of blast radius reduction via account boundaries, practical SCP examples, and networking between accounts without over-complexity.
