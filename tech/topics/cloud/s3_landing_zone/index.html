Build an S3-backed data lake landing zone

A landing zone is policy and layout — buckets without lifecycle or IAM fences become infinite expensive junk drawers.

60-minute agenda

How I'd open the discussion

A data lake landing zone is not a bucket with some folders — it is a set of policies, access controls, and conventions that prevent the lake from becoming an expensive, ungovernable junk drawer. I have inherited lakes where 40% of storage cost was unreferenced files, encryption was inconsistent, and every team had full read/write to every prefix.

The landing zone defines three layers: raw (immutable source data), staging (transformed intermediate data), and curated (clean, governed, queryable tables). Each layer has different access policies, lifecycle rules, and retention requirements. Raw data is append-only — nobody deletes or modifies raw files. Staging has a 7-day TTL. Curated is the production layer with strict access control.

The prefix structure matters for IAM policies and Athena/Spark partition pruning. I use: s3://{bucket}/{layer}/{domain}/{table}/dt={date}/. IAM policies scope access by layer and domain — the analytics team can read curated/* but not raw/*, and each domain team owns their raw/{domain}/ prefix.

Open questions worth asking

  • How many source systems and domains?
  • Expected data volume per day/month?
  • Encryption requirement — SSE-S3, SSE-KMS, or client-side?
  • Compliance framework — do we need audit logs on every access?
  • Who needs access — data eng, analytics, ML, external partners?
  • Retention policies — how long to keep raw, staging, curated?
  • Cross-account access — multiple AWS accounts?
  • File formats — CSV, JSON, Parquet, Avro?
  • Query engine — Athena, Spark, Trino?
  • Existing lake or greenfield?

Scope I'd lock first

Approach / design notes

The landing zone design has four pillars: structure, access, cost, and audit.

Structure: I use one bucket per layer (raw, staging, curated) rather than one mega-bucket with prefix-based separation. Separate buckets allow: different lifecycle rules per bucket (staging auto-deletes, raw transitions to Glacier), different IAM policies at the bucket level (simpler than prefix-level conditions), and independent versioning settings (raw is versioned, staging is not). Within each bucket, the prefix follows {domain}/{table}/dt={date}/. This aligns with Hive-style partitioning for query engines.

Access: IAM roles are scoped by team and layer. The data engineering team has read/write on raw and staging, plus read/write on curated (they publish tables). Analytics has read-only on curated — they cannot touch raw or staging. Domain teams (e.g., the orders team) can write to raw/orders/ but not raw/payments/. Bucket policies enforce guardrails that IAM alone cannot: deny unencrypted uploads, deny public access, require specific KMS key for encryption.

Cost: lifecycle rules are the single biggest cost lever. Raw data transitions from Standard to Standard-IA at 90 days ($0.023 → $0.0125/GB, 46% savings) and to Glacier at 365 days ($0.004/GB, 83% savings). Staging auto-deletes after 7 days. For curated, I add intelligent tiering on partitions older than 180 days. At 182TB of raw data, lifecycle rules save ~$1,700/month.

Audit: CloudTrail data events log every S3 read and write with the IAM identity, timestamp, and object key. This is required for SOC2 and HIPAA. S3 access logs provide additional detail (referrer, TLS version) but overlap with CloudTrail. I enable CloudTrail data events and skip S3 access logs unless compliance specifically requires both. Flow: CloudTrail → S3 → Athena for ad-hoc audit queries.

Deep dive (spend 15–25 minutes here)

Bucket per layer vs single bucket: a single bucket with prefix separation is simpler to manage but harder to govern. Lifecycle rules apply per prefix, which works, but IAM conditions on prefixes (s3:prefix) are error-prone — a trailing slash or wildcard mismatch silently grants broader access than intended. Separate buckets make IAM simple: arn:aws:s3:::lake-curated-prod/* is unambiguous. The trade-off: managing 3-4 buckets per environment instead of 1.

S3 request rate limits: S3 supports 5,500 GET and 3,500 PUT requests per second per prefix. With the Hive-style prefix layout, each dt= partition is a separate prefix, so request limits are effectively unlimited for time-partitioned data. But if all writes target a single prefix (e.g., streaming to a non-partitioned bucket), you can hit limits. Mitigation: add random prefix entropy or use hourly partitions.

Encryption key management: SSE-KMS with a customer-managed key (CMK) gives audit trails on who accessed the key (CloudTrail key events) and the ability to revoke access by disabling the key. But KMS has a request rate limit: 30,000 requests/second per key per region. At high read volumes (millions of S3 GETs/hour), you can hit KMS throttling. Mitigation: use S3 Bucket Keys, which cache the data encryption key at the bucket level, reducing KMS calls by 99%.

Cross-account access: if the lake serves multiple AWS accounts (prod, staging, analytics), bucket policies grant cross-account access to specific IAM roles. The analytics account's role assumes access via sts:AssumeRole with an external ID. The bucket policy grants the role's ARN read access to lake-curated-prod/*. This is more secure than making the bucket public or sharing IAM credentials.

Data retention and compliance: for GDPR, we may need to delete specific records from raw data — but raw is designed as immutable. The approach: tag files containing PII, and when a deletion request arrives, rewrite the affected files with the specific records removed. Iceberg/Delta on the curated layer handle this natively with row-level deletes. Raw file rewriting is expensive and should be batched monthly.

Landing zone bucket setup with encryption and public access block

import boto3
import json

def setup_landing_zone(env='prod', region='us-east-1'):
    s3 = boto3.client('s3', region_name=region)
    layers = ['raw', 'staging', 'curated']

    for layer in layers:
        bucket = f'lake-{layer}-{env}'
        s3.create_bucket(Bucket=bucket)

        # Block all public access
        s3.put_public_access_block(
            Bucket=bucket,
            PublicAccessBlockConfiguration={
                'BlockPublicAcls': True, 'IgnorePublicAcls': True,
                'BlockPublicPolicy': True, 'RestrictPublicBuckets': True
            }
        )

        # Enable default encryption (SSE-KMS)
        s3.put_bucket_encryption(
            Bucket=bucket,
            ServerSideEncryptionConfiguration={
                'Rules': [{'ApplyServerSideEncryptionByDefault': {
                    'SSEAlgorithm': 'aws:kms',
                    'KMSMasterKeyID': f'alias/lake-{layer}-key'
                }, 'BucketKeyEnabled': True}]
            }
        )

        # Versioning on raw only
        if layer == 'raw':
            s3.put_bucket_versioning(
                Bucket=bucket,
                VersioningConfiguration={'Status': 'Enabled'}
            )
use aws_sdk_s3 as s3;
use s3::types::{
    BucketVersioningStatus, PublicAccessBlockConfiguration,
    ServerSideEncryptionByDefault, ServerSideEncryptionConfiguration,
    ServerSideEncryptionRule, VersioningConfiguration,
};

pub async fn setup_landing_zone(env: &str, region: &str) {
    let config = aws_config::defaults(aws_config::BehaviorVersion::latest())
        .region(aws_config::Region::new(region.to_string()))
        .load()
        .await;
    let client = s3::Client::new(&config);
    let layers = ["raw", "staging", "curated"];

    for layer in &layers {
        let bucket = format!("lake-{layer}-{env}");

        client.create_bucket().bucket(&bucket).send().await.unwrap();

        // Block all public access
        client
            .put_public_access_block()
            .bucket(&bucket)
            .public_access_block_configuration(
                PublicAccessBlockConfiguration::builder()
                    .block_public_acls(true)
                    .ignore_public_acls(true)
                    .block_public_policy(true)
                    .restrict_public_buckets(true)
                    .build(),
            )
            .send()
            .await
            .unwrap();

        // SSE-KMS default encryption
        let sse = ServerSideEncryptionConfiguration::builder()
            .rules(
                ServerSideEncryptionRule::builder()
                    .apply_server_side_encryption_by_default(
                        ServerSideEncryptionByDefault::builder()
                            .sse_algorithm(s3::types::ServerSideEncryption::AwsKms)
                            .kms_master_key_id(format!("alias/lake-{layer}-key"))
                            .build(),
                    )
                    .bucket_key_enabled(true)
                    .build(),
            )
            .build();
        client
            .put_bucket_encryption()
            .bucket(&bucket)
            .server_side_encryption_configuration(sse)
            .send()
            .await
            .unwrap();

        // Versioning on raw layer only
        if *layer == "raw" {
            client
                .put_bucket_versioning()
                .bucket(&bucket)
                .versioning_configuration(
                    VersioningConfiguration::builder()
                        .status(BucketVersioningStatus::Enabled)
                        .build(),
                )
                .send()
                .await
                .unwrap();
        }
    }
}
#import <Foundation/Foundation.h>
#include <string>
#include <vector>

// Conceptual AWS S3 client protocol — production would use the
// AWS C++ SDK or signed REST calls.
@protocol AWSS3Client <NSObject>
- (void)createBucket:(NSString *)bucket;
- (void)putPublicAccessBlock:(NSString *)bucket config:(NSDictionary *)cfg;
- (void)putBucketEncryption:(NSString *)bucket config:(NSDictionary *)cfg;
- (void)putBucketVersioning:(NSString *)bucket enabled:(BOOL)enabled;
@end

static void setupLandingZone(id<AWSS3Client> s3,
                             NSString *env,
                             NSString *region) {
    NSArray *layers = @[@"raw", @"staging", @"curated"];

    for (NSString *layer in layers) {
        NSString *bucket = [NSString stringWithFormat:@"lake-%@-%@", layer, env];

        [s3 createBucket:bucket];

        // Block all public access
        [s3 putPublicAccessBlock:bucket config:@{
            @"BlockPublicAcls":       @YES,
            @"IgnorePublicAcls":      @YES,
            @"BlockPublicPolicy":     @YES,
            @"RestrictPublicBuckets": @YES,
        }];

        // SSE-KMS default encryption
        NSString *kmsKey = [NSString stringWithFormat:
                            @"alias/lake-%@-key", layer];
        [s3 putBucketEncryption:bucket config:@{
            @"SSEAlgorithm":    @"aws:kms",
            @"KMSMasterKeyID":  kmsKey,
            @"BucketKeyEnabled": @YES,
        }];

        // Versioning on raw layer only
        if ([layer isEqualToString:@"raw"])
            [s3 putBucketVersioning:bucket enabled:YES];
    }
}

Request path / sequence

Trade-offs I'd say out loud

One bucket per layer vs single bucket

Separate buckets simplify IAM and lifecycle. Single bucket is easier to manage but harder to govern

SSE-S3 vs SSE-KMS

SSE-S3 is free and simpler. SSE-KMS gives key audit trail and revocation but has request rate limits and ~$1/month per key

Versioning on all vs raw only

Versioning on raw protects against accidental deletion. On staging/curated it doubles storage cost for transient data

CloudTrail data events vs S3 access logs

CloudTrail integrates with IAM identity and is queryable via Athena. S3 access logs are free but harder to analyze

Hive-style vs flat prefixes

Hive-style (dt=2024-06-15/) enables automatic partition discovery. Flat paths are simpler but require manual partition registration

Where it usually breaks

  • No lifecycle rules: raw bucket accumulates 500GB/day forever → $4K/month at year 1, $48K/year by year 2; add lifecycle on day 1
  • Staging TTL too short: pipeline retries need staging data that was already deleted → increase staging TTL or pin during retry windows
  • KMS throttling at high read volume: Athena scan triggers millions of decrypt calls → enable S3 Bucket Keys to reduce KMS calls by 99%
  • IAM policy too broad: analytics role with s3:* on curated accidentally deletes production table files → use s3:GetObject only, deny Delete
  • CIDR overlap with peered account: raw bucket inaccessible from analytics account → plan CIDRs and bucket policies before peering

What "good enough" looks like in 60 minutes

A strong answer covers: three-layer architecture (raw, staging, curated), prefix layout for partition pruning, lifecycle rules with concrete tier transitions and cost savings, IAM policies scoped by layer and team, encryption enforcement via bucket policy, and audit logging with CloudTrail.

You do not need to design the data catalog, ETL pipelines, or compliance automation. The interviewer wants to see: understanding that a lake without governance becomes a junk drawer, specific lifecycle rule configuration with cost math, and least-privilege access design.
