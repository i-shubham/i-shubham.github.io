Cloud · Easy · ~60 min

Observe a service you did not write

Inherited services rarely lack code — they lack golden signals and a working dependency map.

60-minute agenda

How I'd open the discussion

You just inherited a service. The previous team is gone or busy. The README is 18 months old. There are no runbooks. The last incident was resolved by someone who 'just knew' where to look. Your job is to make this service observable enough that when it breaks at 3 AM, you can diagnose it without reading every line of code.

I start with the four golden signals: latency, traffic, errors, and saturation. Before reading any code, I check what is already instrumented. Most services have something — CloudWatch metrics from the load balancer, basic application logs, maybe a health check endpoint. My goal in week 1 is not full observability — it is enough visibility to be paged correctly and diagnose the most common failures.

The order matters: (1) health check and uptime monitoring, (2) error rate alerting from logs or ALB metrics, (3) latency percentiles from the load balancer or APM, (4) dependency map — what does this service call and what calls it, (5) resource saturation — CPU, memory, disk, connection pool usage. Each step gives more diagnostic power. By the end of week 2, I should have a dashboard and an on-call runbook.

Open questions worth asking

  • What does this service do — API, worker, cron job?
  • What observability exists today — any metrics, logs, traces?
  • How is it deployed — ECS, EKS, EC2, Lambda?
  • What are the known downstream dependencies?
  • Is there an existing health check endpoint?
  • What broke last time and how was it resolved?
  • Who is currently on-call for this service?
  • What is the SLA — latency, uptime, error rate?

Scope I'd lock first

  • In scope — Golden signals, dependency mapping, basic alerting, on-call runbook
  • In scope — Dashboard with latency, error rate, traffic, and saturation metrics
  • Out of scope — Rewriting the service or refactoring its architecture
  • Defer — Distributed tracing instrumentation, SLO/SLI framework

Approach / design notes

The observability ramp has three phases, executed over 3 weeks.

Phase 1 (Week 1) — Stop the bleeding: before I understand the service, I need to know when it is broken. I check the ALB target group for existing metrics — TargetResponseTime (latency), HTTPCode_Target_5XX_Count (errors), RequestCount (traffic). These are free and already collected. I set up three CloudWatch alarms: 5xx rate > 1% for 5 minutes (P1, pages on-call), p99 latency > 2 seconds for 5 minutes (P2, Slack), and health check failures (P1). If there is no /health endpoint, I create one that returns 200 and checks database connectivity.

Phase 2 (Week 2) — Understand the service: I read the code to identify dependencies and build a dependency map. I create a Grafana dashboard with: traffic (RPS over time), latency (percentile panels), errors (5xx rate with threshold), and saturation (CPU, memory, DB connections, cache usage). I add deployment event annotations so I can correlate changes with metric shifts. I write a runbook: 'When 5xx alert fires → check dashboard → if DB connection saturation is high → check RDS events for failover → if no DB issue → check recent deployments → rollback if deploy within last 30 min.'

Phase 3 (Week 3) — Deepen instrumentation: add custom application metrics (queue depth, cache hit rate, business metrics like orders/minute). If the service makes downstream API calls, add OpenTelemetry or X-Ray traces to understand cross-service latency. Set up log-based metrics: a CloudWatch Logs Insights query that counts specific error patterns (e.g., TimeoutError, ConnectionRefusedError) and alerts on rate changes.

The key insight: you do not need to understand the service to start monitoring it. ALB metrics, container metrics, and database metrics give you the golden signals without touching application code. Code instrumentation (custom metrics, traces) comes later.

Deep dive (spend 15–25 minutes here)

Health check depth: a shallow health check (/health returns 200 if the process is alive) is almost useless — it stays green while the service cannot reach its database. A deep health check verifies: (1) database connection (SELECT 1), (2) Redis PING, (3) downstream API reachability. But a deep check has risks: if the database is slow (not down), the health check times out, the load balancer marks all targets unhealthy, and the service goes dark. Mitigation: set health check timeout shorter than the check's actual timeout (e.g., ALB health check timeout 5s, /health endpoint timeout on DB query 2s with fallback to degraded status, not failure).

Structured logging: if the service logs unstructured text (print statements), the first instrumentation win is switching to structured JSON logs. Each log line includes: timestamp, level, message, request_id, user_id, duration_ms, and error details. This enables CloudWatch Logs Insights queries like: 'fields @timestamp, request_id, duration_ms | filter level = "ERROR" | sort @timestamp desc | limit 100'. Structured logs are searchable; unstructured logs are not.

Deployment correlation: most production incidents correlate with deployments. Adding deployment event markers to the Grafana dashboard (annotations with git SHA, deployer, and timestamp) makes correlation visual: 'p99 latency spiked at 14:30 — deployment at 14:28.' This is the single most useful dashboard feature for incident response. Implementation: a webhook from the CI/CD pipeline that posts an annotation to Grafana's annotation API.

Runbook structure: a good runbook is a decision tree, not a knowledge dump. Start with: 'Which alert fired?' → branch to specific symptoms. For '5xx rate high': check ALB error codes (502 = target crash, 503 = no healthy targets, 504 = timeout). For 502: check container logs for OOM or unhandled exceptions. For 503: check ECS desired count vs running count. For 504: check RDS connections and query latency. Each branch leads to a specific action (restart, rollback, scale up) or an escalation path.

Cost-effective APM: full APM tools (Datadog, New Relic) cost $30+/host/month. For a single inherited service, I start with free tooling: ALB metrics (free), CloudWatch Container Insights ($3/task/month), CloudWatch Logs Insights (pay per query). If the service has complex cross-service interactions, I add X-Ray traces ($5/million traces). Full APM is justified when managing 10+ services, not for one inherited service.

import time
import json
import psycopg2
import redis

def health_check():
    checks = {}
    overall = 'ok'

    # Database check
    try:
        start = time.time()
        conn = psycopg2.connect(DB_URL, connect_timeout=2)
        cur = conn.cursor()
        cur.execute('SELECT 1')
        cur.close()
        conn.close()
        checks['database'] = {'status': 'ok', 'latency_ms': int((time.time()-start)*1000)}
    except Exception as e:
        checks['database'] = {'status': 'error', 'error': str(e)}
        overall = 'degraded'

    # Redis check
    try:
        start = time.time()
        r = redis.Redis.from_url(REDIS_URL, socket_timeout=2)
        r.ping()
        checks['redis'] = {'status': 'ok', 'latency_ms': int((time.time()-start)*1000)}
    except Exception as e:
        checks['redis'] = {'status': 'error', 'error': str(e)}
        overall = 'degraded'

    return {
        'status': overall,
        'checks': checks,
        'timestamp': time.strftime('%Y-%m-%dT%H:%M:%SZ', time.gmtime())
    }
use redis::Commands;
use serde::Serialize;
use std::time::Instant;
use chrono::Utc;

#[derive(Serialize)]
pub struct HealthResult {
    status: String,
    checks: std::collections::HashMap<String, CheckDetail>,
    timestamp: String,
}

#[derive(Serialize)]
struct CheckDetail {
    status: String,
    #[serde(skip_serializing_if = "Option::is_none")]
    latency_ms: Option<u64>,
    #[serde(skip_serializing_if = "Option::is_none")]
    error: Option<String>,
}

pub fn health_check(db_url: &str, redis_url: &str) -> HealthResult {
    let mut checks = std::collections::HashMap::new();
    let mut overall = "ok".to_string();

    // Database check
    let start = Instant::now();
    match postgres::Client::connect(db_url, postgres::NoTls) {
        Ok(mut client) => {
            let _ = client.simple_query("SELECT 1");
            checks.insert("database".into(), CheckDetail {
                status: "ok".into(),
                latency_ms: Some(start.elapsed().as_millis() as u64),
                error: None,
            });
        }
        Err(e) => {
            checks.insert("database".into(), CheckDetail {
                status: "error".into(), latency_ms: None,
                error: Some(e.to_string()),
            });
            overall = "degraded".into();
        }
    }

    // Redis check
    let start = Instant::now();
    match redis::Client::open(redis_url)
        .and_then(|c| c.get_connection())
        .and_then(|mut c| redis::cmd("PING").query::<String>(&mut c))
    {
        Ok(_) => {
            checks.insert("redis".into(), CheckDetail {
                status: "ok".into(),
                latency_ms: Some(start.elapsed().as_millis() as u64),
                error: None,
            });
        }
        Err(e) => {
            checks.insert("redis".into(), CheckDetail {
                status: "error".into(), latency_ms: None,
                error: Some(e.to_string()),
            });
            overall = "degraded".into();
        }
    }

    HealthResult {
        status: overall,
        checks,
        timestamp: Utc::now().format("%Y-%m-%dT%H:%M:%SZ").to_string(),
    }
}

#include <chrono>
#include <string>

// Protocols for the two external dependencies being probed.
@protocol DBClient <NSObject>
- (BOOL)ping:(NSError **)error;
@end

@protocol RedisClient <NSObject>
- (BOOL)ping:(NSError **)error;
@end

@interface HealthChecker : NSObject
@property (nonatomic, strong) id<DBClient>    db;
@property (nonatomic, strong) id<RedisClient> redis;
- (NSDictionary *)check;
@end

@implementation HealthChecker

- (NSDictionary *)check {
    NSMutableDictionary *checks = [NSMutableDictionary dictionary];
    NSString *overall = @"ok";

    // ── Database check ───────────────────────────────────────────────
    {
        auto start = std::chrono::steady_clock::now();
        NSError *err = nil;
        BOOL ok = [_db ping:&err];
        auto elapsed = std::chrono::steady_clock::now() - start;
        int64_t ms = std::chrono::duration_cast<std::chrono::milliseconds>(elapsed).count();

        if (ok) {
            checks[@"database"] = @{@"status": @"ok", @"latency_ms": @(ms)};
        } else {
            checks[@"database"] = @{@"status": @"error",
                                    @"error": err.localizedDescription ?: @"unknown"};
            overall = @"degraded";
        }
    }

    // ── Redis check ──────────────────────────────────────────────────
    {
        auto start = std::chrono::steady_clock::now();
        NSError *err = nil;
        BOOL ok = [_redis ping:&err];
        auto elapsed = std::chrono::steady_clock::now() - start;
        int64_t ms = std::chrono::duration_cast<std::chrono::milliseconds>(elapsed).count();

        if (ok) {
            checks[@"redis"] = @{@"status": @"ok", @"latency_ms": @(ms)};
        } else {
            checks[@"redis"] = @{@"status": @"error",
                                 @"error": err.localizedDescription ?: @"unknown"};
            overall = @"degraded";
        }
    }

    NSDateFormatter *fmt = [[NSDateFormatter alloc] init];
    fmt.dateFormat = @"yyyy-MM-dd'T'HH:mm:ss'Z'";
    fmt.timeZone  = [NSTimeZone timeZoneWithAbbreviation:@"UTC"];

    return @{
        @"status":    overall,
        @"checks":    checks,
        @"timestamp": [fmt stringFromDate:[NSDate date]],
    };
}

Request path / sequence

Trade-offs I'd say out loud

Shallow vs deep health checks

Shallow (process alive) never fires false alarms but misses dependency failures. Deep (check DB, cache) catches real issues but can cascade failures if dependencies are slow

CloudWatch vs Datadog/New Relic

CloudWatch is built-in and cheap. Datadog gives richer dashboards and APM but costs $30+/host/month. Start with CloudWatch, upgrade when managing 10+ services

Alert on symptoms vs causes

Symptom-based (5xx rate) catches all failure types but does not tell you why. Cause-based (DB connection errors) is specific but misses novel failures. Use both: symptom for paging, cause for diagnosis

Dashboard depth

Minimal dashboard (4 golden signals) is quick to build and easy to read. Comprehensive dashboard (20+ panels) gives more detail but takes longer and causes information overload

Instrumentation effort

Infrastructure metrics (ALB, container) are free and immediate. Application metrics require code changes but give business-relevant signals. Start with infra, add app metrics weekly

Where it usually breaks

  • Deep health check takes 10 seconds (DB is slow) → ALB marks target unhealthy → all traffic stops → cascade failure; set health check timeout shorter than dependency timeout
  • Alert threshold too sensitive (5xx > 0.1%) → pages for a single 500 error from a bot → alert fatigue; start at 1% and tighten after establishing baseline
  • Logs are unstructured → Logs Insights queries return garbage → cannot diagnose errors; first fix is structured JSON logging
  • Deployment annotations not set up → latency spike at 2 AM, no idea if someone deployed → add CI/CD webhook to Grafana annotations
  • Runbook says 'check X' but does not say what to do if X is bad → runbook must have actions, not just observations

Follow-ups if time remains

  • How would you set up SLOs and error budgets for this service?
  • How do you handle observability for a service with no source code access (third-party)?
  • How would you add distributed tracing across 10 interdependent services?
  • How do you balance observability cost with insight value as you add more instrumentation?

What "good enough" looks like in 60 minutes

A strong answer covers: the four golden signals as the framework, a phased approach (week 1: alerts from existing metrics, week 2: dashboard + runbook, week 3: custom metrics), dependency mapping, and a health check that verifies downstream dependencies. The key insight: you can monitor a service without understanding its code by using infrastructure metrics.

You do not need to design the full APM platform or SLO framework. The interviewer wants to see: a pragmatic, time-boxed approach to making an unknown service operable, understanding of what 'observable' means in practice (not just 'add logging'), and a runbook mindset — observability is only useful if it reduces time to diagnosis.
