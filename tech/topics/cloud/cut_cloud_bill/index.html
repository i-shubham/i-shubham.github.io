Cut a surprising cloud bill in half

Surprise bills usually hide in egress, idle, orphaned disks, and 'temporary' resources from last quarter.

60-minute agenda

How I'd open the discussion

The cloud bill jumped from $40K to $85K in two months and nobody can explain why. This is a forensics problem first and an optimization problem second. Before cutting anything, I need to understand where the money goes and what changed.

The usual suspects: (1) egress charges — cross-AZ, cross-region, or internet egress that nobody budgeted for, (2) idle compute — EC2 instances, RDS instances, and Kubernetes nodes running 24/7 with 5% CPU utilization, (3) orphaned resources — EBS volumes from terminated instances, old snapshots, unused Elastic IPs, abandoned load balancers, (4) storage — S3 buckets with no lifecycle rules accumulating terabytes, and (5) over-provisioned databases — db.r5.4xlarge for a database that could run on db.r5.large.

I start with the AWS Cost Explorer or the Cost and Usage Report (CUR). Group by service, then by resource tag, then by usage type. The CUR gives line-item detail: which resources, what usage type (DataTransfer-Out-Bytes, EBS:VolumeUsage.gp3), and the unblended cost. Within 30 minutes, I can identify the top 10 cost drivers and which changed the most month-over-month.

Open questions worth asking

  • What is the current monthly bill and what was it 3 months ago?
  • Are resources tagged with owner and cost center?
  • Which AWS services are the top cost drivers?
  • Is there a Cost and Usage Report (CUR) configured?
  • Are Reserved Instances or Savings Plans in place?
  • Multi-account — org-level billing or per-account?
  • Who has permission to create resources — anyone or gated?
  • Is there a FinOps team or owner for cloud costs?

Scope I'd lock first

  • In scope — Identify top cost drivers, eliminate waste, right-size, implement Savings Plans
  • In scope — Tagging enforcement, budget alerts, cost monitoring dashboard
  • Out of scope — Cloud migration to a different provider
  • Defer — Full FinOps program with chargeback, automated governance

Data model

-- Cost analysis queries (on AWS CUR data in Athena)
-- ────────────────────────────────────────────────────

-- Top 10 cost drivers by service
SELECT
  line_item_product_code AS service,
  SUM(line_item_unblended_cost) AS monthly_cost
FROM cur_database.cur_table
WHERE month = '6' AND year = '2024'
GROUP BY line_item_product_code
ORDER BY monthly_cost DESC
LIMIT 10;

-- Orphaned EBS volumes (unattached)
SELECT
  line_item_resource_id,
  SUM(line_item_unblended_cost) AS monthly_cost,
  MAX(line_item_usage_type) AS usage_type
FROM cur_database.cur_table
WHERE line_item_product_code = 'AmazonEC2'
  AND line_item_usage_type LIKE '%EBS:VolumeUsage%'
  AND line_item_resource_id NOT IN (
    SELECT DISTINCT line_item_resource_id
    FROM cur_database.cur_table
    WHERE line_item_operation = 'AttachVolume'
  )
GROUP BY line_item_resource_id
ORDER BY monthly_cost DESC;

Approach / design notes

The cost reduction follows a standard playbook: forensics, quick wins, right-sizing, commitments, and governance.

Forensics (Day 1-3): pull the CUR into Athena and run the queries: top 10 services by cost, top 10 resources by cost, and month-over-month delta by service. In this scenario, the $45K increase came from: (1) 8 new dev instances left running 24/7 ($8K), (2) S3 storage growing unchecked without lifecycle ($5K cumulative), (3) a new data pipeline creating massive cross-AZ transfers ($7K), (4) RDS instances upsized for a one-time migration and never downsized ($6K), and (5) natural growth without Savings Plans ($19K of on-demand at full price).

Quick wins (Week 1-2): delete orphaned resources ($5K), schedule dev instances to stop overnight ($8K), add S3 lifecycle rules ($5K). Total: $18K/month saved with minimal risk.

Right-sizing (Week 3-4): use CloudWatch metrics (CPU, memory, network) over 30 days to identify over-provisioned instances. Right-size in staging first, then production. For RDS, use Performance Insights to validate that the smaller instance handles peak load. Total: $12K saved.

Commitments (Week 5-6): with a stable baseline of $45K/month (after quick wins and right-sizing), commit $20K/month to a Compute Savings Plan (1-year, no upfront). This gives ~30% discount on the committed portion: saves ~$8.5K/month. Additionally, optimize egress: VPC endpoints for S3 ($2K saved), CloudFront for static assets ($1K saved). Total: $11.5K saved.

Total savings: $18K + $12K + $11.5K = $41.5K. New bill: ~$43.5K (49% reduction).

Deep dive (spend 15–25 minutes here)

CUR vs Cost Explorer: Cost Explorer is good for high-level trends but lacks resource-level detail. The CUR (Cost and Usage Report) is a line-item export to S3, queryable via Athena. For cost forensics, CUR is essential — it tells you exactly which EBS volume costs $X/month, which S3 bucket, which data transfer path. I set up CUR on day 1 if it is not already enabled.

Reserved Instances vs Savings Plans: RIs are resource-specific (this instance type in this region). Savings Plans are spend-based (commit $X/hour of compute, apply anywhere). For most organizations, Compute Savings Plans are better because they survive right-sizing: if you downsize from r5.4xlarge to r5.xlarge, the Savings Plan still applies. An RI for the old instance type would become unused.

Cross-AZ transfer: AWS charges $0.01/GB for cross-AZ traffic. An application with 3 AZs, services talking to databases in different AZs, and microservice-to-microservice calls can easily generate 500GB/month of cross-AZ traffic = $5,000/month. Mitigation: use AZ-aware routing (prefer same-AZ replicas for database reads), deploy replicated caches (ElastiCache with replicas in each AZ), and consolidate chatty services into the same AZ when HA allows.

EBS snapshot cost: old snapshots accumulate silently. A 500GB snapshot costs $0.05/GB/month = $25/month. If a team creates daily snapshots with 30-day retention but the lifecycle policy is not configured, after a year you have 365 snapshots × $25 = $9,125/month. I audit snapshots by age and add automated lifecycle: keep 7 daily, 4 weekly, 12 monthly.

Sustained cost governance: savings erode without ongoing discipline. I establish: (1) weekly cost review meeting with engineering leads, (2) budget alerts at 80% and 100% per team, (3) Slack bot that posts daily cost delta, (4) quarterly Savings Plan review to adjust commitments. The Slack bot is the most effective — daily visibility prevents gradual drift.

Orphaned EBS and idle instance detector

import boto3
from datetime import datetime, timedelta

def find_orphaned_ebs_volumes(region='us-east-1'):
    ec2 = boto3.client('ec2', region_name=region)
    volumes = ec2.describe_volumes(
        Filters=[{'Name': 'status', 'Values': ['available']}]
    )['Volumes']

    orphans = []
    for v in volumes:
        age_days = (datetime.now(v['CreateTime'].tzinfo) - v['CreateTime']).days
        monthly_cost = v['Size'] * 0.10  # gp3 at $0.08/GB, estimate
        tags = {t['Key']: t['Value'] for t in v.get('Tags', [])}
        orphans.append({
            'volume_id': v['VolumeId'],
            'size_gb': v['Size'],
            'age_days': age_days,
            'monthly_cost': round(monthly_cost, 2),
            'owner': tags.get('owner', 'UNTAGGED'),
            'name': tags.get('Name', 'unnamed')
        })
    return sorted(orphans, key=lambda x: x['monthly_cost'], reverse=True)

def find_idle_instances(region='us-east-1', cpu_threshold=5.0):
    ec2 = boto3.client('ec2', region_name=region)
    cw = boto3.client('cloudwatch', region_name=region)
    instances = ec2.describe_instances(
        Filters=[{'Name': 'instance-state-name', 'Values': ['running']}]
    )
    idle = []
    for r in instances['Reservations']:
        for i in r['Instances']:
            avg_cpu = cw.get_metric_statistics(
                Namespace='AWS/EC2', MetricName='CPUUtilization',
                Dimensions=[{'Name': 'InstanceId', 'Value': i['InstanceId']}],
                StartTime=datetime.utcnow() - timedelta(days=14),
                EndTime=datetime.utcnow(), Period=86400,
                Statistics=['Average']
            )['Datapoints']
            avg = sum(d['Average'] for d in avg_cpu) / len(avg_cpu) if avg_cpu else 0
            if avg < cpu_threshold:
                idle.append({'id': i['InstanceId'], 'type': i['InstanceType'],
                             'avg_cpu': round(avg, 1)})
    return idle
use aws_sdk_ec2 as ec2;
use aws_sdk_cloudwatch as cw;
use chrono::{Duration, Utc};
use serde::Serialize;

#[derive(Debug, Serialize)]
pub struct OrphanVolume {
    pub volume_id: String,
    pub size_gb: i32,
    pub age_days: i64,
    pub monthly_cost: f64,
    pub owner: String,
    pub name: String,
}

pub async fn find_orphaned_ebs_volumes(region: &str) -> Vec<OrphanVolume> {
    let config = aws_config::defaults(aws_config::BehaviorVersion::latest())
        .region(aws_config::Region::new(region.to_string()))
        .load().await;
    let client = ec2::Client::new(&config);

    let resp = client
        .describe_volumes()
        .filters(ec2::types::Filter::builder().name("status").values("available").build())
        .send().await.unwrap();

    let now = Utc::now();
    let mut orphans: Vec<OrphanVolume> = resp.volumes().iter().map(|v| {
        let created = v.create_time().unwrap();
        let age_days = (now - *created).num_days();
        let size = v.size().unwrap_or(0);
        let monthly_cost = (size as f64) * 0.10;
        let tags: std::collections::HashMap<&str, &str> = v.tags().iter()
            .map(|t| (t.key().unwrap_or(""), t.value().unwrap_or("")))
            .collect();
        OrphanVolume {
            volume_id: v.volume_id().unwrap_or_default().into(),
            size_gb: size,
            age_days,
            monthly_cost: (monthly_cost * 100.0).round() / 100.0,
            owner: tags.get("owner").unwrap_or(&"UNTAGGED").to_string(),
            name: tags.get("Name").unwrap_or(&"unnamed").to_string(),
        }
    }).collect();

    orphans.sort_by(|a, b| b.monthly_cost.partial_cmp(&a.monthly_cost).unwrap());
    orphans
}

#[derive(Debug, Serialize)]
pub struct IdleInstance {
    pub id: String,
    pub instance_type: String,
    pub avg_cpu: f64,
}

pub async fn find_idle_instances(region: &str, cpu_threshold: f64) -> Vec<IdleInstance> {
    let config = aws_config::defaults(aws_config::BehaviorVersion::latest())
        .region(aws_config::Region::new(region.to_string()))
        .load().await;
    let ec2_client = ec2::Client::new(&config);
    let cw_client = cw::Client::new(&config);

    let resp = ec2_client
        .describe_instances()
        .filters(ec2::types::Filter::builder()
            .name("instance-state-name").values("running").build())
        .send().await.unwrap();

    let mut idle = Vec::new();
    let now = Utc::now();

    for reservation in resp.reservations() {
        for inst in reservation.instances() {
            let iid = inst.instance_id().unwrap_or_default();
            let stats = cw_client
                .get_metric_statistics()
                .namespace("AWS/EC2")
                .metric_name("CPUUtilization")
                .dimensions(cw::types::Dimension::builder()
                    .name("InstanceId").value(iid).build())
                .start_time((now - Duration::days(14)).into())
                .end_time(now.into())
                .period(86400)
                .statistics(cw::types::Statistic::Average)
                .send().await.unwrap();

            let pts = stats.datapoints();
            let avg = if pts.is_empty() { 0.0 } else {
                pts.iter().map(|d| d.average().unwrap_or(0.0)).sum::<f64>() / pts.len() as f64
            };
            if avg < cpu_threshold {
                idle.push(IdleInstance {
                    id: iid.into(),
                    instance_type: inst.instance_type()
                        .map(|t| t.as_str().to_string())
                        .unwrap_or_default(),
                    avg_cpu: (avg * 10.0).round() / 10.0,
                });
            }
        }
    }
    idle
}
#import <Foundation/Foundation.h>
#include <vector>
#include <string>
#include <algorithm>

struct OrphanVolume {
    std::string volumeId;
    int         sizeGb;
    int         ageDays;
    double      monthlyCost;
    std::string owner;
    std::string name;
};

struct IdleInstance {
    std::string instanceId;
    std::string instanceType;
    double      avgCpu;
};

// Conceptual AWS client protocols — production uses signed REST or C++ SDK.
@protocol AWSEC2Client <NSObject>
- (NSArray<NSDictionary *> *)describeVolumesAvailable;
- (NSArray<NSDictionary *> *)describeRunningInstances;
@end

@protocol AWSCloudWatchClient <NSObject>
- (NSArray<NSNumber *> *)avgCPUForInstance:(NSString *)iid days:(int)days;
@end

static std::vector<OrphanVolume> findOrphanedEBSVolumes(id<AWSEC2Client> ec2) {
    NSArray *volumes = [ec2 describeVolumesAvailable];
    std::vector<OrphanVolume> orphans;

    for (NSDictionary *v in volumes) {
        int sizeGb = [v[@"Size"] intValue];
        int ageDays = [v[@"AgeDays"] intValue];
        double cost = sizeGb * 0.10;
        NSDictionary *tags = v[@"Tags"] ?: @{};

        orphans.push_back({
            [v[@"VolumeId"] UTF8String],
            sizeGb, ageDays,
            round(cost * 100.0) / 100.0,
            [tags[@"owner"] UTF8String] ?: "UNTAGGED",
            [tags[@"Name"] UTF8String] ?: "unnamed",
        });
    }
    std::sort(orphans.begin(), orphans.end(),
              [](auto &a, auto &b) { return a.monthlyCost > b.monthlyCost; });
    return orphans;
}

static std::vector<IdleInstance> findIdleInstances(id<AWSEC2Client> ec2,
                                                   id<AWSCloudWatchClient> cw,
                                                   double cpuThreshold) {
    NSArray *instances = [ec2 describeRunningInstances];
    std::vector<IdleInstance> idle;

    for (NSDictionary *inst in instances) {
        NSString *iid = inst[@"InstanceId"];
        NSArray<NSNumber *> *points = [cw avgCPUForInstance:iid days:14];

        double avg = 0;
        if (points.count > 0) {
            double sum = 0;
            for (NSNumber *pt in points) sum += pt.doubleValue;
            avg = sum / points.count;
        }
        if (avg < cpuThreshold) {
            idle.push_back({
                iid.UTF8String,
                [inst[@"InstanceType"] UTF8String],
                round(avg * 10.0) / 10.0,
            });
        }
    }
    return idle;
}

Request path / sequence

Trade-offs I'd say out loud

Savings Plans vs Reserved Instances

Savings Plans survive right-sizing and region changes. RIs give slightly higher discounts but lock you to specific instance families

Aggressive vs conservative right-sizing

Aggressive saves more but risks performance degradation. I right-size to 40% peak utilization with monitoring and quick scale-up path

Single AZ vs multi-AZ cost

Single AZ eliminates cross-AZ charges but sacrifices HA. Acceptable for dev/staging; never for production

Spot for production

60-70% savings but risk of interruption. Use for stateless, retryable workloads only; never for databases or single-instance services

Upfront vs no-upfront Savings Plans

All upfront saves ~5% more but locks capital. No-upfront preserves flexibility; start there and upgrade if committed

Where it usually breaks

  • Right-sized instance cannot handle Black Friday peak — monitor 30 days including peak events; keep scale-up automation ready
  • Savings Plan purchased for old instance family, then right-sized to different family — Compute Savings Plan avoids this; EC2 SP does not
  • Dev instances auto-stop breaks CI/CD running at night — whitelist CI runners from schedule; use Fargate for CI instead
  • S3 lifecycle deletes data needed for a compliance audit — Glacier with 7-year retention, not deletion; confirm with legal before setting expiry
  • Cost dashboard shows reduction but bill stays high — data transfer increase offset compute savings; monitor all categories, not just EC2

What "good enough" looks like in 60 minutes

A strong answer covers: CUR-based forensics to identify cost drivers, a phased action plan (quick wins, right-sizing, commitments), specific savings math per phase, and governance to sustain savings. Show concrete numbers: '$13.5K in orphaned resources' is more persuasive than 'delete unused stuff.'

You do not need to design the full FinOps program or chargeback billing system. The interviewer wants to see: systematic cost analysis (not guessing), prioritized actions (biggest impact first), understanding of Savings Plans vs RIs, and a plan to prevent regression.
