Design IAM for a platform team

Platform IAM is about scalable roles and guardrails — not long-lived access keys in a wiki.

60-minute agenda

How I'd open the discussion

Platform IAM is the difference between 'developers can deploy safely' and 'someone accidentally deleted the production database.' The goal is least privilege at scale: 50 engineers across 8 teams need different levels of access to 200+ AWS resources, and the permissions must be auditable, revocable, and impossible to accidentally escalate.

The foundation is roles over users. No IAM user accounts for engineers — everyone authenticates via SSO (Okta/Azure AD) and assumes a role. Roles are scoped by team and environment: team-orders-dev has read/write to dev resources, team-orders-prod has read-only plus deploy permissions, and an SRE on-call role has broader access with a 1-hour session expiry.

Permission boundaries are the guardrail that IAM policies alone cannot provide. A team admin can create roles for their team, but the permission boundary ensures they cannot create a role with more permissions than their boundary allows. This prevents privilege escalation: even if team-orders-admin creates a new role with AdministratorAccess, the boundary caps it.

Open questions worth asking

  • How many engineers and teams?
  • SSO provider — Okta, Azure AD, Google Workspace?
  • Multi-account or single account?
  • Compliance requirements — SOC2, PCI, HIPAA?
  • Current IAM state — users with access keys or roles?
  • CI/CD pipeline — how do deploys authenticate?
  • Break-glass access needs — who and for what?
  • Rotation policy for any remaining service credentials?

Approach / design notes

The IAM architecture has four layers: identity, roles, boundaries, and audit.

Identity: all human access goes through SSO (Okta). No IAM users, no access keys for engineers. SSO maps Okta groups to AWS IAM roles via AWS SSO (IAM Identity Center). When an engineer is added to the 'orders-dev' Okta group, they can assume the team-orders-dev role in the dev account. Removal from the group revokes access immediately — no key rotation needed.

Roles: four levels per team: dev (full access in dev account), prod-read (read-only in prod), prod-deploy (deploy permissions: ECS update, ECR push, but not database admin), and admin (team administration: create roles within the team's permission boundary). Session durations decrease with privilege: dev=8h, prod-read=4h, prod-deploy=1h, break-glass=1h.

Boundaries: every role has a permission boundary attached. The boundary defines the maximum permissions the role can ever have, regardless of what policies are attached. If the boundary allows ec2:*, ecs:*, s3:* but denies iam:CreateUser, no role within that boundary can create IAM users — even if someone attaches AdministratorAccess. This is the guardrail against privilege escalation. Platform team manages boundaries; team admins manage policies within them.

Audit: CloudTrail logs every AssumeRole, API call, and console sign-in. I set up Athena queries to detect: (1) break-glass usage — alert immediately, (2) unused roles — no AssumeRole events in 90 days → candidate for removal, (3) permission escalation attempts — IAM policy changes outside of Terraform, (4) access from unexpected locations — non-VPN IPs assuming sensitive roles.

Deep dive (spend 15–25 minutes here)

Permission boundary mechanics: a boundary is an IAM policy attached as a boundary, not as a permission. The effective permissions are the intersection of the role's policies AND the boundary. If the policy allows s3:* and iam:CreateUser, but the boundary only allows s3:*, the effective permission is s3:* only. The boundary never grants permissions — it only restricts. This means team admins can safely create and modify policies within their team: they cannot accidentally (or maliciously) grant permissions beyond the boundary.

OIDC federation for CI/CD: GitHub Actions generates an OIDC token containing claims like repo, ref, and environment. The AWS IAM role trust policy validates these claims: only the 'main' branch of the 'org/orders' repo can assume the deploy role. No static secrets stored in GitHub. If a repo is compromised, you revoke the trust relationship from the AWS side. Session duration is 30 minutes — enough for a deploy, short enough to limit blast radius.

Break-glass procedure: (1) engineer requests break-glass in PagerDuty incident, (2) PagerDuty notifies the on-call platform engineer, (3) engineer authenticates via SSO with MFA to the sre-break-glass role, (4) CloudTrail captures every API call during the session, (5) after 1 hour the session expires automatically, (6) post-incident review audits all actions taken. Break-glass usage is alarmed: any AssumeRole to the break-glass role triggers a Slack/PD alert.

Unused permission detection: I run a weekly Athena query against CloudTrail to find actions that are in a role's policy but were never invoked in the last 90 days. IAM Access Analyzer also provides this via policy generation from access activity. For each unused permission, I open a PR to remove it from the Terraform-managed policy. This continuously tightens access toward true least privilege.

Service control policies (SCPs): in a multi-account setup, SCPs on the organizational unit provide a second boundary above IAM. An SCP that denies ec2:RunInstances for instance types larger than r5.2xlarge prevents any role in any account from launching expensive instances — regardless of their IAM permissions. SCPs are the nuclear option: use them for organization-wide guardrails (no public S3 buckets, no IAM users, required encryption).

import boto3

def find_unused_roles(days_threshold=90):
    iam = boto3.client('iam')
    roles = iam.list_roles()['Roles']
    unused = []

    for role in roles:
        if role['Path'].startswith('/aws-service-role/'):
            continue
        last_used = role.get('RoleLastUsed', {})
        last_date = last_used.get('LastUsedDate')
        if last_date is None:
            unused.append({'role': role['RoleName'], 'reason': 'never used'})
        else:
            from datetime import datetime, timezone
            age = (datetime.now(timezone.utc) - last_date).days
            if age > days_threshold:
                unused.append({
                    'role': role['RoleName'],
                    'last_used': last_date.isoformat(),
                    'days_idle': age
                })
    return unused
use aws_sdk_iam as iam;
use chrono::{DateTime, Utc};
use serde::Serialize;

#[derive(Debug, Serialize)]
pub struct UnusedRole {
    pub role: String,
    pub reason: String,
    pub last_used: Option<String>,
    pub days_idle: Option<i64>,
}

pub async fn find_unused_roles(days_threshold: i64) -> Vec<UnusedRole> {
    let config = aws_config::load_defaults(aws_config::BehaviorVersion::latest()).await;
    let client = iam::Client::new(&config);

    let resp = client.list_roles().send().await.unwrap();
    let now = Utc::now();
    let mut unused = Vec::new();

    for role in resp.roles() {
        let path = role.path();
        if path.starts_with("/aws-service-role/") {
            continue;
        }
        let role_name = role.role_name().to_string();

        match role.role_last_used().and_then(|r| r.last_used_date()) {
            None => {
                unused.push(UnusedRole {
                    role: role_name,
                    reason: "never used".into(),
                    last_used: None,
                    days_idle: None,
                });
            }
            Some(last_date) => {
                let last_dt: DateTime<Utc> = (*last_date).into();
                let age = (now - last_dt).num_days();
                if age > days_threshold {
                    unused.push(UnusedRole {
                        role: role_name,
                        reason: format!("idle {age} days"),
                        last_used: Some(last_dt.to_rfc3339()),
                        days_idle: Some(age),
                    });
                }
            }
        }
    }
    unused
}
#import <Foundation/Foundation.h>
#include <vector>
#include <string>

struct UnusedRole {
    std::string roleName;
    std::string reason;
    std::string lastUsed; // ISO-8601 or empty
    int         daysIdle;
};

@protocol AWSIAMClient <NSObject>
- (NSArray<NSDictionary *> *)listRoles;
@end

static std::vector<UnusedRole> findUnusedRoles(id<AWSIAMClient> iam,
                                               int daysThreshold) {
    NSArray *roles = [iam listRoles];
    std::vector<UnusedRole> unused;
    NSDate *now = [NSDate date];

    for (NSDictionary *role in roles) {
        NSString *path = role[@"Path"];
        if ([path hasPrefix:@"/aws-service-role/"]) continue;

        NSString *roleName = role[@"RoleName"];
        NSDate *lastDate = role[@"RoleLastUsed"][@"LastUsedDate"];

        if (!lastDate) {
            unused.push_back({roleName.UTF8String, "never used", "", 0});
            continue;
        }

        int age = (int)([now timeIntervalSinceDate:lastDate] / 86400);
        if (age > daysThreshold) {
            NSDateFormatter *fmt = [[NSDateFormatter alloc] init];
            fmt.dateFormat = @"yyyy-MM-dd'T'HH:mm:ssZ";
            unused.push_back({
                roleName.UTF8String,
                "idle " + std::to_string(age) + " days",
                [fmt stringFromDate:lastDate].UTF8String,
                age,
            });
        }
    }
    return unused;
}

Trade-offs I'd say out loud

SSO roles vs IAM users

SSO roles eliminate credential management and enable instant revocation. IAM users are simpler for small teams but create key rotation burden

Permission boundaries vs SCPs

Boundaries scope individual roles; SCPs scope entire accounts. Use both: SCPs for org-wide guardrails, boundaries for team-level limits

Broad roles vs fine-grained

Broad roles are easier to manage but violate least privilege. Fine-grained roles multiply the management burden. 4 levels per team is a reasonable middle ground

OIDC federation vs stored secrets

OIDC eliminates secret management for CI/CD. Stored secrets are simpler but create rotation requirements and leak risk

Short vs long session durations

Shorter sessions reduce blast radius but annoy developers with re-auth. Match duration to the privilege level: 8h for dev, 1h for prod-deploy

Where it usually breaks

  • SSO outage: nobody can access AWS → break-glass IAM user (the only IAM user) with MFA and sealed credentials stored in a vault
  • Permission boundary too restrictive: team cannot deploy because a new service needs a permission not in the boundary → platform team reviews and updates boundary (30-min SLA)
  • Break-glass used for non-emergency: engineer assumes break-glass to avoid waiting for proper role → audit catches it; require incident ID for break-glass access
  • OIDC token for wrong branch: misconfigured trust policy allows feature branches to deploy to prod → condition must include ref:refs/heads/main
  • Access review finds 30% of role assignments unused: engineers moved teams but SSO groups were not updated → automate group sync from HR system

What "good enough" looks like in 60 minutes

A strong answer covers: SSO-based authentication with no IAM users, role hierarchy with environment-based access levels, permission boundaries to prevent escalation, break-glass procedure with full audit, and OIDC federation for CI/CD. Explain the intersection model of boundaries and policies.

You do not need to write the full Terraform or design the ABAC policy engine. The interviewer wants to see: understanding that IAM is a scalability problem (not just a security checklist), permission boundaries as the key guardrail, and operational awareness (break-glass, access review, unused permission detection).
