Design a VPC for a multi-tier app

A VPC diagram is easy; NAT bills and overly wide security groups are where the design meets production.

60-minute agenda

How I'd open the discussion

Every multi-tier app VPC starts the same way: public subnets for the load balancer, private subnets for the application tier, and more private subnets for databases. The diagram is trivial — but production surprises hide in NAT gateway bills, overly permissive security groups, CIDR exhaustion when you need to peer, and the IPv6 question nobody answered upfront.

I sketch public subnets for ALB/NLB only — no EC2 instances with public IPs. Private subnets for app (ECS/EKS tasks, ASGs) and a separate private tier for data (RDS, ElastiCache). Tiers talk through security groups referencing each other: the ALB SG allows 443 inbound from the internet, the app SG allows traffic only from the ALB SG, and the DB SG allows 5432 only from the app SG. This is layered defense: even if someone compromises the ALB, they cannot reach the database directly.

Then the real questions: NAT gateway per AZ is $32/month each plus $0.045/GB processed. For a service pulling 500GB/month of egress through NAT, that is $22.50 on top of the gateway fee. VPC endpoints for S3, DynamoDB, and ECR eliminate that NAT traffic for AWS services. CIDR planning matters once you peer or connect on-prem — overlapping CIDRs are unfixable without rebuilding the VPC.

Open questions worth asking

  • AWS, GCP, or Azure — or multi-cloud?
  • Do we need VPN or Direct Connect to on-prem?
  • IPv6 dual-stack required?
  • How many environments share a VPC vs separate VPCs?
  • Egress inspection or firewall requirements (compliance)?
  • Expected service count — 5 services or 200 microservices?
  • Will we peer with other VPCs or accounts?
  • What compliance framework — SOC2, PCI, HIPAA?
  • Expected egress volume through NAT?
  • Bastion host or SSM Session Manager for SSH access?

Scope I'd lock first

  • In scope — VPC layout for web/app/data tiers, security groups, NAT strategy, CIDR planning
  • In scope — Multi-AZ high availability, VPC endpoints for cost optimization
  • Out of scope — Full org landing zone, multi-account strategy (separate topic)

Public tier

ALB/NLB in public subnets across ≥2 AZs; internet-facing

App tier

ECS/EKS/ASG tasks in private subnets; no public IPs

Data tier

Approach / design notes

The VPC design follows three principles: defense in depth, cost awareness, and growth planning.

Defense in depth: three tiers with escalating isolation. The public tier only contains load balancers — no EC2 instances, no containers. The app tier runs in private subnets with NAT for outbound access (package updates, API calls). The data tier has no internet route at all — RDS and ElastiCache are accessible only from the app tier's security group. NACLs are kept mostly default (allow all) because security groups are the primary control plane, but I add explicit NACL deny rules for any known-bad CIDR ranges if compliance requires it.

Security groups reference each other by SG ID, not by CIDR. This is critical: if the app tier autoscales from 5 to 50 instances, the DB security group does not need updating — it allows traffic from the app SG regardless of how many instances are in it. This also means CIDR changes in the app subnet do not break database access.

Cost awareness: NAT gateways are a hidden cost center. Each gateway costs $32/month base plus $0.045/GB processed. With 3 AZs, that is $96/month before any data flows. I add VPC gateway endpoints for S3 and DynamoDB (free) and interface endpoints for ECR, STS, and CloudWatch Logs (~$7.20/month each per AZ). For a service pulling Docker images from ECR, the interface endpoint eliminates ~50GB/month of NAT traffic, saving $2.25/month per endpoint — it pays for itself at moderate traffic.

Growth planning: the /16 VPC gives 65,536 addresses. With /24 subnets (251 usable each), I have room for 256 subnets — enough for dozens of additional tiers, new AZs, or peered VPCs. The first octet of the third byte indicates the tier (0=public, 10=app, 20=data), leaving 30-255 for future use. When peering with another VPC, the non-overlapping CIDR ensures clean routing. If the office network is 10.0.0.0/8, I would choose 172.16.0.0/16 to avoid conflicts.

Deep dive (spend 15–25 minutes here)

CIDR planning for peering: when two VPCs peer, their CIDRs must not overlap. If VPC-A is 10.1.0.0/16 and VPC-B is 10.2.0.0/16, peering works perfectly. But if VPC-B was also 10.1.0.0/16, you cannot peer them — full stop. This is why I allocate from a pre-planned address scheme at the organization level: dev=10.1.0.0/16, staging=10.2.0.0/16, prod=10.3.0.0/16. If Direct Connect to on-prem is needed, avoid 10.0.0.0/8 entirely if that is the office range — use 172.16.0.0/12 for cloud.

NAT gateway HA: I deploy one NAT gateway per AZ with AZ-specific route tables. If AZ-A's NAT gateway fails, only AZ-A's private subnets lose outbound internet — AZ-B and AZ-C continue normally. The alternative — a single NAT gateway in one AZ — saves money but creates cross-AZ traffic charges ($0.01/GB) and a single point of failure.

Security group rules count: AWS limits each SG to 60 inbound + 60 outbound rules. With microservices, a single app SG allowing traffic from 50 different source SGs approaches this limit. The solution: group services into logical SG tiers rather than one SG per service. For example, all internal microservices share a 'svc-internal' SG that allows traffic from itself (self-referencing rule). This means any service in the SG can talk to any other.

Flow logs for incident response: VPC flow logs capture source/destination IP, port, protocol, and accept/reject status. I send them to S3 (cheaper) for long-term storage and to CloudWatch for real-time alerting. A metric filter on REJECT logs with alert threshold catches port scans or misconfigured services trying to reach the wrong tier.

SSM Session Manager vs bastion: bastion hosts require a public IP, SSH key management, OS patching, and port 22 open in a security group. SSM Session Manager uses IAM for authentication, logs all sessions to CloudWatch, requires no open inbound ports, and costs nothing beyond CloudWatch log storage. The only downside: it requires the SSM agent on instances and a VPC endpoint for SSM in private subnets (or NAT access to the SSM API).

Security group audit for wide-open rules

import boto3

def audit_security_groups(vpc_id: str) -> list:
    ec2 = boto3.client('ec2')
    sgs = ec2.describe_security_groups(
        Filters=[{'Name': 'vpc-id', 'Values': [vpc_id]}]
    )['SecurityGroups']

    issues = []
    for sg in sgs:
        for rule in sg.get('IpPermissions', []):
            for ip_range in rule.get('IpRanges', []):
                cidr = ip_range.get('CidrIp', '')
                if cidr == '0.0.0.0/0' and rule.get('FromPort') != 443:
                    issues.append({
                        'sg_id': sg['GroupId'],
                        'sg_name': sg['GroupName'],
                        'port': rule.get('FromPort'),
                        'issue': f'Wide-open inbound on port {rule.get("FromPort")}'
                    })
                if cidr == '0.0.0.0/0' and sg['GroupName'].startswith('db-'):
                    issues.append({
                        'sg_id': sg['GroupId'],
                        'sg_name': sg['GroupName'],
                        'issue': 'Database SG open to internet — critical'
                    })
    return issues
use aws_sdk_ec2 as ec2;
use serde::Serialize;

#[derive(Debug, Serialize)]
pub struct SgIssue {
    pub sg_id: String,
    pub sg_name: String,
    pub port: Option<i32>,
    pub issue: String,
}

pub async fn audit_security_groups(vpc_id: &str) -> Vec<SgIssue> {
    let config = aws_config::load_defaults(aws_config::BehaviorVersion::latest()).await;
    let client = ec2::Client::new(&config);

    let resp = client
        .describe_security_groups()
        .filters(
            ec2::types::Filter::builder()
                .name("vpc-id")
                .values(vpc_id)
                .build(),
        )
        .send()
        .await
        .expect("Failed to describe security groups");

    let mut issues = Vec::new();

    for sg in resp.security_groups() {
        let sg_id = sg.group_id().unwrap_or_default();
        let sg_name = sg.group_name().unwrap_or_default();

        for rule in sg.ip_permissions() {
            let from_port = rule.from_port();

            for ip_range in rule.ip_ranges() {
                let cidr = ip_range.cidr_ip().unwrap_or_default();

                if cidr == "0.0.0.0/0" && from_port != Some(443) {
                    issues.push(SgIssue {
                        sg_id: sg_id.into(),
                        sg_name: sg_name.into(),
                        port: from_port,
                        issue: format!("Wide-open inbound on port {:?}", from_port),
                    });
                }
                if cidr == "0.0.0.0/0" && sg_name.starts_with("db-") {
                    issues.push(SgIssue {
                        sg_id: sg_id.into(),
                        sg_name: sg_name.into(),
                        port: from_port,
                        issue: "Database SG open to internet — critical".into(),
                    });
                }
            }
        }
    }
    issues
}
#import <Foundation/Foundation.h>
#include <string>
#include <vector>

struct SgIssue {
    std::string sgId;
    std::string sgName;
    int         port;
    std::string issue;
};

// Uses a conceptual AWS EC2 client; production would call the REST API
// or a C++ SDK wrapper.  The audit logic mirrors the Python version.

@protocol AWSEC2Client <NSObject>
- (NSArray<NSDictionary *> *)describeSecurityGroupsInVPC:(NSString *)vpcId;
@end

static std::vector<SgIssue> auditSecurityGroups(id<AWSEC2Client> ec2,
                                                NSString *vpcId) {
    NSArray<NSDictionary *> *sgs = [ec2 describeSecurityGroupsInVPC:vpcId];
    std::vector<SgIssue> issues;

    for (NSDictionary *sg in sgs) {
        NSString *sgId   = sg[@"GroupId"];
        NSString *sgName = sg[@"GroupName"];

        for (NSDictionary *rule in sg[@"IpPermissions"]) {
            int fromPort = [rule[@"FromPort"] intValue];

            for (NSDictionary *ipRange in rule[@"IpRanges"]) {
                NSString *cidr = ipRange[@"CidrIp"];
                if (![cidr isEqualToString:@"0.0.0.0/0"]) continue;

                if (fromPort != 443) {
                    issues.push_back({
                        sgId.UTF8String, sgName.UTF8String, fromPort,
                        "Wide-open inbound on port "
                            + std::to_string(fromPort)
                    });
                }
                if ([sgName hasPrefix:@"db-"]) {
                    issues.push_back({
                        sgId.UTF8String, sgName.UTF8String, fromPort,
                        "Database SG open to internet — critical"
                    });
                }
            }
        }
    }
    return issues;
}

Request path / sequence

Trade-offs I'd say out loud

NAT per AZ vs single NAT

Per-AZ is HA but costs $32/month × N AZs. Single NAT saves money but creates a SPOF and cross-AZ data charges

SG per service vs shared tier SGs

Per-service SGs give fine-grained control but hit rule count limits with many microservices. Tier SGs are simpler but coarser

SSM vs bastion

SSM requires no open ports and uses IAM auth. Bastion is simpler to understand but requires patching, key rotation, and port 22

VPC endpoints cost

Interface endpoints cost $7.20/month/AZ but save NAT processing fees. Worth it when monthly traffic exceeds ~160GB per service

/24 vs /20 subnets

/24 gives 251 hosts — enough for most tiers. /20 gives 4,091 hosts for large EKS clusters but consumes CIDR space quickly

Where it usually breaks

  • CIDR overlap with on-prem network — discovered during Direct Connect setup; VPC must be recreated with new CIDR
  • NAT gateway in one AZ goes down — all private subnets in that AZ lose outbound; deploy NAT per AZ for HA
  • Security group accidentally allows 0.0.0.0/0 on RDS port — database exposed to internet; audit SGs regularly
  • Subnet runs out of IPs: /24 with 251 hosts fills up when EKS pods consume IPs — use /20 for pod subnets or enable prefix delegation
  • VPC endpoint DNS resolution fails — app cannot reach S3 via endpoint; falls back to NAT (silent cost increase)

What "good enough" looks like in 60 minutes

A strong answer covers: three-tier subnet layout with CIDR planning, security group chain referencing SG IDs (not CIDRs), NAT gateway HA strategy with cost awareness, VPC endpoints for S3/DynamoDB, and SSM over bastion. Draw the subnet diagram with AZ layout.

You do not need to design the full Terraform module or explain NACLs in detail. The interviewer wants to see: understanding of defense in depth, awareness of NAT as a cost center, CIDR planning for future peering, and practical security group design.
