Make a Lambda + SQS pipeline production-safe

Lambda+SQS is easy to demo and easy to dual-process when visibility timeout is shorter than the function.

60-minute agenda

How I'd open the discussion

Lambda + SQS is the default serverless event-processing pattern on AWS. It is trivial to demo: message goes into SQS, Lambda polls it, processes it, deletes it. But production reveals every edge case: visibility timeout expires before the Lambda finishes (message reappears and gets processed twice), a poison message that always fails puts the function in an infinite retry loop, batch processing partially fails (some messages succeed, others do not), and concurrency limits cause upstream throttling.

The visibility timeout is the most common misconfiguration. It must be at least 6× the Lambda timeout (AWS recommendation). If Lambda timeout is 30 seconds, visibility timeout should be 180 seconds. If you set both to 30 seconds, a Lambda that takes 25 seconds to process will have the message reappear 5 seconds after processing started — another Lambda invocation picks it up, and you have dual processing.

The dead-letter queue (DLQ) is the safety net. After N failed attempts (I recommend 3), the message moves to the DLQ instead of retrying forever. Without a DLQ, a poison message that always throws an exception gets retried infinitely, consuming Lambda concurrency, incurring costs, and drowning your error logs.

Open questions worth asking

  • What does the Lambda process — orders, notifications, ETL?
  • Message volume — per second, per minute?
  • Processing time — average and worst case?
  • Idempotency requirement — is double-processing safe?
  • Current visibility timeout and Lambda timeout?
  • Is there a DLQ configured?
  • Batch size — single message or batches of 10?
  • Downstream side effects — database writes, API calls, emails?
  • Ordering requirement — FIFO or standard queue?
  • Concurrency limits or reserved concurrency set?

Scope I'd lock first

  • In scope — Visibility timeout, DLQ config, idempotency, partial batch failure handling, concurrency
  • In scope — Monitoring and alerting for DLQ depth, processing errors, and lag
  • Out of scope — Lambda function business logic redesign
  • Defer — FIFO queue ordering guarantees, cross-region SQS replication

-- Idempotency table (DynamoDB)
Table: idempotency_keys
  Partition Key: idempotency_key (String)  -- e.g., "order-{order_id}-{operation}"
  TTL attribute: expires_at (Number)       -- epoch seconds, 24h after creation

Attributes:
  idempotency_key:  String   -- unique per operation
  status:           String   -- 'processing' | 'completed' | 'failed'
  result:           String   -- cached result for completed operations
  created_at:       Number   -- epoch seconds
  expires_at:       Number   -- TTL for auto-cleanup

-- Usage pattern:
-- 1. PutItem with ConditionExpression: attribute_not_exists(idempotency_key)
--    If succeeds: first time processing, proceed
--    If fails (ConditionalCheckFailedException): duplicate, skip or return cached result
-- 2. After processing: UpdateItem status='completed', result=...
-- 3. TTL auto-deletes after 24h

Approach / design notes

The production-safe pipeline addresses five failure modes.

1. Dual processing (visibility timeout): set visibility timeout to 6× Lambda timeout. With Lambda timeout at 30s, visibility is 180s. This gives the Lambda function 30 seconds to complete, and if it fails or times out, the message remains invisible for another 150 seconds before reappearing for retry. If the Lambda succeeds, it deletes the message from the queue.

2. Poison messages (DLQ): after 3 receive attempts (maxReceiveCount=3), the message moves to the DLQ. The DLQ has 14-day retention for inspection. A CloudWatch alarm fires when ApproximateNumberOfMessagesVisible > 0 on the DLQ. I build a simple DLQ consumer that logs the message body for debugging and optionally replays it to the main queue after the bug is fixed.

3. Duplicate processing (idempotency): SQS guarantees at-least-once delivery. A message can be delivered twice during infrastructure events (SQS internal retry). The Lambda must be idempotent: use a DynamoDB table to track processed message IDs (or a domain-specific idempotency key like order_id + operation). Before processing, PutItem with a condition that the key does not exist. If the key exists, skip processing. TTL on the DynamoDB item auto-cleans after 24 hours.

4. Partial batch failure: with batch size 10, if 8 messages succeed and 2 fail, by default the entire batch is retried (including the 8 that already succeeded). Enable ReportBatchItemFailures: the Lambda returns a list of failed message IDs, and SQS only retries those specific messages. This requires the function to catch per-message exceptions and return the partial failure response.

5. Downstream protection (concurrency): if the Lambda writes to RDS, unlimited concurrency could open 1,000 connections and overwhelm the database. Set reserved_concurrent_executions to a safe limit (e.g., 50). SQS automatically adjusts polling rate to match Lambda concurrency. Messages queue up during spikes and drain when capacity is available.

Deep dive (spend 15–25 minutes here)

ReportBatchItemFailures implementation: the Lambda handler must return a specific response format. The batchItemFailures key contains a list of objects with itemIdentifier set to the SQS message ID. SQS uses this to determine which messages to make visible again. If the handler throws an unhandled exception (crashes), ALL messages in the batch are retried. The handler must catch per-message exceptions and accumulate failures, never let one bad message crash the entire batch.

FIFO vs Standard queues: Standard queues give at-least-once delivery with best-effort ordering. FIFO queues give exactly-once processing (via deduplication) and strict ordering within a message group. FIFO queues have a throughput limit: 300 transactions/sec without batching, 3,000/sec with batching. For our 1,000 messages/min, FIFO works if ordering matters. But FIFO adds complexity: message group IDs, deduplication IDs, and the fact that a stuck message blocks all messages in its group.

Concurrency and database connections: with reserved concurrency of 50 and batch size of 10, we process at most 500 messages simultaneously. If each Lambda instance opens a database connection, that is 50 connections. For RDS with 100 max_connections, this leaves 50 for other services. If the connection count is a concern, use RDS Proxy, which multiplexes many Lambda connections into a smaller pool of database connections.

Cost optimization: Lambda charges per invocation and per 100ms of duration. With batch size 10, we reduce invocations by 10×. But larger batches increase the risk of timeout (10 messages × 2 sec each = 20 sec per batch, dangerously close to 30 sec timeout). The batching window (maximum_batching_window_in_seconds=5) waits up to 5 seconds to accumulate a full batch before invoking. This reduces invocations during low-traffic periods without adding latency during spikes.

DLQ replay strategy: after fixing the bug that caused failures, I replay DLQ messages by reading from the DLQ and sending them back to the main queue. But I must be careful: if the fix is not actually correct, replayed messages will fail again and cycle back to the DLQ. I process DLQ messages in small batches (10 at a time) and monitor the error rate before replaying the remaining batch.

Lambda handler with idempotency and partial batch failure

import json
import boto3
import time

dynamodb = boto3.resource('dynamodb')
idemp_table = dynamodb.Table('idempotency_keys')

def handler(event, context):
    batch_failures = []

    for record in event['Records']:
        message_id = record['messageId']
        try:
            body = json.loads(record['body'])
            idemp_key = f"{body['order_id']}-{body['action']}"

            # Idempotency check
            try:
                idemp_table.put_item(
                    Item={
                        'idempotency_key': idemp_key,
                        'status': 'processing',
                        'created_at': int(time.time()),
                        'expires_at': int(time.time()) + 86400  # 24h TTL
                    },
                    ConditionExpression='attribute_not_exists(idempotency_key)'
                )
            except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
                continue  # already processed, skip

            process_order(body)
            idemp_table.update_item(
                Key={'idempotency_key': idemp_key},
                UpdateExpression='SET #s = :s',
                ExpressionAttributeNames={'#s': 'status'},
                ExpressionAttributeValues={':s': 'completed'}
            )
        except Exception as e:
            print(f'Failed message {message_id}: {e}')
            batch_failures.append({'itemIdentifier': message_id})

    return {'batchItemFailures': batch_failures}
use aws_sdk_dynamodb as ddb;
use lambda_runtime::{service_fn, LambdaEvent};
use serde::{Deserialize, Serialize};
use std::time::{SystemTime, UNIX_EPOCH};

#[derive(Deserialize)]
struct SqsEvent { #[serde(rename = "Records")] records: Vec<SqsRecord> }

#[derive(Deserialize)]
struct SqsRecord {
    #[serde(rename = "messageId")] message_id: String,
    body: String,
}

#[derive(Deserialize)]
struct OrderBody { order_id: String, action: String }

#[derive(Serialize)]
struct BatchResponse {
    #[serde(rename = "batchItemFailures")]
    batch_item_failures: Vec<BatchFailure>,
}

#[derive(Serialize)]
struct BatchFailure { #[serde(rename = "itemIdentifier")] item_identifier: String }

async fn handler(
    event: LambdaEvent<SqsEvent>,
    ddb_client: &ddb::Client,
) -> Result<BatchResponse, lambda_runtime::Error> {
    let mut failures = Vec::new();
    let now = SystemTime::now().duration_since(UNIX_EPOCH)?.as_secs() as i64;

    for record in &event.payload.records {
        let result: Result<(), Box<dyn std::error::Error>> = async {
            let body: OrderBody = serde_json::from_str(&record.body)?;
            let idemp_key = format!("{}-{}", body.order_id, body.action);

            // Idempotency check via conditional put
            let put_res = ddb_client
                .put_item()
                .table_name("idempotency_keys")
                .item("idempotency_key", ddb::types::AttributeValue::S(idemp_key.clone()))
                .item("status", ddb::types::AttributeValue::S("processing".into()))
                .item("created_at", ddb::types::AttributeValue::N(now.to_string()))
                .item("expires_at", ddb::types::AttributeValue::N((now + 86400).to_string()))
                .condition_expression("attribute_not_exists(idempotency_key)")
                .send()
                .await;

            if let Err(e) = &put_res {
                if e.to_string().contains("ConditionalCheckFailed") {
                    return Ok(()); // already processed
                }
                put_res?;
            }

            process_order(&body).await?;

            ddb_client
                .update_item()
                .table_name("idempotency_keys")
                .key("idempotency_key", ddb::types::AttributeValue::S(idemp_key))
                .update_expression("SET #s = :s")
                .expression_attribute_names("#s", "status")
                .expression_attribute_values(":s", ddb::types::AttributeValue::S("completed".into()))
                .send()
                .await?;
            Ok(())
        }.await;

        if result.is_err() {
            failures.push(BatchFailure { item_identifier: record.message_id.clone() });
        }
    }
    Ok(BatchResponse { batch_item_failures: failures })
}

@protocol AWSDynamoDB <NSObject>
- (BOOL)putItemIfNotExists:(NSDictionary *)item table:(NSString *)table;
- (void)updateItemStatus:(NSString *)key to:(NSString *)status table:(NSString *)table;
@end

struct BatchFailure {
    std::string itemIdentifier;
};

@interface LambdaSQSHandler : NSObject
@property (nonatomic, strong) id<AWSDynamoDB> ddb;
- (NSDictionary *)handleEvent:(NSDictionary *)event;
@end

@implementation LambdaSQSHandler

- (NSDictionary *)handleEvent:(NSDictionary *)event {
    NSArray *records = event[@"Records"];
    NSMutableArray *failures = [NSMutableArray array];
    NSTimeInterval now = [[NSDate date] timeIntervalSince1970];

    for (NSDictionary *record in records) {
        NSString *messageId = record[@"messageId"];
        @try {
            NSData *bodyData = [record[@"body"] dataUsingEncoding:NSUTF8StringEncoding];
            NSDictionary *body = [NSJSONSerialization JSONObjectWithData:bodyData
                                                                options:0 error:nil];
            NSString *idempKey = [NSString stringWithFormat:@"%@-%@",
                                  body[@"order_id"], body[@"action"]];

            // Idempotency: conditional put — skip if key already exists
            BOOL inserted = [_ddb putItemIfNotExists:@{
                @"idempotency_key": idempKey,
                @"status":          @"processing",
                @"created_at":      @((int64_t)now),
                @"expires_at":      @((int64_t)now + 86400),
            } table:@"idempotency_keys"];

            if (!inserted) continue; // already processed

            // processOrder(body) — application logic placeholder
            [_ddb updateItemStatus:idempKey to:@"completed"
                             table:@"idempotency_keys"];

        } @catch (NSException *ex) {
            NSLog(@"Failed message %@: %@", messageId, ex.reason);
            [failures addObject:@{@"itemIdentifier": messageId}];
        }
    }

    return @{@"batchItemFailures": failures};
}

@end

Trade-offs I'd say out loud

Visibility timeout

Too short: dual processing. Too long: delayed retries on legitimate failures. 6× Lambda timeout is the safe default

Batch size

Larger batches reduce invocations (cost) but increase timeout risk and partial failure complexity. 10 is the sweet spot for most workloads

DLQ max receive count

Lower count (2) moves messages to DLQ faster but may discard transient failures. Higher count (5) gives more retry chances but delays poison message isolation

Idempotency store

DynamoDB is fast and serverless. Redis is cheaper at scale but needs management. For most Lambda use cases, DynamoDB with TTL is ideal

Standard vs FIFO queue

Standard is simpler and higher throughput. FIFO gives ordering and dedup but has throughput limits and message group blocking

Where it usually breaks

  • Visibility timeout shorter than Lambda timeout — message reappears during processing; dual processing of orders
  • No DLQ configured — poison message retries infinitely; consumes all Lambda concurrency; legitimate messages queue up
  • ReportBatchItemFailures not enabled — one bad message in a batch causes all 10 to retry; the 9 good ones are re-processed
  • Idempotency key collision — two different operations generate the same key; second operation silently skipped
  • Lambda concurrency too high — 500 concurrent Lambdas each open a database connection; RDS max_connections exceeded; all invocations fail

What "good enough" looks like in 60 minutes

A strong answer covers: visibility timeout at 6× Lambda timeout, DLQ with maxReceiveCount=3 and alerting, idempotency via DynamoDB conditional writes, partial batch failure reporting, and concurrency limits for downstream protection. Draw the flow and explain what goes wrong without each safeguard.

You do not need to design the full DLQ replay mechanism or the FIFO ordering strategy. The interviewer wants to see: awareness of the specific failure modes (dual processing, poison messages, partial batch), concrete configuration values with reasoning, and idempotency as an application responsibility, not a queue feature.
