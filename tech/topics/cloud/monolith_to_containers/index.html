Move a monolith to ECS/EKS without a big bang

The risky part isn't Docker — it's cutting traffic while the monolith and new services still share a database.

60-minute agenda

How I'd open the discussion

Containerizing a monolith is a migration problem, not a Docker problem. The Dockerfile is the easiest part. The hard parts are: routing traffic between the monolith and new services during the transition, managing a shared database when both systems write to it, and having a rollback plan that does not require a meeting.

I use the strangler fig pattern: new functionality goes to a container service, and existing functionality migrates one route at a time. An API gateway or ALB path-based routing sends /api/v2/orders to the new ECS service and everything else to the monolith. The monolith shrinks over 6–12 months until nothing is left.

The database is the real constraint. Both the monolith and the new service read and write the same tables. During the transition, you have dual-write risks, schema migration coordination, and transaction boundary mismatches. The clean approach is: the monolith keeps ownership of the database, and the new service calls the monolith's API for data access until the route is fully migrated. Only then does the new service get direct database access, and the monolith stops serving that route.

Open questions worth asking

  • What language/framework is the monolith (Java, Python, Node)?
  • How big is the monolith — lines of code, number of routes?
  • Which services to extract first — highest-risk or most independent?
  • Does the team have container/K8s experience?
  • ECS (Fargate) or EKS — build vs operate tradeoff?
  • Current deployment method for the monolith?
  • CI/CD pipeline maturity?
  • Database — single Postgres, multiple databases, or NoSQL?
  • Session management — sticky sessions, Redis, JWT?
  • Timeline pressure — 3 months or 12 months?

Scope I'd lock first

  • In scope — Strangler migration: containerize routes incrementally, traffic routing, shared DB management
  • In scope — ECS/EKS setup, CI/CD pipeline for new services, rollback strategy
  • Out of scope — Full microservices architecture with event sourcing
  • Defer — Service mesh, distributed tracing infrastructure, database decomposition

Approach / design notes

The migration follows three phases: lift, strangle, and decommission.

Phase 1 — Lift (Week 1-4): containerize the monolith itself first. Create a Dockerfile, deploy it on ECS alongside the existing EC2 deployment, and route 1% of traffic to the container via ALB weighted targets. This validates that the monolith works in a container (environment variables, file system assumptions, session handling) without extracting any services yet. Once the containerized monolith is stable at 100% traffic, decommission the EC2 instances.

Phase 2 — Strangle (Month 2-9): extract services one route group at a time. Start with the most independent, highest-value route — Orders API has 5 routes and touches 3 tables. Extract the code into a new repository, write a separate ECS task definition, and deploy with 0% traffic. Run shadow traffic (duplicate requests to the new service, compare responses, discard the new response) for 1 week. Then canary at 10% with real traffic, monitoring error rate and latency. Increase to 50%, then 100% over 2 weeks.

Database strategy during strangling: the new Orders service initially calls the monolith's internal API for database access. This avoids dual-write issues — the monolith is the single writer. Once the route is fully migrated (100% traffic to the new service), we give the service direct database access and remove the monolith's code for those routes. The database tables transfer ownership.

Phase 3 — Decommission (Month 9-12): once all routes are migrated, the monolith serves no traffic. Keep it running for 2 weeks as a rollback safety net. Then shut it down. Clean up the shared database: each service gets its own schema or database, enforced by connection credentials.

Rollback at every stage: ALB rule changes are instant (< 60 seconds). If the new service has errors, flip the ALB rule to send 100% to the monolith. Feature flags provide a second layer: the monolith's code path is never deleted until the service has been stable for 30 days.

Deep dive (spend 15–25 minutes here)

ECS vs EKS decision: ECS with Fargate is operationally simpler — no cluster management, no node scaling, no Kubernetes version upgrades. But EKS gives you the Kubernetes ecosystem: Helm charts, Istio service mesh, custom operators. My default: start with ECS Fargate unless the team already has Kubernetes expertise or needs features like CronJobs, DaemonSets, or custom scheduling. For most monolith-to-container migrations, ECS is sufficient and reduces operational overhead during a period when the team is already learning new patterns.

Session management: if the monolith uses server-side sessions (Express session, Django sessions), containerization breaks sticky sessions because containers scale and terminate freely. The fix: externalize sessions to Redis/ElastiCache before containerizing. This is a prerequisite for the migration, not something you discover after deployment.

Health check design: the ECS health check must distinguish between 'service is starting up' and 'service is unhealthy.' I use a two-stage approach: a startup probe (check that the DB connection is established and migrations are run) and a readiness probe (check that the service can serve requests). ECS supports a startPeriod parameter — health check failures during this period are ignored. I set startPeriod=60 seconds for services that need warm-up time.

Database connection pooling: the monolith maintains 10 persistent connections to Postgres. When the new service also opens 10 connections, the total doubles. With 5 containerized services at 10 connections each = 50 + monolith's 10 = 60. Postgres default max_connections is 100, but performance degrades above 50. Use PgBouncer as a connection pooler: all services connect to PgBouncer, which maintains a smaller pool to Postgres. This is essential before decomposing the monolith into multiple services.

Shadow traffic for validation: before routing real traffic, I replay production requests to the new service and compare responses. This catches: serialization differences (date formats, null handling), missing query parameters, incorrect database queries, and performance issues. The shadow is implemented by the ALB's ability to forward to multiple target groups — but ALB does not support true mirroring. Alternative: a lightweight proxy (nginx mirror module) that duplicates requests to the new service and logs discrepancies.

Extracted service Dockerfile with health check

"""
Equivalent of the Dockerfile's CMD + HEALTHCHECK for the extracted service.

Dockerfile reference:
  HEALTHCHECK --interval=15s --timeout=5s --start-period=60s --retries=3
    CMD curl -f http://localhost:8080/health || exit 1
  CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "4", "app:create_app()"]
"""
import time, threading
from flask import Flask, jsonify

def create_app() -> Flask:
    app = Flask(__name__)
    _startup_time = time.monotonic()

    @app.route('/health')
    def health():
        """Mirrors the Docker HEALTHCHECK endpoint."""
        uptime = time.monotonic() - _startup_time
        return jsonify(status='ok', uptime_s=round(uptime, 1))

    @app.route('/')
    def index():
        return jsonify(service='extracted-svc', version='1.0')

    return app


if __name__ == '__main__':
    # Matches Dockerfile CMD: gunicorn 0.0.0.0:8080, 4 workers.
    # Here we use the dev server; production uses gunicorn.
    app = create_app()
    app.run(host='0.0.0.0', port=8080)
//! Rust equivalent of the Dockerfile's CMD + HEALTHCHECK logic.
//!
//! Dockerfile reference:
//!   HEALTHCHECK --interval=15s --timeout=5s --start-period=60s --retries=3
//!     CMD curl -f http://localhost:8080/health || exit 1
//!   CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "4", ...]

use actix_web::{web, App, HttpServer, HttpResponse};
use std::time::Instant;
use std::sync::Arc;

struct AppData {
    startup: Instant,
}

/// Mirrors the Docker HEALTHCHECK endpoint.
async fn health(data: web::Data<Arc<AppData>>) -> HttpResponse {
    let uptime = data.startup.elapsed().as_secs_f64();
    HttpResponse::Ok().json(serde_json::json!({
        "status": "ok",
        "uptime_s": (uptime * 10.0).round() / 10.0,
    }))
}

async fn index() -> HttpResponse {
    HttpResponse::Ok().json(serde_json::json!({
        "service": "extracted-svc",
        "version": "1.0",
    }))
}

#[actix_web::main]
async fn main() -> std::io::Result<()> {
    let data = Arc::new(AppData { startup: Instant::now() });

    // Matches Dockerfile: bind 0.0.0.0:8080, 4 worker threads.
    HttpServer::new(move || {
        App::new()
            .app_data(web::Data::new(data.clone()))
            .route("/health", web::get().to(health))
            .route("/", web::get().to(index))
    })
    .bind("0.0.0.0:8080")?
    .workers(4)
    .run()
    .await
}
/*
 * ObjC++ equivalent of the Dockerfile's CMD + HEALTHCHECK logic.
 *
 * Dockerfile reference:
 *   HEALTHCHECK --interval=15s --timeout=5s --start-period=60s --retries=3
 *     CMD curl -f http://localhost:8080/health || exit 1
 *   CMD ["gunicorn", "--bind", "0.0.0.0:8080", ...]
 */
#import <Foundation/Foundation.h>
#include <chrono>
#include <string>

static auto gStartup = std::chrono::steady_clock::now();

// ── Health endpoint (mirrors Docker HEALTHCHECK target) ──────────────

@interface HealthCheckHandler : NSObject
+ (NSDictionary *)healthResponse;
+ (NSDictionary *)indexResponse;
@end

@implementation HealthCheckHandler

+ (NSDictionary *)healthResponse {
    auto elapsed = std::chrono::steady_clock::now() - gStartup;
    double uptimeS = std::chrono::duration<double>(elapsed).count();
    return @{
        @"status": @"ok",
        @"uptime_s": @(round(uptimeS * 10.0) / 10.0),
    };
}

+ (NSDictionary *)indexResponse {
    return @{
        @"service": @"extracted-svc",
        @"version": @"1.0",
    };
}

@end

// ── Minimal HTTP server sketch (matches Dockerfile EXPOSE 8080) ──────

@interface ServiceBootstrap : NSObject
// Bind 0.0.0.0:8080 with worker threads — mirrors Docker CMD + workers.
- (void)startOnPort:(uint16_t)port workers:(int)n;
@end

@implementation ServiceBootstrap

- (void)startOnPort:(uint16_t)port workers:(int)n {
    // Production: open BSD socket, spawn `n` dispatch worker queues,
    // route /health -> [HealthCheckHandler healthResponse],
    // route /      -> [HealthCheckHandler indexResponse].
    NSLog(@"Service listening on 0.0.0.0:%d with %d workers", port, n);
}

@end

int main() {
    @autoreleasepool {
        ServiceBootstrap *svc = [[ServiceBootstrap alloc] init];
        // Matches Dockerfile CMD: 4 workers on port 8080
        [svc startOnPort:8080 workers:4];
        [[NSRunLoop mainRunLoop] run];
    }
    return 0;
}

Request path / sequence

Trade-offs I'd say out loud

ECS Fargate vs EKS

Fargate is simpler (no cluster ops) but less flexible. EKS gives Kubernetes ecosystem but requires cluster management expertise

Lift-and-shift first vs extract first

Containerizing the monolith first validates the container runtime. Extracting directly is faster but riskier — you change two things at once

API gateway vs ALB path routing

API gateway (Kong, AWS API GW) gives rate limiting, auth, transforms. ALB is simpler and cheaper for basic routing during migration

Shared DB vs API calls during transition

Shared DB is simpler but risks dual-write bugs. API calls add latency but enforce single writer

Big bang vs gradual migration

Big bang is faster but all-or-nothing. Gradual (strangler) is slower but each step is independently rollback-able

Where it usually breaks

  • Container OOM because memory limit set too low — monitor memory usage during shadow testing; set limits at 2× observed peak
  • Session loss after migration — externalize sessions to Redis before containerizing; not after
  • Database connection exhaustion: 5 services × 10 connections = 50 plus monolith's 10 → PgBouncer needed
  • ALB path routing conflict: /api/orders and /api/orders/batch match different rules → order ALB rules by specificity
  • Rollback after schema migration: new service added a DB column that monolith does not know about → use additive-only migrations

Follow-ups if time remains

  • How would you handle stateful components (file uploads, cron jobs) during migration?
  • How do you manage API versioning when monolith and service return slightly different responses?
  • When would you decompose the database into per-service schemas?
  • How would you add distributed tracing across the monolith and new services?

What "good enough" looks like in 60 minutes

A strong answer covers: the strangler fig pattern with ALB path routing, phased traffic migration (shadow → canary → full), database ownership strategy during transition, and instant rollback via ALB rules. Mention the lift-and-shift-first approach to de-risk the container runtime.

You do not need to design the full Kubernetes manifest or the service mesh. The interviewer wants to see: awareness that the database (not Docker) is the hard part, a rollback plan at every stage, and a migration approach that is incrementally shippable — not a 6-month silence followed by a big bang.
