Two Sum variants under memory pressure

Classic Two Sum, but the interviewer keeps shrinking memory until the hash map answer stops working.

1. Problem statement & explanation

Given an array of integers nums and an integer target, return the indices of the two numbers that add up to target. You may not use the same element twice. Assume exactly one valid answer exists.

Read literally this is a one-liner. The reason it survives as an interview question is the second half of the conversation: the interviewer shrinks your memory budget. First you get the hash map. Then they say “the array has 10 billion entries and you have 8 MB of RAM” and the hash map dies. Every good answer to this problem is really an answer to “what do I trade for space?”

The structural insight to voice early: you are searching for a complement. For each element x, you need to know whether target - x exists elsewhere in the array. Everything after this is a decision about which data structure answers “does this value exist?” fast enough within the space you are allowed.

1.1 Input / output

Signature

contract
two_sum(nums: List[int], target: int) -> List[int]   # exactly two indices, ascending

Worked examples

example 1 — answer at the front
Input:  nums = [2, 7, 11, 15], target = 9
Output: [0, 1]
Why:    nums[0] + nums[1] = 2 + 7 = 9
example 2 — repeated value
Input:  nums = [3, 2, 4], target = 6
Output: [1, 2]
Why:    3 + 3 = 6 would need index 0 twice, which is forbidden.
        2 + 4 = 6 uses two distinct indices.
example 3 — duplicates are legal
Input:  nums = [3, 3], target = 6
Output: [0, 1]
Why:    the same *value* twice is fine as long as the *indices* differ.
example 4 — negatives
Input:  nums = [-1, -2, -3, -4, -5], target = -8
Output: [2, 4]
Why:    -3 + -5 = -8. No assumption of positivity anywhere in the algorithm.

Constraints to state back

  • 2 ≤ nums.length ≤ 10^4 in the textbook version; the interesting variant pushes this to 10^10.
  • -10^9 ≤ nums[i], target ≤ 10^9 — so target - nums[i] can reach 2 × 10^9 and overflows signed 32-bit. Widen the complement to 64-bit.
  • Exactly one valid pair exists; the array is not sorted; values may repeat.
  • Output is a pair of indices, not values — this single word decides whether sorting is allowed.

2. Open questions & clarifications

Ask these before writing a line. Each one changes the code you would write, which is exactly what makes them worth asking out loud.

  • Indices or values? If values are acceptable, sorting becomes legal and O(1) extra space is reachable. If indices are required, sorting must carry the original position.
  • Is the array sorted? If yes, skip straight to two pointers: O(n) time, O(1) space, no hash map at all.
  • Exactly one answer, or all answers? “All pairs” changes the output size to O(n²) in the worst case and rules out early return.
  • Can the input be mutated? In-place sorting is only allowed if the caller does not need the original order.
  • How large is n, and what is my memory budget? This is the question the problem is actually about. Ask it explicitly.
  • Are duplicates allowed, and can a pair reuse one index? Confirm [3,3] with target = 6 returns [0,1].
  • Integer width? 32-bit or 64-bit values; does the sum need to be checked for overflow.
  • What if no pair exists? Return empty, return a sentinel, or raise — pick one and be consistent.
  • Is the data in memory or streaming from disk / network? A stream forbids random access and kills the two-pointer solution.

2.1 Suggestions to the candidate

  • Do not jump to the answer. Everyone in the room knows the hash map. Blurting “use a dictionary, O(n)” in the first ten seconds skips the part being graded: problem framing. Spend 60–90 seconds restating the problem and asking clarifications first.
  • Do not open with the optimal solution either. Say the brute force out loud, give its complexity, and explicitly name what is wasteful about it (“I rescan the same suffix for every i”). The optimal solution then arrives as a consequence of that observation rather than as a memorised fact.
  • Narrate the invariant, not the syntax. “When I reach index i, the map holds every value strictly before i” is worth more than any amount of clean typing.
  • Write one worked example on the board and keep it. Use it later to dry-run your code line by line. Candidates who trace their own code catch their own bugs, which reads far better than the interviewer catching them.
  • Say the trade-off in one sentence before you code. “I will spend O(n) space to buy O(n) time; if space is the constraint I will sort instead and pay O(n log n) time.” That sentence is the whole signal of this question.
  • Do not silently assume the array is sorted. It is the single most common wrong assumption here, and the two-pointer solution is invalid without it.
  • Handle the “insert after lookup” ordering deliberately. Mention that writing to the map before checking it would let an element pair with itself when target = 2 * nums[i].
  • Keep talking while you think. Silence is unscorable. If you need to think, say what you are weighing.

3. Brute-force approach

Enumerate every unordered pair and test its sum. This is the definition of the problem transcribed into two loops, which is exactly why it is the right thing to say first: it is obviously correct, so it fixes the target behaviour that every later optimisation must reproduce.

  1. For each index i from 0 to n-1.
  2. For each index j from i+1 to n-1 — starting at i+1 is what enforces “two distinct indices” and avoids testing the same pair twice.
  3. If nums[i] + nums[j] == target, return [i, j].
  4. If the loops finish, no pair exists.

3.1 Code — Python, Rust, Java, C++

from typing import List


def two_sum_brute(nums: List[int], target: int) -> List[int]:
    """Test every unordered pair (i, j) with i < j.

    Obviously correct, obviously quadratic. Stated first so the optimal
    version has something to be measured against.
    """
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):          # j > i keeps the indices distinct
            if nums[i] + nums[j] == target:
                return [i, j]
    return []                              # no pair; caller decides what this means
/// Test every unordered pair (i, j) with i < j.
/// Returns the indices, or `None` when no pair sums to `target`.
pub fn two_sum_brute(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    for i in 0..nums.len() {
        for j in (i + 1)..nums.len() {          // j > i keeps the indices distinct
            // Widen to i64: two i32 values can sum past i32::MAX.
            if nums[i] as i64 + nums[j] as i64 == target as i64 {
                return Some((i, j));
            }
        }
    }
    None
}
class Solution {

    /**
     * Test every unordered pair (i, j) with i < j.
     * Returns the two indices, or an empty array when no pair exists.
     */
    public int[] twoSumBrute(int[] nums, int target) {
        for (int i = 0; i < nums.length; i++) {
            for (int j = i + 1; j < nums.length; j++) {   // j > i: distinct indices
                // Widen to long: two ints can sum past Integer.MAX_VALUE.
                if ((long) nums[i] + nums[j] == target) {
                    return new int[] {i, j};
                }
            }
        }
        return new int[0];
    }
}

// Returns the two indices, or an empty vector when no pair exists.
std::vector<int> twoSumBrute(const std::vector<int>& nums, int target) {

    for (int i = 0; i < n; ++i) {
        for (int j = i + 1; j < n; ++j) {          // j > i: distinct indices
            // Widen to 64-bit: two ints can sum past INT_MAX.
            if (static_cast<std::int64_t>(nums[i]) + nums[j] == target) {
                return {i, j};
            }
        }
    }
    return {};
}

3.2 Complexity

Time O(n²)

n(n−1)/2 pair tests in the worst case. At n = 10⁵ that is 5 × 10¹⁹ comparisons — roughly an hour of CPU.

Space O(1)

Two loop counters. Nothing allocated, input untouched — this is the one dimension where brute force wins.

Why this is not the final answer

The quadratic term comes from re-reading the suffix for every i. But we do not need to search the array — for a fixed i there is exactly one value that would work, namely target - nums[i]. Replacing a linear scan with a membership test is the entire optimisation.

4. Optimised approach

Key insight: the inner loop answers a membership question — “is target - nums[i] somewhere in the array?” A hash map answers that in expected O(1). And we do not even need two passes: if a pair exists, the later of its two indices will find the earlier one already recorded. So one pass suffices, as long as we look up before we insert.

  1. Create an empty map seen: value → index.
  2. Walk i = 0 … n-1. Compute need = target - nums[i] in 64-bit.
  3. If need is a key in seen, return [seen[need], i] — both indices are distinct because seen only holds elements strictly before i.
  4. Otherwise store seen[nums[i]] = i and continue.
The invariant to say out loud

At the top of iteration i, seen contains exactly the values at indices 0 … i-1. Lookup-before-insert is what makes that true, and it is also what prevents an element pairing with itself when target == 2 * nums[i].

4.1 Code — Python, Rust, Java, C++

from typing import Dict, List


def two_sum(nums: List[int], target: int) -> List[int]:
    """One pass, hash map of everything already walked past.

    Invariant: at the top of iteration i, `seen` holds the values at
    indices 0 .. i-1 -- never index i itself.
    """
    seen: Dict[int, int] = {}                  # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:                       # complement appeared earlier
            return [seen[need], i]
        seen[x] = i                            # insert AFTER the lookup
    return []


# Keeping the FIRST index for a repeated value is deliberate: it is the only
# one that can ever be the earlier half of a pair. `seen.setdefault(x, i)`
# would make that explicit if the interviewer asks about duplicates.
use std::collections::HashMap;

/// One pass, hash map of everything already walked past.
///
/// Invariant: at the top of iteration `i`, `seen` holds the values at
/// indices `0..i` -- never index `i` itself.
///
/// Keys are widened to i64 so `target - x` cannot overflow.
pub fn two_sum(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    let mut seen: HashMap<i64, usize> = HashMap::with_capacity(nums.len());
    for (i, &x) in nums.iter().enumerate() {
        let need = target as i64 - x as i64;
        if let Some(&j) = seen.get(&need) {         // complement appeared earlier
            return Some((j, i));
        }
        // entry().or_insert keeps the FIRST index of a repeated value,
        // which is the only one that can be the earlier half of a pair.
        seen.entry(x as i64).or_insert(i);          // insert AFTER the lookup
    }
    None
}
import java.util.HashMap;
import java.util.Map;

class Solution {

    /**
     * One pass, hash map of everything already walked past.
     *
     * Invariant: at the top of iteration i, `seen` holds the values at
     * indices 0 .. i-1 -- never index i itself.
     *
     * Keys are Long so that `target - nums[i]` cannot overflow.
     */
    public int[] twoSum(int[] nums, int target) {
        Map<Long, Integer> seen = new HashMap<>(nums.length * 2);
        for (int i = 0; i < nums.length; i++) {
            long need = (long) target - nums[i];
            Integer j = seen.get(need);                  // complement seen earlier?
            if (j != null) {
                return new int[] {j, i};
            }
            // putIfAbsent keeps the FIRST index of a repeated value.
            seen.putIfAbsent((long) nums[i], i);         // insert AFTER the lookup
        }
        return new int[0];
    }
}
#include <cstdint>
#include <unordered_map>
#include <vector>

// One pass, hash map of everything already walked past.
//
// Invariant: at the top of iteration i, `seen` holds the values at
// indices 0 .. i-1 -- never index i itself.
//
// Keys are 64-bit so that `target - nums[i]` cannot overflow.
std::vector<int> twoSum(const std::vector<int>& nums, int target) {
    std::unordered_map<std::int64_t, int> seen;
    seen.reserve(nums.size() * 2);                  // avoid rehashing mid-pass

    for (int i = 0; i < static_cast<int>(nums.size()); ++i) {
        const std::int64_t need = static_cast<std::int64_t>(target) - nums[i];
        auto it = seen.find(need);                  // complement seen earlier?
        if (it != seen.end()) {
            return {it->second, i};
        }
        // emplace is a no-op if the key exists, so the FIRST index wins.
        seen.emplace(static_cast<std::int64_t>(nums[i]), i);  // insert AFTER lookup
    }
    return {};
}

4.2 Complexity

Time O(n) expected

One pass, one lookup and at most one insert per element. Worst case O(n²) if every key collides — only reachable with an adversarial hash, which is why Rust and Java randomise or tree-ify buckets.

Space O(n)

Up to n entries. Concretely: ~48–64 bytes per entry in a Java HashMap, so 10⁶ elements is tens of MB — the number that breaks under a memory cap.

Edge cases this version already handles

Duplicates ([3,3]), negatives, zero, target = 2 * nums[i], and the two-element minimum. It does not handle the array being larger than RAM — that is section 4.3.

4.3 Variant: O(1) extra space

This is the pivot the page is named for. When the interviewer caps memory, drop the map and buy the same membership test with order instead: sort the array, then converge two pointers from both ends. The sum is monotone in each pointer, so every move eliminates a whole row or column of the pair matrix.

  1. Sort in place. lo = 0, hi = n - 1.
  2. While lo < hi, look at s = nums[lo] + nums[hi].
  3. s == target → found. s < target → lo++ (only a bigger small end can help). s > target → hi--.
The catch, stated before the interviewer says it

Sorting destroys the original indices. If indices are required you must sort (value, index) pairs — which reintroduces O(n) space and defeats the purpose. So this variant is honest only when the caller wants values, or when the input was already sorted.

from typing import List, Optional, Tuple


def two_sum_sorted(nums: List[int], target: int) -> Optional[Tuple[int, int]]:
    """Sort in place, then converge two pointers. Returns the two VALUES.

    Note: CPython's Timsort needs O(n) auxiliary space in the worst case,
    so "O(1) space" here is really "O(1) space given an in-place sort"
    (heapsort, or C++ std::sort / Java Arrays.sort on primitives).
    """
    nums.sort()
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        s = nums[lo] + nums[hi]
        if s == target:
            return nums[lo], nums[hi]
        if s < target:
            lo += 1                    # small end is too small: raise it
        else:
            hi -= 1                    # big end is too big: lower it
    return None
use std::cmp::Ordering;

/// Sort in place, then converge two pointers. Returns the two VALUES.
/// `sort_unstable` is an in-place pattern-defeating quicksort: no heap buffer.
pub fn two_sum_sorted(nums: &mut [i32], target: i32) -> Option<(i32, i32)> {
    if nums.len() < 2 {
        return None;                        // guard: `len() - 1` would underflow
    }
    nums.sort_unstable();

    let (mut lo, mut hi) = (0usize, nums.len() - 1);
    while lo < hi {
        let sum = nums[lo] as i64 + nums[hi] as i64;
        match sum.cmp(&(target as i64)) {
            Ordering::Equal => return Some((nums[lo], nums[hi])),
            Ordering::Less => lo += 1,      // small end too small: raise it
            Ordering::Greater => hi -= 1,   // big end too big: lower it
        }
    }
    None
}
import java.util.Arrays;

class Solution {

    /**
     * Sort in place, then converge two pointers. Returns the two VALUES.
     * Arrays.sort on an int[] is dual-pivot quicksort: in place, no O(n) buffer.
     */
    public int[] twoSumSorted(int[] nums, int target) {
        if (nums.length < 2) {
            return new int[0];
        }
        Arrays.sort(nums);

        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            long sum = (long) nums[lo] + nums[hi];
            if (sum == target) {
                return new int[] {nums[lo], nums[hi]};
            }
            if (sum < target) {
                lo++;                      // small end too small: raise it
            } else {
                hi--;                      // big end too big: lower it
            }
        }
        return new int[0];
    }
}

#include <cstdint>
#include <vector>

// Sort in place, then converge two pointers. Returns the two VALUES.
// std::sort is introsort: in place, no O(n) scratch buffer.
std::vector<int> twoSumSorted(std::vector<int>& nums, int target) {
    if (nums.size() < 2) {
        return {};
    }
    std::sort(nums.begin(), nums.end());

    int lo = 0;
    int hi = static_cast<int>(nums.size()) - 1;
    while (lo < hi) {
        const std::int64_t sum =
            static_cast<std::int64_t>(nums[lo]) + nums[hi];
        if (sum == target) {
            return {nums[lo], nums[hi]};
        }
        if (sum < target) {
            ++lo;                          // small end too small: raise it
        } else {
            --hi;                          // big end too big: lower it
        }
    }
    return {};
}
Time O(n log n)

Dominated by the sort; the two-pointer sweep is O(n). Slower than the hash map, and that is the price of the space saving.

Space O(1)

Two indices, assuming an in-place sort. Nothing scales with n — this is the version that survives the memory cap.

The comparison table to say out loud

Brute force: O(n²) / O(1). Hash map: O(n) / O(n). Sort + two pointers: O(n log n) / O(1). Already sorted input: O(n) / O(1) — strictly the best of all three, which is why “is it sorted?” was question two in section 2.

5. Follow-up discussion if time permits

  • Return all pairs, not just one. Drop the early return and keep counts instead of indices: count[v] lets you emit each pair once, with the v == target - v case handled as C(count[v], 2).
  • 3Sum. Sort, fix index i, then run the section-4.3 two-pointer sweep on the suffix: O(n²) time, O(1) space. The reduction to Two Sum is the whole answer — say it that way.
  • 4Sum / k-Sum. Either recurse down to Two Sum (O(n^(k-1))) or hash all pair sums (O(n²) time and space for k = 4). Discuss which side of the space/time trade you are on.
  • Two Sum on a stream. No random access, so no sorting. Maintain the seen-values set incrementally — O(1) amortised per element, O(n) space, and a Bloom filter turns that into a bounded-memory approximation with a false-positive re-check.
  • Data larger than RAM. External sort into runs on disk, then one sequential two-pointer pass over the head and tail of the sorted file. Or hash-partition by hash(v) mod m so that v and target - v land in the same pass — partition on min(v, target-v) to guarantee it.
  • Two sorted arrays, find a cross pair. Two pointers starting at the head of one and the tail of the other: O(n + m) time, O(1) space, no merge required.
  • Closest pair to target instead of exact. Two pointers again, tracking the best absolute difference; the same monotonicity argument holds.
  • Concurrency. Shard the array, build per-shard maps in parallel, then check complements across shards. Ask whether the answer must be deterministic, because “any valid pair” and “the lexicographically smallest pair” are different problems once you parallelise.
  • What does “good enough” look like here? Clarify indices-vs-values, state the brute force and discard it with a reason, write the one-pass map correctly on the first try, dry-run it on [3,3], then pivot to sort + two pointers when memory is capped and name the index-loss caveat yourself.
