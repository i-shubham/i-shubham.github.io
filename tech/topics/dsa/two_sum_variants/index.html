Two Sum variants under memory pressure

Classic Two Sum, but the interviewer keeps shrinking memory until the hash map answer stops working.

60-minute agenda

How I'd open the discussion

I'd start by confirming the variant: return indices, return values, count pairs, or just existence. Then I'd ask whether the array is sorted. The textbook answer is a hash map — O(n) time, O(n) space — and most candidates stop there.

The interesting conversation starts when the interviewer says 'what if you can't afford that map?' If the array is sorted or we're allowed to sort, two pointers give O(n log n) time with O(1) extra space. If values live in a small range, a bitset beats the hash map. And if n is truly enormous — streaming input that won't fit in RAM — we're into external sort or Bloom-filter territory. I'd sketch all three before writing code, so the interviewer sees I'm not stuck on one tool.

Open questions worth asking

  • Return indices or just boolean existence?
  • Are duplicates allowed — e.g. [3,3] with target 6?
  • Is the input sorted? Can we sort it?
  • Can we mutate the input array?
  • Integer range — small enough for a bitset?
  • Streaming input that doesn't fit in RAM?
  • Do we need all pairs or any one pair?
  • 32-bit vs 64-bit — overflow on sum?

Scope I'd lock first

  • In: classic Two Sum (indices) + sorted variant + memory-constrained discussion.
  • Out: 3Sum / 4Sum full solutions unless follow-up asks.

Functional requirements

  • Given nums and target, find i, j where nums[i] + nums[j] == target.
  • 0-based indices, i != j enforced.
  • Define behavior when no solution exists (return [] or raise).

Non-functional / rough numbers

Time

O(n) with hash map; O(n log n) with sort + two pointers.

Space

O(n) hash map path; O(1) extra for two-pointer path.

Stability

If returning indices, sorting destroys them unless you carry (value, original_index) pairs.

Approach / design notes

Hash map path: iterate i from 0 to n-1. Compute complement = target - nums[i]. If complement is in the map, return [map[complement], i]. Otherwise store nums[i] → i. The classic bug is using the same element twice when 2*x == target — checking 'complement in map' before inserting nums[i] prevents it.

Two-pointer path: create pairs [(val, original_index)] and sort by val. Set lo=0, hi=n-1. If sum < target, lo++. If sum > target, hi--. If equal, return original indices (sorted). This preserves index information that raw sorting destroys.

Memory-constrained path: if values are in [0, 10^6], a boolean array costs ~125 KB instead of a hash map's overhead per entry. For truly huge n, external sort the file, then scan with two file pointers from each end. I'd mention Bloom filters for probabilistic existence checks on streams.

Deep dive (spend 15–25 minutes here)

Walk through nums = [3, 3] with target = 6.

Hash map approach — i=0: complement = 6-3 = 3, map is empty so 3 is not found. Insert {3: 0}. i=1: complement = 6-3 = 3, map has 3 → 0. Return [0, 1]. This works because we check before inserting.

Now consider nums = [1, 5, 3, 7, 4, 2] with target = 7. Walk through: i=0: comp=6, map={1:0}. i=1: comp=2, map={1:0,5:1}. i=2: comp=4, map={1:0,5:1,3:2}. i=3: comp=0, map adds 7:3. i=4: comp=3, map has 3→2 — return [2, 4] (nums[2]+nums[4] = 3+4 = 7).

Two-pointer on same array: sort with indices → [(1,0),(2,5),(3,2),(4,4),(5,1),(7,3)]. lo=0 hi=5: 1+7=8 > 7 → hi--. lo=0 hi=4: 1+5=6 < 7 → lo++. lo=1 hi=4: 2+5=7 → return sorted([5,1]) = [1,5]. But wait — we wanted the original problem's indices, which are (5) and (1) → return [1, 5]. This is why carrying original indices matters.

Edge case: nums = [0, 0, 0] target = 0. Hash map returns [0, 1] on second iteration. If the problem asks for all pairs, we need to continue scanning and collect [0,1], [0,2], [1,2]. This is where the variant question at the start saves you from writing the wrong code.

Hash map, two-pointer, and bitset implementations

from typing import List, Tuple


def two_sum_hashmap(nums: List[int], target: int) -> List[int]:
    """O(n) time, O(n) space — single pass with complement lookup."""
    seen = {}
    for i, v in enumerate(nums):
        comp = target - v
        if comp in seen:
            return [seen[comp], i]
        seen[v] = i
    return []


def two_sum_two_ptr(nums: List[int], target: int) -> List[int]:
    """O(n log n) time, O(1) extra space — requires sorted input.
    We sort with original indices to recover positions."""
    indexed = sorted((v, i) for i, v in enumerate(nums))
    lo, hi = 0, len(indexed) - 1
    while lo < hi:
        s = indexed[lo][0] + indexed[hi][0]
        if s == target:
            return sorted([indexed[lo][1], indexed[hi][1]])
        elif s < target:
            lo += 1
        else:
            hi -= 1
    return []


def two_sum_bitset(nums: List[int], target: int, max_val: int = 10**6) -> bool:
    """Existence-only variant for bounded non-negative values.
    O(n) time, O(max_val) space — trades index info for memory efficiency."""
    bits = bytearray(max_val + 1)
    for v in nums:
        comp = target - v
        if 0 <= comp <= max_val and bits[comp]:
            return True
        if 0 <= v <= max_val:
            bits[v] = 1
    return False
use std::collections::HashMap;

/// O(n) hash-map approach: store each value's index, look up complement.
fn two_sum_hashmap(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    let mut seen: HashMap<i32, usize> = HashMap::new();
    for (i, &v) in nums.iter().enumerate() {
        let comp = target - v;
        if let Some(&j) = seen.get(&comp) {
            return Some((j, i));
        }
        seen.insert(v, i);
    }
    None
}

/// O(n log n) two-pointer on sorted (value, original_index) pairs.
fn two_sum_two_ptr(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    let mut indexed: Vec<(i32, usize)> = nums.iter()
        .copied().enumerate().map(|(i, v)| (v, i)).collect();
    indexed.sort_unstable();
    let (mut lo, mut hi) = (0, indexed.len().saturating_sub(1));
    while lo < hi {
        let s = indexed[lo].0 + indexed[hi].0;
        if s == target {
            let (a, b) = (indexed[lo].1, indexed[hi].1);
            return Some((a.min(b), a.max(b)));
        } else if s < target { lo += 1; }
        else { hi -= 1; }
    }
    None
}

/// Bitset variant (existence-only): O(n) time, O(max_val) space.
fn two_sum_bitset(nums: &[i32], target: i32, max_val: usize) -> bool {
    let mut bits = vec![false; max_val + 1];
    for &v in nums {
        let comp = target - v;
        if comp >= 0 && (comp as usize) <= max_val && bits[comp as usize] {
            return true;
        }
        if v >= 0 && (v as usize) <= max_val {
            bits[v as usize] = true;
        }
    }
    false
}
#import <Foundation/Foundation.h>
#include <vector>
#include <unordered_map>
#include <algorithm>

// O(n) hash-map approach: store each value's index, look up complement
static std::vector<int> twoSumHashMap(const std::vector<int> &nums, int target) {
    std::unordered_map<int, int> seen;
    for (int i = 0; i < (int)nums.size(); i++) {
        int comp = target - nums[i];
        auto it = seen.find(comp);
        if (it != seen.end())
            return {it->second, i};
        seen[nums[i]] = i;
    }
    return {};
}

// O(n log n) two-pointer on sorted (value, original_index) pairs
static std::vector<int> twoSumTwoPtr(const std::vector<int> &nums, int target) {
    std::vector<std::pair<int,int>> indexed;
    for (int i = 0; i < (int)nums.size(); i++)
        indexed.push_back({nums[i], i});
    std::sort(indexed.begin(), indexed.end());
    int lo = 0, hi = (int)indexed.size() - 1;
    while (lo < hi) {
        int s = indexed[lo].first + indexed[hi].first;
        if (s == target) {
            int a = indexed[lo].second, b = indexed[hi].second;
            return {std::min(a,b), std::max(a,b)};
        }
        s < target ? lo++ : hi--;
    }
    return {};
}

// Bitset variant (existence-only): bounded non-negative values
static bool twoSumBitset(const std::vector<int> &nums, int target, int maxVal) {
    std::vector<bool> bits(maxVal + 1, false);
    for (int v : nums) {
        int comp = target - v;
        if (comp >= 0 && comp <= maxVal && bits[comp]) return true;
        if (v >= 0 && v <= maxVal) bits[v] = true;
    }
    return false;
}

Request path / sequence

Trade-offs I'd say out loud

Hash map vs sort

O(n)/O(n) vs O(n log n)/O(1) — choose based on memory budget.

Indices vs values

Returning indices prevents in-place sort; forces copy + original index tracking.

Single vs all pairs

Single pair exits early; all pairs requires full scan or sorted dedup.

Where it usually breaks

  • Using the same element twice when 2*x == target (insert-after-check fixes it).
  • Integer overflow if the language uses fixed-width ints and target is near max.
  • Sorting in place and losing original indices.
  • Assuming uniqueness when duplicates exist (e.g. [3, 3] target 6).
  • Returning unsorted index pair when the spec says 'i < j'.

Follow-ups if time remains

  • Extend to 3Sum — sort + fix one, two-pointer the rest, skip duplicates.
  • Two Sum in a BST — in-order iterator + reverse in-order iterator as two pointers.
  • Streaming Two Sum with 64 MB memory budget — Bloom filter for probabilistic check.
  • Count pairs modulo 1e9+7 — frequency map, watch double-counting same-value pairs.

What "good enough" looks like in 60 minutes

State both hash map and two-pointer approaches, explain when each wins, handle the duplicate and index edge cases cleanly. Bonus for mentioning bitset under bounded range and external sort for streaming — that shows you think past the leetcode sandbox.
