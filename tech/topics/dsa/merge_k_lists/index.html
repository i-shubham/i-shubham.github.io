1. Problem statement & explanation

You are given an array of k linked lists. Each list is already sorted in ascending order. Merge them into a single sorted linked list and return its head.

The reason this is a Hard and not an Easy: the answer hinges on which quantity you put inside the logarithm. There are two sizes in play — k, the number of lists, and N, the total number of nodes across all lists. A solution that ignores the sortedness costs O(N log N). A solution that exploits it costs O(N log k). With k = 10⁴ and N = 5 × 10⁶ that is the difference between log₂N ≈ 22 and log₂k ≈ 13 comparisons per output element.

The structural observation to lead with: at every step, the next element of the merged output must be the smallest of the k current heads — never anything deeper in a list, because each list is sorted. So the whole problem reduces to “repeatedly give me the minimum of k values, with cheap replacement.” That is the definition of a min-heap, and this is exactly the k-way merge inside every external sort.

Worked examples

example 1 — the standard case
Input:  lists = [[1,4,5], [1,3,4], [2,6]]
Output: [1,1,2,3,4,4,5,6]
Why:    duplicates across lists are kept (both 1s, both 4s) — this is a
        merge, not a set union.
example 2 — degenerate inputs
Input:  lists = []        -> Output: []      (k = 0, no lists at all)
Input:  lists = [[]]      -> Output: []      (k = 1, one EMPTY list)
Input:  lists = [[], [1]] -> Output: [1]     (empty lists must be skipped)
Input:  lists = [[2],[1]] -> Output: [1,2]   (input order is not sorted order)
example 3 — the skew case that kills pairwise merging
Input:  lists = [[1..500], [], [], ..., []]   # one long list, k-1 empty
Output: [1..500]
Why:    a naive "merge list 0 with list 1, then with list 2, ..." walks the
        long accumulator k times: O(N*k). The heap does not care.

Constraints to state back

  • k == lists.length, 0 ≤ k ≤ 10^4 — k = 0 is legal, so lists[0] is not safe to touch unguarded.
  • 0 ≤ lists[i].length ≤ 500, so N ≤ 5 × 10^6 nodes total.
  • -10^4 ≤ node.val ≤ 10^4 — small range, which later opens a counting-sort follow-up.
  • Each input list is already sorted ascending. Duplicates are allowed, within and across lists.
  • Output must be a single sorted linked list. Whether you may relink the given nodes or must allocate new ones is question one in section 2.

2. Open questions & clarifications

  • Can I relink the existing nodes, or must the output be freshly allocated? Relinking is O(1) extra memory per node; copying is O(N). This single answer changes the space complexity of everything that follows.
  • What are the relative magnitudes of k and N? If k is tiny (say 3), a hand-rolled pairwise merge is simpler and just as fast; the heap only earns its complexity when k is large.
  • Do all N values fit in memory? If not, the brute force is off the table entirely and we are really discussing external merge sort.
  • Are the input lists guaranteed sorted, or should I validate? If a caller can hand me an unsorted list, the heap silently produces garbage — worth an explicit assertion or a documented precondition.
  • Ascending or descending? Any custom comparator? A comparator makes the min-heap ordering pluggable and is a one-line change; assuming < on integers is an assumption.
  • Can entries in lists be null / empty? Both, per the examples. Confirm that k = 0 returns null rather than throwing.
  • Is stability required? For equal values, must the node from the earlier list come first? Using ≤ in the merge and the list index as heap tie-breaker gives it to you; say so explicitly.
  • Singly or doubly linked? Doubly linked means prev pointers must be fixed up too — easy to forget.
  • Is recursion acceptable? A recursive two-list merge is elegant but is O(N) stack deep; at N = 5 × 10⁶ it overflows. Prefer iterative and say why.
  • Is the input arriving as streams / iterators rather than lists? The heap solution works unchanged, which is a nice thing to point out.

2.1 Suggestions to the candidate

  • Do not open with “use a heap”. First state the reduction: “the next output element is always the minimum of the k current heads.” The heap is then the obvious data structure for that operation, and you have demonstrated the reasoning rather than pattern-matching.
  • Do not skip the baseline. Spend 90 seconds on collect-and-sort. Then say the sentence that earns the points: “this ignores the fact that the inputs are already sorted, and that is the information I should be exploiting.”
  • Say which variable is inside the log, and why. “O(N log k), because the heap only ever holds k elements” is the single most important sentence in this problem. Candidates who say “O(N log N)” for the heap solution lose the point.
  • Use a dummy head node. Announce it: “I will use a sentinel so the first insertion is not a special case.” Every linked-list off-by-one in an interview comes from not doing this.
  • Mention the tie-break before it bites you. In Python, ListNode is not orderable, so a heap of bare nodes raises TypeError on equal values. Push (val, index, node). In Java and C++ supply a comparator. Naming this before you hit it looks like experience.
  • Do not write recursive merge for 5 million nodes. If you start recursive, say “this is O(N) stack deep, so for the stated N I would convert it to a loop” — then convert it.
  • Terminate the output list. When you relink existing nodes, the final node still points at its old successor. Set tail.next = null and say why: forgetting it can create a cycle.
  • Connect it to the real world once. “This is the merge step of an external sort, and the same structure appears in LSM-tree compaction.” One sentence, high signal, then get back to the code.

3. Brute-force approach

Ignore the structure entirely: walk every list, dump all values into one array, sort it, and rebuild a linked list from the sorted array.

  1. Traverse all k lists, appending each val to an array. This is O(N).
  2. Sort the array — O(N log N).
  3. Rebuild a list from the sorted array — O(N).
There is a second brute force — mention both

Instead of sorting, you could scan all k heads on every output step and pick the smallest by linear search. That is O(N·k) time with O(1) space. At k = 10⁴ and N = 5 × 10⁶ it is 5 × 10¹⁰ operations — far worse than sorting. Comparing the two baselines out loud shows you are reasoning about the inputs, not reciting.

3.1 Code — Python, Rust, Java, C++

from typing import List, Optional


class ListNode:
    def __init__(self, val: int = 0, nxt: "Optional[ListNode]" = None) -> None:
        self.val = val
        self.next = nxt


def merge_k_lists_brute(lists: List[Optional[ListNode]]) -> Optional[ListNode]:
    """Flatten every list into one array, sort, rebuild.

    Correct but wasteful: step 2 re-derives an ordering the input already had.
    """
    values: List[int] = []
    for head in lists:
        node = head
        while node is not None:
            values.append(node.val)
            node = node.next

    values.sort()                          # O(N log N) -- the wasteful part

    dummy = ListNode()                     # sentinel: no special case for head
    tail = dummy
    for v in values:
        tail.next = ListNode(v)            # NEW nodes: O(N) extra memory
        tail = tail.next
    return dummy.next

pub struct ListNode {
    pub val: i32,
    pub next: Option<Box<ListNode>>,
}

impl ListNode {
    pub fn new(val: i32) -> Self {
        ListNode { val, next: None }
    }
}

/// Flatten every list into one Vec, sort, rebuild.
/// Correct but wasteful: the sort re-derives an ordering we already had.
pub fn merge_k_lists_brute(lists: Vec<Option<Box<ListNode>>>) -> Option<Box<ListNode>> {
    let mut values: Vec<i32> = Vec::new();
    for head in lists {
        let mut cur = head;
        while let Some(node) = cur {
            values.push(node.val);
            cur = node.next;               // moves ownership forward
        }
    }

    values.sort_unstable();                // O(N log N) -- the wasteful part

    // Build back-to-front: each new node takes the list built so far as `next`.
    let mut head: Option<Box<ListNode>> = None;
    for v in values.into_iter().rev() {
        head = Some(Box::new(ListNode { val: v, next: head }));
    }
    head
}

3.2 Complexity

Time O(N log N)

N to collect, N log N to sort, N to rebuild. At N = 5 × 10⁶ that is roughly 1.1 × 10⁸ comparisons.

Space O(N)

The value array, plus N freshly allocated nodes if you rebuild rather than relink. Two full copies of the data in the worst case.

Why this is not the final answer

A general-purpose sort assumes nothing about its input. We know a great deal: the data arrives as k already-ordered runs. The minimum of the whole collection is always among the k heads, so we never need to compare against more than k candidates — log k, not log N. And relinking instead of rebuilding removes the O(N) allocation.

4. Optimised approach

Key insight: maintain a min-heap containing exactly one node per non-empty list — its current head. Pop the global minimum, append that node to the output, and push its successor. The heap size never exceeds k, so each of the N pops and N pushes costs O(log k).

  1. Push the head of every non-empty list into a min-heap keyed on val. Skip nulls — this is where [[], [1]] is handled.
  2. Create a dummy sentinel node; tail = dummy.
  3. While the heap is non-empty: pop the smallest node, splice it on with tail.next = node; tail = node.
  4. If the popped node has a successor, push that successor. This keeps the invariant “the heap holds the current head of every list that still has nodes.”
  5. Set tail.next = null so no stale pointer survives, then return dummy.next.
The invariant to say out loud

The heap always contains the smallest unconsumed node of every list that is not yet exhausted. Therefore its minimum is the global minimum of everything unconsumed, so appending it preserves sorted order. Because we push a node only when its predecessor is popped, each node enters and leaves the heap exactly once.

4.1 Code — Python, Rust, Java, C++

import heapq
from typing import List, Optional, Tuple


def merge_k_lists(lists: List[Optional[ListNode]]) -> Optional[ListNode]:
    """Min-heap over the k current heads. Relinks nodes, allocates nothing.

    Invariant: the heap holds the current head of every list that still has
    nodes, so heap[0] is the global minimum of everything unconsumed.
    """
    # (value, list_index, node). The index is a tie-breaker: ListNode is not
    # orderable, so without it equal values raise TypeError on comparison.
    heap: List[Tuple[int, int, ListNode]] = []
    for i, head in enumerate(lists):
        if head is not None:               # skip empty lists up front
            heap.append((head.val, i, head))
    heapq.heapify(heap)                    # O(k), cheaper than k pushes

    dummy = ListNode()
    tail = dummy
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node                   # relink, do not copy
        tail = node
        if node.next is not None:
            heapq.heappush(heap, (node.next.val, i, node.next))

    tail.next = None                       # cut the popped node's stale pointer
    return dummy.next
use std::cmp::Reverse;
use std::collections::BinaryHeap;

/// Min-heap over the k current heads.
///
/// `BinaryHeap` is a max-heap, so entries are wrapped in `Reverse`.
/// We heap on `(value, list_index)` and keep the owned nodes in `lists`,
/// which sidesteps ordering `Box<ListNode>` itself.
pub fn merge_k_lists(mut lists: Vec<Option<Box<ListNode>>>) -> Option<Box<ListNode>> {
    let mut heap: BinaryHeap<Reverse<(i32, usize)>> =
        BinaryHeap::with_capacity(lists.len());

    for (i, head) in lists.iter().enumerate() {
        if let Some(node) = head {         // skip empty lists up front
            heap.push(Reverse((node.val, i)));
        }
    }

    let mut dummy = Box::new(ListNode::new(0));
    let mut tail = &mut dummy;

    while let Some(Reverse((_, i))) = heap.pop() {
        // Detach list i's head; its successor becomes the new head of list i.
        let mut node = lists[i].take().expect("heap entry implies a node");
        lists[i] = node.next.take();       // also clears the stale `next`
        if let Some(next) = lists[i].as_ref() {
            heap.push(Reverse((next.val, i)));
        }
        tail.next = Some(node);
        tail = tail.next.as_mut().unwrap();
    }

    dummy.next.take()
}
import java.util.Comparator;
import java.util.PriorityQueue;

class Solution {

    /**
     * Min-heap over the k current heads. Relinks nodes, allocates no nodes.
     *
     * Invariant: the queue holds the current head of every list that still
     * has nodes, so peek() is the global minimum of everything unconsumed.
     */
    public ListNode mergeKLists(ListNode[] lists) {
        // Explicit comparator: ListNode has no natural ordering.
        PriorityQueue<ListNode> heap = new PriorityQueue<>(
                Math.max(1, lists.length),
                Comparator.comparingInt(n -> n.val));

        for (ListNode head : lists) {
            if (head != null) {            // skip empty lists up front
                heap.add(head);
            }
        }

        ListNode dummy = new ListNode();
        ListNode tail = dummy;
        while (!heap.isEmpty()) {
            ListNode node = heap.poll();
            tail.next = node;              // relink, do not copy
            tail = node;
            if (node.next != null) {
                heap.add(node.next);
            }
        }

        tail.next = null;                  // cut the stale pointer
        return dummy.next;
    }
}
#include <functional>
#include <queue>
#include <vector>

// Min-heap over the k current heads. Relinks nodes, allocates nothing.
//
// Invariant: the queue holds the current head of every list that still has
// nodes, so top() is the global minimum of everything unconsumed.
ListNode* mergeKLists(const std::vector<ListNode*>& lists) {
    // std::priority_queue is a max-heap; invert the comparator for a min-heap.
    auto worse = [](const ListNode* a, const ListNode* b) {
        return a->val > b->val;
    };
    std::priority_queue<ListNode*, std::vector<ListNode*>, decltype(worse)>
        heap(worse);

    for (ListNode* head : lists) {
        if (head != nullptr) {                 // skip empty lists up front
            heap.push(head);
        }
    }

    ListNode dummy;
    ListNode* tail = &dummy;
    while (!heap.empty()) {
        ListNode* node = heap.top();
        heap.pop();
        tail->next = node;                     // relink, do not copy
        tail = node;
        if (node->next != nullptr) {
            heap.push(node->next);
        }
    }

    tail->next = nullptr;                      // cut the stale pointer
    return dummy.next;
}

4.2 Complexity

Time O(N log k)

O(k) to heapify the seeds, then N pops and at most N pushes, each O(log k). At N = 5 × 10⁶, k = 10⁴: ~6.6 × 10⁷ comparisons, roughly 1.7× better than the O(N log N) baseline — and it allocates nothing.

Space O(k)

The heap holds at most one node reference per list. Output nodes are the input nodes relinked, so no O(N) term at all.

Edge cases this version already handles

k = 0 → heap never seeded, returns null. [[]] → the null head is skipped. Lists of wildly different lengths → the heap simply shrinks as lists drain. Duplicate values → kept, and stable if the tie-breaker is the list index.

4.3 Variant: pairwise merge, O(1) extra space

The same O(N log k) time is reachable with no heap at all. Merge lists in pairs bottom-up: round one merges (0,1), (2,3), (4,5)…; round two merges the results in pairs; and so on. There are ⌈log₂ k⌉ rounds and each round touches every node at most once, so the total is O(N log k) — with only a couple of pointers of extra state.

The trap this avoids

Merging sequentially — accumulator ⊕ list 1, then ⊕ list 2, … — walks the growing accumulator k times and degrades to O(N·k). Pairwise merging keeps the merged sizes balanced, which is exactly where the log k comes from. Say this difference out loud; it is the thing being tested.

def merge_two(a: Optional[ListNode], b: Optional[ListNode]) -> Optional[ListNode]:
    """Standard two-list merge, iterative so the stack stays O(1)."""
    dummy = ListNode()
    tail = dummy
    while a is not None and b is not None:
        if a.val <= b.val:                 # <= makes the merge STABLE
            tail.next, a = a, a.next
        else:
            tail.next, b = b, b.next
        tail = tail.next
    tail.next = a if a is not None else b  # attach whatever is left
    return dummy.next


def merge_k_lists_pairwise(lists: List[Optional[ListNode]]) -> Optional[ListNode]:
    """Bottom-up pairwise merge: ceil(log2 k) rounds, each O(N)."""
    if not lists:
        return None

    n = len(lists)
    step = 1
    while step < n:
        for i in range(0, n - step, 2 * step):
            lists[i] = merge_two(lists[i], lists[i + step])
        step *= 2                          # 1, 2, 4, 8, ... doubling reach
    return lists[0]
/// Standard two-list merge, iterative so the stack stays O(1).
/// A recursive version would be O(N) frames deep and overflows at N = 5e6.
fn merge_two(
    mut a: Option<Box<ListNode>>,
    mut b: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    let mut dummy = Box::new(ListNode::new(0));
    let mut tail = &mut dummy;

    while a.is_some() && b.is_some() {
        // <= makes the merge stable: ties take from `a` first.
        let take_a = a.as_ref().unwrap().val <= b.as_ref().unwrap().val;
        let mut node = if take_a {
            a.take().unwrap()
        } else {
            b.take().unwrap()
        };
        let rest = node.next.take();
        if take_a { a = rest; } else { b = rest; }

        tail.next = Some(node);
        tail = tail.next.as_mut().unwrap();
    }

    tail.next = if a.is_some() { a } else { b };   // attach the remainder
    dummy.next.take()
}

/// Bottom-up pairwise merge: ceil(log2 k) rounds, each O(N).
pub fn merge_k_lists_pairwise(
    mut lists: Vec<Option<Box<ListNode>>>,
) -> Option<Box<ListNode>> {
    if lists.is_empty() {
        return None;
    }

    let n = lists.len();
    let mut step = 1;
    while step < n {
        let mut i = 0;
        while i + step < n {
            let left = lists[i].take();
            let right = lists[i + step].take();
            lists[i] = merge_two(left, right);
            i += 2 * step;
        }
        step *= 2;                         // 1, 2, 4, 8, ... doubling reach
    }
    lists[0].take()
}
class Solution {

    /** Standard two-list merge, iterative so the stack stays O(1). */
    private ListNode mergeTwo(ListNode a, ListNode b) {
        ListNode dummy = new ListNode();
        ListNode tail = dummy;
        while (a != null && b != null) {
            if (a.val <= b.val) {          // <= makes the merge STABLE
                tail.next = a;
                a = a.next;
            } else {
                tail.next = b;
                b = b.next;
            }
            tail = tail.next;
        }
        tail.next = (a != null) ? a : b;   // attach whatever is left
        return dummy.next;
    }

    /** Bottom-up pairwise merge: ceil(log2 k) rounds, each O(N). */
    public ListNode mergeKListsPairwise(ListNode[] lists) {
        if (lists.length == 0) {
            return null;
        }
        int n = lists.length;
        for (int step = 1; step < n; step *= 2) {   // 1, 2, 4, 8, ...
            for (int i = 0; i + step < n; i += 2 * step) {
                lists[i] = mergeTwo(lists[i], lists[i + step]);
            }
        }
        return lists[0];
    }
}

// Standard two-list merge, iterative so the stack stays O(1).
static ListNode* mergeTwo(ListNode* a, ListNode* b) {
    ListNode dummy;
    ListNode* tail = &dummy;
    while (a != nullptr && b != nullptr) {
        if (a->val <= b->val) {                // <= makes the merge STABLE
            tail->next = a;
            a = a->next;
        } else {
            tail->next = b;
            b = b->next;
        }
        tail = tail->next;
    }
    tail->next = (a != nullptr) ? a : b;       // attach whatever is left
    return dummy.next;
}

// Bottom-up pairwise merge: ceil(log2 k) rounds, each O(N).
ListNode* mergeKListsPairwise(std::vector<ListNode*>& lists) {
    if (lists.empty()) {
        return nullptr;
    }
    const int n = static_cast<int>(lists.size());
    for (int step = 1; step < n; step *= 2) {  // 1, 2, 4, 8, ...
        for (int i = 0; i + step < n; i += 2 * step) {
            lists[i] = mergeTwo(lists[i], lists[i + step]);
        }
    }
    return lists[0];
}
Time O(N log k)

Same as the heap. In practice often faster: pure pointer comparisons, sequential memory access, no heap sift.

Space O(1)

Bottom-up and iterative, so no heap and no recursion stack. The lists array is reused in place as the accumulator.

Which one would I ship?

Pairwise, when all k lists are available up front — better constants, less memory, no comparator plumbing. The heap, when the lists are streams that arrive incrementally or live on separate machines, because it consumes exactly one element at a time from each source. Say both and say why; that is the senior answer.

5. Follow-up discussion if time permits

  • The data does not fit in memory. This is external merge sort: sort chunks that do fit, spill them as sorted runs on disk, then k-way merge the runs with exactly the section-4 heap, reading each run through a buffered reader. The heap is O(k) memory regardless of file size — that is why the merge step is a heap and not a sort.
  • What if k is larger than the number of file handles / memory for buffers? Merge in multiple passes: merge k' runs at a time so that k' buffers fit, producing fewer, longer runs, and repeat. The total cost becomes O(N logk' k) passes over the data — the classic I/O-bound trade-off.
  • Tournament tree / loser tree instead of a binary heap. Same asymptotics but ~1 comparison per output element instead of ~log k, which matters when comparisons are expensive (long string keys). This is what real database merge operators use.
  • Merge k sorted arrays instead of lists. Identical heap, but store (value, array_index, position) because arrays have no next pointer. Also allows binary-search-based “galloping” merges when one array dominates.
  • Values in a small fixed range. Here |val| ≤ 10⁴, so counting sort over 20 001 buckets gives O(N + R) time — linear, beating O(N log k), at the cost of O(R) space and losing generality. Good demonstration that constraints can beat cleverness.
  • Deduplicate while merging. Skip a popped node whose value equals the previous output value. One extra comparison, no extra memory — and it turns the merge into a sorted set union.
  • Parallel merge across machines. Range-partition the key space so each worker merges an independent key range, then concatenate. Discuss skew: hot ranges need splitting, which is where sampling-based partitioning comes in.
  • Stability and total ordering. If nodes carry payloads and values tie, the tie-breaker defines the output. Using the list index makes it deterministic; not defining it means the output depends on heap internals, which is a bug waiting to be filed.
  • Memory ownership in C++/Rust. The relinking versions transfer ownership rather than copying, so the caller must not free the input lists separately. Worth stating explicitly — interviewers notice candidates who think about lifetimes.
  • What does “good enough” look like here? Reduce the problem to “minimum of k heads”, state the baseline and reject it for a reason, write the heap version with the tie-break and the null-head skip correct, say O(N log k) and justify the k, then offer pairwise merge as the O(1)-space alternative and connect it to external sort.
