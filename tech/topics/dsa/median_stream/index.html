Find median from data stream

Running median is the two-heap invariant problem — once the sizes and tops are right, the rest is bookkeeping.

60-minute agenda

How I'd open the discussion

I'd frame this as: we need O(log n) insertion and O(1) median retrieval. A sorted list gives O(1) median but O(n) insertion (shifting elements). A balanced BST works but is annoying to implement. The elegant solution is two heaps: a max-heap for the lower half and a min-heap for the upper half.

The invariant is simple: max-heap size is always equal to or one more than min-heap size. The median is either the top of the max-heap (odd count) or the average of both tops (even count). Every insertion either goes to the correct heap directly or requires a rebalance — pop from the overfull heap and push to the other. I'd draw the invariant before writing a single line of code.

Open questions worth asking

  • Integer or floating-point values?

  • Is the stream finite or truly unbounded?
  • Precision requirements for the average of two numbers?
  • Thread-safe access needed?
  • Do we need percentiles beyond median (p99, p50)?

  • Out: removal, percentiles, distributed median unless follow-up.

Functional requirements

  • addNum(num): insert a number into the data structure.
  • findMedian(): return the median of all numbers added so far.
  • Median of even count is average of two middle values.

Data model

sql
lower: List[int]   # max-heap (values negated for Python heapq)
upper: List[int]   # min-heap
Invariant: len(lower) == len(upper) or len(lower) == len(upper) + 1
Invariant: -lower[0] <= upper[0]  (max of lower half ≤ min of upper half)

Approach / design notes

Use a max-heap (lower) and a min-heap (upper). In Python, simulate max-heap by negating values.

addNum(num): if lower is empty or num <= -lower[0] (top of max-heap), push to lower. Else push to upper. Then rebalance: if len(lower) > len(upper) + 1, pop from lower and push to upper. If len(upper) > len(lower), pop from upper and push to lower. This maintains the invariant that len(lower) == len(upper) or len(lower) == len(upper) + 1.

findMedian(): if sizes are equal, return (-lower[0] + upper[0]) / 2. If lower is bigger, return -lower[0].

Why this works: lower's max <= upper's min, always. The median sits at the boundary between the halves. Rebalancing ensures neither heap gets more than one element ahead, so the tops are always the middle elements.

Add 8: 8 > 2 (top of lower), push to upper. lower=[-2], upper=[5,8]. |upper|=2 > |lower|=1, rebalance: pop 5, push to lower. lower=[-5,-2], upper=[8]. Median = 5.

Two-heap MedianFinder with rebalance

import heapq


class MedianFinder:
    """Two-heap approach:
    - lower: max-heap (via negation) holds the smaller half
    - upper: min-heap holds the larger half
    Invariant: len(lower) == len(upper) or len(lower) == len(upper) + 1."""

    def __init__(self):
        self.lower = []  # max-heap (store negated values)
        self.upper = []  # min-heap

    def add_num(self, num: int) -> None:
        if not self.lower or num <= -self.lower[0]:
            heapq.heappush(self.lower, -num)
        else:
            heapq.heappush(self.upper, num)
        # Rebalance so lower always has equal or one more element
        if len(self.lower) > len(self.upper) + 1:
            heapq.heappush(self.upper, -heapq.heappop(self.lower))
        elif len(self.upper) > len(self.lower):
            heapq.heappush(self.lower, -heapq.heappop(self.upper))

    def find_median(self) -> float:
        if len(self.lower) > len(self.upper):
            return float(-self.lower[0])
        return (-self.lower[0] + self.upper[0]) / 2.0
use std::collections::BinaryHeap;
use std::cmp::Reverse;

/// Two-heap MedianFinder:
/// - lower: max-heap (BinaryHeap default) for the smaller half
/// - upper: min-heap (via Reverse) for the larger half
struct MedianFinder {
    lower: BinaryHeap<i32>,          // max-heap
    upper: BinaryHeap<Reverse<i32>>, // min-heap via Reverse wrapper
}

impl MedianFinder {
    fn new() -> Self {
        Self { lower: BinaryHeap::new(), upper: BinaryHeap::new() }
    }

    fn add_num(&mut self, num: i32) {
        if self.lower.is_empty() || num <= *self.lower.peek().unwrap() {
            self.lower.push(num);
        } else {
            self.upper.push(Reverse(num));
        }
        // Rebalance: lower always has equal or one more element
        if self.lower.len() > self.upper.len() + 1 {
            self.upper.push(Reverse(self.lower.pop().unwrap()));
        } else if self.upper.len() > self.lower.len() {
            self.lower.push(self.upper.pop().unwrap().0);
        }
    }

    fn find_median(&self) -> f64 {
        if self.lower.len() > self.upper.len() {
            *self.lower.peek().unwrap() as f64
        } else {
            (*self.lower.peek().unwrap() + self.upper.peek().unwrap().0) as f64 / 2.0
        }
    }
}
#import <Foundation/Foundation.h>
#include <queue>
#include <functional>

// Two-heap median finder:
// lower (max-heap) holds smaller half, upper (min-heap) holds larger half
@interface MedianFinder : NSObject
- (void)addNum:(int)num;
- (double)findMedian;
@end

@implementation MedianFinder {
    std::priority_queue<int> _lower;                              // max-heap
    std::priority_queue<int, std::vector<int>, std::greater<>> _upper; // min-heap
}

- (void)addNum:(int)num {
    if (_lower.empty() || num <= _lower.top()) {
        _lower.push(num);
    } else {
        _upper.push(num);
    }
    // Rebalance: lower always has equal or one more element
    if (_lower.size() > _upper.size() + 1) {
        _upper.push(_lower.top()); _lower.pop();
    } else if (_upper.size() > _lower.size()) {
        _lower.push(_upper.top()); _upper.pop();
    }
}

- (double)findMedian {
    if (_lower.size() > _upper.size())
        return (double)_lower.top();
    return (_lower.top() + _upper.top()) / 2.0;
}
@end

Request path / sequence

Trade-offs I'd say out loud

Two heaps vs sorted list

O(log n) insert vs O(n) insert; heaps win for large streams.

Max-heap negation

Python lacks a native max-heap; negating values is the standard hack.

Exact vs approximate

For billions of values, t-digest or count-min sketch gives approximate percentiles in O(1) space.

Where it usually breaks

  • Forgetting to negate values for the max-heap — lower half returns wrong top.
  • Rebalance in wrong direction — upper grows larger than lower.
  • Integer division instead of float for even-count median.
  • Not handling single-element stream (findMedian before any add).
  • Comparing heap sizes with wrong inequality — off-by-one on the rebalance trigger.

Follow-ups if time remains

  • Sliding window median — add + remove with lazy deletion from heaps.
  • Distributed median — each node has a local sketch; merge sketches for global percentile.
  • Weighted median — elements have weights; adjust heap sizes by weight sum.
  • Find k-th largest in a stream — single min-heap of size k.

What "good enough" looks like in 60 minutes

Clearly state the two-heap invariant and why it gives O(1) median access. Write clean code with correct negation and rebalancing. Walk through 5–6 insertions showing both heaps after each step. Mention the approximate percentile approach for truly massive streams — that shows production awareness.
