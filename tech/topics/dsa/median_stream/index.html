Find median from data stream

Running median is the two-heap invariant problem — once the sizes and tops are right, the rest is bookkeeping.

1. Problem statement & explanation

Design a data structure that supports two operations on a stream of numbers:

  • addNum(num) — add an integer to the collection.
  • findMedian() — return the median of everything added so far.

The median is the middle value when the count is odd, and the mean of the two middle values when the count is even. Note the wording: “so far”. This is not a batch problem — queries interleave with insertions arbitrarily, so you cannot sort once at the end.

The reason a heap shows up: you never need the data sorted, you only need the one or two elements that sit at the middle boundary. So the right question is not “how do I keep this sorted cheaply?” but “how do I keep just the boundary elements cheap to reach?” Split the data into a lower half and an upper half, and you only ever need the largest of the lower half and the smallest of the upper half. Those are exactly the two operations a heap makes O(1) to read and O(log n) to maintain.

1.1 Input / output

Signature

contract
class MedianFinder:

    def add_num(self, num: int) -> None: ...

Worked example

example 1 — the canonical trace
mf = MedianFinder()
mf.add_num(1)        # data = [1]
mf.find_median()     # -> 1.0     (odd count: the middle element)
mf.add_num(2)        # data = [1, 2]
mf.find_median()     # -> 1.5     (even count: MEAN of the two middles)
mf.add_num(3)        # data = [1, 2, 3]
mf.find_median()     # -> 2.0
example 2 — order of arrival is arbitrary
add 5, 15, 1, 3      # sorted view: [1, 3, 5, 15]
find_median()        # -> 4.0     ((3 + 5) / 2)
add 8                # sorted view: [1, 3, 5, 8, 15]
find_median()        # -> 5.0
Note: values arrive unsorted; every median must be correct at the time asked.
example 3 — the cases that break naive code
add 2; find_median()             -> 2.0      (single element)
add 1; add 1; find_median()      -> 1.0      (duplicates are kept, not deduped)
add -5; add 5; find_median()     -> 0.0      (negatives, and a zero result)
add 100000; add 100000           -> 100000.0 (sum of two middles can exceed
                                              int range -- widen before adding)

Constraints to state back

  • -10^5 ≤ num ≤ 10^5 — a bounded domain of only 200 001 distinct values. That bound is the door to the counting/Fenwick solution in 4.3; say it out loud when you read the constraint.
  • At most 5 × 10^4 calls in total to addNum and findMedian combined.
  • findMedian is only called when at least one element has been added, so the empty case need not return a sentinel — but say that you are relying on it.
  • Return type is a floating-point number. Two integer middles must be averaged in floating point (or the sum widened first), or (1 + 2) / 2 silently becomes 1 in Java, C++ and Rust.

2. Open questions & clarifications

  • What is the read/write ratio? This is the design question. Write-heavy with rare reads favours append-and-sort-on-query. Read-heavy favours keeping the structure ordered. Balanced favours two heaps. Ask before choosing.
  • Confirm the even-count rule. Mean of the two middles, or lower middle? Different products define it differently and it costs one line either way.
  • Integers or arbitrary floats? Bounded integers unlock counting structures; floats force comparison-based ones.
  • Is the value range bounded? It is here, and that is a much stronger hint than most candidates notice. A bounded domain makes the cost O(log R) — independent of how many elements arrive.
  • Do we ever remove elements? Heaps cannot delete an arbitrary element cheaply. If removal is needed, say so early and switch to a Fenwick tree, an ordered multiset, or lazy deletion with a tombstone map.
  • Is it the median of all history, or of a sliding window? Windowed median is a materially harder variant — it is the classic follow-up, so pre-empt it.
  • Must the answer be exact? At scale, monitoring systems accept approximate quantiles (t-digest, HdrHistogram) for a large constant-factor win. Knowing when exactness is negotiable is a senior signal.
  • How much data in total? If it does not fit in memory, exact median needs multiple passes or an approximate sketch.
  • Concurrent access? Multiple producers and one reader changes everything: the two-heap rebalance is not atomic, so you need a lock or a lock-free design.
  • Will other percentiles be asked for later? If p95 is coming, build the Fenwick/histogram version now — two heaps give you the median and nothing else.

2.1 Suggestions to the candidate

  • Do not say “two heaps” in the first ten seconds. It is the most memorised answer in this problem set, and saying it early reads as recall, not reasoning. First say why: “I only ever need the boundary between the halves, not the full order.” Then the heaps are a conclusion.
  • Do not skip the baseline, and use it to ask about the workload. “If reads are rare, appending and sorting on query is genuinely the right engineering answer.” That sentence shows judgement rather than reflex optimisation.
  • Write both invariants on the board before coding. (1) every element of lo ≤ every element of hi; (2) len(lo) == len(hi) or len(lo) == len(hi) + 1. Almost every bug in this problem is one of these two being violated, and having them written down lets you check your own code.
  • Use push-then-rebalance, not if/else placement. Always push into lo, move lo's max into hi, then move back if hi grew too large. Three unconditional lines. The “compare against the current median and decide which heap” version has four branches and is where candidates lose time.
  • Decide which heap holds the extra element and never waver. This page keeps it in lo, so an odd count means the answer is lo.top(). Flip-flopping mid-solution guarantees an off-by-one.
  • Watch the integer division and the overflow. (lo.top() + hi.top()) / 2 is wrong in Java, C++ and Rust for two reasons: integer division truncates, and the sum can exceed the type. Cast to floating point or widen first.
  • Trace 1 → 2 → 3 out loud. Three insertions exercise both parity cases and both rebalance directions. It takes 40 seconds and proves the invariants hold.
  • Point out the bounded range yourself. Even if you implement the heaps, say “given |num| ≤ 10⁵ a Fenwick tree over the domain is O(log R) and also gives me deletions and arbitrary percentiles.” That single observation is what separates a correct answer from a strong one.

3. Brute-force approach

Keep every number in a plain list. addNum appends. findMedian sorts and reads the middle. Obviously correct, and it makes the trade-off visible: all of the cost has been pushed onto the read path.

  1. addNum: append. O(1) amortised.
  2. findMedian: sort the list, then return data[n//2] for odd n, or the mean of data[n//2 - 1] and data[n//2] for even n.
There is a second baseline — contrast them explicitly

Keep the list sorted instead: binary-search the insertion point (O(log n)) and shift the tail (O(n)). That gives addNum O(n) and findMedian O(1) — the exact mirror image. Which baseline is better depends entirely on the read/write ratio, which is why that was question one in section 2. Worth adding: the O(n) shift is a single contiguous memmove, so in practice sorted-insert beats a heap up to roughly 10⁵ elements. Knowing that constants sometimes win is a real-engineering signal.

3.1 Code — Python, Rust, Java, C++

from typing import List


class MedianFinderBrute:
    """Store everything, sort on every query.

    All the cost sits on the read path -- which is the right choice only if
    reads are rare compared to writes.
    """

    def __init__(self) -> None:
        self.data: List[int] = []

    def add_num(self, num: int) -> None:
        self.data.append(num)              # O(1) amortised

    def find_median(self) -> float:
        self.data.sort()                   # O(n log n) on EVERY query
        n = len(self.data)
        mid = n // 2
        if n % 2 == 1:
            return float(self.data[mid])
        # Averaging in float: (1 + 2) / 2 must be 1.5, not 1.
        return (self.data[mid - 1] + self.data[mid]) / 2.0

    /// the "read" path is not actually read-only.
    pub fn find_median(&mut self) -> f64 {
        self.data.sort_unstable();         // O(n log n) on EVERY query
        let n = self.data.len();
        let mid = n / 2;
        if n % 2 == 1 {
            self.data[mid] as f64
        } else {
            // Cast BEFORE adding: the i32 sum could overflow.
            (self.data[mid - 1] as f64 + self.data[mid] as f64) / 2.0
        }
    }
}

import java.util.Collections;
import java.util.List;

class MedianFinderBrute {

    private final List<Integer> data = new ArrayList<>();

    public void addNum(int num) {
        data.add(num);                     // O(1) amortised
    }

    public double findMedian() {
        Collections.sort(data);            // O(n log n) on EVERY query
        int n = data.size();
        int mid = n / 2;
        if (n % 2 == 1) {
            return data.get(mid);
        }
        // Widen to long before adding, then divide as a double:

3.2 Complexity

Time add O(1) · find O(n log n)

Worst case is alternating add/find: n queries each sorting n elements gives O(n² log n) overall. At n = 5 × 10⁴ that is ~4 × 10⁶ × 10⁴ comparisons — far too slow.

Space O(n)

Every element retained. Unavoidable for an exact median over unbounded values — but not unavoidable for a bounded domain, which is section 4.3.

Why this is not the final answer

Sorting produces the full ordering, but the query reads only the middle one or two positions. Everything else is discarded work — and it is redone from scratch on every query even though only one element changed. We need a structure that maintains just enough order to keep the middle reachable, and updates incrementally.

4. Optimised approach

Key insight: partition the data into a lower half and an upper half. Store the lower half in a max-heap (lo) and the upper half in a min-heap (hi). Then the median depends only on the two heap tops — which is exactly what heaps make free to read.

The two invariants — the whole solution

Order: every element in lo ≤ every element in hi.
Balance: len(lo) == len(hi) (even count) or len(lo) == len(hi) + 1 (odd count — the extra element always lives in lo).
Given both, the median is lo.top() when the sizes differ, and the mean of the two tops when they match.

  1. addNum, step 1: push num into lo unconditionally. This may break the order invariant.
  2. Step 2: pop lo's maximum and push it into hi. Now the order invariant is restored — whatever the largest of the lower half is, it has been promoted — but hi may now be too large.
  3. Step 3: if len(hi) > len(lo), pop hi's minimum and push it back into lo. Balance restored.
  4. findMedian: sizes differ → return lo.top(). Sizes equal → return (lo.top() + hi.top()) / 2.0.
Why push-then-rebalance is correct — and why it is worth preferring

Routing on a comparison (“if num ≤ lo.top() push to lo else push to hi, then fix sizes”) works but has four branches and an empty-heap special case. Push-then-rebalance is three unconditional lines and no special cases: the mandatory hop through hi guarantees the promoted element is the correct boundary regardless of where num belonged. It costs one extra pair of heap operations and removes the entire class of branch bugs.

4.1 Code — Python, Rust, Java, C++

import heapq
from typing import List


class MedianFinder:
    """Two heaps straddling the median.

    Invariants after every add_num:
      1. ORDER:   max(lo) <= min(hi)
      2. BALANCE: len(lo) == len(hi)  or  len(lo) == len(hi) + 1
    The extra element (odd count) always lives in `lo`.
    """

    def __init__(self) -> None:
        # heapq is a MIN-heap only, so `lo` stores negated values to
        # behave as a max-heap. lo[0] == -max(lower half).
        self.lo: List[int] = []            # max-heap (negated)
        self.hi: List[int] = []            # min-heap

    def add_num(self, num: int) -> None:
        # Push, then rebalance. Three unconditional steps, no branches on
        # where `num` belongs and no empty-heap special case.
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))   # lo's max -> hi
        if len(self.hi) > len(self.lo):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))

    def find_median(self) -> float:
        # Precondition: at least one element has been added.
        if len(self.lo) > len(self.hi):    # odd count
            return float(-self.lo[0])
        return (-self.lo[0] + self.hi[0]) / 2.0            # even count
use std::cmp::Reverse;
use std::collections::BinaryHeap;

/// Two heaps straddling the median.
///
/// Invariants after every `add_num`:
///   1. ORDER:   max(lo) <= min(hi)
///   2. BALANCE: lo.len() == hi.len()  or  lo.len() == hi.len() + 1
/// The extra element (odd count) always lives in `lo`.
pub struct MedianFinder {
    lo: BinaryHeap<i32>,           // BinaryHeap is a max-heap: lower half
    hi: BinaryHeap<Reverse<i32>>,  // Reverse makes it a min-heap: upper half
}

impl MedianFinder {
    pub fn new() -> Self {
        MedianFinder {
            lo: BinaryHeap::new(),
            hi: BinaryHeap::new(),
        }
    }

    pub fn add_num(&mut self, num: i32) {
        // Push, then rebalance. No branch on where `num` belongs.
        self.lo.push(num);
        let promoted = self.lo.pop().expect("just pushed, cannot be empty");
        self.hi.push(Reverse(promoted));               // lo's max -> hi

        if self.hi.len() > self.lo.len() {
            let Reverse(demoted) = self.hi.pop().unwrap();
            self.lo.push(demoted);
        }
    }

    /// Precondition: at least one element has been added.
    pub fn find_median(&self) -> f64 {
        let lo_top = *self.lo.peek().expect("no elements yet") as f64;
        if self.lo.len() > self.hi.len() {
            lo_top                                     // odd count
        } else {
            let Reverse(hi_top) = *self.hi.peek().unwrap();
            (lo_top + hi_top as f64) / 2.0             // even count
        }
    }
}
import java.util.Collections;
import java.util.PriorityQueue;

/**
 * Two heaps straddling the median.
 *
 * Invariants after every addNum:
 *   1. ORDER:   lo.peek() <= hi.peek()
 *   2. BALANCE: lo.size() == hi.size()  or  lo.size() == hi.size() + 1
 * The extra element (odd count) always lives in `lo`.
 */
class MedianFinder {

    private final PriorityQueue<Integer> lo =            // max-heap: lower half
            new PriorityQueue<>(Collections.reverseOrder());
    private final PriorityQueue<Integer> hi =            // min-heap: upper half
            new PriorityQueue<>();

    public void addNum(int num) {
        // Push, then rebalance. No branch on where `num` belongs.
        lo.add(num);
        hi.add(lo.poll());                              // lo's max -> hi
        if (hi.size() > lo.size()) {
            lo.add(hi.poll());
        }
    }

    /** Precondition: at least one element has been added. */
    public double findMedian() {
        if (lo.size() > hi.size()) {
            return lo.peek();                           // odd count
        }
        // Widen to long before adding: two values near 10^5 are fine, but
        // the habit matters -- and /2.0 avoids integer truncation.
        return ((long) lo.peek() + hi.peek()) / 2.0;    // even count
    }
}

#include <functional>
#include <queue>

// Two heaps straddling the median.
//
// Invariants after every addNum:
//   1. ORDER:   lo_.top() <= hi_.top()
//   2. BALANCE: lo_.size() == hi_.size()  or  lo_.size() == hi_.size() + 1
// The extra element (odd count) always lives in lo_.
class MedianFinder {
public:
    void addNum(int num) {
        // Push, then rebalance. No branch on where `num` belongs.
        lo_.push(num);
        hi_.push(lo_.top());                   // lo_'s max -> hi_
        lo_.pop();
        if (hi_.size() > lo_.size()) {
            lo_.push(hi_.top());
            hi_.pop();
        }
    }

    // Precondition: at least one element has been added.
    double findMedian() const {
        if (lo_.size() > hi_.size()) {
            return static_cast<double>(lo_.top());          // odd count
        }
        // Widen before adding, and divide by 2.0 to avoid truncation.
        return (static_cast<std::int64_t>(lo_.top()) + hi_.top()) / 2.0;
    }

private:
    // std::priority_queue is a max-heap by default.
    std::priority_queue<int> lo_;                                  // lower half
    std::priority_queue<int, std::vector<int>, std::greater<int>> hi_;  // upper
};

4.2 Complexity

Time add O(log n) · find O(1)

Each addNum performs at most 3 pushes and 2 pops, all O(log n). findMedian reads one or two heap tops — no traversal, no sorting. Over 5 × 10⁴ operations that is ~8 × 10⁵ comparisons total.

Space O(n)

Every element is stored exactly once, split across the two heaps. No duplication, no index structures.

Edge cases this version already handles

First insertion: lo gets it, hi is empty, the size check keeps it in lo. Duplicates: nothing is keyed on value, so they simply occupy two slots. Negatives and a zero median: fine, since only comparisons are used. All-equal input: both heaps fill with the same value and the mean is that value.

4.3 Variant: Fenwick tree over a bounded domain

The constraint |num| ≤ 10⁵ means there are only R = 200 001 distinct possible values. Instead of storing elements, store counts per value in a Fenwick tree (binary indexed tree). Insertion is a point update; the median is a search for the k-th smallest, which the Fenwick structure answers by binary lifting in a single descent.

Three things this buys that two heaps cannot: deletion in O(log R), any percentile (p50, p95, p99) at the same cost, and memory that depends on the value range rather than the number of elements — so a billion insertions still cost 800 KB.

  1. add_num(v): increment position v + OFFSET + 1 and every Fenwick ancestor. O(log R).
  2. remove_num(v): the same walk with -1. Heaps have no cheap equivalent.
  3. kth(k): descend from the highest power of two, taking a step whenever the subtree count is still below k. Lands on the smallest value whose prefix count reaches k.
  4. find_median(): odd total → kth(total/2 + 1). Even total → mean of kth(total/2) and kth(total/2 + 1).
class MedianFinderCounting:
    """Fenwick tree of counts over the value domain [-OFFSET, OFFSET].

    Supports insertion, DELETION, and any percentile in O(log R), with
    memory O(R) that is independent of how many elements arrive.
    """

    OFFSET = 100_000
    SIZE = 200_001                         # distinct legal values
    TOP_BIT = 1 << 17                      # largest power of two <= SIZE

    def __init__(self) -> None:
        self.tree = [0] * (self.SIZE + 1)  # 1-indexed Fenwick counts
        self.total = 0

    def _update(self, num: int, delta: int) -> None:
        i = num + self.OFFSET + 1          # map value -> 1-based position
        while i <= self.SIZE:
            self.tree[i] += delta
            i += i & -i                    # move to the next covering node
        self.total += delta

    def add_num(self, num: int) -> None:
        self._update(num, 1)

    def remove_num(self, num: int) -> None:
        self._update(num, -1)              # heaps cannot do this cheaply

    def _kth(self, k: int) -> int:
        """Smallest value whose prefix count reaches k (k is 1-indexed)."""
        idx = 0
        remaining = k
        bit = self.TOP_BIT
        while bit:
            nxt = idx + bit
            if nxt <= self.SIZE and self.tree[nxt] < remaining:
                idx = nxt                  # skip this whole subtree
                remaining -= self.tree[nxt]
            bit >>= 1
        # `idx` is the last position with prefix count < k, so idx+1 is the
        # answer position; converting back to a value cancels the +1.
        return idx - self.OFFSET

    def find_median(self) -> float:
        if self.total % 2 == 1:
            return float(self._kth(self.total // 2 + 1))
        lower = self._kth(self.total // 2)
        upper = self._kth(self.total // 2 + 1)
        return (lower + upper) / 2.0

    def percentile(self, p: float) -> int:
        """Any percentile, same cost. p in [0, 100]."""
        k = max(1, min(self.total, int(self.total * p / 100.0 + 0.5)))
        return self._kth(k)
const OFFSET: i32 = 100_000;
const SIZE: usize = 200_001;      // distinct legal values
const TOP_BIT: usize = 1 << 17;   // largest power of two <= SIZE

/// Fenwick tree of counts over the value domain [-OFFSET, OFFSET].
///
/// Insertion, DELETION and any percentile in O(log R), with memory O(R)
/// independent of how many elements arrive.
pub struct MedianFinderCounting {
    tree: Vec<i64>,               // 1-indexed Fenwick counts
    total: i64,
}

impl MedianFinderCounting {
    pub fn new() -> Self {
        MedianFinderCounting {
            tree: vec![0; SIZE + 1],
            total: 0,
        }
    }

    fn update(&mut self, num: i32, delta: i64) {
        let mut i = (num + OFFSET) as usize + 1;    // value -> 1-based position
        while i <= SIZE {
            self.tree[i] += delta;
            i += i & i.wrapping_neg();              // next covering node
        }
        self.total += delta;
    }

    pub fn add_num(&mut self, num: i32) {
        self.update(num, 1);
    }

    pub fn remove_num(&mut self, num: i32) {
        self.update(num, -1);                       // heaps cannot do this
    }

    /// Smallest value whose prefix count reaches `k` (k is 1-indexed).
    fn kth(&self, k: i64) -> i32 {
        let mut idx = 0usize;
        let mut remaining = k;
        let mut bit = TOP_BIT;
        while bit > 0 {
            let next = idx + bit;
            if next <= SIZE && self.tree[next] < remaining {
                idx = next;                         // skip this whole subtree
                remaining -= self.tree[next];
            }
            bit >>= 1;
        }
        idx as i32 - OFFSET
    }

    pub fn find_median(&self) -> f64 {
        if self.total % 2 == 1 {
            self.kth(self.total / 2 + 1) as f64
        } else {
            let lower = self.kth(self.total / 2) as f64;
            let upper = self.kth(self.total / 2 + 1) as f64;
            (lower + upper) / 2.0
        }
    }

    /// Any percentile, same cost. `p` in [0, 100].
    pub fn percentile(&self, p: f64) -> i32 {
        let k = ((self.total as f64) * p / 100.0).round() as i64;
        self.kth(k.clamp(1, self.total.max(1)))
    }
}
/**
 * Fenwick tree of counts over the value domain [-OFFSET, OFFSET].
 *
 * Insertion, DELETION and any percentile in O(log R), with memory O(R)
 * independent of how many elements arrive.
 */
class MedianFinderCounting {

    private static final int OFFSET = 100_000;
    private static final int SIZE = 200_001;     // distinct legal values
    private static final int TOP_BIT = 1 << 17;  // largest 2^k <= SIZE

    private final long[] tree = new long[SIZE + 1];   // 1-indexed Fenwick
    private long total = 0;

    public void addNum(int num) {
        update(num, 1);
    }

    public void removeNum(int num) {
        update(num, -1);                        // heaps cannot do this cheaply
    }

    private void update(int num, long delta) {
        // value -> 1-based position; i += i & -i walks the covering nodes.
        for (int i = num + OFFSET + 1; i <= SIZE; i += i & -i) {
            tree[i] += delta;
        }
        total += delta;
    }

    /** Smallest value whose prefix count reaches k (k is 1-indexed). */
    private int kth(long k) {
        int idx = 0;
        long remaining = k;
        for (int bit = TOP_BIT; bit > 0; bit >>= 1) {
            int next = idx + bit;
            if (next <= SIZE && tree[next] < remaining) {
                idx = next;                     // skip this whole subtree
                remaining -= tree[next];
            }
        }
        return idx - OFFSET;
    }

    public double findMedian() {
        if (total % 2 == 1) {
            return kth(total / 2 + 1);
        }
        return (kth(total / 2) + (double) kth(total / 2 + 1)) / 2.0;
    }

    /** Any percentile, same cost. p in [0, 100]. */
    public int percentile(double p) {
        long k = Math.round(total * p / 100.0);
        return kth(Math.max(1, Math.min(total, k)));
    }
}
#include <algorithm>
#include <cmath>
#include <cstdint>
#include <vector>

// Fenwick tree of counts over the value domain [-kOffset, kOffset].
//
// Insertion, DELETION and any percentile in O(log R), with memory O(R)
// independent of how many elements arrive.
class MedianFinderCounting {
public:
    void addNum(int num) { update(num, 1); }

    void removeNum(int num) { update(num, -1); }   // heaps cannot do this

    double findMedian() const {
        if (total_ % 2 == 1) {
            return static_cast<double>(kth(total_ / 2 + 1));
        }
        const std::int64_t lower = kth(total_ / 2);
        const std::int64_t upper = kth(total_ / 2 + 1);
        return (static_cast<double>(lower) + upper) / 2.0;
    }

    // Any percentile, same cost. p in [0, 100].
    int percentile(double p) const {
        std::int64_t k = static_cast<std::int64_t>(
            std::llround(static_cast<double>(total_) * p / 100.0));
        k = std::clamp<std::int64_t>(k, 1, std::max<std::int64_t>(total_, 1));
        return kth(k);
    }

private:
    static constexpr int kOffset = 100000;
    static constexpr int kSize = 200001;        // distinct legal values
    static constexpr int kTopBit = 1 << 17;     // largest 2^k <= kSize

    std::vector<std::int64_t> tree_ =
        std::vector<std::int64_t>(kSize + 1, 0);   // 1-indexed Fenwick
    std::int64_t total_ = 0;

    void update(int num, std::int64_t delta) {
        // value -> 1-based position; i += i & -i walks the covering nodes.
        for (int i = num + kOffset + 1; i <= kSize; i += i & -i) {
            tree_[i] += delta;
        }
        total_ += delta;
    }

    // Smallest value whose prefix count reaches k (k is 1-indexed).
    int kth(std::int64_t k) const {
        int idx = 0;
        std::int64_t remaining = k;
        for (int bit = kTopBit; bit > 0; bit >>= 1) {
            const int next = idx + bit;
            if (next <= kSize && tree_[next] < remaining) {
                idx = next;                     // skip this whole subtree
                remaining -= tree_[next];
            }
        }
        return idx - kOffset;
    }
};
Time add O(log R) · find O(log R)

R = 200 001 so log₂R ≈ 18 — a fixed cost that does not grow with the number of elements. Slightly worse than the heaps' O(1) read, better than their O(log n) write once n exceeds R.

Space O(R)

~800 KB for 200 001 64-bit counters, regardless of whether you insert a thousand elements or a billion. Only viable because the domain is bounded — state that precondition explicitly.

Which one would I ship?

Two heaps for the interview and for unbounded or floating-point values: less code, O(1) reads, no domain assumption. The Fenwick tree the moment the requirements include deletions, other percentiles, or a very high element count over a small value range — which describes almost every real latency-monitoring system. Naming that boundary is the answer the interviewer wants.

5. Follow-up discussion if time permits

  • Sliding-window median (last k elements). Now you must evict the element leaving the window, which heaps cannot do by value. Options: two heaps with lazy deletion (a tombstone count per value, purged when it reaches a top), an ordered multiset with an iterator kept at the middle, or the Fenwick tree from 4.3, which handles it natively. Say which and why.
  • Only p95 and p99 are needed, at millions of events per second. Exactness stops being worth its cost. HdrHistogram or t-digest gives bounded relative error in O(1) amortised per insert and a few KB of state — and t-digest is mergeable, so shards can be combined. This is what production monitoring actually runs.
  • Median across many machines. Exact distributed median needs several rounds: broadcast a candidate pivot, have every shard report how many of its values fall below it, and binary-search the value space. That is O(log R) rounds. Mergeable sketches replace it with one round and an error bound.
  • Data does not fit in memory at all. Two passes: build a coarse histogram to locate the bucket containing the median, then re-scan only that bucket. This is the median-of-medians idea applied to external data.
  • The stream is weighted or time-decayed. A recent value should count more than an hour-old one. Exponentially decaying counts in the Fenwick tree, or a sliding set of time buckets that are dropped wholesale as they age out.
  • Why not a balanced BST or skip list? An order-statistic tree (nodes annotated with subtree sizes) gives O(log n) insert, delete and arbitrary rank query — strictly more capable than two heaps. C++ hands you this via __gnu_pbds::tree_order_statistics_node_update; Java and Python have no ordered multiset in the standard library, which is the practical reason heaps win in interviews.
  • Concurrency. The rebalance in addNum spans several heap mutations, so a reader can observe a broken invariant mid-update. Simplest fix: one lock around both heaps. Better under load: per-thread histograms merged periodically, which is exactly the mergeable-sketch answer again.
  • Median of two already-sorted arrays. Different problem, worth naming: binary search on the partition point gives O(log(min(m, n))). Interviewers sometimes pivot to it to see whether you pattern-match on the word “median”.
  • Testing this. Property-based: after every operation, assert both invariants directly (max of lo ≤ min of hi, and the size relation) and compare the result against a naive sorted-list oracle on random operation sequences. Invariant assertions plus an oracle is far stronger than a handful of examples.
  • What does “good enough” look like here? Ask about the read/write ratio, state both baselines and which operation each taxes, write both invariants down, implement push-then-rebalance correctly on the first attempt, avoid the integer-division trap in findMedian, trace 1→2→3, and volunteer the bounded-range Fenwick alternative with deletions and percentiles as the reason to prefer it in production.
