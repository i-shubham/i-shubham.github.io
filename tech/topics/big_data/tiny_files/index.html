Compact a tiny-file disaster

Millions of 12KB Parquet files make S3 LIST and Spark planning slower than the actual compute.

60-minute agenda

How I'd open the discussion

I have inherited lake tables with 3 million files averaging 12KB each — about 36GB of data stored in files that should have been 256MB each, meaning ~140 files total. The symptom is not disk space — it is query time. Spark spends 8 minutes listing files and building the execution plan before it even reads a byte. Trino times out during metadata loading. Hive metastore crashes under the partition listing load.

Tiny files happen for predictable reasons: streaming jobs committing every 5 seconds, over-partitioned tables (partition by minute when hour would suffice), reduce tasks with low parallelism writing many small outputs, and Hive dynamic partitions spreading thin data across hundreds of buckets.

The fix has two parts: compact existing files and prevent new tiny files from accumulating. Compaction rewrites small files into larger ones. Prevention means fixing the root cause: right-sizing partitions, adjusting commit intervals, and using coalesce/repartition before writes. Iceberg and Delta have built-in compaction, but with 3 million files you cannot compact them all at once without melting the cluster.

Open questions worth asking

  • How many total files and what is the average file size?
  • What creates the tiny files — streaming, over-partitioning, or small reduce tasks?
  • Table format — Hive, Iceberg, Delta?
  • Can we do in-place compaction or must we rewrite to a new table?
  • What is the query latency impact — how bad is it now?
  • Concurrent read traffic — can we compact while queries run?
  • Partition scheme — too granular (minute/hour) or reasonable (day)?
  • Budget for compaction — how much cluster time can we dedicate?

Scope I'd lock first

  • In scope — Compact existing tiny files to target 256MB, prevent recurrence
  • In scope — Measure impact: file count, listing time, query latency before/after
  • Out of scope — Redesigning the entire data model or partition scheme
  • Defer — Automated continuous compaction service for all tables

Approach / design notes

The compaction strategy has three phases: assess, compact, and prevent.

Assess: query the Iceberg metadata table (or S3 listing for Hive) to identify partitions with the worst file-count-to-size ratio. Sort partitions by file count descending. The top 20% of partitions usually contain 80% of the tiny files — compact those first for maximum impact.

Compact: for Iceberg, use rewrite_data_files() with partial-progress enabled. This means the compaction job can commit progress incrementally — if it fails mid-way, the already-compacted partitions stay compacted. Set target-file-size to 256MB, min to 128MB, max to 512MB. The sort strategy (sort by user_id or event_ts within each partition) improves query performance beyond just reducing file count, because related rows are colocated.

For Hive tables without Iceberg/Delta: read the partition, coalesce to the target file count, and overwrite. This is riskier because overwrite is not atomic — if the job fails mid-write, the partition has partial data. Mitigation: write to a temp location, verify row count, then swap the partition location.

Rate limiting: compact at most 4 partitions in parallel, and only during off-peak hours (02:00–06:00 UTC). The compaction cluster is separate from production query clusters. For 3 million files across ~1,000 partitions, with 4-way parallelism and ~3 minutes per partition, the full compaction takes about 12 hours spread across 3 nights.

Prevent: fix the upstream writer. If it is a streaming job, increase commit interval from 5 seconds to 60 seconds. If it is over-partitioned (by minute), change to hourly. If Spark writes with too many reduce tasks, add .coalesce() or .repartition() before .write(). Add an Airflow sensor that checks avg file size after each write and alerts if below 64MB.

Deep dive (spend 15–25 minutes here)

Why 256MB? This is the sweet spot for Parquet on S3. S3 GET requests have a ~20ms overhead per request, so reading 3 million 12KB files means 60,000 seconds of request overhead alone. At 256MB per file, the overhead is negligible relative to transfer time. Parquet's columnar encoding works best when row groups are 64–128MB (which fits nicely in a 256MB file with multiple row groups). Larger files (1GB+) cause problems: single-task reads take too long, and retries on failure waste more work.

S3 LIST pagination: S3 returns at most 1,000 keys per LIST request. With 3M files, you need 3,000 LIST requests, each taking ~100ms = 300 seconds = 5 minutes just to list. If the partition scheme has thousands of prefixes, each requiring its own LIST, it compounds. Iceberg avoids this by tracking files in metadata — no S3 LIST needed for query planning. This is a strong argument for migrating Hive tables to Iceberg even if you do nothing else.

Compaction during active reads: with Iceberg, compaction is safe — the rewrite creates new files and a new snapshot. Readers on the old snapshot continue reading old files until their query completes. After expire_snapshots removes old snapshots, the old files are garbage collected. With Hive, overwriting a partition while a query reads it causes the query to fail with FileNotFoundException. Schedule compaction when query traffic is low.

Coalesce vs repartition: coalesce(N) reduces partitions without a shuffle — it merges adjacent partitions, so task locality is preserved. Repartition(N) does a full shuffle, distributing rows evenly. For compaction, coalesce is preferred because we do not need even distribution — we just need fewer, larger files. The exception: if the data is heavily skewed across the existing partitions, coalesce will produce uneven file sizes. In that case, repartition is worth the shuffle cost.

Preventing recurrence with Spark: add .coalesce() or .repartition() before .write(), using estimated output size to calculate the target. Formula: target_files = max(1, estimated_bytes // 256MB). For streaming, increase trigger interval to at least 60 seconds and enable compaction in the table format (Iceberg's write.target-file-size-bytes property).

Partition-level compaction with row count verification

from pyspark.sql import SparkSession


def compact_partition(spark: SparkSession, table: str, partition_filter: str,
                      target_file_size_mb: int = 256):
    """
    Compact a tiny-file disaster into properly sized files.
    - Reads the partition, calculates optimal file count based on data size.
    - Uses coalesce to reduce file count (avoids full shuffle of repartition).
    - Verifies row count before and after to ensure no data loss.
    - Returns compaction metrics for monitoring.
    """
    df = spark.read.format('iceberg').load(table).filter(partition_filter)

    # Calculate current total size across all input files
    input_files = df.inputFiles()
    hadoop_fs = spark._jvm.org.apache.hadoop.fs.FileSystem.get(
        spark._jsc.hadoopConfiguration()
    )
    current_size = sum(
        hadoop_fs.getContentSummary(
            spark._jvm.org.apache.hadoop.fs.Path(f)
        ).getLength()
        for f in input_files
    )

    # Target: one file per target_file_size_mb chunk
    target_files = max(1, int(current_size / (target_file_size_mb * 1024 * 1024)))

    # Verify row count before compaction
    before_count = df.count()

    # Coalesce to target file count (no shuffle, just merges partitions)
    compacted = df.coalesce(target_files)
    compacted.writeTo(table).overwritePartitions()

    # Verify row count after compaction — must match exactly
    after_count = spark.read.format('iceberg').load(table).filter(partition_filter).count()
    assert before_count == after_count, (
        f'Row count mismatch: {before_count} -> {after_count}'
    )

    return {
        'partition': partition_filter,
        'files_before': len(input_files),
        'files_after': target_files,
        'rows': after_count,
    }
// Conceptual partition compaction using Polars + object store.
// In production, you'd either call Iceberg's rewrite_data_files API
// or use this as a standalone compaction binary.

use polars::prelude::*;
use object_store::{ObjectStore, path::Path as ObjPath};
use std::sync::Arc;

pub struct CompactionResult {
    pub partition: String,
    pub files_before: usize,
    pub files_after: usize,
    pub rows: usize,
}

/// Compact tiny files in a partition into properly sized files.
/// - Reads all small files in the partition.
/// - Calculates optimal output file count based on total data size.
/// - Rewrites with target file size (~256 MB).
/// - Verifies row count before and after to ensure no data loss.
pub async fn compact_partition(
    store: Arc<dyn ObjectStore>,
    table_path: &str,
    partition_filter: &str,
    target_file_size_mb: usize,
) -> Result<CompactionResult, Box<dyn std::error::Error>> {
    let prefix = ObjPath::from(format!("{}/{}", table_path, partition_filter));

    // List all files in the partition
    let files: Vec<_> = store.list(Some(&prefix)).try_collect().await?;
    let files_before = files.len();

    // Calculate total size
    let total_bytes: usize = files.iter().map(|f| f.size).sum();
    let target_files = std::cmp::max(1, total_bytes / (target_file_size_mb * 1024 * 1024));

    // Read all parquet files into a single DataFrame
    let mut frames = Vec::new();
    for file_meta in &files {
        let bytes = store.get(&file_meta.location).await?.bytes().await?;
        let cursor = std::io::Cursor::new(bytes);
        let df = ParquetReader::new(cursor).finish()?;
        frames.push(df);
    }
    let combined = concat_df(&frames)?;
    let before_count = combined.height();

    // Split into target_files chunks and write back
    let rows_per_file = (before_count + target_files - 1) / target_files;
    let mut written_rows = 0;

    for i in 0..target_files {
        let start = i * rows_per_file;
        let end = std::cmp::min(start + rows_per_file, before_count);
        let chunk = combined.slice(start as i64, end - start);

        let output_path = ObjPath::from(format!(
            "{}/{}/compacted_{:04}.parquet", table_path, partition_filter, i
        ));
        let mut buf = Vec::new();
        ParquetWriter::new(&mut buf).finish(&mut chunk.clone())?;
        store.put(&output_path, buf.into()).await?;
        written_rows += chunk.height();
    }

    // Verify row count — must match exactly
    assert_eq!(
        before_count, written_rows,
        "Row count mismatch: {} -> {}", before_count, written_rows
    );

    // Delete old files
    for file_meta in &files {
        store.delete(&file_meta.location).await?;
    }

    Ok(CompactionResult {
        partition: partition_filter.to_string(),
        files_before,
        files_after: target_files,
        rows: written_rows,
    })
}

// Partition compaction orchestrator for a tiny-file disaster.
// Submits a compaction job to Spark/Iceberg and verifies row counts.

struct CompactionResult {
    std::string partition;
    int files_before;
    int files_after;
    long long rows;
};

@interface CompactionService : NSObject
@property (nonatomic, strong) NSString *sparkEndpoint;
@property (nonatomic, strong) NSString *icebergCatalog;

- (instancetype)initWithSpark:(NSString *)spark catalog:(NSString *)catalog;
- (CompactionResult)compactPartition:(NSString *)table
                              filter:(NSString *)partitionFilter
                      targetSizeMB:(int)targetSizeMB;
@end

@implementation CompactionService

- (instancetype)initWithSpark:(NSString *)spark catalog:(NSString *)catalog {
    self = [super init];
    if (self) {
        _sparkEndpoint = spark;
        _icebergCatalog = catalog;
    }
    return self;
}

/// Compact tiny files in a partition to the target file size.
/// Verifies row count before and after to ensure no data loss.
- (CompactionResult)compactPartition:(NSString *)table
                              filter:(NSString *)partitionFilter
                      targetSizeMB:(int)targetSizeMB {
    CompactionResult result;
    result.partition = std::string([partitionFilter UTF8String]);

    // Step 1: Get current file count and total size via Iceberg metadata
    NSDictionary *metadata = [self getPartitionMetadata:table filter:partitionFilter];
    result.files_before = [metadata[@"file_count"] intValue];
    long long totalBytes = [metadata[@"total_bytes"] longLongValue];

    // Step 2: Calculate target file count
    result.files_after = (int)std::max(1LL, totalBytes / (targetSizeMB * 1024LL * 1024LL));

    // Step 3: Get row count before compaction
    long long beforeCount = [self getRowCount:table filter:partitionFilter];

    // Step 4: Submit compaction job
    // Uses Iceberg's rewriteDataFiles action via Spark
    NSDictionary *jobConfig = @{
        @"action": @"rewrite_data_files",
        @"table": table,
        @"filter": partitionFilter,
        @"target_file_size_bytes": @(targetSizeMB * 1024 * 1024),
        @"min_input_files": @2  // only compact if 2+ files exist
    };
    [self submitSparkAction:jobConfig];

    // Step 5: Verify row count after compaction
    long long afterCount = [self getRowCount:table filter:partitionFilter];
    NSAssert(beforeCount == afterCount,
        @"Row count mismatch: %lld -> %lld", beforeCount, afterCount);

    result.rows = afterCount;
    return result;
}

Request path / sequence

Trade-offs I'd say out loud

Coalesce vs repartition

Coalesce avoids shuffle but may produce uneven file sizes with skewed data. Repartition guarantees even sizing but costs a full shuffle

In-place vs copy-and-swap

In-place (Iceberg rewrite) is atomic and safe. Copy-and-swap (Hive) requires manual verification but works without table format migration

Target file size

256MB is the sweet spot for S3 + Parquet. Larger files reduce file count but increase single-task read time and retry cost

Continuous vs scheduled compaction

Continuous (e.g., Iceberg auto-compaction) keeps files tidy but adds background load. Scheduled (nightly) concentrates cost but allows tiny-file accumulation during the day

Sort during compaction

Sorting by a query-relevant column (user_id) improves query speed via min/max pruning. But sorting adds shuffle cost to compaction

Where it usually breaks

  • Compaction job OOMs reading a partition with 100K files — use partial-progress mode to commit incrementally
  • Hive partition overwrite fails mid-write — partition has partial data; write to temp then swap
  • Compaction runs during peak query hours — competing for cluster resources; schedule off-peak
  • Streaming job continues writing tiny files while compaction runs — net file count does not decrease; fix the root cause first
  • expire_snapshots deletes files still referenced by a running query — set retention > max query duration
