Build a daily orders pipeline that can be re-run safely

A green Airflow square means nothing if yesterday's re-run duplicated revenue or wiped a partial partition.

60-minute agenda

How I'd open the discussion

I'd define success as: re-running dt=2024-06-15 twice leaves curated.orders identical, and a late file arriving at 11:00 still lands without manual surgery. That sounds trivial — but most pipelines I have inherited fail this test because tasks append directly into curated, retry logic re-inserts, or partition-overwrite mode is off and nobody noticed.

The pattern that works every time: write to a staging location keyed by dt + run_id, validate row counts and null thresholds, then atomically publish into the curated dt partition via Iceberg/Delta MERGE or whole-partition overwrite. Never append straight into curated from a task that might restart.

The raw zone must be append-only and immutable. If a source file lands late, the re-run picks it up because we scan raw/orders/dt=2024-06-15/** — any file dropped there by any run_id gets included. The staging write is idempotent because we either replace the staging directory entirely or use MERGE with a deterministic surrogate key. The publish step is atomic: Hive ALTER TABLE PARTITION … SET LOCATION or Delta REPLACE WHERE dt = '2024-06-15'.

Late data is handled by a lookback window. The daily job for dt processes not just today but also dt-1 and dt-2 raw partitions, checks if any new files appeared since the last successful run, and re-publishes affected partitions. The watermark table tracks what was processed, so downstream consumers know which dates are fresh.

Approach / design notes

The core insight is separating the write from the publish. Every pipeline run writes to a staging location that includes the run_id, so concurrent or retried runs never collide. The quality gate reads staging and either passes (triggering atomic publish) or fails (blocking the DAG and alerting).

Transform logic: Spark reads all Parquet files under raw/orders/dt=YYYY-MM-DD/ — regardless of run_id. This is what makes late files work: a file that lands at 11:00 in a new run_id subdirectory is simply another file in the same dt prefix. The transform deduplicates by order_id using ROW_NUMBER() partitioned by order_id, ordered by updated_at DESC, keeping rank=1. This handles both duplicates from retries and updates to the same order.

Publish uses INSERT OVERWRITE with dynamic partition mode or Iceberg's replacePartitions(). The key property: this is atomic at the catalog level. Downstream queries either see the old partition or the new one — never a half-written state. If the publish fails mid-write, the old partition is still intact.

For late data, the daily DAG includes a lookback window. On the run for dt=2024-06-15, we also check raw/orders/dt=2024-06-13/ and dt=2024-06-14/ for files newer than the watermark. If found, we re-stage and re-publish those dates too. The watermark table records the latest published_at for each dt, so we can efficiently detect new arrivals.

Airflow behavior on clear+re-run: because we use partition overwrite (not append), clearing a task and re-running it produces identical output. No manual partition deletion needed. The run_id in staging prevents collisions between the original run and the retry.

Deep dive (spend 15–25 minutes here)

The dedup strategy deserves scrutiny. ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) keeps the latest version of each order. But what if two source files contain the same order_id with the same updated_at? Then ROW_NUMBER is non-deterministic. I add a tiebreaker: ORDER BY updated_at DESC, _file_modification_time DESC, _input_file_name DESC. The file metadata columns make the ordering deterministic even with timestamp ties.

Partition overwrite modes matter. In Hive/Spark, there are two modes: static and dynamic. Static overwrites ALL partitions in the table — catastrophic if you only meant to replace one day. Dynamic overwrites only the partitions that appear in the output data. You must set spark.sql.sources.partitionOverwriteMode=dynamic. I have seen production incidents where this config was missing and a re-run of dt=2024-06-15 deleted every other date in the table.

Quality gate design: I run three tiers of checks. Tier 1 (blocking): row count > 0, row count within ±10% of yesterday, PK uniqueness (COUNT DISTINCT order_id = COUNT *). Tier 2 (warning): null rate on revenue < 1%, null rate on customer_id < 0.5%, no negative order_total values. Tier 3 (monitoring): reconciliation against source system's count API. Tier 1 failures block the publish and page on-call. Tier 2 sends a Slack alert but publishes. Tier 3 is logged for audit.

Iceberg vs Delta for the curated layer: both support atomic partition replacement. Iceberg's replacePartitions() is cleaner for this use case because it explicitly scopes the overwrite to the specified partition filter — there is no risk of accidentally touching other partitions. Delta's REPLACE WHERE achieves the same but requires careful predicate matching. Both maintain time-travel history, so if a publish is wrong, you can rollback to the previous snapshot.

Watermark table atomicity: the publish and watermark update should be in the same transaction if possible. With Iceberg, I commit a custom metadata property on the table snapshot that includes the watermark. With Hive, I use a separate Postgres table and wrap the ALTER PARTITION and watermark INSERT in a single Airflow task so they succeed or fail together.

Backfill mode: when re-processing 30 days, I fan out into parallel Airflow tasks — one per dt. Each runs the same stage → validate → publish pipeline independently. The parallelism is bounded by pool slots (I set max 5 concurrent dt partitions to avoid starving production jobs). The watermark table tracks which dates completed, so a partial backfill failure is resumable.

Spark transform with dedup and quality gate

from pyspark.sql import SparkSession, Window
from pyspark.sql import functions as F
from datetime import datetime, timedelta


def transform_orders(spark: SparkSession, dt: str, run_id: str, lookback: int = 2):
    """
    Daily orders pipeline that can be re-run safely.
    - Processes target date plus lookback days for late-arriving files.
    - Deduplicates on order_id using latest updated_at timestamp.
    - Quality gates block bad data from reaching the curated layer.
    - Atomic publish via overwrite ensures idempotent reruns.
    """
    # Build date list: target date + lookback for late-file detection
    base = datetime.strptime(dt, '%Y-%m-%d')
    dates = [dt] + [
        (base - timedelta(days=i)).strftime('%Y-%m-%d')
        for i in range(1, lookback + 1)
    ]

    for process_dt in dates:
        raw_path = f's3://lake/raw/orders/dt={process_dt}/'
        raw_df = spark.read.parquet(raw_path)

        # Deduplicate: keep latest version of each order_id
        w = Window.partitionBy('order_id').orderBy(
            F.col('updated_at').desc(),
            F.col('_metadata.file_modification_time').desc()
        )
        deduped = (
            raw_df
            .withColumn('_rank', F.row_number().over(w))
            .filter(F.col('_rank') == 1)
            .drop('_rank')
        )

        # Write to staging (run_id makes it idempotent)
        staging_path = f's3://lake/staging/orders/dt={process_dt}/run_id={run_id}/'
        deduped.write.mode('overwrite').parquet(staging_path)

        # Quality gates: block if data looks wrong
        count = deduped.count()
        null_revenue = deduped.filter(F.col('order_total').isNull()).count()
        assert count > 0, f'Zero rows for {process_dt}'
        assert null_revenue / count < 0.01, f'Null revenue rate {null_revenue/count:.2%}'

        # Atomic publish to curated layer (overwrite = idempotent)
        deduped.write.mode('overwrite').insertInto('curated.orders')

// In production, this would run as a compiled binary on the cluster
// or orchestrate Spark via REST API (Livy/Spark Connect).

use polars::prelude::*;
use chrono::{NaiveDate, Duration};
use std::path::Path;

/// Daily orders pipeline that can be re-run safely.
/// - Deduplicates on order_id using latest updated_at.
/// - Quality gates block bad data from reaching curated layer.
/// - Atomic publish via overwrite ensures idempotent reruns.
pub fn transform_orders(
    dt: &str,
    run_id: &str,
    lookback: usize,
) -> Result<(), PolarsError> {
    let base = NaiveDate::parse_from_str(dt, "%Y-%m-%d").expect("Invalid date");

    // Build date list: target date + lookback for late-file detection
    let mut dates = vec![dt.to_string()];
    for i in 1..=lookback {
        let d = base - Duration::days(i as i64);
        dates.push(d.format("%Y-%m-%d").to_string());
    }

    for process_dt in &dates {
        let raw_path = format!("s3://lake/raw/orders/dt={}/", process_dt);

        // Read parquet files from the raw layer
        let raw_df = LazyFrame::scan_parquet(&raw_path, Default::default())?;

        // Deduplicate: sort by updated_at descending, keep first per order_id
        let deduped = raw_df
            .sort(
                ["updated_at"],
                SortMultipleOptions::default().with_order_descending(true),
            )
            .unique(Some(vec!["order_id".into()]), UniqueKeepStrategy::First)
            .collect()?;

        // Write to staging (run_id makes reruns idempotent)
        let staging_path = format!(
            "s3://lake/staging/orders/dt={}/run_id={}/data.parquet",
            process_dt, run_id
        );
        let mut file = std::fs::File::create(&staging_path)?;
        ParquetWriter::new(&mut file).finish(&mut deduped.clone())?;

        // Quality gates
        let count = deduped.height();
        assert!(count > 0, "Zero rows for {}", process_dt);

        let null_revenue = deduped
            .column("order_total")?
            .null_count();
        let null_rate = null_revenue as f64 / count as f64;
        assert!(
            null_rate < 0.01,
            "Null revenue rate {:.2}% exceeds 1% threshold",
            null_rate * 100.0
        );

        // Atomic publish: overwrite the curated partition
        let curated_path = format!("s3://lake/curated/orders/dt={}/data.parquet", process_dt);
        let mut file = std::fs::File::create(&curated_path)?;
        ParquetWriter::new(&mut file).finish(&mut deduped.clone())?;
    }

    Ok(())
}

// Orchestration layer for a daily orders pipeline.
// In an Objective-C++ context this would typically call a Spark/Livy REST API
// or invoke spark-submit as a subprocess. The logic below shows the full
// pipeline structure with dedup, quality gates, and atomic publish.

@interface OrdersPipeline : NSObject
@property (nonatomic, strong) NSString *sparkEndpoint;

- (instancetype)initWithEndpoint:(NSString *)endpoint;
- (BOOL)transformOrdersForDate:(NSString *)dt runId:(NSString *)runId lookback:(int)lookback;
@end

@implementation OrdersPipeline

- (instancetype)initWithEndpoint:(NSString *)endpoint {
    self = [super init];
    if (self) { _sparkEndpoint = endpoint; }
    return self;
}

/// Submit the daily orders transform via Spark Connect / Livy REST API.
/// Handles lookback dates, dedup, quality gates, and atomic publish.
- (BOOL)transformOrdersForDate:(NSString *)dt runId:(NSString *)runId lookback:(int)lookback {
    // Build list of dates to process (target + lookback for late arrivals)
    NSDateFormatter *fmt = [[NSDateFormatter alloc] init];
    fmt.dateFormat = @"yyyy-MM-dd";
    NSDate *baseDate = [fmt dateFromString:dt];
    NSMutableArray<NSString *> *dates = [NSMutableArray arrayWithObject:dt];

    for (int i = 1; i <= lookback; i++) {
        NSDate *d = [baseDate dateByAddingTimeInterval:-(i * 86400)];
        [dates addObject:[fmt stringFromDate:d]];
    }

    for (NSString *processDt in dates) {
        // Submit PySpark job via REST API with these parameters:
        // - raw_path: s3://lake/raw/orders/dt={processDt}/
        // - Dedup logic: ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC)
        // - Staging write: s3://lake/staging/orders/dt={processDt}/run_id={runId}/
        // - Quality gate: count > 0, null_revenue_rate < 1%
        // - Atomic publish: overwrite into curated.orders

        NSDictionary *jobConfig = @{
            @"raw_path": [NSString stringWithFormat:@"s3://lake/raw/orders/dt=%@/", processDt],
            @"staging_path": [NSString stringWithFormat:
                @"s3://lake/staging/orders/dt=%@/run_id=%@/", processDt, runId],
            @"dedup_key": @"order_id",
            @"dedup_order": @"updated_at DESC",
            @"quality_checks": @[
                @{@"type": @"row_count", @"min": @1},
                @{@"type": @"null_rate", @"column": @"order_total", @"max_rate": @0.01}
            ],
            @"target_table": @"curated.orders",
            @"write_mode": @"overwrite"
        };

        BOOL success = [self submitSparkJob:jobConfig];
        if (!success) {
            NSLog(@"Pipeline failed for dt=%@", processDt);
            return NO;
        }
    }
    return YES;
}

/// Submit a Spark job via the configured REST endpoint (Livy/Spark Connect).
- (BOOL)submitSparkJob:(NSDictionary *)config {
    NSError *err = nil;
    NSData *body = [NSJSONSerialization dataWithJSONObject:config options:0 error:&err];
    if (err) return NO;

    NSURL *url = [NSURL URLWithString:
        [NSString stringWithFormat:@"%@/batches", _sparkEndpoint]];
    NSMutableURLRequest *req = [NSMutableURLRequest requestWithURL:url];
    req.HTTPMethod = @"POST";
    req.HTTPBody = body;
    [req setValue:@"application/json" forHTTPHeaderField:@"Content-Type"];

    // Synchronous for illustration; production would use async + polling
    NSURLResponse *resp = nil;
    NSData *data = [NSURLConnection sendSynchronousRequest:req
                                        returningResponse:&resp error:&err];
    NSHTTPURLResponse *httpResp = (NSHTTPURLResponse *)resp;
    return httpResp.statusCode == 200 || httpResp.statusCode == 201;
}

Request path / sequence

Trade-offs I'd say out loud

Append vs overwrite

Append is cheaper but non-idempotent — retries duplicate data. Overwrite costs a full partition rewrite but guarantees identical output on re-run

Iceberg vs Delta vs Hive

Iceberg and Delta give atomic partition replacement and time travel. Hive requires careful ALTER PARTITION management but has zero migration cost for existing warehouses

Lookback window size

Larger lookback catches more late data but increases compute. I default to 2 days and expand to 7 for known-late sources

In-DAG quality checks vs separate job

In-DAG is simpler and blocks bad data. Separate quality DAG adds flexibility but introduces timing gaps where bad data is briefly visible

Staging TTL

7-day retention balances debuggability against storage cost. Shorter TTL saves money but makes post-incident investigation harder

Dedup strategy

ROW_NUMBER is deterministic and correct; DISTINCT is cheaper but loses update ordering. GROUP BY + MAX(updated_at) works but drops other columns

Where it usually breaks

  • Partition overwrite mode set to 'static' — re-run of one date wipes entire table; set dynamic mode explicitly
  • Sensor times out before vendor file arrives — task fails, Airflow retry picks it up; but if retry exhaustion hits, late-file lookback catches it next day
  • Quality gate false positive: yesterday had a holiday dip, today's +15% looks suspicious — use day-of-week baselines, not just yesterday
  • Staging write fails mid-way: partial Parquet files in staging — overwrite mode on next run replaces them; no corruption propagates to curated
  • Concurrent DAG runs for the same dt: run_id isolation prevents collision, but publish order matters — last writer wins, which is correct if transform is deterministic
  • Iceberg snapshot accumulates: 365 daily publishes × 3 years = 1095 snapshots with data files — run expire_snapshots weekly
  • Watermark update fails after publish succeeds: lookback will re-process an already-correct partition — harmless due to idempotency but wastes compute

What "good enough" looks like in 60 minutes

A strong answer covers: immutable raw zone design, the stage → validate → atomic publish pattern, dedup logic with deterministic ordering, quality gates that block bad data before it reaches curated, and late-file handling via lookback windows. You should draw the linear DAG flow and explain why append mode breaks on retry.

You do not need to design the full Airflow DAG YAML, the downstream dependency graph, or the schema evolution automation. Mentioning Iceberg/Delta time travel for rollback and watermark tracking for downstream freshness shows depth. The interviewer wants to see that you understand idempotency is a property of the entire pipeline, not just one task.
