Design a near-real-time clickstream lake

Clickstream wants minutes of lag, cheap storage, and honest language about exactly-once.

60-minute agenda

How I'd open the discussion

Clickstream is the canonical 'high volume, low value per event' data problem. We are talking about 2–5 billion events per day — page views, clicks, scrolls, impressions — each 300–500 bytes. The business wants near-real-time analytics (minutes, not hours) but also cheap long-term storage for ML training data and retrospective analysis.

The architecture is: browser/app SDK → Kafka → stream processor (Flink or Spark Structured Streaming) → Iceberg/Delta tables on S3. The stream processor handles schema validation, sessionization, enrichment (geo-IP, user-agent parsing), and writes micro-batches to the lake every 1–2 minutes.

The 'exactly-once' question is where most designs get dishonest. Kafka gives at-least-once by default. Flink's exactly-once requires checkpointing + two-phase commit to the sink. With Iceberg, we get atomic commits, so a failed micro-batch either fully commits or fully rolls back. But duplicates can still arrive from the SDK (user retries, network blips). True exactly-once is an application-level property: we need event deduplication either in the stream processor (windowed dedup on event_id) or downstream (MERGE on event_id in the lake table).

Open questions worth asking

  • Event volume — peak events per second?
  • Freshness SLA — minutes or sub-second?
  • Do we need sessionization in the streaming layer or batch?
  • Which enrichments — geo-IP, device type, user lookup?
  • Retention policy — how long to keep raw events?
  • Downstream consumers — real-time dashboards, batch ML, or both?
  • Schema evolution — how often do new event types appear?
  • Exactly-once requirement — is at-least-once with dedup acceptable?
  • Are there PII fields that need masking before lake landing?
  • Multi-region — do events originate from multiple continents?

Approach / design notes

The pipeline has four stages: ingest, process, land, and maintain.

Ingest: the SDK sends events to a Kafka REST proxy or directly to Kafka. Events are partitioned by hash(user_id) so all events from the same user land on the same partition — essential for sessionization. We use Avro with a schema registry to enforce structure at the producer level. Malformed events go to a dead-letter topic.

Process: Flink reads from clickstream.raw with exactly-once source semantics (consumer offsets committed as part of checkpoints). The processing pipeline: (1) schema validation — reject events missing required fields, (2) deduplication — maintain a keyed state of event_ids seen in the last 10 minutes, (3) enrichment — geo-IP lookup from a MaxMind database loaded as a broadcast variable, user-agent parsing, (4) sessionization — assign session_id using a session window with 30-minute gap.

Land: Flink writes to Iceberg using the IcebergSink with micro-batch commits every 60 seconds. Each commit is atomic — either all events in the batch land or none do. The table is partitioned by hours(event_ts) for time-range query efficiency and sorted by user_id within partitions for user-centric queries.

Maintain: compaction runs every hour to merge small files (the 60-second micro-batches produce many small files). Target file size is 256MB. Snapshot expiry runs daily, keeping 72 hours of snapshots for time-travel debugging. Old partitions (>90 days) are moved to S3 Glacier via lifecycle rules, but the Iceberg metadata remains — queries transparently read from Glacier with higher latency.

Exactly-once semantics: Flink's checkpointing guarantees that on recovery, processing resumes from the last checkpoint — no events are reprocessed that were already committed to Iceberg. The remaining gap is SDK-level duplicates: the user's browser might retry an event that was already sent. The dedup window catches most of these; for the rest, downstream consumers should use event_id as a natural key for idempotent processing.

Deep dive (spend 15–25 minutes here)

Sessionization strategy: I use event-time session windows with a 30-minute gap. Flink's session window merges events within the gap into a single session. The session_id is deterministic: hash(user_id + session_start_ts). Late events (arriving after the window closes) either extend an existing session or create a new one, depending on the allowed-lateness configuration. I set allowed lateness to 1 hour — events arriving more than 1 hour late are still processed but may create a separate session that gets merged in a downstream batch job.

Watermarking: Flink tracks event-time progress using watermarks. With out-of-order events, I use a bounded-out-of-orderness strategy with a 30-second tolerance. This means: when Flink sees an event at T=10:30:00, it advances the watermark to T=10:29:30. Any event with timestamp before 10:29:30 is considered late. The 30-second bound is a tradeoff: larger bounds improve completeness but increase latency (windows cannot close until the watermark passes their end).

Iceberg commit conflicts: with multiple Flink subtasks writing to the same table, commit conflicts can occur. Iceberg uses optimistic concurrency — each commit validates against the current table state. If another commit happened since the snapshot was read, the commit retries with a merge. For append-only workloads (our case), conflicts are rare because subtasks write to different files. The risk is during compaction: if a compaction commit and a write commit overlap, one retries.

Geo-IP enrichment: I load the MaxMind database (~50MB) as a Flink broadcast state, refreshed every 24 hours. The lookup is in-memory, adding <1ms per event. User-agent parsing uses a compiled regex library (ua-parser) — also <1ms. Total enrichment overhead is ~2ms per event, negligible at 50k eps.

Compaction strategy: every micro-batch commit adds files. With 60-second batches and 18 parallelism, we add 18 files per minute = 1,080 files per hour. Without compaction, a single hourly partition would have 1,080 tiny files. The compaction job (Iceberg's rewriteDataFiles) runs hourly, targeting 256MB files. After compaction, an hourly partition has ~32 files (8GB / 256MB). This is critical for query performance — Trino/Spark plan time scales linearly with file count.

from pyflink.datastream import StreamExecutionEnvironment
from pyflink.table import StreamTableEnvironment

def build_clickstream_pipeline():
    """
    Near-real-time clickstream lake using Flink.
    - Consumes from Kafka topic in Avro format.
    - Watermark at 30s handles late events.
    - Deduplicates on event_id using ROW_NUMBER window.
    - Enriches with geo and device type UDFs.
    - Sinks to Iceberg table for lakehouse queries.
    """
    env = StreamExecutionEnvironment.get_execution_environment()
    # Checkpoint every 60s for fault tolerance
    env.enable_checkpointing(60_000)
    env.get_checkpoint_config().set_min_pause_between_checkpoints(30_000)

    t_env = StreamTableEnvironment.create(env)

    # Source: Kafka topic with Avro deserialization
    t_env.execute_sql("""
    CREATE TABLE clickstream_raw (
      event_id STRING,
      event_type STRING,
      user_id STRING,
      event_ts TIMESTAMP(3),
      url STRING,
      ip_address STRING,
      user_agent STRING,
      WATERMARK FOR event_ts AS event_ts - INTERVAL '30' SECOND
    ) WITH (
      'connector' = 'kafka',
      'topic' = 'clickstream.raw',
      'properties.bootstrap.servers' = 'kafka:9092',
      'format' = 'avro',
      'scan.startup.mode' = 'latest-offset'
    )
    """)

    # Sink: Iceberg table with dedup and enrichment
    t_env.execute_sql("""
    INSERT INTO iceberg_clickstream
    SELECT event_id, event_type, user_id, event_ts,
           geo_lookup(ip_address) AS country_code,
           parse_ua(user_agent) AS device_type
    FROM (
      SELECT *, ROW_NUMBER() OVER (
        PARTITION BY event_id ORDER BY event_ts
      ) AS rn
      FROM clickstream_raw
    ) WHERE rn = 1
    """)

/// Deduplication window that tracks seen event_ids within a time window.
/// Rejects duplicates and evicts entries older than the watermark.
pub struct DedupWindow {
    seen: HashMap<String, u64>,  // event_id -> first_seen_ts
    watermark_ms: u64,
}

impl DedupWindow {
    pub fn new(watermark_ms: u64) -> Self {
        Self { seen: HashMap::new(), watermark_ms }
    }

    /// Returns true if this event_id has NOT been seen before.
    pub fn is_new(&mut self, event_id: &str, event_ts: u64) -> bool {
        // Evict entries below watermark
        let cutoff = event_ts.saturating_sub(self.watermark_ms);
        self.seen.retain(|_, ts| *ts >= cutoff);

        if self.seen.contains_key(event_id) {
            false  // duplicate
        } else {
            self.seen.insert(event_id.to_string(), event_ts);
            true
        }
    }
}

/// Dedup check: returns YES if event_id not seen within watermark window.
- (BOOL)isNewEvent:(const ClickEvent &)event {
    // Evict entries older than watermark
    uint64_t cutoff = event.event_ts > _watermarkMs ? event.event_ts - _watermarkMs : 0;
    for (auto it = _seenEvents.begin(); it != _seenEvents.end();) {
        if (it->second < cutoff) {
            it = _seenEvents.erase(it);
        } else {
            ++it;
        }
    }

    if (_seenEvents.count(event.event_id)) {
        return NO;  // duplicate
    }
    _seenEvents[event.event_id] = event.event_ts;
    return YES;
}

Request path / sequence

Trade-offs I'd say out loud

Flink vs Spark Structured Streaming

Flink has true event-time processing and lower latency. Spark SS is simpler for teams already on Spark but micro-batch latency is 30s+ minimum

Iceberg vs Delta Lake

Both support atomic commits. Iceberg has better partition evolution and Flink integration. Delta has tighter Spark integration and Unity Catalog

Dedup in stream vs lake

Stream dedup (Flink state) catches duplicates in real time but costs memory. Lake dedup (MERGE) is cheaper but duplicates are visible briefly

Avro vs JSON

Avro with schema registry enforces contracts and is 30-40% smaller. JSON is human-readable and easier to debug but schema violations are silent

Hourly vs daily partitions

Hourly gives finer query granularity and smaller compaction units. Daily reduces partition count but means larger compaction jobs

Exactly-once vs at-least-once

Exactly-once requires Flink checkpointing + 2PC to Iceberg — higher latency on recovery. At-least-once with dedup is simpler and usually sufficient

Where it usually breaks

  • Flink checkpoint fails — recovery replays from last checkpoint, causing duplicate processing; Iceberg atomic commits prevent duplicate files but dedup state may re-emit
  • Kafka consumer lag spikes during traffic surge — autoscale Flink parallelism or accept temporary increased latency
  • Schema change in SDK without registry update — events fail validation and flood the DLQ; need backward-compatible schema evolution
  • Compaction job and write job commit simultaneously — Iceberg optimistic concurrency handles it, but one commit retries with slight delay
  • Late events arrive 2 hours after window close — sessionization is incorrect for those users; batch reconciliation job needed
  • S3 throttling at 5,500 PUT/s per prefix — partition Iceberg output across multiple prefixes using hive-style partitioning
  • MaxMind geo-IP database becomes stale — weekly refresh via broadcast update in Flink
