Model slowly changing dimensions at scale

SCD2 is correct and expensive — at warehouse scale you need merge strategy and query patterns that don't scan five years of versions by accident.

60-minute agenda

How I'd open the discussion

SCD Type 2 tracks every historical version of a dimension record. When a customer changes their address, we do not overwrite — we close the old record (set valid_to = now()) and insert a new one (valid_from = now(), valid_to = '9999-12-31'). This gives us point-in-time queries: 'What was this customer's segment on 2023-03-15?'

At small scale, SCD2 is straightforward. At warehouse scale — 50M customers with an average of 12 versions each = 600M rows — it becomes an operational challenge. Every query that joins to the dimension must filter WHERE valid_from <= event_date AND valid_to > event_date. Without a partition or sort strategy, this means scanning all 600M rows for every join.

The merge strategy matters too. Daily CDC delivers 500K changed records. A naive MERGE INTO scans the entire 600M-row table to match on customer_id. With Iceberg or Delta, merge-on-read strategies and partition pruning can reduce this to a much smaller working set. The daily merge should take minutes, not hours.

Open questions worth asking

  • How many dimension records and what is the average version count?
  • How often do changes arrive — daily CDC, real-time, or weekly?
  • Do we need point-in-time queries, or is current-state sufficient?
  • What is the downstream join pattern — fact tables with event dates?
  • Storage budget — can we keep all versions forever?
  • Query latency expectations for dimension lookups?
  • Do hard-deletes in the source need to be tracked?
  • Is the surrogate key strategy deterministic or auto-increment?

Scope I'd lock first

  • In scope — SCD2 table design, daily MERGE logic, query optimization, storage management
  • In scope — Point-in-time join patterns, current-view materialization
  • Out of scope — Full CDC pipeline design, MDM (master data management)

Approach / design notes

The core design has three pillars: efficient MERGE, optimized queries, and storage management.

Efficient MERGE: the daily CDC delivers 500K changed records. A naive MERGE scans all 600M rows. With is_current partitioning, the MERGE only needs to match against the 50M current rows (the is_current=TRUE partition). The row_hash column enables change detection: we only close and reopen records where the hash differs. If the CDC sends a record identical to the current version, we skip it. This reduces the actual MERGE work to only genuinely changed records — often 100K out of the 500K CDC records.

The MERGE is a two-step atomic operation: (1) UPDATE matching current records with changed hash to set is_current=FALSE and valid_to=now(), (2) INSERT new versions with is_current=TRUE and valid_to='9999-12-31'. Both steps are within the same Iceberg commit, so readers see either the pre-MERGE or post-MERGE state, never a mix.

Query optimization: 90% of analytical queries only need the current dimension state. The is_current partition means these queries scan 50M rows instead of 600M — 12× less data. For point-in-time queries, the table is sorted by (customer_id, valid_from) within partitions. This means a range filter on valid_from/valid_to combined with a customer_id equality filter can use min/max pruning to skip most files. A query for 5M fact rows joining on customer_id with a single date scans approximately 2M dimension rows instead of 600M.

Storage management: at 500K new versions/day, the table grows by ~250MB/day in Parquet. After 5 years, historical versions total ~3.5TB. For versions older than 2 years, I archive to a separate cold-storage table with lifecycle rules on S3 Glacier. The dim.customers table retains only 2 years of history + all current records. A view unions both for rare full-history queries.

Deep dive (spend 15–25 minutes here)

Row hash for change detection: I use MD5(concat_ws('|', tracked_columns)). This catches any change across all tracked columns in a single comparison. The alternative — comparing each column individually — is more expensive and harder to maintain as columns are added. MD5 has collision risk, but at 50M records, the probability is astronomically low (~10^-24) and a collision means we miss one update, not data corruption.

Surrogate key generation: I use a Snowflake ID for the surrogate key (sk). Each version of a customer gets a new sk, while customer_id (the natural key) stays the same. Fact tables should store customer_id (the natural key), not the surrogate key, because the sk changes with every dimension update. This is a departure from classic Kimball, where facts store the sk — but at scale, updating fact tables to point to new surrogate keys is impractical.

Late-arriving dimension changes: if a CDC event for a change that happened at 14:00 arrives at 22:00, we need to insert a version with valid_from = 14:00, not 22:00. This means splitting the current record: close the current version at 14:00, insert the changed version from 14:00 to 22:00, and insert another current version from 22:00. This three-way operation is more complex and I only implement it if business requirements demand accurate historical timestamps.

Version explosion: some entities change frequently — a product with daily price changes accumulates 365 versions/year. After 5 years: 1,825 versions per product. With 1M products, that is 1.8B rows in the dimension table. Mitigations: (1) micro-batch CDC to catch intraday changes and collapse them into a single daily version, (2) only track columns that matter for analytics (exclude frequently-changing metadata), (3) use SCD4 (separate history table) for columns that change constantly.

Merge-on-read vs copy-on-write: Iceberg supports both. Copy-on-write rewrites affected files during MERGE — expensive for a 500K-record MERGE. Merge-on-read writes delta files that are reconciled at query time — cheaper MERGE but slower queries until compaction runs. For a daily MERGE cadence, I prefer copy-on-write because the query latency impact of merge-on-read accumulates throughout the day, and compaction adds operational complexity.

SCD2 merge with hash-based change detection

from pyspark.sql import SparkSession, functions as F


def scd2_merge(spark: SparkSession, target_table: str, cdc_table: str, dt: str,
               natural_key: str = 'customer_id',
               tracked_cols: list = None):
    """
    SCD Type 2 merge with hash-based change detection.
    - Compares MD5 hash of tracked columns to detect actual changes.
    - Closes old versions (sets valid_to, is_current=False).
    - Inserts new versions with valid_from=now, is_current=True.
    - Avoids unnecessary writes when data hasn't changed.
    """
    cdc = spark.table(cdc_table).filter(F.col('dt') == dt)
    current = spark.table(target_table).filter(F.col('is_current') == True)

    if tracked_cols is None:
        tracked_cols = ['customer_name', 'address', 'segment', 'region']

    # Hash tracked columns for efficient change detection
    hash_expr = F.md5(F.concat_ws('|', *[F.col(c) for c in tracked_cols]))
    cdc = cdc.withColumn('_new_hash', hash_expr)
    current = current.withColumn('_cur_hash', hash_expr)

    # Find rows where the hash differs (actual changes only)
    changed = (
        cdc.alias('s')
        .join(current.alias('t'), natural_key, 'inner')
        .filter(F.col('s._new_hash') != F.col('t._cur_hash'))
        .select('s.*')
    )

    now = F.current_timestamp()

    # Close old versions: set valid_to and mark as not current
    closed = (
        current.join(changed.select(natural_key), natural_key, 'inner')
        .withColumn('valid_to', now)
        .withColumn('is_current', F.lit(False))
    )

    # New versions: open-ended validity, marked as current
    new_versions = (
        changed
        .withColumn('valid_from', now)
        .withColumn('valid_to', F.lit('9999-12-31').cast('timestamp'))
        .withColumn('is_current', F.lit(True))
        .withColumn('row_hash', F.col('_new_hash'))
    )

    return closed, new_versions
// SCD Type 2 merge with hash-based change detection using Polars.
// Conceptual implementation showing the merge logic pattern.

use polars::prelude::*;
use md5;
use chrono::Utc;

/// SCD Type 2 merge result: rows to close and new versions to insert.
pub struct SCD2Result {
    pub closed_versions: DataFrame,
    pub new_versions: DataFrame,
}

/// Perform SCD2 merge with hash-based change detection.
/// - Compares MD5 hash of tracked columns to detect actual changes.
/// - Returns closed rows (to update) and new versions (to insert).
pub fn scd2_merge(
    current: &DataFrame,
    cdc: &DataFrame,
    natural_key: &str,
    tracked_cols: &[&str],
) -> Result<SCD2Result, PolarsError> {
    // Compute hash for tracked columns in both DataFrames
    let cdc_hashed = add_row_hash(cdc, tracked_cols, "_new_hash")?;
    let current_hashed = add_row_hash(current, tracked_cols, "_cur_hash")?;

    // Join on natural key to find matching records
    let joined = cdc_hashed.join(
        &current_hashed,
        &[natural_key],
        &[natural_key],
        JoinArgs::new(JoinType::Inner),
    )?;

    // Filter to rows where hash differs (actual changes only)
    let changed_mask = joined.column("_new_hash")?
        .not_equal(joined.column("_cur_hash")?)?;
    let changed_keys = joined.filter(&changed_mask)?
        .select([natural_key])?;

    let now = Utc::now().naive_utc();

    // Close old versions: set valid_to and is_current=false
    let closed = current_hashed.join(
        &changed_keys,
        &[natural_key],
        &[natural_key],
        JoinArgs::new(JoinType::Inner),
    )?
    .lazy()
    .with_columns([
        lit(now).alias("valid_to"),
        lit(false).alias("is_current"),
    ])
    .collect()?;

    // New versions: valid_from=now, valid_to=9999-12-31, is_current=true
    let far_future = chrono::NaiveDate::from_ymd_opt(9999, 12, 31)
        .unwrap().and_hms_opt(0, 0, 0).unwrap();

    let new_versions = cdc_hashed.join(
        &changed_keys,
        &[natural_key],
        &[natural_key],
        JoinArgs::new(JoinType::Inner),
    )?
    .lazy()
    .with_columns([
        lit(now).alias("valid_from"),
        lit(far_future).alias("valid_to"),
        lit(true).alias("is_current"),
        col("_new_hash").alias("row_hash"),
    ])
    .collect()?;

    Ok(SCD2Result { closed_versions: closed, new_versions })
}

/// Compute MD5 hash of concatenated tracked columns and add as a new column.
fn add_row_hash(
    df: &DataFrame,
    tracked_cols: &[&str],
    hash_col_name: &str,
) -> Result<DataFrame, PolarsError> {
    let concatenated: Vec<String> = (0..df.height()).map(|i| {
        tracked_cols.iter()
            .map(|&col_name| {
                df.column(col_name)
                    .ok()
                    .and_then(|s| s.get(i).ok())
                    .map(|v| format!("{}", v))
                    .unwrap_or_default()
            })
            .collect::<Vec<_>>()
            .join("|")
    }).collect();

    let hashes: Vec<String> = concatenated.iter()
        .map(|s| format!("{:x}", md5::compute(s.as_bytes())))
        .collect();

    let hash_series = Series::new(hash_col_name, hashes);
    let mut result = df.clone();
    result.with_column(hash_series)?;
    Ok(result)
}
#import <Foundation/Foundation.h>
#include <CommonCrypto/CommonDigest.h>
#include <string>
#include <vector>
#include <unordered_map>

// SCD Type 2 merge with hash-based change detection.
// Conceptual implementation for orchestrating the merge logic.

struct DimensionRow {
    std::string natural_key;
    std::string customer_name;
    std::string address;
    std::string segment;
    std::string region;
    std::string valid_from;
    std::string valid_to;
    bool is_current;
    std::string row_hash;
};

@interface SCD2Merger : NSObject

/// Compute MD5 hash of tracked columns for change detection.
+ (NSString *)computeRowHash:(NSDictionary *)row trackedCols:(NSArray<NSString *> *)cols;

/// Perform SCD2 merge: detect changes, close old versions, create new versions.
+ (NSDictionary *)mergeCurrentRows:(NSArray<NSDictionary *> *)currentRows
                       withCDCRows:(NSArray<NSDictionary *> *)cdcRows
                        naturalKey:(NSString *)naturalKey
                       trackedCols:(NSArray<NSString *> *)trackedCols;
@end

@implementation SCD2Merger

/// MD5 hash of pipe-concatenated tracked column values.
+ (NSString *)computeRowHash:(NSDictionary *)row trackedCols:(NSArray<NSString *> *)cols {
    NSMutableString *concat = [NSMutableString string];
    for (NSUInteger i = 0; i < cols.count; i++) {
        if (i > 0) [concat appendString:@"|"];
        [concat appendString:row[cols[i]] ?: @""];
    }

    unsigned char digest[CC_MD5_DIGEST_LENGTH];
    CC_MD5([concat UTF8String],
           (CC_LONG)[concat lengthOfBytesUsingEncoding:NSUTF8StringEncoding],
           digest);

    NSMutableString *hex = [NSMutableString stringWithCapacity:CC_MD5_DIGEST_LENGTH * 2];
    for (int i = 0; i < CC_MD5_DIGEST_LENGTH; i++) {
        [hex appendFormat:@"%02x", digest[i]];
    }
    return hex;
}

/// Perform SCD2 merge and return closed rows + new versions.
+ (NSDictionary *)mergeCurrentRows:(NSArray<NSDictionary *> *)currentRows
                       withCDCRows:(NSArray<NSDictionary *> *)cdcRows
                        naturalKey:(NSString *)naturalKey
                       trackedCols:(NSArray<NSString *> *)trackedCols {
    // Build lookup: natural_key -> current row hash
    NSMutableDictionary *currentHashes = [NSMutableDictionary dictionary];
    for (NSDictionary *row in currentRows) {
        NSString *key = row[naturalKey];
        NSString *hash = [self computeRowHash:row trackedCols:trackedCols];
        currentHashes[key] = @{@"hash": hash, @"row": row};
    }

    NSMutableArray *closedRows = [NSMutableArray array];
    NSMutableArray *newVersions = [NSMutableArray array];
    NSString *now = [self currentTimestamp];

    for (NSDictionary *cdcRow in cdcRows) {
        NSString *key = cdcRow[naturalKey];
        NSString *newHash = [self computeRowHash:cdcRow trackedCols:trackedCols];

        NSDictionary *existing = currentHashes[key];
        if (!existing) continue;  // new inserts handled separately

        NSString *curHash = existing[@"hash"];
        if ([newHash isEqualToString:curHash]) {
            continue;  // no change, skip
        }

        // Close old version: set valid_to and is_current=false
        NSMutableDictionary *closed = [existing[@"row"] mutableCopy];
        closed[@"valid_to"] = now;
        closed[@"is_current"] = @NO;
        [closedRows addObject:closed];

        // Create new version: valid_from=now, is_current=true
        NSMutableDictionary *newVersion = [cdcRow mutableCopy];
        newVersion[@"valid_from"] = now;
        newVersion[@"valid_to"] = @"9999-12-31T00:00:00Z";
        newVersion[@"is_current"] = @YES;
        newVersion[@"row_hash"] = newHash;
        [newVersions addObject:newVersion];
    }

    return @{@"closed": closedRows, @"new_versions": newVersions};
}

+ (NSString *)currentTimestamp {
    NSDateFormatter *fmt = [[NSDateFormatter alloc] init];
    fmt.dateFormat = @"yyyy-MM-dd'T'HH:mm:ss'Z'";
    fmt.timeZone = [NSTimeZone timeZoneWithName:@"UTC"];
    return [fmt stringFromDate:[NSDate date]];
}
@end

Request path / sequence

Trade-offs I'd say out loud

SCD2 vs SCD1 (overwrite)

SCD2 preserves history for point-in-time queries but costs 12× storage. SCD1 is simpler and cheaper if history is not needed

is_current partition vs full scan

Partitioning by is_current gives 12× speedup for current-state queries but adds partition management and MERGE complexity

Row hash vs column-by-column comparison

Hash is faster and simpler as columns grow. Column comparison allows identifying which specific column changed

Natural key in facts vs surrogate key

Natural key avoids updating facts on dimension changes. Surrogate key follows Kimball but is impractical at scale

Copy-on-write vs merge-on-read

COW has expensive MERGE but fast queries. MOR has cheap MERGE but slower queries until compaction

Where it usually breaks

  • MERGE scans all 600M rows because is_current partition filter was missing from the ON clause — always include it
  • CDC delivers the same record twice — row_hash match means no change; second delivery is a no-op (correct behavior)
  • Late-arriving change: CDC event timestamped 14:00 arrives at 22:00 — current version's valid_from is wrong; need temporal insert logic
  • Version explosion: one customer changes address 50 times in a day — collapse intraday changes before MERGE
  • Point-in-time join misses events exactly at valid_from boundary — use >= for valid_from and < for valid_to (half-open interval)

What "good enough" looks like in 60 minutes

A strong answer covers: SCD2 schema design with valid_from/valid_to and is_current, the MERGE strategy with hash-based change detection, partition-by-is_current for query optimization, point-in-time join patterns, and storage growth management. Show the MERGE SQL and explain why it needs to be atomic.

You do not need to design the full CDC pipeline or handle bi-temporal modeling. The interviewer wants to see: understanding of why SCD2 is expensive at scale, practical optimization through partitioning and sorting, and awareness of the query-side implications (range joins, current views).
