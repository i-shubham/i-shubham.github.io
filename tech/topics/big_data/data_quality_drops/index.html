Detect silent data quality drops

The pipeline stayed green while revenue_null_rate went from 0.4% to 18% — silent failure is the default without checks.

60-minute agenda

How I'd open the discussion

Silent data quality degradation is the default failure mode. I have seen a pipeline run green for 6 weeks while the null rate on revenue went from 0.4% to 18%. No alert fired because the checks only looked at row count (which was fine) and schema (which had not changed). The business discovered it when a finance report showed $0 revenue for 12% of orders — two weeks after the problem started.

The fix is multi-layer checks with appropriate sensitivity. Row count checks catch catastrophic failures (empty partitions, source outages). Statistical checks catch drift: null rates, value distributions, cardinality changes. Reconciliation checks catch systemic issues: our total revenue should match the source system's total within 0.1%. Each layer catches a different class of failure.

The hard part is not writing checks — it is tuning thresholds and handling false positives. A 5% row count variance might be normal on Monday (fewer weekend orders) but alarming on Tuesday. Day-of-week baselines, rolling averages, and seasonal adjustments reduce false positives while catching genuine degradation.

Open questions worth asking

  • What types of quality issues have bitten us before?
  • Which columns are business-critical — revenue, customer_id, status?
  • Do we have a source system to reconcile against?
  • What is the acceptable false-positive rate for alerts?
  • Should failed checks block the pipeline or only alert?
  • How fast must we detect a problem — minutes, hours, next day?
  • Are there known seasonal patterns (weekends, holidays)?
  • Who gets paged — data team, analytics, or product?
  • Current tooling: Great Expectations, dbt tests, custom?
  • Is schema evolution a source of quality issues?

Scope I'd lock first

  • In scope — Volume checks, null/distribution checks, reconciliation checks, alerting
  • In scope — Day-of-week baselines, false-positive reduction, tiered severity
  • Out of scope — ML-based anomaly detection, data lineage tracking
  • Defer — Data contracts with upstream teams, automated root-cause attribution

-- Quality check results history
CREATE TABLE meta.quality_results (
  check_id        STRING,
  table_name      STRING,
  check_name      STRING,
  dt              STRING,
  check_type      STRING,
  metric_value    DOUBLE,
  baseline_value  DOUBLE,
  threshold       DOUBLE,
  passed          BOOLEAN,
  severity        STRING,
  executed_at     TIMESTAMP,
  PRIMARY KEY (check_id)
);

-- Baseline computation
SELECT
  check_name,
  DAYOFWEEK(dt) AS dow,
  AVG(metric_value) AS baseline,
  STDDEV(metric_value) AS stddev
FROM meta.quality_results
WHERE dt >= CURRENT_DATE - 28
  AND passed = TRUE           -- exclude known-bad days
GROUP BY check_name, DAYOFWEEK(dt);

Approach / design notes

The quality framework has three tiers, each catching a different failure class.

Tier 1 — Volume checks: these are the smoke test. COUNT(*) for the current date compared to the day-of-week rolling average over 28 days. Monday's baseline is the average of the last 4 Mondays, not yesterday (which was Sunday). A variance > 10% triggers a P1 alert and blocks the publish step. This catches: source outages (0 rows), partial loads (50% of expected), and unexpected surges (data duplication).

Tier 2 — Statistical checks: null rates, cardinality, and distribution metrics. For revenue, the null rate must stay below 1%. For status, the cardinality must match the expected set — a new unknown status value is a schema change that should be investigated. For numeric columns, I track p50/p95/p99 over time — a sudden shift in the p95 of order_total suggests a pricing change or data corruption. These checks alert at P2 (Slack notification) but do not block.

Tier 3 — Reconciliation: compare our aggregated totals against the source system. For orders, SUM(order_total) should match the source system's daily total within 0.1%. This catches: dedup errors (we dropped or duplicated rows), transformation bugs (currency conversion), and schema misinterpretation (a column meaning changed). Reconciliation is the most expensive check (requires querying the source system) but catches the most insidious bugs.

False positive reduction: besides day-of-week baselines, I implement: (1) holiday calendar — widen thresholds on known holidays, (2) alert muting — if the same check fails 3 days in a row and has been acknowledged, auto-mute further alerts until the metric recovers, (3) human feedback loop — when an analyst marks an alert as false positive, feed that into baseline adjustment.

Deep dive (spend 15–25 minutes here)

Great Expectations integration: I define expectations in a JSON suite per table, executed by a SparkDFValidation action within the Airflow DAG. The checkpoint runs after the transform task and before publish. Failed critical expectations raise an exception that stops the DAG. The validation result is stored in a GE data docs site (S3-hosted) for post-mortem review.

Statistical checks need care. A simple null-rate threshold of 1% works for revenue, but for optional fields like referrer, the baseline null rate might be 40%. The threshold should be relative: alert if null rate increases by more than 5 percentage points from the 28-day average, not if it exceeds an absolute value. This requires per-column baseline computation.

Reconciliation timing: source systems and the lake pipeline may process data at different times. If the source system reports 50M orders at 23:00 and our pipeline runs at 02:00, late-arriving orders in our pipeline may cause a positive discrepancy. I add a tolerance window: reconciliation compares our dt partition against the source's dt minus a ±2% timing tolerance. If the discrepancy exceeds tolerance, I wait one hour and re-check — often the source system's count catches up.

Anomaly detection at scale: for 25 tables with 150 checks, manual threshold tuning is unsustainable. I use a simple z-score approach: if today's metric is > 3 standard deviations from the 28-day same-DOW mean, alert. This automatically adapts to each check's natural variance without manual threshold configuration. The exception: business-critical checks (revenue null rate, reconciliation) always have explicit hard thresholds regardless of historical variance.

Root cause attribution: when a check fails, the alert should include not just the failing metric but also what changed. I run a delta analysis: which partitions contributed the most null revenue? Which source files are new since the last good run? Which column changed the most? This turns a 'revenue null rate is 18%' alert into 'revenue null rate spiked to 18% in partition dt=2024-06-15, caused by file vendor_drop_eu.csv which has 100% null revenue column.'

Volume and null-rate checks with DOW baselines

from dataclasses import dataclass
from typing import Optional


@dataclass
class CheckResult:
    name: str
    metric_value: float
    baseline: float
    threshold: float
    passed: bool
    severity: str


def volume_check(spark, table, dt, baseline_days=28) -> CheckResult:
    """
    Detect silent row count drops using day-of-week baselines.
    Compares current count against the average for the same weekday
    over the past N days. Flags if variance exceeds 10%.
    """
    current = spark.sql(f"SELECT COUNT(*) FROM {table} WHERE dt='{dt}'").first()[0]

    # Use same day-of-week baseline to account for weekly patterns
    dow = get_day_of_week(dt)
    baselines = spark.sql(f"""
        SELECT AVG(row_count) AS avg_count
        FROM meta.quality_results
        WHERE table_name='{table}'
          AND check_name='row_count'
          AND DAYOFWEEK(dt) = {dow}
          AND dt >= DATE_SUB('{dt}', {baseline_days})
          AND passed = TRUE
    """).first()

    baseline = baselines.avg_count or current
    variance = abs(current - baseline) / baseline if baseline > 0 else 0

    return CheckResult(
        name='row_count',
        metric_value=current,
        baseline=baseline,
        threshold=0.10,
        passed=variance <= 0.10,
        severity='P1',
    )


def null_rate_check(spark, table, column, dt, max_rate=0.01) -> CheckResult:
    """
    Check null rate for a critical column.
    Flags if null percentage exceeds the configured threshold.
    """
    stats = spark.sql(f"""
        SELECT COUNT(*) AS total,
               SUM(CASE WHEN {column} IS NULL THEN 1 ELSE 0 END) AS nulls
        FROM {table} WHERE dt='{dt}'
    """).first()

    rate = stats.nulls / stats.total if stats.total > 0 else 0

    return CheckResult(
        name=f'{column}_null_rate',
        metric_value=rate,
        baseline=0,
        threshold=max_rate,
        passed=rate <= max_rate,
        severity='P1',
    )
// Data quality checks implemented in Rust using Polars.
// Suitable for running as a sidecar validator or compiled quality gate.

use polars::prelude::*;
use chrono::{NaiveDate, Datelike};

#[derive(Debug)]
pub struct CheckResult {
    pub name: String,
    pub metric_value: f64,
    pub baseline: f64,
    pub threshold: f64,
    pub passed: bool,
    pub severity: String,
}

/// Detect silent row count drops using day-of-week baselines.
/// Compares current count against average for same weekday over past N days.
pub fn volume_check(
    current_df: &DataFrame,
    baseline_df: &DataFrame,
    table: &str,
    dt: &str,
    baseline_days: u32,
) -> CheckResult {
    let current_count = current_df.height() as f64;

    // Filter baseline to same day-of-week
    let target_date = NaiveDate::parse_from_str(dt, "%Y-%m-%d").unwrap();
    let target_dow = target_date.weekday().num_days_from_sunday();

    // Calculate baseline from historical quality results
    let baseline_avg = baseline_df
        .lazy()
        .filter(
            col("check_name").eq(lit("row_count"))
            .and(col("table_name").eq(lit(table)))
            .and(col("passed").eq(lit(true)))
        )
        .select([col("row_count").mean().alias("avg_count")])
        .collect()
        .ok()
        .and_then(|df| df.column("avg_count").ok()?.f64().ok()?.get(0))
        .unwrap_or(current_count);

    let variance = if baseline_avg > 0.0 {
        (current_count - baseline_avg).abs() / baseline_avg
    } else {
        0.0
    };

    CheckResult {
        name: "row_count".to_string(),
        metric_value: current_count,
        baseline: baseline_avg,
        threshold: 0.10,
        passed: variance <= 0.10,
        severity: "P1".to_string(),
    }
}

/// Check null rate for a critical column.
/// Flags if null percentage exceeds the configured threshold.
pub fn null_rate_check(
    df: &DataFrame,
    column: &str,
    max_rate: f64,
) -> CheckResult {
    let total = df.height() as f64;
    let null_count = df.column(column)
        .map(|s| s.null_count() as f64)
        .unwrap_or(0.0);

    let rate = if total > 0.0 { null_count / total } else { 0.0 };

    CheckResult {
        name: format!("{}_null_rate", column),
        metric_value: rate,
        baseline: 0.0,
        threshold: max_rate,
        passed: rate <= max_rate,
        severity: "P1".to_string(),
    }
}

#include <string>
#include <cmath>

// Data quality check framework.
// Detects silent drops in volume and null rate violations.

struct CheckResult {
    std::string name;
    double metric_value;
    double baseline;
    double threshold;
    bool passed;
    std::string severity;
};

@interface DataQualityChecker : NSObject
@property (nonatomic, strong) NSString *sparkEndpoint;

- (instancetype)initWithEndpoint:(NSString *)endpoint;
- (CheckResult)volumeCheck:(NSString *)table
                        dt:(NSString *)dt
              baselineDays:(int)baselineDays;
- (CheckResult)nullRateCheck:(NSString *)table
                      column:(NSString *)column
                          dt:(NSString *)dt
                     maxRate:(double)maxRate;
@end

@implementation DataQualityChecker

- (instancetype)initWithEndpoint:(NSString *)endpoint {
    self = [super init];
    if (self) { _sparkEndpoint = endpoint; }
    return self;
}

/// Detect silent row count drops using day-of-week baselines.
/// Compares current count against same-weekday average over baseline_days.
- (CheckResult)volumeCheck:(NSString *)table
                        dt:(NSString *)dt
              baselineDays:(int)baselineDays {
    CheckResult result;
    result.name = "row_count";
    result.threshold = 0.10;
    result.severity = "P1";

    // Query current row count via Spark SQL
    NSString *countQuery = [NSString stringWithFormat:
        @"SELECT COUNT(*) FROM %@ WHERE dt='%@'", table, dt];
    double currentCount = [self executeScalarQuery:countQuery];
    result.metric_value = currentCount;

    // Get day-of-week for the target date
    NSDateFormatter *fmt = [[NSDateFormatter alloc] init];
    fmt.dateFormat = @"yyyy-MM-dd";
    NSDate *date = [fmt dateFromString:dt];
    NSCalendar *cal = [NSCalendar currentCalendar];
    NSInteger dow = [cal component:NSCalendarUnitWeekday fromDate:date];

    // Query baseline: average row count for same weekday over past N days
    NSString *baselineQuery = [NSString stringWithFormat:
        @"SELECT AVG(row_count) FROM meta.quality_results "
        @"WHERE table_name='%@' AND check_name='row_count' "
        @"AND DAYOFWEEK(dt) = %ld AND dt >= DATE_SUB('%@', %d) "
        @"AND passed = TRUE",
        table, (long)dow, dt, baselineDays];
    double baselineAvg = [self executeScalarQuery:baselineQuery];
    if (baselineAvg == 0) baselineAvg = currentCount;
    result.baseline = baselineAvg;

    // Check variance against threshold
    double variance = (baselineAvg > 0)
        ? std::abs(currentCount - baselineAvg) / baselineAvg
        : 0.0;
    result.passed = (variance <= result.threshold);

    return result;
}

/// Check null rate for a critical column against max allowed rate.
- (CheckResult)nullRateCheck:(NSString *)table
                      column:(NSString *)column
                          dt:(NSString *)dt
                     maxRate:(double)maxRate {
    CheckResult result;
    result.name = std::string([column UTF8String]) + "_null_rate";
    result.baseline = 0.0;
    result.threshold = maxRate;
    result.severity = "P1";

    NSString *query = [NSString stringWithFormat:
        @"SELECT COUNT(*) AS total, "
        @"SUM(CASE WHEN %@ IS NULL THEN 1 ELSE 0 END) AS nulls "
        @"FROM %@ WHERE dt='%@'",
        column, table, dt];

    // Execute and parse results
    NSDictionary *stats = [self executeRowQuery:query];
    double total = [stats[@"total"] doubleValue];
    double nulls = [stats[@"nulls"] doubleValue];
    double rate = (total > 0) ? nulls / total : 0.0;

    result.metric_value = rate;
    result.passed = (rate <= maxRate);
    return result;
}

// Helpers: execute queries via Spark SQL REST endpoint
- (double)executeScalarQuery:(NSString *)query { return 0; }
- (NSDictionary *)executeRowQuery:(NSString *)query {
    return @{@"total": @1000000, @"nulls": @50};
}
@end

Request path / sequence

Trade-offs I'd say out loud

Hard thresholds vs adaptive

Hard thresholds are simple but need manual tuning. Adaptive (z-score) handles variance automatically but may miss slow drift that stays within bounds

Blocking vs alerting

Blocking checks prevent bad data from reaching consumers but can halt the pipeline on false positives. Alert-only is safer for availability but risks serving bad data

GE vs dbt tests vs custom

Great Expectations has rich validation logic. dbt tests are simpler and native to dbt workflows. Custom checks offer full flexibility but need more maintenance

Check granularity

Per-column checks catch more issues but multiply runtime and alert volume. Per-table checks are faster but miss column-level degradation

Real-time vs batch

Batch checks after pipeline completion detect issues once. Real-time streaming checks catch degradation earlier but add operational complexity

Where it usually breaks

  • Volume check false alarm on a holiday: Monday after Thanksgiving has 30% fewer orders — use a holiday calendar to widen thresholds
  • Reconciliation fails due to source system timing: source updates its count at 04:00, pipeline runs at 02:00 — add a retry with 2-hour delay
  • Alert fatigue: 10 P2 alerts per day → team ignores all of them — reduce sensitivity, improve specificity, use auto-muting for persistent known issues
  • Null rate drifts slowly: 0.4% → 0.6% → 0.9% → 1.1% over 4 weeks — z-score misses because each day is within 1 stddev; need trend detection
  • Schema change breaks check: new column added, old check references removed column — checks must be version-aware or fail gracefully

Follow-ups if time remains

  • How would you build a data contract system with upstream producers?
  • How do you prioritize which tables get quality checks first?
  • How would you detect data quality issues in a streaming pipeline?
  • How do you handle a quality check that has been failing for weeks and the team has not fixed the root cause?

What "good enough" looks like in 60 minutes

A strong answer covers: the three-tier check taxonomy (volume, statistical, reconciliation), day-of-week baselines for reducing false positives, severity-based alert routing (P1 blocks, P2 warns), and an honest discussion of the false-positive vs false-negative tradeoff. You should give a concrete example of a silent quality drop and how your checks would catch it.

You do not need to design the full monitoring dashboard or the ML-based anomaly detection system. The interviewer wants to see: understanding that quality checks are about sensitivity AND specificity, practical experience with false positives, and a tiered approach that matches severity to business impact.
