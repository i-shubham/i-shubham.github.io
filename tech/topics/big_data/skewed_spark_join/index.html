Fix a skewed Spark join

One key with 5% of rows turns a 20-minute join into a 3-hour wait on a single executor.

60-minute agenda

How I'd open the discussion

I'd start by confirming skew in the Spark UI: one task in the join stage at 10× the median duration, with massive spill to disk while the other 199 tasks finished in 30 seconds. That single task is processing all rows for a hot key — often null, 'UNKNOWN', or a mega-customer that generates 5% of all orders.

The naive fix is 'throw more memory at it' — increase executor memory from 8GB to 32GB. That hides the OOM but does not fix the wall time: you still have one task doing 50× the work of its peers. The cluster sits idle waiting for it.

Broadcast join is the first thing people reach for, but it only works if one side is genuinely small. I have seen 'small' dimension tables that were 12GB after a bad filter push-down — well beyond the broadcast threshold. And broadcasting a 12GB table to 200 executors means 2.4TB of network transfer.

The real fix depends on the skew pattern. If it is null keys, filter them out before the join and union them back (nulls never match anyway in equi-joins). If it is a genuine hot key, salt it: append a random integer 0..N-1 to the hot key on the big side, and replicate the matching rows N times on the small side. This spreads the hot partition across N tasks. AQE (Adaptive Query Execution) in Spark 3.x can do this automatically, but it has configuration thresholds that are often too conservative for real skew.

Open questions worth asking

  • Approximate row counts for both sides of the join?
  • Which keys are hot — top 10 by frequency?
  • Is AQE enabled and what Spark version?
  • Are null join keys present in significant volume?
  • Is the join selective enough to pre-filter before joining?
  • SLA constraint — can we afford a two-pass approach?
  • Is the small side actually small (< 1GB), or has it grown?
  • Join type — inner, left, or full outer?
  • How many executors and how much memory per executor?
  • Is the skew stable (same keys every run) or shifting?

Scope I'd lock first

  • In scope — Fix one skewed equi-join to balance task runtimes
  • In scope — Verify correctness: output matches naive join exactly
  • Out of scope — Redesigning the entire warehouse data model
  • Defer — Automating skew detection across all jobs

Approach / design notes

The approach has three layers, applied in order of simplicity.

Layer 1 — Filter nulls: NULL keys never match in an equi-join, so they consume shuffle and memory for zero output. I filter WHERE customer_id IS NOT NULL before the join and UNION ALL the null rows with NULL dimension columns after. This alone removes 8M rows from the shuffle and eliminates one source of skew.

Layer 2 — AQE skew join: In Spark 3.2+, AQE detects partitions that are N× larger than the median and automatically splits them, replicating the small side for the split portions. I set skewedPartitionFactor=5 and skewedPartitionThresholdInBytes=256MB. This handles moderate skew without code changes. But AQE only kicks in after the shuffle — if the hot partition causes OOM during the shuffle write, AQE cannot help.

Layer 3 — Manual salting: For severe skew (one key with 5%+ of rows), I salt explicitly. On the big side, I add a column: salt = abs(hash(order_id)) % 10. On the small side, I explode: for each customer row where customer_id is in the hot-key set, I generate 10 copies with salt 0..9. Non-hot keys get salt=0 and one copy. The join becomes ON (customer_id, salt). The hot partition splits into 10 balanced tasks.

The two-pass variant is cleaner for production: separate hot keys into a dedicated Spark job that broadcasts the filtered small side (only hot-key rows), and run the non-skewed majority as a normal join. UNION the results. This avoids polluting the main job with salting logic.

Deep dive (spend 15–25 minutes here)

Salting math: the hot key has 25M rows. With salt factor N=10, each salted partition gets ~2.5M rows — roughly equal to the median non-skewed partition. The small side replication adds 10 × 1 row (for the hot customer) × 10 = 10 extra rows. If there are 50 hot keys, replication adds 500 rows — negligible. The cost is the salt column in the shuffle: 4 bytes × 500M = 2GB extra shuffle data, acceptable.

Choosing the salt factor: N should make hot partitions roughly equal to the median. If the hot key has 25M rows and the median is 2.5M, N = 25M / 2.5M = 10. Over-salting (N=100) wastes shuffle partitions and increases small-side replication. Under-salting (N=3) still leaves the hot partition at 8M — better but not balanced.

AQE internals: AQE's skew join works at the physical plan level. After the shuffle, it inspects partition sizes. If a partition is > skewedPartitionFactor × median AND > skewedPartitionThreshold, it splits the partition into sub-partitions and reads the corresponding small-side partition multiple times (one read per sub-partition). The limitation: AQE cannot prevent OOM during shuffle write if the hot partition materializes in memory before AQE inspects sizes.

Broadcast join pitfalls: the broadcast threshold default is 10MB (spark.sql.autoBroadcastJoinThreshold). Engineers often bump it to 1GB+ without checking actual table size after filters. I have seen a 'small' dimension that was 12GB because a filter push-down failed silently. Broadcasting 12GB to 200 executors = 2.4TB of driver memory allocation + network transfer. Always verify with df.persist().count() + spark.catalog.isCached() before relying on broadcast.

Full outer join with skew: salting is harder here because both sides contribute unmatched rows. The approach is: (1) inner join with salting, (2) anti-join left side for unmatched left, (3) anti-join right side for unmatched right, (4) UNION ALL. More complex but correct.

Monitoring skew proactively: I add a post-job check that reads the Spark event log, extracts task-level metrics for shuffle read bytes, and alerts if max/median > 10. This catches new skew before it becomes a 3-hour incident. The check runs in 2 seconds against the JSON log.

Salted join with null handling

from pyspark.sql import SparkSession, functions as F


def salted_join(spark, orders_df, customers_df, hot_keys, salt_n=10):
    """
    Fix a skewed join by salting hot keys.
    Strategy:
    - Separate hot keys (large customers) from cold keys.
    - Salt hot-key rows with random bucket to spread them across partitions.
    - Replicate the dimension side for hot keys to match the salted buckets.
    - Handle NULL join keys separately to avoid data loss.
    - Union all three paths for the final result.
    """
    # Separate hot, cold, and null-key rows
    hot_orders = orders_df.filter(F.col('customer_id').isin(hot_keys))
    cold_orders = orders_df.filter(
        ~F.col('customer_id').isin(hot_keys) & F.col('customer_id').isNotNull()
    )
    null_orders = orders_df.filter(F.col('customer_id').isNull())

    # Salt the hot path: add random bucket column
    hot_orders = hot_orders.withColumn('_salt', (F.rand() * salt_n).cast('int'))

    # Replicate dimension rows for hot keys across all salt buckets
    hot_customers = (
        customers_df.filter(F.col('customer_id').isin(hot_keys))
        .crossJoin(spark.range(salt_n).withColumnRenamed('id', '_salt'))
    )

    # Join hot path on (customer_id, _salt) — evenly distributed
    hot_result = hot_orders.join(hot_customers, ['customer_id', '_salt']).drop('_salt')

    # Cold path: standard equi-join (no skew)
    cold_result = cold_orders.join(customers_df, 'customer_id')

    # Null path: preserve rows with NULL join key (left-side only columns)
    null_result = null_orders.select(
        *[null_orders[c] for c in orders_df.columns],
        F.lit(None).alias('customer_name'),
        F.lit(None).alias('segment'),
    )

    return hot_result.unionByName(cold_result).unionByName(null_result)
// Conceptual salted join using Polars DataFrames.
// Polars handles skew differently (parallel hash joins), but the salting
// pattern is useful when interfacing with distributed systems.

use polars::prelude::*;
use rand::Rng;

/// Fix a skewed join by salting hot keys.
/// - Hot keys are salted with a random bucket to spread across partitions.
/// - Dimension side is replicated for hot keys to match salt buckets.
/// - NULL keys are preserved separately to avoid data loss.
pub fn salted_join(
    orders: &DataFrame,
    customers: &DataFrame,
    hot_keys: &[&str],
    salt_n: u32,
) -> Result<DataFrame, PolarsError> {
    let hot_set: Vec<String> = hot_keys.iter().map(|s| s.to_string()).collect();

    // Separate hot, cold, and null-key rows
    let customer_id_col = orders.column("customer_id")?;
    let is_hot = customer_id_col.utf8()?.into_iter().map(|opt| {
        opt.map_or(false, |v| hot_set.contains(&v.to_string()))
    });

    let hot_mask = BooleanChunked::from_iter_values("mask", is_hot.clone());
    let null_mask = customer_id_col.is_null();
    let cold_mask = !&hot_mask & !&null_mask;

    let hot_orders = orders.filter(&hot_mask)?;
    let cold_orders = orders.filter(&cold_mask)?;
    let null_orders = orders.filter(&null_mask)?;

    // Add random salt column to hot orders
    let mut rng = rand::thread_rng();
    let salt_values: Vec<u32> = (0..hot_orders.height())
        .map(|_| rng.gen_range(0..salt_n))
        .collect();
    let salt_col = Series::new("_salt", salt_values);
    let hot_orders = hot_orders.hstack(&[salt_col])?;

    // Replicate hot customers across all salt buckets
    let hot_customers = customers.filter(
        &customers.column("customer_id")?.utf8()?.into_iter().map(|opt| {
            opt.map_or(false, |v| hot_set.contains(&v.to_string()))
        }).collect::<BooleanChunked>()
    )?;

    // Cross-join with salt range [0..salt_n)
    let mut replicated_frames = Vec::new();
    for bucket in 0..salt_n {
        let mut frame = hot_customers.clone();
        let salt_col = Series::new("_salt", vec![bucket; frame.height()]);
        frame = frame.hstack(&[salt_col])?;
        replicated_frames.push(frame);
    }
    let hot_customers_salted = concat_df(&replicated_frames)?;

    // Join hot path on (customer_id, _salt)
    let hot_result = hot_orders.join(
        &hot_customers_salted,
        &["customer_id", "_salt"],
        &["customer_id", "_salt"],
        JoinArgs::new(JoinType::Inner),
    )?.drop("_salt")?;

    // Cold path: standard equi-join
    let cold_result = cold_orders.join(
        customers,
        &["customer_id"],
        &["customer_id"],
        JoinArgs::new(JoinType::Inner),
    )?;

    // Null path: add NULL columns for customer fields
    let null_result = null_orders.hstack(&[
        Series::new("customer_name", vec![None::<&str>; null_orders.height()]),
        Series::new("segment", vec![None::<&str>; null_orders.height()]),
    ])?;

    // Union all three paths
    let combined = concat_df(&[hot_result, cold_result, null_result])?;
    Ok(combined)
}
#import <Foundation/Foundation.h>
#include <vector>
#include <string>
#include <set>
#include <cstdlib>

// Conceptual salted join for fixing data skew in a distributed pipeline.
// In an Objective-C++ context, this would orchestrate a Spark job or
// implement the logic for an in-process DataFrame library.

struct OrderRow {
    std::string order_id;
    std::string customer_id;  // empty string represents NULL
    double amount;
};

struct CustomerRow {
    std::string customer_id;
    std::string customer_name;
    std::string segment;
};

struct JoinedRow {
    std::string order_id;
    std::string customer_id;
    double amount;
    std::string customer_name;
    std::string segment;
};

@interface SaltedJoinExecutor : NSObject

/// Execute a salted join to fix data skew on hot keys.
/// - hotKeys: set of customer_ids that cause skew
/// - saltN: number of salt buckets to spread hot keys across
+ (std::vector<JoinedRow>)saltedJoin:(const std::vector<OrderRow> &)orders
                           customers:(const std::vector<CustomerRow> &)customers
                             hotKeys:(const std::set<std::string> &)hotKeys
                               saltN:(int)saltN;
@end

@implementation SaltedJoinExecutor

+ (std::vector<JoinedRow>)saltedJoin:(const std::vector<OrderRow> &)orders
                           customers:(const std::vector<CustomerRow> &)customers
                             hotKeys:(const std::set<std::string> &)hotKeys
                               saltN:(int)saltN {
    std::vector<JoinedRow> results;

    // Partition orders into hot, cold, and null-key buckets
    std::vector<OrderRow> hotOrders, coldOrders, nullOrders;
    for (const auto &o : orders) {
        if (o.customer_id.empty()) {
            nullOrders.push_back(o);
        } else if (hotKeys.count(o.customer_id)) {
            hotOrders.push_back(o);
        } else {
            coldOrders.push_back(o);
        }
    }

    // Build lookup map for customers
    std::unordered_map<std::string, CustomerRow> custMap;
    for (const auto &c : customers) {
        custMap[c.customer_id] = c;
    }

    // Hot path: salted join — assign random bucket and match with replicated dimension
    // The salt distributes hot-key rows evenly across partitions
    for (const auto &o : hotOrders) {
        int salt = std::rand() % saltN;
        // In distributed execution, dimension rows are replicated per salt bucket.
        // Here we simulate by direct lookup (same logical result).
        auto it = custMap.find(o.customer_id);
        if (it != custMap.end()) {
            results.push_back({o.order_id, o.customer_id, o.amount,
                              it->second.customer_name, it->second.segment});
        }
    }

    // Cold path: standard equi-join (no skew, direct lookup)
    for (const auto &o : coldOrders) {
        auto it = custMap.find(o.customer_id);
        if (it != custMap.end()) {
            results.push_back({o.order_id, o.customer_id, o.amount,
                              it->second.customer_name, it->second.segment});
        }
    }

    // Null path: preserve rows with NULL join key
    for (const auto &o : nullOrders) {
        results.push_back({o.order_id, "", o.amount, "", ""});
    }

    return results;
}

Request path / sequence

Trade-offs I'd say out loud

Salting vs AQE

Salting gives full control and works on all Spark versions. AQE is zero-code but has thresholds that may not trigger for moderate skew

Two-pass vs inline salt

Two-pass (separate hot/cold jobs) is cleaner but doubles job management. Inline salt is one job but adds complexity to the query

Broadcast vs shuffle join

Broadcast eliminates shuffle but requires the small side to fit in driver + executor memory. Wrong assumption here causes OOM at scale

Salt factor tuning

Too low: hot partition still dominates. Too high: excessive small-side replication and empty shuffle partitions

Filter push-down reliance

AQE and broadcast both assume accurate size estimation; broken filter push-down silently inflates the small side

Where it usually breaks

  • Broadcasting a 'small' table that grew to 12GB after filter push-down failure — driver OOM
  • Salt factor too low (N=2) for a key with 50M rows — still skewed, just less obviously
  • Forgot to handle nulls — 8M null-key rows silently joined to nothing, dropped from output
  • AQE splits partition but replication of small side causes memory pressure on executors with limited heap
  • Full outer join with salting: unmatched rows on both sides need separate anti-join passes
  • Hot keys change over time — static hot-key list goes stale; need periodic profiling
  • Salting adds a column to the output: downstream queries break if they SELECT * and expect fixed schema

Follow-ups if time remains

  • How would you automate hot-key detection across all jobs in the warehouse?
  • What if both sides of the join are skewed on the same key?
  • How does this change for a streaming join in Structured Streaming?
  • What if the skew is not on the join key but on the partition key (post-shuffle)?
  • How would you handle skew in a multi-way join (3+ tables)?

What "good enough" looks like in 60 minutes

A strong answer covers: diagnosing skew via Spark UI (task duration imbalance, spill metrics), the null-key optimization, broadcast join with its limitations, salting with clear math on salt factor, and AQE configuration. You should show before/after metrics (wall time, task balance) and explain why increasing executor memory is not a real fix.

You do not need to implement the full Spark job or explain AQE internals in detail. The interviewer wants to see systematic debugging: identify the hot key, quantify the skew, apply the simplest fix first (nulls, broadcast), and escalate to salting only when simpler approaches are insufficient.
