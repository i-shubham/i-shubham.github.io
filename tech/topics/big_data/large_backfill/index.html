Backfill 18 months without melting the cluster

An 18-month backfill will either be a quiet background crawl or the reason today's jobs miss SLA.

60-minute agenda

How I'd open the discussion

Someone changed a business rule retroactively, or a new column was added that needs historical values, or the pipeline was buggy for 6 months and nobody noticed. Now you need to reprocess 18 months of daily partitions — 540 dates — on a cluster that is already 70% utilized by today's production jobs.

The naive approach: loop through all 540 dates and submit them as Airflow tasks. This melts the cluster. 540 Spark jobs competing for executors means none of them finish, production jobs queue behind the backfill, SLAs break, and someone pages you at 3 AM.

The right approach treats the backfill as a managed background workload: bound concurrency (at most 5 dates in parallel), use a separate resource pool or queue with lower priority, process dates in reverse-chronological order (recent data is more valuable), and include a kill switch that pauses the backfill if production job latency exceeds threshold. Each completed date goes through the same validate → publish pipeline as the daily run — you do not skip quality checks just because it is a backfill.

Open questions worth asking

  • What changed — business rule, new column, or bug fix?
  • How many dates and what is the data volume per date?
  • Is the cluster shared with production jobs?
  • What is the production SLA — must daily jobs finish by 08:00?
  • Can we use a separate backfill cluster, or must we share?
  • Is the backfill idempotent — can we restart a failed date safely?
  • Do downstream consumers need to be notified when historical data changes?
  • Priority: all 18 months equally, or recent months first?
  • Time budget: must complete in 3 days, or can it run for 2 weeks?
  • Are there dependencies between dates (e.g., running totals)?

Scope I'd lock first

  • In scope — Reprocess 540 daily partitions with bounded concurrency and production safety
  • In scope — Quality gates per date, progress tracking, kill switch
  • Out of scope — Redesigning the pipeline logic itself — just re-running it
  • Defer — Downstream notification and dependency re-triggering

from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

BACKFILL_START = '2023-01-01'
BACKFILL_END = '2024-06-30'
MAX_CONCURRENT = 5

dag = DAG(
    'orders_backfill',
    schedule_interval=None,       # manual trigger
    max_active_tasks=MAX_CONCURRENT,
    catchup=False
)

def process_date(dt: str, **ctx):
    if is_already_done(dt): return
    if production_latency_exceeded(): raise AirflowSkipException('Kill switch')
    run_transform(dt)
    run_quality_checks(dt)
    publish_partition(dt)
    mark_done(dt)

# Generate tasks in reverse-chronological order
dates = generate_date_range(BACKFILL_END, BACKFILL_START, step=-1)
for dt in dates:
    PythonOperator(task_id=f'backfill_{dt}', python_callable=process_date,
                   op_kwargs={'dt': dt}, pool='backfill_pool', dag=dag)

Approach / design notes

The design centers on three principles: bounded concurrency, production priority, and resumability.

Bounded concurrency: I use an Airflow pool with 5 slots. Each backfill date is a task in a non-scheduled DAG (manual trigger). The pool ensures at most 5 tasks run simultaneously, regardless of how many dates are pending. Tasks are submitted in reverse-chronological order so recent data is backfilled first.

Production priority: the backfill jobs run in a separate YARN queue (or K8s namespace) with a resource ceiling of 30% of cluster capacity. If production jobs need more resources, YARN preempts backfill executors. Additionally, each backfill task checks production job latency before starting: if the daily orders pipeline's p99 runtime exceeds 2× its 7-day average, the backfill task raises AirflowSkipException and retries later.

Resumability: the backfill_progress table tracks the status of every date. On restart, tasks check this table first — if status='done', skip. If status='running' (from a crashed previous attempt), reset to 'pending' and re-run. Since the underlying pipeline is idempotent (stage → validate → overwrite), re-running a date is safe.

Quality gates: every backfilled date goes through the same quality checks as the daily run. I do not lower the bar for backfill — if a date fails quality checks, it is marked 'failed' and the next date proceeds. Failed dates are reviewed manually and retried after fixing.

Cost optimization: the backfill cluster uses Spot instances with 70% savings. If Spot capacity is reclaimed, the task fails and automatically retries with a new Spot instance. The bounded concurrency ensures we never have more than 50 executors on Spot, limiting blast radius.

Deep dive (spend 15–25 minutes here)

Date dependencies: most backfills are embarrassingly parallel — each date can be processed independently. But if the pipeline computes running totals (e.g., cumulative revenue), dates must be processed in order. For serial dependencies, I reduce parallelism to 1 and process oldest-first. For partial dependencies (e.g., month-to-date aggregations), I batch by month and process dates within each month serially, but months in parallel.

Downstream notification: when a historical partition is rewritten, downstream consumers (dashboards, ML training data) may need to know. I publish a backfill_complete event to a Kafka topic with the affected date range. Dashboard materialization jobs can subscribe and refresh affected views. ML training pipelines can invalidate cached feature datasets.

Cost modeling: 540 dates × 25 min/date at 10 executors = 2,250 executor-hours. At Spot pricing ($0.62/hr for m5.2xlarge), total cost is ~$1,400. On-demand would be ~$5,625. The key risk with Spot is interruption: if Spot capacity drops, mid-run tasks fail. The idempotent pipeline ensures retries are safe, and the progress tracker skips completed dates. Worst case: a task is interrupted 3 times, adding ~75 min of wasted work per date.

Monitoring during backfill: I set up a Grafana dashboard showing: (1) backfill progress — completed/failed/pending counts, (2) production latency — overlay of daily pipeline runtime with the kill-switch threshold, (3) cluster utilization — queue-level resource consumption, (4) cost tracking — accumulated Spot spend vs budget. The kill switch sends a Slack alert when it triggers so the team knows the backfill is paused.

Validation thoroughness: for the first few dates of a backfill, I run both the old and new pipeline logic and diff the outputs. If the diff shows only the expected changes (e.g., the new column is populated, the business rule produces different revenue numbers), I trust the rest of the backfill. If unexpected differences appear, I stop and investigate before processing the remaining 530 dates.

Backfill manager with kill switch

from datetime import datetime, timedelta


class BackfillManager:
    """
    Backfill 18 months of data without melting the cluster.
    Features:
    - Processes dates in reverse-chronological order (most valuable first).
    - Kill switch: pauses if production latency exceeds threshold.
    - Progress tracking for resumability after failures.
    - Configurable concurrency limit.
    """

    def __init__(self, start_dt, end_dt, max_concurrent=5, prod_latency_threshold=2.0):
        self.dates = self._generate_dates(start_dt, end_dt)
        self.max_concurrent = max_concurrent
        self.threshold = prod_latency_threshold
        self.progress = {}  # dt -> status

    def _generate_dates(self, start, end):
        """Generate dates in reverse-chronological order."""
        dates = []
        current = datetime.strptime(end, '%Y-%m-%d')
        stop = datetime.strptime(start, '%Y-%m-%d')
        while current >= stop:
            dates.append(current.strftime('%Y-%m-%d'))
            current -= timedelta(days=1)
        return dates

    def should_pause(self) -> bool:
        """Kill switch: check if production latency is dangerously elevated."""
        avg_latency = get_prod_avg_latency_7d()
        current_latency = get_prod_current_p99()
        return current_latency > self.threshold * avg_latency

    def run_date(self, dt: str):
        """Process a single date partition with safety checks."""
        if self.progress.get(dt) == 'done':
            return  # already completed, skip

        # Kill switch check before starting
        if self.should_pause():
            raise RuntimeError(
                f'Kill switch: prod latency exceeded {self.threshold}x baseline'
            )

        self.progress[dt] = 'running'
        try:
            run_transform(dt)
            run_quality_checks(dt)
            publish_partition(dt)
            self.progress[dt] = 'done'
        except Exception as e:
            self.progress[dt] = 'failed'
            raise
use chrono::{NaiveDate, Duration};
use std::collections::HashMap;
use tokio::sync::Semaphore;
use std::sync::Arc;

#[derive(Clone, PartialEq)]
pub enum BackfillStatus {
    Pending,
    Running,
    Done,
    Failed(String),
}

/// Backfill 18 months of data without melting the cluster.
/// - Reverse-chronological processing (most valuable data first).
/// - Kill switch pauses if production latency spikes.
/// - Semaphore limits concurrent partition processing.
pub struct BackfillManager {
    dates: Vec<String>,
    max_concurrent: usize,
    prod_latency_threshold: f64,
    progress: HashMap<String, BackfillStatus>,
}

impl BackfillManager {
    pub fn new(
        start_dt: &str,
        end_dt: &str,
        max_concurrent: usize,
        prod_latency_threshold: f64,
    ) -> Self {
        let dates = Self::generate_dates(start_dt, end_dt);
        let progress = dates.iter()
            .map(|d| (d.clone(), BackfillStatus::Pending))
            .collect();

        Self { dates, max_concurrent, prod_latency_threshold, progress }
    }

    /// Generate dates in reverse-chronological order.
    fn generate_dates(start: &str, end: &str) -> Vec<String> {
        let start_date = NaiveDate::parse_from_str(start, "%Y-%m-%d").unwrap();
        let end_date = NaiveDate::parse_from_str(end, "%Y-%m-%d").unwrap();

        let mut dates = Vec::new();
        let mut current = end_date;
        while current >= start_date {
            dates.push(current.format("%Y-%m-%d").to_string());
            current -= Duration::days(1);
        }
        dates
    }

    /// Kill switch: check if production latency is dangerously elevated.
    async fn should_pause(&self) -> bool {
        let avg_latency = get_prod_avg_latency_7d().await;
        let current_latency = get_prod_current_p99().await;
        current_latency > self.prod_latency_threshold * avg_latency
    }

    /// Process a single date partition with safety checks.
    pub async fn run_date(&mut self, dt: &str) -> Result<(), String> {
        if self.progress.get(dt) == Some(&BackfillStatus::Done) {
            return Ok(());  // already completed
        }

        // Kill switch check before starting
        if self.should_pause().await {
            return Err(format!(
                "Kill switch: prod latency exceeded {}x baseline",
                self.prod_latency_threshold
            ));
        }

        self.progress.insert(dt.to_string(), BackfillStatus::Running);

        match self.execute_partition(dt).await {
            Ok(()) => {
                self.progress.insert(dt.to_string(), BackfillStatus::Done);
                Ok(())
            }
            Err(e) => {
                self.progress.insert(dt.to_string(), BackfillStatus::Failed(e.clone()));
                Err(e)
            }
        }
    }

    async fn execute_partition(&self, dt: &str) -> Result<(), String> {
        run_transform(dt).await?;
        run_quality_checks(dt).await?;
        publish_partition(dt).await?;
        Ok(())
    }
}

#import <Foundation/Foundation.h>
#include <string>
#include <vector>
#include <map>

// Backfill manager for processing 18 months of historical data.
// Kill switch, progress tracking, and concurrency control.

typedef NS_ENUM(NSInteger, BackfillStatus) {
    BackfillStatusPending,
    BackfillStatusRunning,
    BackfillStatusDone,
    BackfillStatusFailed
};

@interface BackfillManager : NSObject {
    std::vector<std::string> _dates;
    std::map<std::string, BackfillStatus> _progress;
}

@property (nonatomic) int maxConcurrent;
@property (nonatomic) double prodLatencyThreshold;

- (instancetype)initWithStartDate:(NSString *)startDt
                          endDate:(NSString *)endDt
                    maxConcurrent:(int)maxConcurrent
              latencyThreshold:(double)threshold;
- (BOOL)runDate:(NSString *)dt error:(NSError **)error;
- (BOOL)shouldPause;
@end

@implementation BackfillManager

- (instancetype)initWithStartDate:(NSString *)startDt
                          endDate:(NSString *)endDt
                    maxConcurrent:(int)maxConcurrent
              latencyThreshold:(double)threshold {
    self = [super init];
    if (self) {
        _maxConcurrent = maxConcurrent;
        _prodLatencyThreshold = threshold;
        [self generateDatesFrom:startDt to:endDt];
    }
    return self;
}

/// Generate dates in reverse-chronological order (most valuable first).
- (void)generateDatesFrom:(NSString *)start to:(NSString *)end {
    NSDateFormatter *fmt = [[NSDateFormatter alloc] init];
    fmt.dateFormat = @"yyyy-MM-dd";

    NSDate *startDate = [fmt dateFromString:start];
    NSDate *endDate = [fmt dateFromString:end];
    NSDate *current = endDate;

    while ([current compare:startDate] != NSOrderedAscending) {
        std::string dateStr([[fmt stringFromDate:current] UTF8String]);
        _dates.push_back(dateStr);
        _progress[dateStr] = BackfillStatusPending;
        current = [current dateByAddingTimeInterval:-86400];
    }
}

/// Kill switch: pause if production latency exceeds threshold.
- (BOOL)shouldPause {
    double avgLatency = [self getProdAvgLatency7d];
    double currentLatency = [self getProdCurrentP99];
    return currentLatency > (_prodLatencyThreshold * avgLatency);
}

/// Process a single date partition with safety checks.
- (BOOL)runDate:(NSString *)dt error:(NSError **)error {
    std::string dtStr([dt UTF8String]);

    // Skip if already completed
    if (_progress[dtStr] == BackfillStatusDone) {
        return YES;
    }

    // Kill switch check before starting
    if ([self shouldPause]) {
        if (error) {
            *error = [NSError errorWithDomain:@"BackfillError" code:1
                userInfo:@{NSLocalizedDescriptionKey:
                    [NSString stringWithFormat:
                        @"Kill switch: prod latency exceeded %.1fx baseline",
                        _prodLatencyThreshold]}];
        }
        return NO;
    }

    _progress[dtStr] = BackfillStatusRunning;

    @try {
        [self runTransform:dt];
        [self runQualityChecks:dt];
        [self publishPartition:dt];
        _progress[dtStr] = BackfillStatusDone;
        return YES;
    } @catch (NSException *e) {
        _progress[dtStr] = BackfillStatusFailed;
        if (error) {
            *error = [NSError errorWithDomain:@"BackfillError" code:2
                userInfo:@{NSLocalizedDescriptionKey: e.reason ?: @"Unknown"}];
        }
        return NO;
    }
}

Request path / sequence

Trade-offs I'd say out loud

Parallelism level

More parallelism finishes faster but risks starving production. 5 slots is conservative; 10 works if the cluster is large enough

Reverse-chrono vs oldest-first

Recent data has more business value; reverse-chrono prioritizes it. Oldest-first is needed when dates have dependencies

Shared cluster vs dedicated

Shared saves money but needs resource isolation. Dedicated backfill cluster is cleaner but doubles cost

Spot vs on-demand

Spot saves 70% but tasks can be interrupted. Idempotent pipelines make Spot safe; non-idempotent pipelines should use on-demand

Quality gates on backfill

Same checks as production ensures correctness but slows backfill. Lowering thresholds risks publishing bad data

Where it usually breaks

  • Backfill steals too many executors — production daily job misses SLA; kill switch should have triggered earlier
  • Spot instance reclaimed mid-transform — task fails, retries on new instance; 25 min of work lost per interruption
  • Quality check fails for historical date: data was genuinely different 18 months ago — adjust thresholds or manually approve
  • Progress table becomes stale: task marked 'running' from a crashed attempt blocks re-submission — add a TTL that resets stale running tasks
  • Date dependency missed: running totals computed wrong because dates processed out of order — validate running totals separately

Follow-ups if time remains

  • How would you handle a backfill that also changes the schema (adding a new column)?
  • How do you validate that the backfill produced correct results for all 540 dates?
  • What if the source data for old dates is in a different format or location?
  • How would you communicate to stakeholders that historical data changed?

What "good enough" looks like in 60 minutes

A strong answer covers: bounded concurrency with a pool or queue, production priority with resource isolation, reverse-chronological processing, resumability via progress tracking, quality gates that do not get skipped, and a kill switch for production safety. Show the math on timeline and cost.

You do not need to design the monitoring dashboard or the downstream notification system. The interviewer wants to see: awareness that uncontrolled backfills break production, a systematic approach to throttling and prioritization, and idempotency that makes retries safe.
