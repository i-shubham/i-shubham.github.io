Cost-control an overgrown EMR / Databricks bill

The bill usually isn't 'Spark is expensive' — it's idle clusters, oversized executors, and jobs that shuffle like it's free.

60-minute agenda

How I'd open the discussion

The monthly EMR/Databricks bill went from $15K to $45K in three months. The CTO wants it halved. When I dig into the cost breakdown, it is never one thing — it is a combination of idle clusters (30% of the bill), oversized executors (20%), jobs with excessive shuffle (15%), and the remaining 35% is legitimate compute that could still be optimized with Spot instances and right-sizing.

Idle clusters are the low-hanging fruit. Teams create interactive clusters for development and forget to shut them down. A 10-node m5.2xlarge cluster costs $2.50/node/hr × 10 × 24 × 30 = $18,000/month — even if nobody runs a query on it. The fix is autoscaling with aggressive scale-to-zero (terminate after 15 minutes of inactivity) and tagging policies that require owner and cost-center tags.

After idle clusters, the next target is right-sizing. Engineers default to m5.4xlarge (64GB) because one job OOM'd on m5.2xlarge (32GB). But 80% of their jobs use less than 8GB per executor. The fix is profiling jobs (Spark UI executor memory utilization) and creating right-sized instance pools per workload tier.

Open questions worth asking

  • What is the current monthly bill and target budget?
  • How many clusters and what percentage are interactive vs job clusters?
  • Are clusters tagged with owner and cost center?
  • Spot instance usage — what percentage?
  • Are autoscaling and auto-termination configured?
  • Top 10 most expensive jobs — what do they do?
  • Is there a chargeback model (teams pay for their usage)?
  • Databricks Unity Catalog or raw EMR?

Scope I'd lock first

  • In scope — Identify and eliminate idle clusters, right-size instances, Spot adoption, job optimization
  • In scope — Tagging policy, autoscaling config, cost monitoring dashboard
  • Out of scope — Migrating to a different compute platform
  • Defer — Chargeback model implementation, FinOps team creation

-- Cost tracking table (populated from AWS CUR or Databricks usage logs)
CREATE TABLE meta.cluster_costs (
  cluster_id     STRING,
  cluster_name   STRING,
  owner          STRING,
  cost_center    STRING,
  date           DATE,
  instance_type  STRING,
  instance_hours DOUBLE,

  total_cost     DOUBLE
);

-- Weekly cost summary query
SELECT
  owner,
  SUM(total_cost) AS weekly_cost,
  SUM(idle_hours) / SUM(instance_hours) AS idle_pct,
  SUM(spot_savings) AS spot_saved,
  LAG(SUM(total_cost)) OVER (PARTITION BY owner ORDER BY MIN(date)) AS prev_week
FROM meta.cluster_costs
WHERE date >= CURRENT_DATE - 7
GROUP BY owner
ORDER BY weekly_cost DESC;

Approach / design notes

The cost reduction program has four phases, executed over 8 weeks.

Phase 1 (Week 1-2) — Eliminate idle waste: enable auto-termination on all clusters with a 15-minute timeout. For interactive clusters, add a warning notification at 10 minutes. For job clusters, they already terminate after the job completes — verify this is configured. Audit existing clusters: any cluster running > 2 hours with no active tasks gets flagged for review. Expected savings: $13.5K/month.

Phase 2 (Week 2-3) — Right-size instances: analyze the last 30 days of Spark UI metrics (executor memory peak, GC overhead, task CPU utilization) across all jobs. Categorize into three tiers: small (< 16GB peak → m5.xlarge at $0.19/hr), medium (16-32GB → m5.2xlarge at $0.38/hr), large (> 32GB → m5.4xlarge at $0.77/hr). Currently, 80% of jobs run on medium or large when small would suffice. Create instance pools per tier and update job configs. Expected savings: $6K/month.

Phase 3 (Week 3-4) — Spot adoption: move all batch/ETL jobs to SPOT_WITH_FALLBACK. The driver node stays on-demand (first_on_demand=1) to avoid losing job state. Workers use Spot with automatic fallback to on-demand if Spot capacity is unavailable. For Spot interruption, Spark's dynamic allocation handles graceful decommissioning — tasks on interrupted executors are retried on remaining nodes. Expected savings: $5K/month.

Phase 4 (Week 4-8) — Job optimization: target the top 10 most expensive jobs. Common wins: (1) add broadcast hints for small dimension joins, (2) filter before join to reduce shuffle, (3) cache intermediate results used multiple times, (4) increase partition count for large shuffles (avoid spill), (5) enable AQE for automatic coalesce. Expected savings: $2.5K/month.

Deep dive (spend 15–25 minutes here)

Spot instance failure modes: the primary risk is Spot interruption during a long-running job. A 4-hour Spark job losing 3 executors at hour 3 must retry affected tasks, not the whole job. Spark's dynamic allocation with decommission support (spark.decommission.enabled=true) handles this: when AWS sends the 2-minute interruption notice, the executor migrates its shuffle files to another node and completes in-flight tasks. The job continues with reduced parallelism until a new Spot instance is allocated.

Right-sizing methodology: I pull executor metrics from Spark's event log or Ganglia: peak heap usage, GC overhead percentage, and CPU utilization per task. If a job's executor peak heap is 6GB and we allocated 32GB, we are at 19% utilization — switch to m5.xlarge (16GB) and leave headroom for growth. I create a script that analyzes the last 30 days of event logs and produces a recommendation per job: current instance → recommended instance → estimated savings.

Shuffle reduction: the worst offender in our cost profile is a job that shuffles 800GB because it joins a 500M-row fact table with a 10K-row dimension table using a sort-merge join. Adding a broadcast hint (/*+ BROADCAST(dim) */) eliminates the shuffle entirely — the 10K-row table is broadcast to all executors, reducing runtime from 45 minutes to 8 minutes and cluster cost from $35/run to $6/run. At daily frequency, that is $870/month saved from one hint.

Governance enforcement: Databricks cluster policies are the enforcement mechanism. I create a policy that requires tags, sets max cluster size, enforces auto-termination, and defaults to Spot. Clusters created without the policy are blocked. For emergency overrides (a job that genuinely needs 64GB instances), the engineer requests an exception through a Jira ticket — the exception is time-bound (2 weeks) and reviewed.

Monitoring: I build a Grafana dashboard showing: daily cost by team, idle percentage trend, Spot vs on-demand ratio, and the top 10 most expensive jobs. Weekly email goes to engineering managers with their team's cost and comparison to target. Teams that exceed budget get a Slack notification. This visibility alone drives a 10-15% reduction as teams self-optimize.

Idle cluster detector for EMR

import boto3
from datetime import datetime, timedelta


def find_idle_clusters(region='us-east-1', idle_threshold_min=30):
    """
    Detect idle EMR clusters that are wasting money.
    - Checks clusters in WAITING/RUNNING state with no active steps.
    - Calculates idle duration from the ReadyDateTime.
    - Estimates hourly cost for prioritization.
    - Returns sorted by cost (highest waste first).
    """
    emr = boto3.client('emr', region_name=region)
    clusters = emr.list_clusters(
        CreatedAfter=datetime.now() - timedelta(days=30),
        ClusterStates=['WAITING', 'RUNNING']
    )['Clusters']

    idle = []
    for c in clusters:
        cluster_id = c['Id']
        # Check if any steps are currently running
        steps = emr.list_steps(ClusterId=cluster_id, StepStates=['RUNNING'])['Steps']
        if not steps:
            ready_since = c.get('Status', {}).get('Timeline', {}).get('ReadyDateTime')
            if ready_since:
                idle_min = (datetime.now(ready_since.tzinfo) - ready_since).total_seconds() / 60
                if idle_min > idle_threshold_min:
                    tags = {
                        t['Key']: t['Value']
                        for t in emr.describe_cluster(ClusterId=cluster_id)
                                    ['Cluster'].get('Tags', [])
                    }
                    idle.append({
                        'cluster_id': cluster_id,
                        'name': c['Name'],
                        'idle_minutes': int(idle_min),
                        'owner': tags.get('owner', 'UNTAGGED'),
                        'est_hourly_cost': estimate_cost(cluster_id),
                    })

    return sorted(idle, key=lambda x: x['est_hourly_cost'], reverse=True)

// Identifies clusters wasting money by sitting idle.

use aws_sdk_emr::{Client as EmrClient, types::ClusterState};
use chrono::{Utc, Duration as ChronoDuration};
use std::collections::HashMap;

#[derive(Debug)]
pub struct IdleCluster {
    pub cluster_id: String,
    pub name: String,
    pub idle_minutes: i64,
    pub owner: String,
    pub est_hourly_cost: f64,
}

/// Find EMR clusters that have been idle beyond the threshold.
/// Returns clusters sorted by estimated hourly cost (highest waste first).
pub async fn find_idle_clusters(
    client: &EmrClient,
    idle_threshold_min: i64,
) -> Result<Vec<IdleCluster>, aws_sdk_emr::Error> {
    let cutoff = Utc::now() - ChronoDuration::days(30);

    // List clusters in WAITING or RUNNING state
    let clusters = client.list_clusters()
        .set_created_after(Some(cutoff.into()))
        .set_cluster_states(Some(vec![
            ClusterState::Waiting,
            ClusterState::Running,
        ]))
        .send()
        .await?;

    let mut idle = Vec::new();

    for cluster_summary in clusters.clusters().unwrap_or_default() {
        let cluster_id = cluster_summary.id().unwrap_or_default();

        // Check if any steps are currently running
        let steps = client.list_steps()
            .cluster_id(cluster_id)
            .set_step_states(Some(vec![aws_sdk_emr::types::StepState::Running]))
            .send()
            .await?;

        if steps.steps().unwrap_or_default().is_empty() {
            // No running steps — check how long it's been idle
            let detail = client.describe_cluster()
                .cluster_id(cluster_id)
                .send()
                .await?;

            let cluster = detail.cluster().unwrap();
            let ready_dt = cluster.status()
                .and_then(|s| s.timeline())
                .and_then(|t| t.ready_date_time());

            if let Some(ready_since) = ready_dt {
                let idle_secs = (Utc::now() - *ready_since).num_seconds();
                let idle_min = idle_secs / 60;

                if idle_min > idle_threshold_min {
                    // Extract owner tag
                    let tags: HashMap<String, String> = cluster.tags()
                        .unwrap_or_default()
                        .iter()
                        .filter_map(|t| {
                            Some((t.key()?.to_string(), t.value()?.to_string()))
                        })
                        .collect();

                    idle.push(IdleCluster {
                        cluster_id: cluster_id.to_string(),
                        name: cluster_summary.name().unwrap_or("unnamed").to_string(),
                        idle_minutes: idle_min,
                        owner: tags.get("owner").cloned().unwrap_or("UNTAGGED".into()),
                        est_hourly_cost: estimate_cost(cluster_id),
                    });
                }
            }
        }
    }

    // Sort by cost descending (highest waste first)
    idle.sort_by(|a, b| b.est_hourly_cost.partial_cmp(&a.est_hourly_cost).unwrap());
    Ok(idle)
}

/// Find idle EMR clusters via AWS API.
/// Returns clusters sorted by estimated hourly cost (highest waste first).
- (NSArray<NSDictionary *> *)findIdleClusters {
    NSMutableArray *results = [NSMutableArray array];

    // Call AWS EMR ListClusters API for WAITING/RUNNING clusters
    NSArray *clusters = [self listClustersWithStates:@[@"WAITING", @"RUNNING"]];

    for (NSDictionary *cluster in clusters) {
        NSString *clusterId = cluster[@"Id"];

        // Check if any steps are currently running
        NSArray *runningSteps = [self listRunningSteps:clusterId];
        if (runningSteps.count > 0) continue;

        // Get ReadyDateTime to calculate idle duration
        NSDictionary *detail = [self describeCluster:clusterId];
        NSDate *readySince = detail[@"ReadyDateTime"];
        if (!readySince) continue;

        NSTimeInterval idleSec = -[readySince timeIntervalSinceNow];
        int idleMin = (int)(idleSec / 60.0);

        if (idleMin > _idleThresholdMin) {
            // Extract owner from tags
            NSDictionary *tags = detail[@"Tags"] ?: @{};
            NSString *owner = tags[@"owner"] ?: @"UNTAGGED";

            [results addObject:@{
                @"cluster_id": clusterId,
                @"name": cluster[@"Name"] ?: @"unnamed",
                @"idle_minutes": @(idleMin),
                @"owner": owner,
                @"est_hourly_cost": @([self estimateCost:clusterId])
            }];
        }
    }

    // Sort by cost descending (highest waste first)
    return [results sortedArrayUsingComparator:^NSComparisonResult(NSDictionary *a, NSDictionary *b) {
        return [b[@"est_hourly_cost"] compare:a[@"est_hourly_cost"]];
    }];
}

Request path / sequence

Trade-offs I'd say out loud

Auto-termination timeout

15 min is aggressive for interactive work; 30 min is safer but wastes more money. I default to 15 and let teams request exceptions

Spot vs on-demand for production

Spot saves 60-70% but risks interruption. Mitigation: driver on-demand, workers Spot with decommission. Never Spot for latency-sensitive serving

Right-sizing precision

Tight right-sizing saves money but leaves no headroom for data growth. I recommend 50% headroom above peak usage

Central governance vs team autonomy

Central policies prevent waste but slow teams. Balance: default policies with exception process for justified overrides

Instance pools vs individual sizing

Pools amortize startup time but restrict to a few instance types. Individual sizing is more precise but creates cold-start delays

Where it usually breaks

  • Auto-termination kills an interactive cluster while a data scientist is thinking — add warning notification at 10 min; extend timeout for notebook clusters
  • Spot interruption hits during the only remaining executor — job fails completely; first_on_demand=1 ensures driver survives but tasks need at least 1 worker
  • Right-sizing recommendation based on stale metrics — a job's data volume doubled since profiling; add 50% headroom to recommendations
  • Tagging enforcement blocks a critical cluster creation — add a 'bypass for emergencies' escape hatch with automatic Jira ticket creation
  • Cost dashboard shows team A's bill dropped to $0 — they moved workloads to a shared cluster under team B's tag; chargeback model needed

Follow-ups if time remains

  • How would you implement a chargeback model so teams pay for their own usage?
  • How do you handle a team that refuses to right-size because 'it might break'?
  • How would you extend this to cover S3 storage costs alongside compute?
  • How do you prevent cost regression — savings eroding over time as teams create new clusters?

What "good enough" looks like in 60 minutes

A strong answer covers: identifying the four cost buckets (idle, oversized, Spot opportunity, job optimization), the phased execution plan with estimated savings per phase, auto-termination and Spot configuration specifics, and a governance model with tagging enforcement. Show concrete numbers — '$13.5K in idle waste' is more convincing than 'some clusters are idle.'

You do not need to design the full FinOps organization or chargeback billing system. The interviewer wants to see: systematic cost analysis, prioritized action plan (biggest savings first), awareness of the operational risks of each optimization (Spot interruption, auto-termination annoyance), and a monitoring plan to sustain the savings.
