Detect and drain a bad deploy safely

Bad deploys become incidents when canaries are cosmetic and rollbacks need a meeting.

60-minute agenda

How I'd open the discussion

I've been on-call during deploys where the canary was purely cosmetic — it got 1% of traffic for 30 seconds, nobody looked at metrics, and the full rollout went ahead. The bad version hit 100% in 3 minutes and caused a 45-minute outage because rollback required someone to find the right Jenkins job and remember the last good SHA.

A safe deploy pipeline has three legs. First, health checks that actually check something: not just 'the process is alive' but 'the database connection pool is healthy, the cache is warm enough, and the dependency endpoints are reachable.' Second, canary deployment with automated analysis: 5% of traffic for 10 minutes, comparing error rates and p99 latency against the baseline — auto-promote if within thresholds, auto-rollback if not. Third, graceful draining: when a bad instance is pulled, it stops accepting new requests, finishes in-flight ones (up to a 30-second grace period), then shuts down.

The blast-radius principle: never let more than X% of instances serve a new version simultaneously. Start at 5%, bake for 10 minutes, go to 25%, bake, then 100%. At each stage, the rollback surface is small enough that reverting takes seconds, not minutes.

Open questions worth asking

  • What's the deployment target — Kubernetes, ECS, bare metal, Lambda?
  • Current deployment strategy — rolling update, blue-green, or manual?
  • How long does the application take to start up and become healthy?
  • What metrics define a healthy deploy — error rate, latency, business KPIs?
  • How many instances serve production traffic?
  • Are there long-running requests (WebSocket, streaming) that need special draining?
  • Is there a service mesh or load balancer that supports traffic splitting?
  • What's the current rollback process and how long does it take?
  • Do we have feature flags to decouple deploy from release?
  • What's the acceptable blast radius — maximum % of instances on new version at once?

Scope I'd lock first

  • In: health checks (liveness/readiness), canary with auto-rollback, graceful draining, blast radius.
  • Out: full CI/CD pipeline design, container orchestration internals.
  • Stretch: feature flag integration for dark launches and gradual rollouts.

Functional requirements

health_check()

Returns 200 if the instance is ready to serve; 503 if not.

canary_analyze(baseline_metrics, canary_metrics)

Compares error rate and latency; returns promote/rollback.

drain(instance, grace_period_s)

Stops new traffic, completes in-flight requests, shuts down.

rollback(deployment, target_version)

Reverts all instances to the last known good version.

Non-functional / rough numbers

Health check latency

p99 < 50 ms — must not slow down the load balancer's polling.

Canary detection

Detect a 2× error rate increase within 5 minutes of canary start.

Drain completeness

99.9% of in-flight requests complete before shutdown; < 0.1% dropped.

Rollback speed

Full rollback completes within 2 minutes from trigger to all instances reverted.

Capacity estimate (do this on the board)

Fleet size

100 instances across 2 availability zones.

Canary size

5 instances (5%) for initial canary; 25 instances (25%) for bake stage.

Grace period

30 seconds for HTTP; 60 seconds for WebSocket/streaming.

Health check interval

Every 5 seconds from the load balancer, 3 consecutive failures = unhealthy.

Approach / design notes

Health checks: Kubernetes distinguishes liveness (is the process alive?) from readiness (should it receive traffic?). Liveness failures restart the container. Readiness failures remove it from the service. A startup probe gives slow-starting apps extra time. The deep health check verifies database connectivity, cache health, and downstream dependencies — but be careful: if the database is down for everyone, deep checks make all instances unready, and the load balancer has nowhere to route traffic. Use deep checks for readiness, shallow checks for liveness.

Canary deployment: deploy the new version to 5% of instances. Route 5% of traffic to them (via load balancer weights or service mesh). Collect error rate, p99 latency, and business metrics for 10 minutes. Compare against the baseline (the other 95%). If the canary's error rate is > 2× baseline or p99 > 1.5× baseline, auto-rollback. If within thresholds, promote to 25%, bake for another 10 minutes, then 100%.

Graceful draining: when an instance receives SIGTERM (from Kubernetes or the deployment system), it should: (1) deregister from the load balancer (or fail readiness checks so the LB stops sending new requests), (2) finish processing in-flight requests (up to the grace period), (3) close connections and exit. In Kubernetes, the terminationGracePeriodSeconds controls how long before SIGKILL. Set it to grace_period + buffer (e.g., 40 s).

Blast-radius control: cap the maximum percentage of fleet on a new version at each stage. A rolling update that replaces 25% at a time limits blast radius to 25%. With canary, it's 5% initially. Feature flags decouple deployment from activation — deploy the code to 100% but enable the feature for 0%, then ramp gradually. This separates deploy risk (process crash, startup failure) from feature risk (business logic bugs).

Deep dive (spend 15–25 minutes here)

Health check design traps: a deep health check that queries the database adds latency and creates a dependency — if the DB is slow, the health check is slow, and the LB might mark the instance unhealthy even though it could serve cached responses. Solution: separate the liveness check (shallow: process alive, goroutines not deadlocked) from the readiness check (deep: DB connected, cache warm). And set a timeout on the deep check (500 ms) so a slow dependency doesn't cascade into a fleet-wide readiness failure.

Canary analysis pitfalls: with 5% traffic, you might only get 500 requests in 10 minutes for a low-traffic endpoint. A single slow request can skew p99 dramatically. Use statistical significance tests (chi-squared for error rates, Mann-Whitney U for latency distributions) rather than raw threshold comparisons. Also compare business metrics: a deploy that drops error rate but also drops conversion rate has a bug that manifests as 200 OK with wrong data.

Drain edge cases: WebSocket connections and server-sent events (SSE) are long-lived. A 30-second grace period kills them mid-stream. Solutions: (1) send a 'reconnect' frame before shutting down the WebSocket, letting the client reconnect to a healthy instance; (2) extend the grace period for WebSocket instances (60–120 s); (3) use a separate drain signal for long-lived connections that gives more warning.

Kubernetes-specific: when a Pod is terminated, Kubernetes simultaneously sends SIGTERM and removes the Pod from the Endpoints object. But the Endpoints change propagates asynchronously — there's a window (typically 1–5 seconds) where the LB still sends traffic to the draining Pod. Fix: add a preStop hook with a sleep (e.g., 5 s) before the container starts shutting down, giving time for the Endpoints update to propagate.

Blast-radius real-world failure: a team deployed a version with a memory leak. The canary passed (10-minute window was too short for the leak to matter). At 100%, memory grew over 30 minutes until OOM kills cascaded across the fleet. Fix: extend bake times based on the type of change. Memory-intensive changes get a 1-hour bake at 25% before full rollout. Monitor memory growth rate, not just absolute memory usage.

HTTP server with readiness check and graceful drain

import signal, threading, time
from http.server import HTTPServer, BaseHTTPRequestHandler


class AppState:
    def __init__(self):
        self.ready = False
        self.draining = False
        self.in_flight = 0
        self.lock = threading.Lock()

    def start_request(self) -> bool:
        with self.lock:
            if self.draining:
                return False
            self.in_flight += 1
            return True

    def end_request(self):
        with self.lock:
            self.in_flight -= 1

    def drain(self, grace_s: int = 30):
        self.draining = True
        self.ready = False
        deadline = time.monotonic() + grace_s
        while time.monotonic() < deadline:
            with self.lock:
                if self.in_flight == 0:
                    return
            time.sleep(0.5)


state = AppState()


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == '/healthz':
            self.send_response(200)
            self.end_headers()
            self.wfile.write(b'{"status":"alive"}')
        elif self.path == '/readyz':
            code = 200 if (state.ready and not state.draining) else 503
            self.send_response(code)
            self.end_headers()
        else:
            if not state.start_request():
                self.send_response(503)
                self.end_headers()
                return
            try:
                self.send_response(200)
                self.end_headers()
                self.wfile.write(b'{"ok":true}')
            finally:
                state.end_request()


def shutdown_handler(signum, frame):
    state.drain(grace_s=30)
    raise SystemExit(0)


if __name__ == '__main__':
    signal.signal(signal.SIGTERM, shutdown_handler)
    state.ready = True
    HTTPServer(('', 8080), Handler).serve_forever()
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
use std::sync::Arc;
use std::time::Duration;
use hyper::{Body, Request, Response, Server, StatusCode};
use hyper::service::{make_service_fn, service_fn};
use tokio::signal::unix::{signal, SignalKind};

struct AppState {
    ready: AtomicBool,
    draining: AtomicBool,
    in_flight: AtomicUsize,
}

impl AppState {
    fn new() -> Self {
        Self {
            ready: AtomicBool::new(false),
            draining: AtomicBool::new(false),
            in_flight: AtomicUsize::new(0),
        }
    }

    fn start_request(&self) -> bool {
        if self.draining.load(Ordering::Acquire) { return false; }
        self.in_flight.fetch_add(1, Ordering::AcqRel);
        // Double-check after increment to avoid race with drain
        if self.draining.load(Ordering::Acquire) {
            self.in_flight.fetch_sub(1, Ordering::AcqRel);
            return false;
        }
        true
    }

    fn end_request(&self) {
        self.in_flight.fetch_sub(1, Ordering::AcqRel);
    }

    async fn drain(&self, grace_s: u64) {
        self.draining.store(true, Ordering::Release);
        self.ready.store(false, Ordering::Release);
        let deadline = tokio::time::Instant::now() + Duration::from_secs(grace_s);
        while tokio::time::Instant::now() < deadline {
            if self.in_flight.load(Ordering::Acquire) == 0 { return; }
            tokio::time::sleep(Duration::from_millis(500)).await;
        }
    }
}

async fn handle(req: Request<Body>, state: Arc<AppState>) -> Result<Response<Body>, hyper::Error> {
    match req.uri().path() {
        "/healthz" => Ok(Response::new(Body::from(r#"{"status":"alive"}"#))),
        "/readyz" => {
            let code = if state.ready.load(Ordering::Acquire)
                && !state.draining.load(Ordering::Acquire) {
                StatusCode::OK
            } else {
                StatusCode::SERVICE_UNAVAILABLE
            };
            Ok(Response::builder().status(code).body(Body::empty()).unwrap())
        }
        _ => {
            if !state.start_request() {
                return Ok(Response::builder()
                    .status(StatusCode::SERVICE_UNAVAILABLE)
                    .body(Body::empty()).unwrap());
            }
            let resp = Response::new(Body::from(r#"{"ok":true}"#));
            state.end_request();
            Ok(resp)
        }
    }
}

#[tokio::main]
async fn main() {
    let state = Arc::new(AppState::new());
    state.ready.store(true, Ordering::Release);
    let st = state.clone();

    let make_svc = make_service_fn(move |_| {
        let st = st.clone();
        async move { Ok::<_, hyper::Error>(service_fn(move |r| handle(r, st.clone()))) }
    });
    let server = Server::bind(&([0, 0, 0, 0], 8080).into()).serve(make_svc);

    let drain_state = state.clone();
    tokio::spawn(async move {
        let mut sigterm = signal(SignalKind::terminate()).unwrap();
        sigterm.recv().await;
        drain_state.drain(30).await;
        std::process::exit(0);
    });

    server.await.unwrap();
}
#import <Foundation/Foundation.h>
#include <atomic>
#include <thread>
#include <chrono>
#include <signal.h>

// ── Shared application state ─────────────────────────────────────────

class AppState {
public:
    std::atomic<bool>   ready{false};
    std::atomic<bool>   draining{false};
    std::atomic<int>    inFlight{0};

    bool startRequest() {
        if (draining.load()) return false;
        inFlight.fetch_add(1);
        if (draining.load()) { inFlight.fetch_sub(1); return false; }
        return true;
    }
    void endRequest() { inFlight.fetch_sub(1); }

    void drain(int graceS = 30) {
        draining.store(true);
        ready.store(false);
        auto deadline = std::chrono::steady_clock::now()
                      + std::chrono::seconds(graceS);
        while (std::chrono::steady_clock::now() < deadline) {
            if (inFlight.load() == 0) return;
            std::this_thread::sleep_for(std::chrono::milliseconds(500));
        }
    }
};

static AppState gState;

- (NSData *)responseForPath:(NSString *)path statusCode:(int *)code {

        *code = 200;
        return [@"{\"status\":\"alive\"}" dataUsingEncoding:NSUTF8StringEncoding];
    }
    if ([path isEqualToString:@"/readyz"]) {
        *code = (gState.ready.load() && !gState.draining.load()) ? 200 : 503;
        return [NSData data];
    }
    // Application route — gate on drain state
    if (!gState.startRequest()) {
        *code = 503;
        return [NSData data];
    }
    *code = 200;
    NSData *body = [@"{\"ok\":true}" dataUsingEncoding:NSUTF8StringEncoding];
    gState.endRequest();
    return body;
}

Request path / sequence

Trade-offs I'd say out loud

Deep vs shallow health check

Deep checks catch more issues but create dependency chains; shallow checks are resilient but miss broken dependencies.

Canary duration vs speed

Longer canary bake catches slow-onset issues (memory leaks) but delays deployments.

Grace period length

Longer grace completes more in-flight work but delays rollback completion.

Feature flags vs canary

Flags decouple deploy from release but add code complexity; canaries test the full binary.

Where it usually breaks

  • Health check that always returns 200 — hides all failures from the load balancer.
  • Canary window too short to catch memory leaks or connection pool exhaustion.
  • No preStop hook in Kubernetes — traffic arrives during shutdown, gets 503.
  • Rolling update replacing 100% of instances simultaneously — no rollback surface.
  • Rollback requiring a new build/deploy instead of reverting to the previous image.
  • Deep health check without timeout — slow DB makes all instances unready.
  • Ignoring business metrics in canary analysis — functional bugs ship with green error rates.

Follow-ups if time remains

  • Integrate feature flags for dark launches: deploy code to 100%, enable for 0%, ramp separately.
  • Build automated rollback triggered by PagerDuty alert severity.
  • Design a progressive rollout across regions: US-West canary → US-East → EU.
  • Add replay-based validation: replay production traffic against canary in shadow mode before live traffic.
