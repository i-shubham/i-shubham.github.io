Handle split-brain in a leader election

Two leaders are worse than none — fencing and quorums are how you keep reality single.

60-minute agenda

How I'd open the discussion

Split-brain is the scenario where a network partition isolates the current leader, and the remaining nodes elect a new leader. Now you have two nodes that both believe they're the leader. If both accept writes, you get divergent state that's extremely hard to reconcile — especially for non-commutative operations like balance decrements.

The core defense has three layers. First, quorum: a leader must be able to reach a majority of nodes to serve writes. A partitioned leader that can only reach a minority automatically stalls. Second, term numbers: each election increments a monotonic term. Followers reject requests from leaders with stale terms. Third, fencing: even if the old leader doesn't know it's been deposed, the storage layer rejects its writes using a fencing token tied to the current term.

I'd walk through a concrete 5-node cluster where the leader gets isolated with 1 follower — the other 3 elect a new leader at term 4. The old leader at term 3 tries to replicate to its 1 follower, but that follower hears from the new leader at term 4 and rejects term 3 requests. The old leader can't get quorum (needs 3, has 1) and steps down.

Open questions worth asking

  • How many nodes in the cluster — 3, 5, 7?
  • What consensus protocol is in use — Raft, ZAB, Paxos?
  • What kind of state does the leader manage — replicated log, K-V store, metadata?
  • Is the storage layer separate from the consensus nodes?
  • Can we use a shared storage device with SCSI fencing?
  • What is the acceptable unavailability window during leader election?
  • Do we need to handle asymmetric partitions (A can reach B but not C)?
  • Is there an external failure detector (e.g., a watchdog or IPMI)?
  • What is the heartbeat interval and election timeout?

  • Out: full Raft / Paxos implementation, Byzantine fault tolerance.

Functional requirements

elect_leader(cluster)

Exactly one leader per term, elected by majority vote.

replicate(entry, term)

Leader replicates log entry; followers accept only if term is current.

step_down(leader, reason)

Leader relinquishes role when it detects loss of quorum.

fence_write(storage, term, data)

Storage rejects writes from terms older than current.

Non-functional / rough numbers

Safety

At most one leader can commit writes in any given term — no split-brain commits.

Availability

New leader elected within 2× election timeout (~2–10 seconds).

Consistency

Committed entries are never lost — the new leader has all committed entries.

Partition tolerance

Minority partition stalls gracefully; majority continues serving.

Approach / design notes

Split-brain occurs when a network partition separates the leader from the majority. The leader on the minority side continues to believe it's the leader (it hasn't received a higher term message). Meanwhile, the majority side times out on heartbeats and starts an election. A candidate with the most up-to-date log gets elected at term+1.

Quorum prevents the old leader from committing: to commit an entry, the leader must replicate it to a majority (including itself). If the old leader only has 1 follower in a 5-node cluster, it can't reach quorum (needs 3). Its writes stall. Client requests time out. The old leader eventually receives a message with a higher term and steps down.

Term numbers are the universal protocol-level defense. Every message carries a term. If a follower receives an AppendEntries from term 3 but its current_term is 4 (because it voted in a new election), it rejects the request and responds with term 4. The old leader sees a term higher than its own and immediately steps down.

Fencing adds defense-in-depth at the storage layer. Even if the old leader somehow gets a write past the consensus layer (shouldn't happen, but defense-in-depth), the storage rejects writes from stale terms. STONITH (Shoot The Other Node In The Head) goes further: the new leader power-cycles the old leader's machine via IPMI/BMC, guaranteeing it can't write. This is common in database HA setups (Pacemaker/Corosync).

In practice, the combination of quorum + term numbers is sufficient for well-implemented consensus protocols. Fencing and STONITH are extra layers for environments where the consensus implementation might have bugs or where shared storage is involved.

Deep dive (spend 15–25 minutes here)

Consider a 5-node Raft cluster: nodes A (leader, term 3), B, C, D, E. A network partition isolates A and B from C, D, E. Node A continues sending AppendEntries(term=3) to B. B accepts because its current_term is 3 and A is the known leader.

Meanwhile, C, D, E stop receiving heartbeats. After a randomized election timeout (say C times out first at 350 ms), C increments its term to 4, votes for itself, and sends RequestVote(term=4) to D and E. Both have current_term=3, so they grant votes. C wins with 3/5 votes and becomes leader for term 4.

Now there are two 'leaders': A at term 3, C at term 4. But A can only replicate to B — that's 2 nodes, not a majority. A's writes stall at the replication step. No entry is committed because A needs match_index confirmation from at least 2 followers. Meanwhile, C can replicate to D and E (3 nodes total with itself) and commits normally.

When the partition heals, A sends a heartbeat to C (or any node in the other partition). The response includes term=4. A sees 4 > 3, immediately sets current_term=4, transitions to follower, and clears voted_for. Any uncommitted entries on A from term 3 get overwritten by C's log during the next AppendEntries. This is safe because those entries were never committed — no client got an acknowledgment.

The STONITH variant: in an active-passive database setup (e.g., PostgreSQL with Patroni), the standby that gets promoted sends an IPMI power-off command to the old primary. This prevents the old primary from accepting writes during the window between promotion and the old primary receiving the demotion notice. It's brutal but effective when shared storage makes fencing tokens impractical.

Raft node with term-based stale leader rejection

from dataclasses import dataclass, field

@dataclass
class RaftNode:
    node_id: str
    current_term: int = 0
    voted_for: str | None = None
    role: str = 'follower'  # follower | candidate | leader
    log: list = field(default_factory=list)
    cluster_size: int = 5

    @property
    def quorum(self) -> int:
        return self.cluster_size // 2 + 1

    def on_append_entries(self, term: int, leader_id: str, entries: list) -> tuple:
        if term < self.current_term:
            return (self.current_term, False)  # reject stale leader
        if term > self.current_term:
            self.current_term = term
            self.role = 'follower'
            self.voted_for = None
        self.log.extend(entries)
        return (self.current_term, True)

    def on_request_vote(self, term: int, candidate_id: str, last_log_idx: int) -> tuple:
        if term < self.current_term:
            return (self.current_term, False)
        if term > self.current_term:
            self.current_term = term
            self.role = 'follower'
            self.voted_for = None
        if self.voted_for is None or self.voted_for == candidate_id:
            if last_log_idx >= len(self.log) - 1:
                self.voted_for = candidate_id
                return (self.current_term, True)
        return (self.current_term, False)

    def start_election(self):
        self.current_term += 1
        self.role = 'candidate'
        self.voted_for = self.node_id
        votes = 1  # self-vote
        return self.current_term, votes

    def become_leader(self):
        self.role = 'leader'

    def step_down(self, new_term: int):
        self.current_term = new_term
        self.role = 'follower'
        self.voted_for = None
use std::fmt;

#[derive(Debug, Clone, PartialEq)]
enum Role { Follower, Candidate, Leader }

#[derive(Debug, Clone)]
struct LogEntry(String); // simplified payload

pub struct RaftNode {
    node_id: String,
    current_term: u64,
    voted_for: Option<String>,
    role: Role,
    log: Vec<LogEntry>,
    cluster_size: usize,
}

impl RaftNode {
    pub fn new(node_id: &str, cluster_size: usize) -> Self {
        Self {
            node_id: node_id.into(),
            current_term: 0,
            voted_for: None,
            role: Role::Follower,
            log: Vec::new(),
            cluster_size,
        }
    }

    pub fn quorum(&self) -> usize {
        self.cluster_size / 2 + 1
    }

    /// Reject stale leader (term < ours); step down if term is newer.
    pub fn on_append_entries(
        &mut self, term: u64, _leader_id: &str, entries: Vec<LogEntry>,
    ) -> (u64, bool) {
        if term < self.current_term {
            return (self.current_term, false);
        }
        if term > self.current_term {
            self.current_term = term;
            self.role = Role::Follower;
            self.voted_for = None;
        }
        self.log.extend(entries);
        (self.current_term, true)
    }

    pub fn on_request_vote(
        &mut self, term: u64, candidate_id: &str, last_log_idx: usize,
    ) -> (u64, bool) {
        if term < self.current_term {
            return (self.current_term, false);
        }
        if term > self.current_term {
            self.current_term = term;
            self.role = Role::Follower;
            self.voted_for = None;
        }
        let dominated = self.log.len().saturating_sub(1);
        let can_vote = self.voted_for.is_none()
            || self.voted_for.as_deref() == Some(candidate_id);
        if can_vote && last_log_idx >= dominated {
            self.voted_for = Some(candidate_id.into());
            return (self.current_term, true);
        }
        (self.current_term, false)
    }

    pub fn start_election(&mut self) -> (u64, usize) {
        self.current_term += 1;
        self.role = Role::Candidate;
        self.voted_for = Some(self.node_id.clone());
        (self.current_term, 1) // 1 = self-vote
    }

    pub fn become_leader(&mut self) { self.role = Role::Leader; }

    pub fn step_down(&mut self, new_term: u64) {
        self.current_term = new_term;
        self.role = Role::Follower;
        self.voted_for = None;
    }
}

@implementation RaftNode

- (instancetype)initWithId:(NSString *)nodeId clusterSize:(NSUInteger)sz {
    if ((self = [super init])) {
        _nodeId      = [nodeId copy];
        _currentTerm = 0;
        _votedFor    = nil;
        _role        = RaftRoleFollower;
        _clusterSize = sz;
    }
    return self;
}

- (NSUInteger)quorum { return _clusterSize / 2 + 1; }

- (std::pair<uint64_t, BOOL>)onAppendEntries:(uint64_t)term
                                    leaderId:(NSString *)leaderId
                                     entries:(const std::vector<std::string> &)entries {
    if (term < _currentTerm)
        return {_currentTerm, NO}; // reject stale leader

    if (term > _currentTerm) {
        _currentTerm = term;
        _role        = RaftRoleFollower;
        _votedFor    = nil;
    }
    _log.insert(_log.end(), entries.begin(), entries.end());
    return {_currentTerm, YES};
}

- (std::pair<uint64_t, BOOL>)onRequestVote:(uint64_t)term
                               candidateId:(NSString *)candidateId
                                lastLogIdx:(NSUInteger)lastLogIdx {
    if (term < _currentTerm)
        return {_currentTerm, NO};

    if (term > _currentTerm) {
        _currentTerm = term;
        _role        = RaftRoleFollower;
        _votedFor    = nil;
    }
    NSUInteger dominated = _log.empty() ? 0 : _log.size() - 1;
    BOOL canVote = (_votedFor == nil || [_votedFor isEqualToString:candidateId]);
    if (canVote && lastLogIdx >= dominated) {
        _votedFor = [candidateId copy];
        return {_currentTerm, YES};
    }
    return {_currentTerm, NO};
}

- (std::pair<uint64_t, NSUInteger>)startElection {
    _currentTerm += 1;
    _role     = RaftRoleCandidate;
    _votedFor = [_nodeId copy];
    return {_currentTerm, 1}; // 1 = self-vote
}

- (void)becomeLeader { _role = RaftRoleLeader; }

- (void)stepDown:(uint64_t)newTerm {
    _currentTerm = newTerm;
    _role        = RaftRoleFollower;
    _votedFor    = nil;
}

Request path / sequence

Trade-offs I'd say out loud

Quorum size vs availability

Larger quorum is safer but tolerates fewer failures — 5-node cluster tolerates 2 vs 3-node's 1.

Election timeout tuning

Too short → spurious elections under load; too long → slow failover.

STONITH vs graceful stepdown

STONITH is immediate but requires IPMI/BMC; graceful stepdown depends on the old leader cooperating.

Fencing tokens vs trusting consensus

Fencing is defense-in-depth but adds complexity to the storage layer.

Where it usually breaks

  • Election timeout too similar across nodes — multiple candidates split votes indefinitely.
  • Not persisting current_term and voted_for before responding — violates safety after crash.
  • Old leader not stepping down on receiving higher term — continues accepting writes.
  • Truncating committed entries on leader change — data loss.
  • Asymmetric partition where old leader can reach storage but not followers — bypasses quorum.
  • Clock-based leader lease that doesn't account for clock skew between nodes.

Follow-ups if time remains

  • Implement pre-vote protocol to prevent disruptive elections from partitioned nodes.
  • Add read leases so followers can serve linearizable reads without leader round-trip.
  • Design a joint-consensus protocol for safe cluster membership changes.
  • Build a split-brain detector that alerts when quorum loss is detected.
