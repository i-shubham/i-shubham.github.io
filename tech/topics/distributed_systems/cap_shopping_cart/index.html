Explain CAP for a shopping cart

CAP is not a vibe — for a cart, say which user-visible failure you choose when the network splits.

60-minute agenda

How I'd open the discussion

I think the most common mistake with CAP is treating it as a philosophy instead of an engineering decision with concrete consequences. For a shopping cart, the question isn't 'do we want consistency or availability' in the abstract — it's 'when the network between our data centers splits, does the user see an error page or a potentially stale cart?'

For most e-commerce carts, I'd choose AP: let every region accept writes (adds, removes, quantity changes) even during a partition. The user can keep shopping. When the partition heals, merge the carts. The merge isn't trivial — if user added item X in region A and removed item X in region B during the partition, what's the final state? — but it's solvable with CRDTs (an OR-Set for the item set, a PN-Counter for quantities).

The CP alternative: during a partition, refuse cart writes. The user gets a 503 or a 'cart temporarily unavailable' message. This is appropriate for inventory-sensitive items (limited edition, flash sales) where overselling is worse than a brief outage. In practice, many systems are AP for the cart and CP for the checkout (payment + inventory decrement).

Open questions worth asking

  • Is the cart single-region or multi-region?
  • What's more important: always letting users add to cart, or never showing stale data?
  • How many regions need to serve writes?
  • Is inventory check part of add-to-cart or deferred to checkout?
  • Are there flash-sale or limited-edition items where overselling is unacceptable?
  • What's the expected cart conflict rate (same user, different regions)?
  • Do we need the cart to survive a full region outage?
  • How long do network partitions typically last in our environment?

Approach / design notes

CAP states: in the presence of a network partition (P), a distributed system must choose between consistency (C — every read sees the most recent write) and availability (A — every request gets a non-error response). Since network partitions happen in practice, P is not optional — the real choice is CP or AP.

CP for a shopping cart: during a partition, the cart service refuses writes because it can't confirm whether the other region has conflicting updates. The user sees 'cart temporarily unavailable.' No data conflicts, no merge needed. This is appropriate when correctness is critical — e.g., inventory-tracked items where overselling is unacceptable.

AP for a shopping cart: both regions accept writes during a partition. The user keeps shopping. But now there might be two divergent versions of the same cart. When the partition heals, we merge them. The merge strategy matters: last-writer-wins drops one side's changes. A CRDT-based merge preserves all operations.

CRDT merge for carts: model each item as an OR-Set entry (add wins over concurrent remove) and each quantity as a PN-Counter (increments and decrements merge independently). User adds item X in US-East and removes item X in EU-West during partition. Merge policy: if the add has a unique tag that wasn't in the remove's observed set, the add wins — item X is in the merged cart. This is Amazon's original Dynamo paper approach.

In practice, the hybrid approach is most common: AP for the cart (let users keep shopping), CP for checkout (the payment + inventory decrement must be consistent). This matches the business reality: a slightly stale cart is tolerable, but a double-charged payment is not.

Deep dive (spend 15–25 minutes here)

Let's trace a concrete partition scenario. User Alice has a cart with {SKU-123: qty 1}. The network between US-East and EU-West splits. Alice's browser is routed to US-East. She adds SKU-456 (qty 2). Meanwhile, a background process in EU-West expires SKU-123 from her cart (items expire after 24 hours). Now:

US-East cart: {SKU-123: 1, SKU-456: 2} EU-West cart: {}

The partition heals. How do we merge? With LWW on the whole cart, one side wins — either Alice loses her new item (SKU-456) or the expired item (SKU-123) comes back. Both are wrong.

With per-item OR-Set: SKU-123 was in the original set. EU-West removed it. US-East didn't touch it. The remove wins (it observed the original add and removed it). SKU-456 was added in US-East with a new unique tag. EU-West never observed this tag, so it can't remove it. The add is preserved. Merged cart: {SKU-456: 2}. This is the correct result: the expiry is respected, and the new addition is preserved.

Now consider a trickier case: Alice adds SKU-789 in US-East during the partition. At the same time, she's on her phone, routed to EU-West, and also adds SKU-789 with qty 3. US-East cart: {SKU-789: qty 1}. EU-West cart: {SKU-789: qty 3}. With a PN-Counter: US-East incremented by 1, EU-West incremented by 3. Merge: total = 1 + 3 = 4. But Alice probably wanted qty 3, not 4. This is a known CRDT limitation — the merge is mathematically correct (it preserves all increments) but semantically surprising. Solutions: use a last-writer-wins register for quantity (simpler, loses one write) or prompt the user on next cart view ('you have 4 of SKU-789 — is that right?').

PACELC extension: CAP only describes behavior during partitions. PACELC adds: else (E, when there's no partition), do you favor latency (L) or consistency (C)? DynamoDB is PA/EL: available during partitions, low-latency during normal operation. Spanner is PC/EC: consistent during partitions (it stalls), consistent during normal operation (external consistency via TrueTime). Most shopping carts are PA/EL — optimize for latency and availability, accept eventual consistency.

from dataclasses import dataclass, field
from typing import Dict, Set


@dataclass
class CartItem:
    add_tags: Set[str] = field(default_factory=set)
    remove_tags: Set[str] = field(default_factory=set)
    qty_inc: Dict[str, int] = field(default_factory=dict)
    qty_dec: Dict[str, int] = field(default_factory=dict)

    @property
    def present(self) -> bool:
        return bool(self.add_tags - self.remove_tags)

    @property
    def qty(self) -> int:
        return max(0, sum(self.qty_inc.values()) - sum(self.qty_dec.values()))


class CRDTCart:
    def __init__(self, region: str):
        self.region = region
        self.items: Dict[str, CartItem] = {}
        self.seq = 0

    def _tag(self) -> str:
        self.seq += 1
        return f'{self.region}:{self.seq}'

    def add(self, item_id: str, qty: int = 1):
        item = self.items.setdefault(item_id, CartItem())
        item.add_tags.add(self._tag())
        item.qty_inc[self.region] = item.qty_inc.get(self.region, 0) + qty

    def remove(self, item_id: str):
        if item_id in self.items:
            item = self.items[item_id]
            item.remove_tags |= item.add_tags.copy()

    def view(self) -> dict:
        return {iid: it.qty for iid, it in self.items.items() if it.present and it.qty > 0}

    def merge(self, other: 'CRDTCart') -> 'CRDTCart':
        merged = CRDTCart(self.region)
        all_ids = set(self.items) | set(other.items)
        for iid in all_ids:
            a = self.items.get(iid, CartItem())
            b = other.items.get(iid, CartItem())
            m = CartItem(
                add_tags=a.add_tags | b.add_tags,
                remove_tags=a.remove_tags | b.remove_tags,
            )
            for region in set(a.qty_inc) | set(b.qty_inc):
                m.qty_inc[region] = max(a.qty_inc.get(region, 0),
                                        b.qty_inc.get(region, 0))
            for region in set(a.qty_dec) | set(b.qty_dec):
                m.qty_dec[region] = max(a.qty_dec.get(region, 0),
                                        b.qty_dec.get(region, 0))
            merged.items[iid] = m
        return merged
use std::collections::{HashMap, HashSet};

#[derive(Debug, Clone, Default)]
pub struct CartItem {
    pub add_tags: HashSet<String>,
    pub remove_tags: HashSet<String>,
    pub qty_inc: HashMap<String, i64>,
    pub qty_dec: HashMap<String, i64>,
}

impl CartItem {
    /// Item is present when at least one add-tag has not been removed.
    pub fn present(&self) -> bool {
        self.add_tags.difference(&self.remove_tags).next().is_some()
    }

    pub fn qty(&self) -> i64 {
        let inc: i64 = self.qty_inc.values().sum();
        let dec: i64 = self.qty_dec.values().sum();
        (inc - dec).max(0)
    }
}

pub struct CRDTCart {
    region: String,
    items: HashMap<String, CartItem>,
    seq: u64,
}

impl CRDTCart {
    pub fn new(region: &str) -> Self {
        Self { region: region.into(), items: HashMap::new(), seq: 0 }
    }

    fn tag(&mut self) -> String {
        self.seq += 1;
        format!("{}:{}", self.region, self.seq)
    }

    pub fn add(&mut self, item_id: &str, qty: i64) {
        let tag = self.tag();
        let item = self.items.entry(item_id.into()).or_default();
        item.add_tags.insert(tag);
        *item.qty_inc.entry(self.region.clone()).or_insert(0) += qty;
    }

    pub fn remove(&mut self, item_id: &str) {
        if let Some(item) = self.items.get_mut(item_id) {
            let tags: HashSet<String> = item.add_tags.clone();
            item.remove_tags.extend(tags);
        }
    }

    pub fn view(&self) -> HashMap<String, i64> {
        self.items.iter()
            .filter(|(_, it)| it.present() && it.qty() > 0)
            .map(|(id, it)| (id.clone(), it.qty()))
            .collect()
    }

    pub fn merge(&self, other: &CRDTCart) -> CRDTCart {
        let mut merged = CRDTCart::new(&self.region);
        let all_ids: HashSet<&String> =
            self.items.keys().chain(other.items.keys()).collect();

        for iid in all_ids {
            let a = self.items.get(iid.as_str()).cloned().unwrap_or_default();
            let b = other.items.get(iid.as_str()).cloned().unwrap_or_default();
            let mut m = CartItem {
                add_tags: &a.add_tags | &b.add_tags,
                remove_tags: &a.remove_tags | &b.remove_tags,
                ..Default::default()
            };
            for r in a.qty_inc.keys().chain(b.qty_inc.keys()) {
                let va = a.qty_inc.get(r).copied().unwrap_or(0);
                let vb = b.qty_inc.get(r).copied().unwrap_or(0);
                m.qty_inc.insert(r.clone(), va.max(vb));
            }
            for r in a.qty_dec.keys().chain(b.qty_dec.keys()) {
                let va = a.qty_dec.get(r).copied().unwrap_or(0);
                let vb = b.qty_dec.get(r).copied().unwrap_or(0);
                m.qty_dec.insert(r.clone(), va.max(vb));
            }
            merged.items.insert(iid.clone(), m);
        }
        merged
    }
}
#import <Foundation/Foundation.h>
#include <string>
#include <map>
#include <set>
#include <algorithm>

// ── CartItem: OR-Set membership + PN-Counter quantity ────────────────

struct CartItem {
    std::set<std::string> addTags;
    std::set<std::string> removeTags;
    std::map<std::string, int64_t> qtyInc; // region -> count
    std::map<std::string, int64_t> qtyDec;

    bool present() const {
        for (auto &t : addTags)
            if (removeTags.find(t) == removeTags.end()) return true;
        return false;
    }

    int64_t qty() const {
        int64_t inc = 0, dec = 0;
        for (auto &[_, v] : qtyInc) inc += v;
        for (auto &[_, v] : qtyDec) dec += v;
        return std::max<int64_t>(0, inc - dec);
    }
};

// ── CRDTCart ─────────────────────────────────────────────────────────

@interface CRDTCart : NSObject {
    std::string _region;
    std::map<std::string, CartItem> _items;
    uint64_t _seq;
}
- (instancetype)initWithRegion:(NSString *)region;
- (void)addItem:(NSString *)itemId qty:(int64_t)qty;
- (void)removeItem:(NSString *)itemId;
- (NSDictionary<NSString *, NSNumber *> *)view;
- (CRDTCart *)mergeWith:(CRDTCart *)other;
@end

@implementation CRDTCart

- (instancetype)initWithRegion:(NSString *)region {
    if ((self = [super init])) {
        _region = region.UTF8String;
        _seq = 0;
    }
    return self;
}

- (std::string)_tag {
    _seq += 1;
    return _region + ":" + std::to_string(_seq);
}

- (void)addItem:(NSString *)itemId qty:(int64_t)qty {
    std::string iid = itemId.UTF8String;
    auto &item = _items[iid];
    item.addTags.insert([self _tag]);
    item.qtyInc[_region] += qty;
}

- (void)removeItem:(NSString *)itemId {
    auto it = _items.find(itemId.UTF8String);
    if (it != _items.end())
        it->second.removeTags.insert(it->second.addTags.begin(),
                                     it->second.addTags.end());
}

- (NSDictionary<NSString *, NSNumber *> *)view {
    NSMutableDictionary *result = [NSMutableDictionary dictionary];
    for (auto &[iid, item] : _items) {
        if (item.present() && item.qty() > 0)
            result[@(iid.c_str())] = @(item.qty());
    }
    return result;
}

- (CRDTCart *)mergeWith:(CRDTCart *)other {
    CRDTCart *merged = [[CRDTCart alloc]
        initWithRegion:@(_region.c_str())];

    std::set<std::string> allIds;
    for (auto &[k, _] : _items) allIds.insert(k);
    for (auto &[k, _] : other->_items) allIds.insert(k);

    for (auto &iid : allIds) {
        CartItem a, b;
        if (_items.count(iid)) a = _items[iid];
        if (other->_items.count(iid)) b = other->_items[iid];
        CartItem m;
        m.addTags.insert(a.addTags.begin(), a.addTags.end());
        m.addTags.insert(b.addTags.begin(), b.addTags.end());
        m.removeTags.insert(a.removeTags.begin(), a.removeTags.end());
        m.removeTags.insert(b.removeTags.begin(), b.removeTags.end());

        std::set<std::string> regions;
        for (auto &[r, _] : a.qtyInc) regions.insert(r);
        for (auto &[r, _] : b.qtyInc) regions.insert(r);
        for (auto &r : regions)
            m.qtyInc[r] = std::max(a.qtyInc[r], b.qtyInc[r]);

        regions.clear();
        for (auto &[r, _] : a.qtyDec) regions.insert(r);
        for (auto &[r, _] : b.qtyDec) regions.insert(r);
        for (auto &r : regions)
            m.qtyDec[r] = std::max(a.qtyDec[r], b.qtyDec[r]);

        merged->_items[iid] = m;
    }
    return merged;
}

Request path / sequence

Trade-offs I'd say out loud

AP (availability) vs CP (consistency)

AP lets users keep shopping during partitions but requires conflict merge; CP avoids conflicts but shows errors.

LWW vs CRDT merge

LWW is simple but loses one side's writes; CRDTs preserve all operations but can produce surprising quantities.

Cart AP + checkout CP

Matches business reality — stale cart is OK, double-charge is not — but adds architectural complexity.

OR-Set 'add wins' vs 'remove wins'

Add-wins is better for commerce (don't lose items from cart); remove-wins risks phantom items.

Where it usually breaks

  • Treating CAP as a permanent system-wide choice instead of per-operation.
  • LWW on entire cart document — one region's changes completely overwrite the other's.
  • Not handling the add+remove conflict for the same item during partition.
  • CRDT quantity counter giving unexpected sums when user sets absolute quantity.
  • Forgetting that checkout must be CP even if cart is AP — overselling or double-charging.
