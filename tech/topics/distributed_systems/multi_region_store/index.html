Design a multi-region active-active store

Active-active means you will get conflicts — pick the data model that survives them, or admit you're active-passive.

60-minute agenda

How I'd open the discussion

I'd start by making sure we actually need active-active. If the traffic can tolerate routing to one primary region with a standby for failover, active-passive is dramatically simpler — no conflicts, strong consistency, straightforward failover. Active-active only makes sense when you need writes in multiple regions for latency (users in EU and US both need < 50 ms write latency) or for availability during a full region outage.

Once we commit to active-active, we commit to conflicts. Two users in different regions can update the same record within the replication lag window (typically 50–200 ms cross-region). The question is: how do we resolve those conflicts? Last-writer-wins (LWW) with HLC timestamps is the simplest — one write silently drops. CRDTs (counters, sets, registers) resolve automatically with mathematically guaranteed convergence. Application-level merge functions give the most control but are the hardest to get right.

The sneaky problem is read-your-writes. A user writes in US-East, then reads from US-West (because DNS rotated them). If replication hasn't caught up, they see stale data — their own write vanished. Solutions: sticky sessions (route the user to the same region), causal tokens (the write returns a token; the read includes it, and the local replica waits for replication to reach that point), or read-after-write routing (forward reads to the write region if the causal token hasn't arrived locally).

Open questions worth asking

  • Which regions need to accept writes — 2, 3, more?
  • What is the data model — key-value, document, relational?
  • What is the acceptable replication lag between regions?
  • Are conflicts expected to be rare (< 0.1%) or common?
  • Can the data model be redesigned to avoid conflicts (CRDTs, append-only)?
  • Do users expect read-your-writes consistency?
  • What is the conflict resolution strategy — LWW, merge function, user prompt?
  • What is the region failover time SLA?
  • Is this a greenfield design or retrofitting an existing single-region store?
  • What is the cross-region RTT between the chosen regions?

Scope I'd lock first

  • In: replication topology, conflict resolution (LWW, CRDT, merge), read-your-writes, lag SLOs.
  • Out: full CRDT implementation library, network infrastructure design.
  • Stretch: design a conflict audit log and manual resolution workflow for non-mergeable conflicts.

Approach / design notes

Active-active replication: each region has a full copy of the data. Writes go to the local region's store and are appended to a changelog. A replication service continuously ships changelog entries to remote regions. On the receiving end, each entry is applied with conflict resolution.

Last-writer-wins (LWW): on conflict (same key modified in both regions within the lag window), compare HLC timestamps. The higher timestamp wins. The loser is silently discarded. This is simple and deterministic but can lose data. It works for data where the latest value is genuinely the correct one (user profile updates, settings).

CRDTs: for counters (likes, inventory decrements), use a G-Counter (grow-only) or PN-Counter (positive-negative). Each region maintains its own count; the merged value is the sum. For sets, use an OR-Set (observed-remove set). These resolve automatically with mathematical guarantees: commutativity, associativity, idempotency. The trade-off is that not all data models fit CRDTs — a free-form JSON document doesn't have a natural merge function.

Read-your-writes with causal tokens: the write response includes a token encoding (region, sequence_number, hlc_ts). On subsequent reads, the client sends this token. If the local replica hasn't reached that sequence number yet, it either waits (up to a timeout) or routes the read to the origin region. This guarantees the user sees their own writes without requiring strong consistency for all reads.

Lag SLO monitoring: track replication_lag_ms = current_time − last_applied_changelog_entry_time. Alert at p99 > 500 ms. If lag grows unbounded, the replication stream may be falling behind — common causes: changelog consumer is slow, network partition, or receiving region is overloaded.

Deep dive (spend 15–25 minutes here)

Conflict trace: User A in US-East updates profile.name = 'Alice' at HLC (1000, 0, us-east). User B in EU-West updates profile.name = 'Alicia' at HLC (1000, 2, eu-west) — B's clock is slightly ahead. The changelog entries ship asynchronously. US-East receives EU-West's entry and compares: (1000, 2, eu-west) > (1000, 0, us-east), so LWW picks 'Alicia'. EU-West receives US-East's entry and also sees (1000, 2, eu-west) > (1000, 0, us-east) — same winner. Both regions converge to 'Alicia'. But Alice's update was lost — she doesn't know.

CRDT counter trace: a product has stock_count tracked as a PN-Counter. US-East decrements by 1 (local delta: -1). EU-West decrements by 2 (local delta: -2). Replication ships both deltas. Each region merges: total delta = -1 + -2 = -3. Both converge to the same stock count without conflicts. The key insight: commutative operations don't conflict.

Read-your-writes failure without causal tokens: User writes order in US-East (seq 42), gets a 200 OK. DNS routes their next request to EU-West, which is at seq 40. The user sees no order — they think the system lost it. With causal tokens: the write returns token 'us-east:42'. The read includes this token. EU-West sees it needs seq 42 but only has 40. It waits up to 200 ms for replication. At seq 41... 42 — arrived. Serve the read with the user's order visible.

Operational concern — replication lag during region failover: if US-East goes down with unreplicated changelog entries (seq 42–45), those writes are lost until US-East recovers. Mitigation: synchronous replication for critical writes (e.g., payments) — the write doesn't acknowledge until at least one remote region confirms. This adds cross-region RTT (~80 ms) to write latency but prevents data loss on region failure.

from dataclasses import dataclass, field
from typing import Any


@dataclass
class HLCTimestamp:
    physical: int
    logical: int
    region: str

    def __gt__(self, other: 'HLCTimestamp') -> bool:
        return (self.physical, self.logical, self.region) > \
               (other.physical, other.logical, other.region)


@dataclass
class VersionedValue:
    value: Any
    ts: HLCTimestamp


def lww_resolve(local: VersionedValue, remote: VersionedValue) -> VersionedValue:
    return remote if remote.ts > local.ts else local


@dataclass
class PNCounter:
    """Positive-Negative CRDT counter — merges without conflicts."""
    increments: dict = field(default_factory=dict)  # region -> count
    decrements: dict = field(default_factory=dict)  # region -> count

    def increment(self, region: str, amount: int = 1):
        self.increments[region] = self.increments.get(region, 0) + amount

    def decrement(self, region: str, amount: int = 1):
        self.decrements[region] = self.decrements.get(region, 0) + amount

    @property
    def value(self) -> int:
        return sum(self.increments.values()) - sum(self.decrements.values())

    def merge(self, other: 'PNCounter') -> 'PNCounter':
        merged = PNCounter()
        all_regions = set(self.increments) | set(other.increments)
        for r in all_regions:
            merged.increments[r] = max(self.increments.get(r, 0),
                                       other.increments.get(r, 0))
        all_regions = set(self.decrements) | set(other.decrements)
        for r in all_regions:
            merged.decrements[r] = max(self.decrements.get(r, 0),
                                       other.decrements.get(r, 0))
        return merged
use std::cmp::Ordering;
use std::collections::HashMap;

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct HLCTimestamp {
    pub physical: u64,
    pub logical: u64,
    pub region: String,
}

impl PartialOrd for HLCTimestamp {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> { Some(self.cmp(other)) }
}
impl Ord for HLCTimestamp {
    fn cmp(&self, other: &Self) -> Ordering {
        (self.physical, self.logical, &self.region)
            .cmp(&(other.physical, other.logical, &other.region))
    }
}

#[derive(Debug, Clone)]
pub struct VersionedValue<T> {
    pub value: T,
    pub ts: HLCTimestamp,
}

/// Last-Writer-Wins: keep the value with the greater timestamp.
pub fn lww_resolve<T: Clone>(
    local: &VersionedValue<T>,
    remote: &VersionedValue<T>,
) -> VersionedValue<T> {
    if remote.ts > local.ts { remote.clone() } else { local.clone() }
}

/// Positive-Negative CRDT counter — merges without conflicts.
#[derive(Debug, Clone, Default)]
pub struct PNCounter {
    pub increments: HashMap<String, i64>,
    pub decrements: HashMap<String, i64>,
}

impl PNCounter {
    pub fn increment(&mut self, region: &str, amount: i64) {
        *self.increments.entry(region.into()).or_insert(0) += amount;
    }

    pub fn decrement(&mut self, region: &str, amount: i64) {
        *self.decrements.entry(region.into()).or_insert(0) += amount;
    }

    pub fn value(&self) -> i64 {
        let inc: i64 = self.increments.values().sum();
        let dec: i64 = self.decrements.values().sum();
        inc - dec
    }

    pub fn merge(&self, other: &PNCounter) -> PNCounter {
        let mut merged = PNCounter::default();
        for key in self.increments.keys().chain(other.increments.keys()) {
            let a = self.increments.get(key).copied().unwrap_or(0);
            let b = other.increments.get(key).copied().unwrap_or(0);
            merged.increments.insert(key.clone(), a.max(b));
        }
        for key in self.decrements.keys().chain(other.decrements.keys()) {
            let a = self.decrements.get(key).copied().unwrap_or(0);
            let b = other.decrements.get(key).copied().unwrap_or(0);
            merged.decrements.insert(key.clone(), a.max(b));
        }
        merged
    }
}
#import <Foundation/Foundation.h>
#include <string>
#include <map>
#include <algorithm>

struct HLCTimestamp {
    uint64_t physical;
    uint64_t logical;
    std::string region;

    bool operator>(const HLCTimestamp &o) const {
        return std::tie(physical, logical, region)
             > std::tie(o.physical, o.logical, o.region);
    }
};

template <typename T>
struct VersionedValue {
    T value;
    HLCTimestamp ts;
};

/// Last-Writer-Wins: keep the value with the greater timestamp.
template <typename T>
VersionedValue<T> lwwResolve(const VersionedValue<T> &local,
                             const VersionedValue<T> &remote) {
    return (remote.ts > local.ts) ? remote : local;
}

/// Positive-Negative CRDT counter — merges without conflicts.
@interface PNCounter : NSObject {
    std::map<std::string, int64_t> _increments;
    std::map<std::string, int64_t> _decrements;
}
- (void)increment:(const std::string &)region amount:(int64_t)amount;
- (void)decrement:(const std::string &)region amount:(int64_t)amount;
- (int64_t)value;
- (PNCounter *)mergeWith:(PNCounter *)other;
@end

@implementation PNCounter

- (void)increment:(const std::string &)region amount:(int64_t)amount {
    _increments[region] += amount;
}

- (void)decrement:(const std::string &)region amount:(int64_t)amount {
    _decrements[region] += amount;
}

- (int64_t)value {
    int64_t inc = 0, dec = 0;
    for (auto &[_, v] : _increments) inc += v;
    for (auto &[_, v] : _decrements) dec += v;
    return inc - dec;
}

- (PNCounter *)mergeWith:(PNCounter *)other {
    PNCounter *merged = [[PNCounter alloc] init];
    // Take per-region max for increments
    for (auto &[r, v] : _increments)
        merged->_increments[r] = std::max(v, other->_increments[r]);
    for (auto &[r, v] : other->_increments)
        merged->_increments[r] = std::max(v, _increments[r]);
    // Same for decrements
    for (auto &[r, v] : _decrements)
        merged->_decrements[r] = std::max(v, other->_decrements[r]);
    for (auto &[r, v] : other->_decrements)
        merged->_decrements[r] = std::max(v, _decrements[r]);
    return merged;
}

@end

Trade-offs I'd say out loud

Active-active vs active-passive

Active-active gives lower latency and better availability but introduces conflict resolution complexity.

LWW vs CRDTs

LWW is simple but loses data; CRDTs preserve all updates but only work for commutative data models.

Async vs sync replication

Async gives low write latency but risks data loss on region failure; sync adds cross-region RTT.

Causal tokens vs sticky sessions

Tokens are more flexible but add complexity; sticky sessions are simple but break on failover.

Where it usually breaks

  • LWW with wall-clock timestamps instead of HLC — clock skew causes wrong winner.
  • No read-your-writes guarantee — users see stale data after writes.
  • Replication lag growing unbounded — regions diverge for minutes.
  • Failing over to a region with unreplicated changelog entries — data loss.
  • CRDT counter going negative due to decrements exceeding increments — needs business-logic guard.
  • Circular replication (A→B→A) without deduplication — changelog entries loop forever.
