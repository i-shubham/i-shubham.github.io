Implement a distributed lock

A lock that isn't fenced is a suggestion — expired holders must not keep writing.

60-minute agenda

How I'd open the discussion

I'd start by pinning down what the lock actually guards. If it protects an idempotent cache refresh, a best-effort SETNX with a TTL is fine — double execution is harmless. If it guards a financial transfer, we need a fencing token that the downstream storage checks before accepting writes, because the lock holder can pause (GC, page fault, swap storm) past the TTL and never know it lost the lock.

The single-node Redis lock is the starting point: SET key owner_token NX EX 30. Release is a Lua compare-and-delete so we never free someone else's lock. The real conversation is what breaks: the holder pauses for 35 seconds, the lock expires, a second holder acquires, and now both think they own it. No TTL fixes this — only fencing tokens do.

Then I'd walk through Redlock — acquiring on N/2+1 independent Redis nodes within a validity window — and honestly acknowledge the Martin Kleppmann critique: Redlock assumes bounded process pauses and synchronized clocks, which are exactly the things that break in production. For strong mutual exclusion I'd lean toward ZooKeeper or etcd.

Open questions worth asking

  • What operation does the lock protect — idempotent or side-effecting?
  • Single data center or cross-region?
  • What is the maximum acceptable lock hold time?
  • Do we need re-entrant locking (same owner re-acquires)?
  • Is there a downstream storage that can enforce fencing tokens?
  • How many concurrent lock contenders at peak?
  • Is Redis already in the stack, or are we free to choose ZooKeeper / etcd?
  • Do we need fair queuing (FIFO) or is best-effort acquisition okay?
  • What happens if the lock service itself is unavailable — fail open or fail closed?
  • What SLA do we target for lock acquisition latency?

Scope I'd lock first

  • In: single-node Redis lock, fencing tokens, Redlock overview, failure taxonomy.
  • Out: full ZooKeeper / etcd implementation, Paxos derivation.
  • Stretch: compare Redlock vs ZooKeeper ephemeral nodes vs etcd lease.

Functional requirements

acquire(resource, owner, ttl)

Returns fencing token or failure within timeout.

release(resource, owner, token)

Releases only if caller still owns the lock.

renew(resource, owner, token, ttl)

Extends TTL if ownership hasn't changed.

fenced_write(storage, token, data)

Storage rejects writes with stale tokens.

Non-functional / rough numbers

Mutual exclusion

At most one holder can successfully write at any instant, enforced via fencing.

Liveness

Lock is released within TTL even if holder crashes — no deadlocks.

Acquire latency

p99 < 10 ms for single-node Redis, < 50 ms for Redlock quorum.

Throughput

Sustain 5 000 acquire/release cycles per second per resource.

Capacity estimate (do this on the board)

Lock contenders

~200 concurrent clients contending on ~50 distinct resources.

Redis nodes (Redlock)

5 independent masters — quorum is 3.

TTL

30 s default, clock drift bound δ = 2 s, validity = TTL − 2δ − RTT.

Throughput

~5 000 acquire + release ops/s on a single Redis instance.

Approach / design notes

The simplest correct lock is SET key owner NX EX ttl on a single Redis. The owner token is a UUID — release compares it atomically in Lua so we never delete someone else's lock. This handles the crash case: the TTL expires and another client acquires. But it does not handle the pause case.

The pause problem: holder acquires, then hits a 40-second GC pause. The TTL (30 s) fires, a new holder acquires with a new token. The old holder wakes up, believes it still owns the lock (it cached the OK response before pausing), and writes. Both wrote. No amount of TTL tuning fixes this — the holder cannot know it paused.

Fencing tokens solve it. On acquire, the lock service returns a monotonically increasing token (e.g., a Redis INCR counter). The protected storage records the highest token it has seen. Any write with a token <= stored token is rejected. The stale holder's write carries token 41; the new holder already wrote with token 42; storage rejects 41.

Redlock extends this to N independent Redis masters (typically 5). The client tries to acquire on all N with the same key and token, measuring wall-clock elapsed. If it gets OK from >= N/2+1 nodes within (TTL − clock_drift − RTT), the lock is valid for the remaining time. If not, it releases on all nodes. The Kleppmann critique is that Redlock still assumes bounded pauses between acquiring and using the lock — fencing tokens are still needed.

For truly strong mutual exclusion, consensus-based systems (ZooKeeper ephemeral + sequential znodes, etcd lease + compare-and-swap) provide linearizable locks with session semantics. The trade-off is latency: ZooKeeper acquire is ~5–15 ms vs Redis's ~1 ms, and you need a ZK ensemble (3 or 5 nodes).

Deep dive (spend 15–25 minutes here)

Let's trace a concrete failure. Client A calls SET mylock A NX EX 30 at t=0 and gets OK. At t=1 it begins a database transaction. At t=2 a full GC kicks in and freezes the process for 35 seconds. At t=30 the TTL expires. At t=31 Client B calls SET mylock B NX EX 30 and gets OK. At t=33 Client B writes row X = 100. At t=37 Client A wakes up from GC. It still holds the cached OK from t=0. It writes row X = 50. Now X = 50 but should be 100.

With fencing: Client A acquired token 41, Client B acquired token 42. Client B's write carries token 42 — storage updates last_token to 42 and accepts. Client A's write carries token 41. Storage sees 41 < 42, rejects. X stays at 100. Correctness is preserved.

Redlock timing math: suppose N=5, TTL=30 s, clock drift rate ρ = 200 μs/s (NTP-synced), so total drift bound δ = TTL × ρ = 6 ms. The client records start_time before the first SET. After getting 3 OKs, elapsed = now − start_time. Lock validity = TTL − elapsed − 2δ. If validity <= 0, the lock is already invalid — release everywhere and retry. In practice, if the 3 acquires take 5 ms total, validity ≈ 29.988 s, plenty of margin.

The subtle Redlock flaw: even with 3/5 quorum, if Client A acquires, pauses 31 seconds, its lock expires on all 5 nodes. Client B acquires with a new quorum. Client A wakes and doesn't know it lost the lock — it never checks Redis again. Without fencing tokens on the storage side, Redlock has the same stale-holder problem as the single-node lock. Kleppmann's argument is precisely this: the algorithm doesn't protect you at the point of use.

ZooKeeper alternative: create an ephemeral sequential znode /locks/mylock/lock-00000042. Watch the znode with the next-lower sequence number. When it disappears, you hold the lock. If the client's session dies (heartbeat timeout, typically 10–30 s), ZK deletes the ephemeral node automatically. The sequential ordering gives fair FIFO queuing. The downside: session timeout adds latency to failover, and ZK's throughput (~10k ops/s) is far below Redis.

Redis lock with fencing token and safe release

import time, uuid, redis

class RedisLock:
    def __init__(self, client: redis.Redis, resource: str, ttl_ms: int = 30000):
        self.r = client
        self.resource = f'lock:{resource}'
        self.seq_key = f'lock:{resource}:seq'
        self.ttl_ms = ttl_ms
        self.owner = str(uuid.uuid4())
        self.token = None

    _ACQUIRE_LUA = """
    if redis.call('set', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
        return redis.call('incr', KEYS[2])
    end
    return nil
    """

    _RELEASE_LUA = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        redis.call('del', KEYS[1])
        return 1
    end
    return 0
    """

    def acquire(self, timeout_ms: int = 5000) -> int | None:
        deadline = time.monotonic() + timeout_ms / 1000
        while time.monotonic() < deadline:
            token = self.r.eval(
                self._ACQUIRE_LUA, 2,
                self.resource, self.seq_key,
                self.owner, str(self.ttl_ms),
            )
            if token is not None:
                self.token = int(token)
                return self.token
            time.sleep(0.05)
        return None

    def release(self) -> bool:
        return self.r.eval(self._RELEASE_LUA, 1, self.resource, self.owner) == 1


def fenced_write(conn, token: int, resource_id: str, value: str) -> bool:
    """Accept write only if token > last accepted token."""
    result = conn.execute(
        "UPDATE fenced_resources SET value = %s, last_token = %s "
        "WHERE resource_id = %s AND last_token < %s",
        (value, token, resource_id, token),
    )
    return result.rowcount == 1
use redis::{Client, Script};
use std::time::{Duration, Instant};
use uuid::Uuid;

pub struct RedisLock {
    client: Client,
    resource: String,
    seq_key: String,
    ttl_ms: u64,
    owner: String,
    token: Option<i64>,
}

const ACQUIRE_LUA: &str = r#"
if redis.call('set', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
    return redis.call('incr', KEYS[2])
end
return nil
"#;

const RELEASE_LUA: &str = r#"
if redis.call('get', KEYS[1]) == ARGV[1] then
    redis.call('del', KEYS[1])
    return 1
end
return 0
"#;

impl RedisLock {
    pub fn new(client: Client, resource: &str, ttl_ms: u64) -> Self {
        Self {
            resource: format!("lock:{resource}"),
            seq_key: format!("lock:{resource}:seq"),
            client,
            ttl_ms,
            owner: Uuid::new_v4().to_string(),
            token: None,
        }
    }

    pub fn acquire(&mut self, timeout_ms: u64) -> Option<i64> {
        let script = Script::new(ACQUIRE_LUA);
        let deadline = Instant::now() + Duration::from_millis(timeout_ms);
        let mut conn = self.client.get_connection().ok()?;

        while Instant::now() < deadline {
            let result: Option<i64> = script
                .key(&self.resource)
                .key(&self.seq_key)
                .arg(&self.owner)
                .arg(self.ttl_ms)
                .invoke(&mut conn)
                .ok()?;
            if let Some(tok) = result {
                self.token = Some(tok);
                return Some(tok);
            }
            std::thread::sleep(Duration::from_millis(50));
        }
        None
    }

    pub fn release(&mut self) -> bool {
        let script = Script::new(RELEASE_LUA);
        let Ok(mut conn) = self.client.get_connection() else {
            return false;
        };
        script
            .key(&self.resource)
            .arg(&self.owner)
            .invoke::<i64>(&mut conn)
            .map(|v| v == 1)
            .unwrap_or(false)
    }
}

/// Accept write only if fencing token exceeds the last accepted token.
pub fn fenced_write(
    client: &mut postgres::Client,
    token: i64, resource_id: &str, value: &str,
) -> bool {
    let rows = client
        .execute(
            "UPDATE fenced_resources SET value = $1, last_token = $2 \
             WHERE resource_id = $3 AND last_token < $4",
            &[&value, &token, &resource_id, &token],
        )
        .unwrap_or(0);
    rows == 1
}
#import <Foundation/Foundation.h>
#include <string>
#include <optional>
#include <chrono>
#include <thread>

// Protocol modelling the subset of Redis commands used by the lock.
@protocol RedisClient <NSObject>
- (nullable NSNumber *)evalLua:(NSString *)script
                          keys:(NSArray<NSString *> *)keys
                          args:(NSArray<NSString *> *)args;
@end

@interface RedisLock : NSObject {
    NSString *_resource;
    NSString *_seqKey;
    NSString *_owner;
    int64_t   _ttlMs;
    int64_t   _token;
    id<RedisClient> _client;
}
- (instancetype)initWithClient:(id<RedisClient>)client
                      resource:(NSString *)resource
                         ttlMs:(int64_t)ttlMs;
- (std::optional<int64_t>)acquireWithTimeout:(int64_t)timeoutMs;
- (BOOL)release;
@end

@implementation RedisLock

static NSString *const kAcquireLua =
    @"if redis.call('set',KEYS[1],ARGV[1],'NX','PX',ARGV[2]) then "
     "return redis.call('incr',KEYS[2]) end return nil";

static NSString *const kReleaseLua =
    @"if redis.call('get',KEYS[1])==ARGV[1] then "
     "redis.call('del',KEYS[1]) return 1 end return 0";

- (instancetype)initWithClient:(id<RedisClient>)client
                      resource:(NSString *)resource
                         ttlMs:(int64_t)ttlMs {
    if ((self = [super init])) {
        _client   = client;
        _resource = [NSString stringWithFormat:@"lock:%@", resource];
        _seqKey   = [NSString stringWithFormat:@"lock:%@:seq", resource];
        _owner    = NSUUID.UUID.UUIDString;
        _ttlMs    = ttlMs;
        _token    = -1;
    }
    return self;
}

- (std::optional<int64_t>)acquireWithTimeout:(int64_t)timeoutMs {
    auto deadline = std::chrono::steady_clock::now()
                  + std::chrono::milliseconds(timeoutMs);
    NSString *ttlStr = [NSString stringWithFormat:@"%lld", _ttlMs];

    while (std::chrono::steady_clock::now() < deadline) {
        NSNumber *res = [_client evalLua:kAcquireLua
                                    keys:@[_resource, _seqKey]
                                    args:@[_owner, ttlStr]];
        if (res) {
            _token = res.longLongValue;
            return _token;
        }
        std::this_thread::sleep_for(std::chrono::milliseconds(50));
    }
    return std::nullopt;
}

- (BOOL)release {
    NSNumber *res = [_client evalLua:kReleaseLua
                                keys:@[_resource]
                                args:@[_owner]];
    return res && res.intValue == 1;
}
@end

// Accept write only when fencing token exceeds the stored one.
// Uses a conceptual SQL executor; mirrors the Python / Rust logic.
static BOOL fencedWrite(id /* db conn */ conn, int64_t token,
                        NSString *resourceId, NSString *value) {
    // In production, bind parameters to avoid SQL injection.
    NSString *sql = [NSString stringWithFormat:
        @"UPDATE fenced_resources SET value='%@', last_token=%lld "
         "WHERE resource_id='%@' AND last_token < %lld",
        value, token, resourceId, token];
    // executeUpdate: returns affected-row count (conceptual).
    return /* [conn executeUpdate:sql] */ 1 == 1;
}

Request path / sequence

Trade-offs I'd say out loud

TTL too short vs too long

Short TTL risks false expiry under GC pauses; long TTL delays recovery after crashes.

Fencing token complexity vs correctness

Fencing requires storage to enforce tokens — extra write path logic, but prevents stale writes.

Redlock vs single-node

Redlock survives one Redis failure but adds latency and still needs fencing for safety.

Redis vs ZooKeeper / etcd

Redis is faster (~1 ms) but weaker guarantees; ZK/etcd give linearizable locks at ~10 ms.

Where it usually breaks

  • Releasing someone else's lock because you didn't compare-and-delete atomically.
  • GC pause longer than TTL — holder wakes up thinking it still owns the lock.
  • Clock skew on Redis nodes making TTL expire early on some, late on others.
  • Forgetting to release on all Redlock nodes after a failed quorum attempt.
  • Using wall-clock time instead of monotonic clock for elapsed-time calculation.
  • Not setting a retry backoff on acquire — thundering herd under contention.

Follow-ups if time remains

  • Add lock queuing with ZooKeeper sequential ephemeral znodes for fairness.
  • Implement auto-renewal (watchdog thread) that extends TTL while the holder is alive.
  • Design a lock service dashboard showing current holders, wait times, and acquisition rates.
  • Handle the 'lock inherited after failover' case in a Redis Sentinel setup.
  • Compare Redlock with consensus-based locks in a latency-vs-safety matrix.
