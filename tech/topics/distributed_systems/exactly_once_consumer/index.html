Design an exactly-once consumer

Brokers give at-least-once. Exactly-once is an application effect — or a transactional ecosystem with sharp edges.

60-minute agenda

How I'd open the discussion

I'd open by saying that exactly-once delivery is impossible in the general case — it's the Two Generals problem. What we actually build is at-least-once delivery with exactly-once processing, and there are two ways to get there: make the handler idempotent, or make the processing and offset commit atomic.

The idempotent handler path is the most general. Every message carries a unique ID (or we derive one from its content). Before processing, we check a dedupe store. After processing, we record the ID. The critical detail is that the check-process-record sequence must be atomic with respect to the side effect — otherwise a crash between processing and recording means we'll process again on replay.

The transactional path is cleaner when the side effect is a database write: wrap the business write and the offset/dedupe record in a single DB transaction. If the transaction commits, both happened. If it rolls back, neither did. Kafka's EOS (Exactly-Once Semantics) does this within the Kafka ecosystem — but the moment your side effect leaves Kafka (HTTP call, DB write), you're back to idempotent handlers.

Open questions worth asking

  • What broker are we consuming from — Kafka, SQS, RabbitMQ?
  • What is the side effect — DB write, HTTP call, another message?
  • Can we derive a natural idempotency key from the message content?
  • What is the acceptable processing latency per message?
  • How long should we retain dedupe keys before expiry?
  • Is the consumer single-threaded or multi-partition concurrent?
  • Do we need ordering guarantees within a partition?
  • What is the message volume — 100/s or 100 000/s?
  • Can we use a transactional DB for offset + business write?
  • What is the cost of a duplicate side effect if dedup fails?

Functional requirements

consume(topic, group)

Pulls messages, guarantees each is processed exactly once.

dedupe_check(msg_id)

Returns True if message was already processed.

process_and_record(msg, side_effect)

Atomically applies effect and marks message done.

commit_offset(partition, offset)

Advances consumer offset after successful processing.

Approach / design notes

At-least-once is the baseline: consume, process, commit offset. If the consumer crashes after processing but before committing, the broker replays the message. The side effect happens twice. For a DB insert, that's a duplicate row; for an HTTP POST, a double charge.

Idempotent handler: before processing, SET dedupe:{msg_id} 1 NX EX 604800 in Redis. If Redis returns nil, the message was already processed — skip. If OK, process, then commit offset. Crash between Redis SET and processing means we skip a message that wasn't processed — so we need to reverse the order: process first, then SET. But then crash between process and SET means duplicate. The resolution: make the side effect itself idempotent (upsert, not insert) or wrap process + SET in a transaction.

Transactional outbox: the business write and the processed_messages insert happen in the same DB transaction. On replay, the consumer checks processed_messages before processing. The offset commit is asynchronous — a replay just hits the dedupe check. This is the strongest guarantee for DB-bound side effects.

Kafka EOS: the producer calls initTransactions(), then beginTransaction(), sends output messages + sendOffsetsToTransaction() for the consumer group, then commitTransaction(). The broker treats all of these atomically using a transaction coordinator and two-phase commit internally. The limitation: this only works for consume-transform-produce within Kafka. External side effects are not covered.

In practice, I combine approaches: natural idempotency keys where possible (e.g., order_id + event_type), Redis dedupe for hot path, and a DB outbox for financial operations. The dedupe TTL is set to max(consumer_lag) + safety margin — typically 7 days.

Deep dive (spend 15–25 minutes here)

Trace a concrete failure: consumer reads message M (offset 42, msg_id='order-7891-placed'). It processes M — inserts a row in the orders table. Before it can call commitSync(), the consumer crashes. On restart, Kafka delivers M again (offset 42). Without dedup, the consumer inserts a second row. With a UNIQUE constraint on order_id, the INSERT fails — but now the consumer is stuck on a poison message unless it catches the duplicate-key exception and commits past it.

With the idempotent handler: on replay, the consumer calls SET dedupe:order-7891-placed 1 NX. If the first processing succeeded and the dedupe key was set, Redis returns nil — skip. But what if the consumer crashed after the INSERT but before the Redis SET? Then the dedupe key is missing, and we process again. The orders table gets a duplicate. This is the window-of-vulnerability problem: the side effect and the dedupe record are in different stores, so they can't be atomic without a distributed transaction.

The transactional outbox eliminates this gap. We INSERT the order row and INSERT INTO processed_messages(msg_id, ...) in the same PostgreSQL transaction. If the transaction commits, both are durable. If it rolls back, neither is. On replay, we SELECT from processed_messages before processing. Found? Skip and commit offset. Not found? Process in a new transaction. The offset commit is best-effort — a missed commit just means an extra dedupe check on next restart, not a duplicate.

Kafka EOS internals: the transaction coordinator (a broker with a __transaction_state partition) writes a PREPARE marker to all involved partitions, then a COMMIT marker. Consumers with isolation.level=read_committed skip records belonging to open transactions. The overhead is real: EOS adds ~10–20% latency per produce call and limits throughput because transactions are per-producer, serialized. At 100k msgs/s, this matters.

Kafka consumer with Redis dedupe and idempotent DB write

import json, redis, psycopg2
from kafka import KafkaConsumer

DEDUPE_TTL = 7 * 86400  # 7 days

def make_consumer(topic, group):
    return KafkaConsumer(
        topic,
        group_id=group,
        enable_auto_commit=False,
        auto_offset_reset='earliest',
    )

def run(topic='orders', group='order-processor'):
    consumer = make_consumer(topic, group)
    rds = redis.Redis()
    db = psycopg2.connect(dsn='dbname=app')

    for msg in consumer:
        payload = json.loads(msg.value)
        msg_id = payload['order_id'] + ':' + payload['event_type']

        if not rds.set(f'dedupe:{msg_id}', 1, nx=True, ex=DEDUPE_TTL):
            consumer.commit()
            continue  # already processed

        try:
            with db:
                cur = db.cursor()
                cur.execute(
                    "INSERT INTO orders (order_id, event_type, payload) "
                    "VALUES (%s, %s, %s) ON CONFLICT (order_id, event_type) DO NOTHING",
                    (payload['order_id'], payload['event_type'], json.dumps(payload)),
                )
        except Exception:
            rds.delete(f'dedupe:{msg_id}')  # allow retry
            raise

        consumer.commit()

if __name__ == '__main__':
    run()
use rdkafka::consumer::{Consumer, StreamConsumer};
use rdkafka::config::ClientConfig;
use rdkafka::message::Message;
use redis::Commands;
use tokio_postgres::NoTls;

const DEDUPE_TTL: usize = 7 * 86400; // 7 days

async fn run(topic: &str, group: &str) -> anyhow::Result<()> {
    let consumer: StreamConsumer = ClientConfig::new()
        .set("group.id", group)
        .set("enable.auto.commit", "false")
        .set("auto.offset.reset", "earliest")
        .create()?;
    consumer.subscribe(&[topic])?;

    let rds = redis::Client::open("redis://127.0.0.1/")?;
    let mut rds_conn = rds.get_connection()?;

    let (db, conn) = tokio_postgres::connect("dbname=app", NoTls).await?;
    tokio::spawn(async move { conn.await.unwrap() });

    loop {
        let msg = consumer.recv().await?;
        let bytes = msg.payload().unwrap_or_default();
        let payload: serde_json::Value = serde_json::from_slice(bytes)?;

        let msg_id = format!(
            "{}:{}",
            payload["order_id"].as_str().unwrap_or_default(),
            payload["event_type"].as_str().unwrap_or_default(),
        );
        let key = format!("dedupe:{msg_id}");

        // SET NX with TTL — skip if already processed
        let set: bool = redis::cmd("SET")
            .arg(&key).arg(1).arg("NX").arg("EX").arg(DEDUPE_TTL)
            .query(&mut rds_conn)?;
        if !set {
            consumer.commit_message(&msg, rdkafka::consumer::CommitMode::Sync)?;
            continue;
        }

        let result = db.execute(
            "INSERT INTO orders (order_id, event_type, payload) \
             VALUES ($1, $2, $3) ON CONFLICT (order_id, event_type) DO NOTHING",
            &[
                &payload["order_id"].as_str().unwrap_or_default(),
                &payload["event_type"].as_str().unwrap_or_default(),
                &serde_json::to_string(&payload)?,
            ],
        ).await;

        if result.is_err() {
            rds_conn.del::<_, ()>(&key)?; // allow retry
            result?;
        }

        consumer.commit_message(&msg, rdkafka::consumer::CommitMode::Sync)?;
    }
}
#import <Foundation/Foundation.h>
#include <string>

static const NSTimeInterval kDedupeTTL = 7 * 86400; // 7 days

// Protocols abstract the broker, cache, and DB so the logic mirrors Python.
@protocol KafkaConsumer <NSObject>
- (nullable NSDictionary *)poll;  // blocks until next message
- (void)commit;
@end

@protocol RedisClient <NSObject>
- (BOOL)setNX:(NSString *)key value:(int)val expiry:(NSTimeInterval)ttl;
- (void)del:(NSString *)key;
@end

@protocol DBClient <NSObject>
- (BOOL)execute:(NSString *)sql params:(NSArray *)params error:(NSError **)err;
@end

@interface ExactlyOnceConsumer : NSObject
@property (nonatomic, strong) id<KafkaConsumer> consumer;
@property (nonatomic, strong) id<RedisClient>   redis;
@property (nonatomic, strong) id<DBClient>      db;
@end

@implementation ExactlyOnceConsumer

- (void)run {
    while (true) {
        NSDictionary *payload = [_consumer poll];
        if (!payload) continue;

        NSString *msgId = [NSString stringWithFormat:@"%@:%@",
                           payload[@"order_id"], payload[@"event_type"]];
        NSString *dedupeKey = [@"dedupe:" stringByAppendingString:msgId];

        // Dedupe via SET NX — skip if key already exists
        if (![_redis setNX:dedupeKey value:1 expiry:kDedupeTTL]) {
            [_consumer commit];
            continue;
        }

        NSError *err = nil;
        NSData *jsonData = [NSJSONSerialization dataWithJSONObject:payload
                                                          options:0 error:nil];
        NSString *jsonStr = [[NSString alloc] initWithData:jsonData
                                                  encoding:NSUTF8StringEncoding];

        BOOL ok = [_db execute:
            @"INSERT INTO orders (order_id, event_type, payload) "
             "VALUES ($1, $2, $3) ON CONFLICT (order_id, event_type) DO NOTHING"
                        params:@[payload[@"order_id"],
                                 payload[@"event_type"],
                                 jsonStr]
                         error:&err];
        if (!ok) {
            [_redis del:dedupeKey]; // allow retry on next delivery
            @throw [NSException exceptionWithName:@"DBError"
                                           reason:err.localizedDescription
                                         userInfo:nil];
        }
        [_consumer commit];
    }
}

@end

Request path / sequence

Trade-offs I'd say out loud

Dedupe in Redis vs DB

Redis is faster (~0.5 ms) but adds a second failure domain; DB dedupe is atomic but slower.

Kafka EOS vs app-level idempotency

EOS is transparent but only works within Kafka; app-level works for any side effect.

Dedupe TTL length

Longer TTL catches more replays but costs more storage — 7 days covers most lag scenarios.

Auto-commit vs manual commit

Auto-commit risks committing before processing; manual adds code complexity.

Where it usually breaks

  • Auto-committing offsets before processing completes — at-most-once, not at-least-once.
  • Dedup store and side effect in different transactions — crash between them causes inconsistency.
  • Dedupe TTL shorter than max consumer lag — old replays slip through.
  • Using message offset as dedupe key — offsets reset on partition reassignment.
  • Forgetting ON CONFLICT in the DB upsert — duplicate-key exceptions on replay.
  • Not handling rebalance during processing — half-processed message re-delivered to another consumer.

Follow-ups if time remains

  • Extend to multi-partition parallel processing with per-partition dedupe scopes.
  • Add a dead-letter queue for messages that fail N times despite idempotency.
  • Build a dedupe store compaction job that purges entries older than 7 days.
  • Compare latency profiles: Redis dedupe vs transactional outbox vs Kafka EOS.
