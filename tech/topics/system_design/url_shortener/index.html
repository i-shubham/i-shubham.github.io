Design a URL shortener

Short links look trivial until a celebrity posts one, analytics want every click, and someone asks for custom vanity URLs that never collide.

60-minute agenda

How I'd open the discussion

I'd start by pinning down the read-to-write ratio — URL shorteners are overwhelmingly read-heavy. A typical service sees maybe 100M new links per month but billions of redirects. That tells me the write path can afford a round-trip to a relational DB, but the read path needs aggressive caching. I'd also ask whether custom vanity aliases are in scope, because they turn a simple auto-increment problem into a uniqueness-contention problem.

The other question that shapes architecture is analytics. If we just redirect, the system is almost stateless on reads. But if product wants per-click tracking — referer, geo, device — every redirect becomes a write. I'd push that to an async pipeline so the user never waits on analytics.

I'd sketch three components: a write service that mints short codes, a redirect service backed by a massive cache, and an analytics pipeline that tails a click-event stream. Then I'd drill into the ID-generation strategy, which is where most designs either shine or fall apart.

Open questions worth asking

  • What is the expected read-to-write ratio?
  • Do we support custom vanity aliases or only system-generated codes?
  • What analytics do we need — just click count, or full referer/geo/device breakdown?
  • Should links expire, and if so, what is the default TTL?
  • Do we need to block malicious or phishing URLs?
  • Is there a maximum length for the original URL?
  • Do we need user accounts, or is it anonymous creation?
  • What latency target for the redirect — sub-50 ms?
  • Do we serve a 301 (permanent) or 302 (temporary) redirect?
  • Should the same long URL always produce the same short code?

Scope I'd lock first

  • In: short-code generation, redirect, basic click analytics, custom aliases.
  • In: cache layer for redirect reads, async analytics pipeline.
  • Out: abuse/phishing detection, OAuth user management, link-in-bio pages.
  • Defer: A/B testing on redirect targets, QR code generation.

Approach / design notes

The write path starts at an API gateway that validates the long URL and checks for duplicates if idempotency is desired. For ID generation I'd use a counter-based approach: a Snowflake-style ID generator gives each application server a pre-allocated range of IDs (e.g., 1000 IDs at a time from a coordination service like ZooKeeper). The server base62-encodes the ID into a 7-character code. This avoids write contention — no two servers ever mint the same ID. Custom aliases go through a separate path that does a uniqueness check against the DB with a unique constraint as the final safety net.

The read path is where performance matters. A user clicks a short link and expects an instant redirect. The redirect service first checks a local in-process cache (LRU, ~1M entries), then a Redis cluster holding the hot set, and finally falls back to the database. Cache hit rates above 95% are realistic because link access follows a heavy power-law distribution — a tiny fraction of links get the vast majority of clicks.

I'd use 302 (temporary) redirects by default instead of 301 (permanent), because 301 lets browsers cache the redirect and skip our service entirely — which means we lose analytics data and cannot change the destination later. The trade-off is slightly higher load on our servers, but that is manageable with the caching layer.

For analytics, every redirect emits a click event to a Kafka topic. A stream processor (Flink or Spark Streaming) aggregates counts, geo breakdowns, and referer stats into a columnar store like ClickHouse. This keeps the redirect path fast — the analytics write is async and non-blocking. Pre-aggregated rollups serve the stats API without scanning raw events.

For geographic distribution I'd put redirect PoPs in major regions. Each PoP has its own Redis replica. Cache misses go to the primary database region. Since the mapping is immutable after creation, cache invalidation is trivial — only link deletion or expiry requires a cache bust.

Deep dive (spend 15–25 minutes here)

The ID generation strategy deserves close scrutiny. Auto-increment is simple but creates a single-writer bottleneck and leaks creation order (competitor can enumerate your total link count). MD5/SHA256 hashing of the long URL gives deterministic codes but produces 128+ bit outputs that need truncation, introducing collision risk. A counter service that pre-allocates ranges is my preferred approach: each app server fetches a batch of 1,000 sequential IDs from ZooKeeper or etcd. Within that batch, it encodes IDs locally with zero coordination. When the batch runs out, it fetches the next one. Failure mid-batch wastes at most 1,000 IDs — negligible in a 3.5-trillion code space.

Base62 encoding (a-z, A-Z, 0-9) maps a 64-bit integer to a compact string. A 7-character code supports 62^7 ≈ 3.5 trillion unique values. The encoding is a simple repeated mod-62 operation. I'd avoid base64 because the '+' and '/' characters are URL-unfriendly and require percent-encoding, which defeats the purpose of a short URL.

Custom vanity aliases add a uniqueness challenge. The user submits 'myco/launch' and we need to guarantee no collision with system-generated codes. I'd reserve a separate namespace: system codes are always exactly 7 characters; custom aliases can be 3–20 characters. A unique index on short_code is the safety net, but I'd also check Redis first to give a fast 'alias taken' response without hitting the DB on every attempt.

Cache invalidation is simple because URL mappings are essentially immutable. The only mutations are deletion and expiry. For deletion, we publish an invalidation event to Redis Pub/Sub so all PoP caches evict the key within seconds. For expiry, we set a Redis TTL matching the link's expiry time so the cache self-evicts. The database is the source of truth — on a cache miss, we re-check is_active and expires_at before serving the redirect.

Hot-link thundering herd is the real production headache. When a celebrity tweets a short link, thousands of requests hit the same key simultaneously. If that key is not in cache (cold start or cache eviction), all requests stampede to the database. I'd use a request-coalescing pattern: the first cache miss starts a DB lookup and all other concurrent requests for the same key wait on that single lookup via a local mutex or a distributed lock with a short TTL. This collapses N identical queries into one.

Counter-based ID generator with base62 encoding

import string, threading

# Base62 alphabet: [a-z][A-Z][0-9] → 62^7 ≈ 3.5 trillion unique codes
BASE62 = string.ascii_lowercase + string.ascii_uppercase + string.digits


def base62_encode(num: int) -> str:
    """Convert a non-negative integer to a compact base-62 string."""
    if num == 0:
        return BASE62[0]
    chars = []
    while num > 0:
        chars.append(BASE62[num % 62])
        num //= 62
    return "".join(reversed(chars))


class CounterService:
    """Simulates a ZooKeeper-backed range allocator.
    Each app node claims a disjoint batch to avoid cross-node contention."""

    def __init__(self, batch_size=1000):
        self._counter = 0
        self._batch = batch_size
        self._lock = threading.Lock()

    def allocate_range(self) -> tuple[int, int]:
        with self._lock:
            start = self._counter
            self._counter += self._batch
            return start, start + self._batch - 1


class URLShortener:
    def __init__(self, counter_svc: CounterService):
        self._counter_svc = counter_svc
        self._current_id = 0
        self._max_id = -1
        self._store: dict[str, str] = {}  # short_code → long_url
        self._lock = threading.Lock()

    def _next_id(self) -> int:
        with self._lock:
            # Fetch a fresh batch when the local range is exhausted
            if self._current_id > self._max_id:
                self._current_id, self._max_id = (
                    self._counter_svc.allocate_range()
                )
            nid = self._current_id
            self._current_id += 1
            return nid

    def shorten(self, long_url: str, custom_alias: str = None) -> str:
        if custom_alias:
            if custom_alias in self._store:
                raise ValueError("Alias already taken")
            self._store[custom_alias] = long_url
            return custom_alias
        # Pad to 7 chars so every short URL has uniform length
        code = base62_encode(self._next_id()).rjust(7, BASE62[0])
        self._store[code] = long_url
        return code

    def resolve(self, code: str) -> str | None:
        return self._store.get(code)
use std::collections::HashMap;
use std::sync::Mutex;

const BASE62: &[u8] = b"abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";

fn base62_encode(mut num: u64) -> String {
    if num == 0 {
        return String::from(BASE62[0] as char);
    }
    let mut chars = Vec::new();
    while num > 0 {
        chars.push(BASE62[(num % 62) as usize] as char);
        num /= 62;
    }
    chars.iter().rev().collect()
}

/// Simulates ZooKeeper range allocator — each node claims a disjoint batch
struct CounterService {
    counter: Mutex<u64>,
    batch_size: u64,
}
impl CounterService {
    fn new(batch: u64) -> Self {
        Self { counter: Mutex::new(0), batch_size: batch }
    }
    fn allocate_range(&self) -> (u64, u64) {
        let mut c = self.counter.lock().unwrap();
        let start = *c;
        *c += self.batch_size;
        (start, start + self.batch_size - 1)
    }
}

struct URLShortener {
    svc: CounterService,
    cur: Mutex<u64>,
    max: Mutex<u64>,
    store: Mutex<HashMap<String, String>>, // short_code → long_url
}
impl URLShortener {
    fn new(svc: CounterService) -> Self {
        Self { svc, cur: Mutex::new(0), max: Mutex::new(0), store: Mutex::new(HashMap::new()) }
    }
    fn next_id(&self) -> u64 {
        let mut cur = self.cur.lock().unwrap();
        let mut max = self.max.lock().unwrap();
        if *cur > *max {
            // Replenish batch from the counter service
            (*cur, *max) = self.svc.allocate_range();
        }
        let id = *cur;
        *cur += 1;
        id
    }
    /// Returns Ok(short_code) or Err if alias is taken
    fn shorten(&self, long_url: &str, alias: Option<&str>) -> Result<String, &'static str> {
        let mut store = self.store.lock().unwrap();
        if let Some(a) = alias {
            if store.contains_key(a) {
                return Err("Alias already taken");
            }
            store.insert(a.into(), long_url.into());
            return Ok(a.into());
        }
        // Pad to 7 chars for uniform length
        let raw = base62_encode(self.next_id());
        let code = format!("{:a>7}", raw);
        store.insert(code.clone(), long_url.into());
        Ok(code)
    }
    fn resolve(&self, code: &str) -> Option<String> {
        self.store.lock().unwrap().get(code).cloned()
    }
}
#import <Foundation/Foundation.h>
#include <string>
#include <unordered_map>
#include <mutex>

static const char *kBase62 =
    "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";

static std::string base62Encode(uint64_t num) {
    if (num == 0) return std::string(1, kBase62[0]);
    std::string chars;
    while (num > 0) {
        chars.push_back(kBase62[num % 62]);
        num /= 62;
    }
    return std::string(chars.rbegin(), chars.rend()); // reverse in-place
}

// ObjC class wrapping C++ internals for thread-safe URL shortening
@interface URLShortener : NSObject
- (NSString *)shorten:(NSString *)longURL alias:(NSString *)alias;
- (NSString *)resolve:(NSString *)code;
@end

@implementation URLShortener {
    std::unordered_map<std::string, std::string> _store; // code → URL
    std::mutex _mu;
    uint64_t _curID, _maxID, _counter, _batch;
}
- (instancetype)init {
    if (self = [super init]) { _batch = 1000; _maxID = 0; _counter = 0; }
    return self;
}
- (uint64_t)_nextID {
    std::lock_guard<std::mutex> lock(_mu);
    if (_curID > _maxID) {
        _curID = _counter;           // allocate next batch
        _counter += _batch;
        _maxID = _curID + _batch - 1;
    }
    return _curID++;
}
- (NSString *)shorten:(NSString *)longURL alias:(NSString *)alias {
    std::lock_guard<std::mutex> lock(_mu);
    if (alias) {
        std::string a = alias.UTF8String;
        if (_store.count(a)) return nil; // alias already taken
        _store[a] = longURL.UTF8String;
        return alias;
    }
    std::string code = base62Encode([self _nextID]);
    while (code.size() < 7) code.insert(code.begin(), kBase62[0]); // pad
    _store[code] = longURL.UTF8String;
    return @(code.c_str()); // bridge C++ string back to NSString
}
- (NSString *)resolve:(NSString *)code {
    std::lock_guard<std::mutex> lock(_mu);
    auto it = _store.find(code.UTF8String);
    return it != _store.end() ? @(it->second.c_str()) : nil;
}
@end

Request path / sequence

Trade-offs I'd say out loud

Auto-increment vs counter service

Auto-increment is simpler but creates a write bottleneck and leaks total count.

301 vs 302 redirect

301 saves server load but loses analytics and prevents destination changes.

Hash-based vs counter-based codes

Hashing is stateless but risks collisions; counters need coordination but guarantee uniqueness.

Inline analytics vs async pipeline

Inline is simpler but adds 5-10 ms latency to every redirect.

Single DB vs sharded

Single node handles 360 GB/year easily; sharding only needed at 10B+ links.

Where it usually breaks

  • Counter service goes down — app servers exhaust their pre-allocated range and cannot mint new codes.
  • Cache stampede on a viral link — thousands of simultaneous cache misses overwhelm the database.
  • Custom alias collision under concurrent requests — two users claim the same alias in a race window.
  • Analytics pipeline lag during traffic spikes — Kafka consumer falls behind, stats become stale.
  • Link expiry not enforced in cache — expired links keep redirecting until the cache TTL expires.
  • Base62 decode collision if code length changes — mixing 6-char and 7-char codes without namespace separation.
