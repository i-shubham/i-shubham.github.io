Design an e-commerce checkout

Checkout is a distributed transaction you cannot actually run as one — inventory, payment, and order records disagree under failure.

60-minute agenda

How I'd open the discussion

Checkout looks like a simple sequence — reserve inventory, charge the card, create the order — but it is really a distributed transaction across three independent services, and distributed transactions are where optimism goes to die. What happens if payment succeeds but the order service is down? What if inventory was reserved but the user abandoned the checkout? Every failure mode needs a compensating action.

I'd model this as a saga with an orchestrator. The checkout orchestrator drives the sequence: reserve inventory, process payment, create order. If any step fails, it runs compensating actions in reverse: refund payment, release inventory. The key insight is that each step must be idempotent — retrying a step should not double-charge the user or double-reserve inventory.

I'd walk through the happy path first, then systematically cover every failure mode and its compensating action.

Open questions worth asking

  • What payment methods — credit card, PayPal, buy-now-pay-later?
  • Do we reserve inventory at add-to-cart or at checkout initiation?
  • What is the cart/reservation TTL before items are released?
  • How do we handle flash sales with massive concurrent demand for limited inventory?
  • Is split payment (partial gift card + credit card) in scope?
  • Do we need to support promo codes and discount calculations?
  • What is the acceptable checkout latency?
  • How do we handle payment provider timeouts — retry or abandon?
  • Do we need to support guest checkout (no account)?
  • Is multi-currency / multi-region in scope?
  • What happens if the item price changes between add-to-cart and checkout?

Scope I'd lock first

  • In: cart management, inventory reservation with TTL, payment processing with idempotency, order creation.
  • In: saga orchestrator with compensating actions, abandoned cart recovery.
  • Out: fulfillment/shipping, fraud detection ML model, multi-currency.
  • Defer: promo code engine, tax calculation, split payments.

POST /cart/items adds SKU with quantity. No inventory lock yet.

Initiate checkout

Process payment

POST /checkout/{id}/pay with payment method. Idempotent via idempotency_key.

Confirm order

On successful payment, creates immutable order record and triggers fulfillment.

Cancel

POST /checkout/{id}/cancel releases inventory and voids any pending auth.

Data model

sql
-- Inventory (sharded by sku_id)
CREATE TABLE inventory (
  sku_id        VARCHAR(32) PRIMARY KEY,
  total_stock   INT NOT NULL,
  reserved      INT DEFAULT 0,
  -- available = total_stock - reserved
  version       INT DEFAULT 0         -- optimistic locking
);

-- Reservations (auto-expire via TTL)
CREATE TABLE reservations (
  reservation_id  UUID PRIMARY KEY,
  checkout_id     UUID NOT NULL,
  sku_id          VARCHAR(32),
  quantity        INT,
  expires_at      TIMESTAMP NOT NULL,
  status          VARCHAR(16) DEFAULT 'active'  -- active|confirmed|released
);

-- Orders (immutable after creation)
CREATE TABLE orders (
  order_id      UUID PRIMARY KEY,
  user_id       BIGINT NOT NULL,
  total_cents   INT NOT NULL,
  currency      CHAR(3) DEFAULT 'USD',
  status        VARCHAR(16) DEFAULT 'confirmed',
  created_at    TIMESTAMP DEFAULT now()
);

-- Payments (idempotency enforced via unique key)
CREATE TABLE payments (
  payment_id       UUID PRIMARY KEY,
  order_id         UUID,
  idempotency_key  VARCHAR(64) UNIQUE,
  amount_cents     INT,
  provider         VARCHAR(32),
  provider_ref     VARCHAR(128),
  status           VARCHAR(16),  -- pending|captured|failed|refunded
  created_at       TIMESTAMP DEFAULT now()
);

Approach / design notes

The checkout flow is orchestrated as a saga with three steps: reserve inventory, process payment, and confirm order. Each step is idempotent and has a compensating action.

Step 1: Reserve Inventory. When the user initiates checkout, the orchestrator calls the inventory service to reserve each item. The reservation uses optimistic locking: UPDATE inventory SET reserved = reserved + qty, version = version + 1 WHERE sku_id = ? AND version = ? AND (total_stock - reserved) >= qty. If the WHERE clause fails (version changed or insufficient stock), the reservation fails immediately — no overselling. Each reservation has a 15-minute TTL. A background reaper job releases expired reservations and decrements the reserved count.

Step 2: Process Payment. The orchestrator calls the payment service with an idempotency key (a UUID generated by the client and stored in the checkout record). The payment service checks if a payment with this idempotency key already exists — if so, it returns the existing result instead of charging again. This prevents double-charges on retry. The payment service calls Stripe (or similar) with the idempotency key forwarded, so even Stripe deduplicates.

Step 3: Confirm Order. On successful payment, the orchestrator creates an immutable order record, transitions the reservation status from 'active' to 'confirmed' (removing the TTL), and emits an 'order_confirmed' event for downstream services (fulfillment, email notification).

Compensating actions: if payment fails, the orchestrator releases the inventory reservation. If the order service is unreachable after successful payment, the orchestrator retries with exponential backoff (the order creation is idempotent via checkout_id). If retries are exhausted, an alert fires for manual reconciliation — we never auto-refund without human review because the payment already succeeded.

Cart expiry: if the user abandons the checkout, the 15-minute reservation TTL expires, the reaper releases inventory, and the checkout record transitions to 'expired'. An abandoned-cart email is triggered 30 minutes after expiry.

Deep dive (spend 15–25 minutes here)

Payment idempotency is the most critical piece. Without it, a network timeout after Stripe processes the charge leads to a retry that double-charges the customer. The solution has three layers. First, the client generates a UUID idempotency key and includes it in the pay request. Second, our payment service stores (idempotency_key, result) in the payments table with a unique constraint — a retry hits the constraint and returns the stored result. Third, we forward the idempotency key to Stripe, which has its own dedup mechanism. Belt, suspenders, and a parachute.

Inventory reservation under flash-sale load requires careful concurrency control. Optimistic locking works well when contention is moderate — say, 10 concurrent buyers for 1,000 units. But during a flash sale where 10,000 users hit 'buy' on 100 units simultaneously, the retry rate on optimistic lock failures becomes unsustainable. For hot SKUs, I'd switch to a Redis-based atomic decrement: DECRBY inventory:{sku} {qty} and check the result. If the result goes negative, INCRBY to restore and reject. Redis handles 100K ops/sec on a single key, far outperforming a database row lock.

The 15-minute reservation TTL is a trade-off. Too short (5 min) and users entering payment details slowly lose their reservation. Too long (30 min) and scarce inventory is tied up by indecisive shoppers, preventing real buyers from purchasing. I'd start at 15 minutes and show a countdown timer on the checkout page. For high-demand items (detected by reservation rate relative to stock), we could dynamically shorten the TTL to 10 minutes.

The abandoned cart recovery flow is revenue-critical. When a checkout expires, we emit an event that triggers a marketing pipeline: 30 minutes later, send a 'you left items in your cart' email with a deep link back to the checkout. If the user returns, we attempt to re-reserve the items. If stock has been depleted, we show a 'sorry, these items are no longer available' message. Industry data shows abandoned cart emails recover 5-10% of lost revenue.

Webhook reconciliation is the safety net for payment edge cases. Stripe sends webhooks for payment_intent.succeeded, payment_intent.payment_failed, and charge.refunded. Our webhook handler reconciles these events against our payments table. If we have a payment in 'pending' status (we never got the synchronous response) and a webhook arrives saying it succeeded, we complete the checkout asynchronously. This handles the case where our server crashed between Stripe charging the card and our code running the confirmation logic.

Checkout saga orchestrator with compensating rollbacks

import uuid
from enum import Enum
from dataclasses import dataclass


class CheckoutStatus(Enum):
    PENDING = "pending"
    PAID = "paid"
    FAILED = "failed"
    EXPIRED = "expired"


@dataclass
class CheckoutResult:
    order_id: str | None
    status: CheckoutStatus
    error: str | None = None


class CheckoutOrchestrator:
    """Saga-style orchestrator: reserve → charge → confirm.
    Any failure triggers compensating rollbacks in reverse order."""

    def __init__(self, inventory_svc, payment_svc, order_svc):
        self.inventory = inventory_svc
        self.payment = payment_svc
        self.orders = order_svc

    def execute(
        self, checkout_id: str, cart_items: list[dict],
        payment_method: str, idempotency_key: str,
    ) -> CheckoutResult:
        # Step 1: Reserve inventory for each SKU
        reservation_ids = []
        try:
            for item in cart_items:
                rid = self.inventory.reserve(
                    sku=item["sku"], qty=item["qty"], ttl_min=15,
                )
                reservation_ids.append(rid)
        except self.inventory.InsufficientStock as e:
            self._release_all(reservation_ids)  # compensating action
            return CheckoutResult(None, CheckoutStatus.FAILED, str(e))

        # Step 2: Charge the payment (idempotency key prevents double-charge)
        total = sum(i["price"] * i["qty"] for i in cart_items)
        try:
            payment = self.payment.charge(
                amount_cents=total,
                method=payment_method,
                idempotency_key=idempotency_key,
            )
        except self.payment.PaymentFailed as e:
            self._release_all(reservation_ids)  # compensating action
            return CheckoutResult(None, CheckoutStatus.FAILED, str(e))

        # Step 3: Create order and confirm reservations
        order_id = str(uuid.uuid4())
        self.orders.create(
            order_id=order_id, checkout_id=checkout_id,
            items=cart_items, total_cents=total,
            payment_ref=payment.provider_ref,
        )
        for rid in reservation_ids:
            self.inventory.confirm(rid)
        return CheckoutResult(order_id, CheckoutStatus.PAID)

    def _release_all(self, reservation_ids: list[str]):
        """Best-effort release; reaper job cleans up any missed ones."""
        for rid in reservation_ids:
            try:
                self.inventory.release(rid)
            except Exception:
                pass  # log and alert; TTL-based reaper will clean up
use std::collections::HashMap;

#[derive(Debug)]
enum CheckoutStatus { Pending, Paid, Failed, Expired }

#[derive(Debug)]
struct CheckoutResult {
    order_id: Option<String>,
    status: CheckoutStatus,
    error: Option<String>,
}

struct CartItem { sku: String, qty: u32, price_cents: u64 }

/// Saga-style orchestrator: reserve → charge → confirm.
/// Any step failure triggers compensating rollbacks in reverse.
struct CheckoutOrchestrator;

impl CheckoutOrchestrator {
    fn execute(
        &self, checkout_id: &str, items: &[CartItem],
        payment_method: &str, idempotency_key: &str,
    ) -> CheckoutResult {
        // Step 1: Reserve inventory for each SKU
        let mut reservations: Vec<String> = Vec::new();
        for item in items {
            match self.reserve_inventory(&item.sku, item.qty) {
                Ok(rid) => reservations.push(rid),
                Err(e) => {
                    self.release_all(&reservations); // compensate
                    return CheckoutResult {
                        order_id: None, status: CheckoutStatus::Failed,
                        error: Some(e),
                    };
                }
            }
        }

        // Step 2: Charge payment (idempotency key prevents double-charge)
        let total: u64 = items.iter().map(|i| i.price_cents * i.qty as u64).sum();
        let payment_ref = match self.charge(total, payment_method, idempotency_key) {
            Ok(r) => r,
            Err(e) => {
                self.release_all(&reservations); // compensate
                return CheckoutResult {
                    order_id: None, status: CheckoutStatus::Failed,
                    error: Some(e),
                };
            }
        };

        // Step 3: Create order, confirm reservations
        let order_id = uuid::Uuid::new_v4().to_string();
        for rid in &reservations { self.confirm_reservation(rid); }
        CheckoutResult { order_id: Some(order_id), status: CheckoutStatus::Paid, error: None }
    }

    // Placeholder trait methods — in production these call external services
    fn reserve_inventory(&self, _sku: &str, _qty: u32) -> Result<String, String> { Ok("r1".into()) }
    fn charge(&self, _cents: u64, _m: &str, _k: &str) -> Result<String, String> { Ok("pay_ref".into()) }
    fn confirm_reservation(&self, _rid: &str) {}

    /// Best-effort release; TTL reaper cleans up any missed ones
    fn release_all(&self, reservations: &[String]) {
        for rid in reservations {
            let _ = self.release(rid); // swallow errors, log in production
        }
    }
    fn release(&self, _rid: &str) -> Result<(), String> { Ok(()) }
}
#import <Foundation/Foundation.h>
#include <vector>
#include <string>

typedef NS_ENUM(NSInteger, CheckoutStatus) {
    CheckoutPending, CheckoutPaid, CheckoutFailed, CheckoutExpired
};

// Saga orchestrator: reserve → charge → confirm.
// Any step failure triggers compensating rollbacks.
@interface CheckoutOrchestrator : NSObject
- (NSDictionary *)executeCheckout:(NSString *)checkoutID
                            items:(NSArray<NSDictionary *> *)items
                           method:(NSString *)method
                    idempotencyKey:(NSString *)key;
@end

@implementation CheckoutOrchestrator

- (NSDictionary *)executeCheckout:(NSString *)checkoutID
                            items:(NSArray<NSDictionary *> *)items
                           method:(NSString *)method
                    idempotencyKey:(NSString *)key {
    // Step 1: Reserve inventory for each SKU
    NSMutableArray<NSString *> *reservations = [NSMutableArray new];
    for (NSDictionary *item in items) {
        NSString *rid = [self _reserve:item[@"sku"] qty:[item[@"qty"] intValue]];
        if (!rid) {
            [self _releaseAll:reservations]; // compensating rollback
            return @{@"status": @(CheckoutFailed), @"error": @"Insufficient stock"};
        }
        [reservations addObject:rid];
    }

    // Step 2: Charge payment (idempotency key prevents double-charge)
    NSInteger total = 0;
    for (NSDictionary *item in items)
        total += [item[@"price"] integerValue] * [item[@"qty"] integerValue];
    NSString *payRef = [self _charge:total method:method key:key];
    if (!payRef) {
        [self _releaseAll:reservations]; // compensating rollback
        return @{@"status": @(CheckoutFailed), @"error": @"Payment failed"};
    }

    // Step 3: Create order, confirm all reservations
    NSString *orderID = [NSUUID UUID].UUIDString;
    for (NSString *rid in reservations)
        [self _confirm:rid];
    return @{@"order_id": orderID, @"status": @(CheckoutPaid)};
}

// Best-effort release; reaper cleans up any missed reservations
- (void)_releaseAll:(NSArray<NSString *> *)rids {
    for (NSString *rid in rids)
        @try { [self _release:rid]; } @catch (id e) { /* log */ }
}

// Placeholder methods — production calls external services
- (NSString *)_reserve:(NSString *)sku qty:(int)qty { return @"r1"; }
- (NSString *)_charge:(NSInteger)cents method:(NSString *)m key:(NSString *)k { return @"pay"; }
- (void)_confirm:(NSString *)rid {}
- (void)_release:(NSString *)rid {}
@end

Request path / sequence

Trade-offs I'd say out loud

Reserve at cart vs checkout

Cart reservation locks stock longer but prevents disappointment; checkout reservation is leaner.

Optimistic vs pessimistic locking

Optimistic fails fast but retries under contention; pessimistic serializes but is slower.

Sync payment vs async

Sync gives immediate feedback but blocks the user; async is resilient but adds status polling.

Saga vs 2PC

Saga is more resilient and doesn't lock resources across services; 2PC is stronger but fragile.

Auto-refund vs manual review

Auto-refund is faster but risks refunding valid charges; manual is safer but slower.

Where it usually breaks

  • Payment succeeds but order service is down — money charged, no order record. Requires webhook reconciliation.
  • Reservation TTL expires during slow payment entry — user pays for out-of-stock items.
  • Double-click on 'Pay' button sends two requests — without idempotency key, user is double-charged.
  • Flash sale: 10K concurrent reservations for 100 units — optimistic lock retry storm.
  • Price changed between add-to-cart and checkout — user charged a different amount than displayed.
  • Reaper job and payment confirmation race — reservation released just as payment succeeds.
  • Stripe webhook arrives before synchronous response — duplicate processing if not idempotent.
