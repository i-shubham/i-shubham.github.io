Design a live video streaming platform

YouTube Live style streaming is ingest plus transcode plus CDN — and a celebrity going live will melt any single-region plan.

60-minute agenda

How I'd open the discussion

I'd nail the latency SLA first. Traditional HLS with 6-second segments sits around 20–30 seconds glass-to-glass — fine for concerts, unacceptable for auctions or sports betting. Low-latency HLS or WebRTC-to-CDN hybrids target 2–5 seconds. That choice changes ingest protocol, segmenter settings, and CDN config.

The pipeline is asymmetric: one publisher (or a small multi-cam set) and millions of viewers. So we optimize ingest reliability and encode quality on the left, and massive fan-out on the right. Viewers never talk to the transcoder directly — they pull segments from a CDN, ideally with an origin shield so hot streams do not stampede the packager.

I'd sketch RTMP/SRT ingest → live transcoder ladder → CMAF/HLS packager → CDN, then deep-dive adaptive bitrate and how we survive a 1M-viewer spike when a celebrity goes live.

Open questions worth asking

  • Target glass-to-glass latency (30s classic vs <5s low-latency)?
  • One-to-many broadcast only, or interactive co-hosts?
  • Do we archive to VOD automatically?
  • Max concurrent viewers on a single stream?
  • Geographic distribution of audience?
  • Is live chat in scope?
  • DRM / signed URLs for paid streams?
  • Mobile uplink quality — assume unstable publisher networks?
  • Multi-bitrate ladder requirements (240p–1080p)?
  • DVR: can viewers scrub back in the live window?

Scope I'd lock first

  • In: one-to-many live broadcast, ABR ladder, CDN delivery, stream lifecycle APIs.
  • In: optional live chat as a side system, basic health metrics.
  • Out: full video-on-demand catalog UX, recommendation ranking, ads insertion UI.
  • Defer: WebRTC ultra-low-latency interactive mode unless interviewer pushes sports betting latency.

Functional requirements

Publish

Watch

ABR

Archive

Optionally record the live event to VOD object storage.

Non-functional / rough numbers

Latency

~15–25s standard HLS; ~2–5s with LL-HLS if required.

Availability

99.9% for ingest; CDN edges absorb regional blips for viewers.

Scale

Hot stream: 1M concurrent viewers without origin collapse.

Quality

Startup < 2s on warm CDN; rebuffering ratio < 1%.

Capacity estimate (do this on the board)

Viewer bandwidth

1M viewers × 3 Mbps avg ABR ≈ 3 Tbps egress — must be CDN, not origin.

Ingest

One publisher at 6–12 Mbps to ingest POP; redundant second ingest optional.

Transcode

Ladder e.g. 1080p/720p/480p/360p → ~4× realtime CPU/GPU per stream.

Segments

2s segments × 4 renditions × 1M viewers cached at edge — origin sees tiny fraction.

Chat

1M viewers × 0.01 msgs/sec = 10K chat msgs/sec — separate WS fleet.

Storage

2-hour 1080p archive ≈ tens of GB per event after packaging.

Approach / design notes

Creators authenticate and receive a region-local ingest endpoint plus a stream key. OBS or a mobile encoder pushes RTMP/SRT to an ingest POP. The ingest gateway authenticates the key, terminates the publish session, and forwards elementary streams to a live transcoder worker assigned to that stream_id.

The transcoder produces an ABR ladder (aligned GOPs). A packager cuts CMAF segments and updates the media playlist. Segments land in object storage / origin; CDN edges pull through an origin shield. Players request the master playlist and switch renditions based on bandwidth. For low-latency mode, use partial segments (LL-HLS) and shorter playlists — at the cost of less CDN aggregation efficiency and more request QPS.

Control plane (stream CRUD, keys, viewer counts) is orthogonal to the media plane. Viewer counts are approximate: edges report samples to a metrics aggregator. Live chat is a separate pub/sub channel keyed by stream_id — reuse patterns from chat messaging, with aggressive fan-out batching for mega-streams.

Deep dive (spend 15–25 minutes here)

Latency is mostly buffer. Classic HLS waits for full segments and holds 3 segments in the player buffer. Cutting segment duration from 6s to 2s helps but increases encode overhead and CDN request rate. LL-HLS adds blocking playlist reloads and chunked transfer of partial segments so players start before the segment finishes — explain the trade: more origin/CDN load, harder cache hit ratios.

GOP alignment across renditions matters for seamless ABR switches. If keyframes are not aligned, the player must wait or glitch when dropping from 1080p to 480p. Transcoders should force aligned IDR frames on segment boundaries.

Failure handling: if the publisher disconnects briefly, keep the stream 'live' with a slate or last-frame hold for 15–30s before ending — reconnects are common on mobile uplink. Dual ingest (primary + backup) lets the transcoder failover without viewers noticing. Transcoder crash: checkpoint packager state and relaunch on another worker using the still-open ingest session or a short reconnect.

Hot-stream protection: never let edges stampede origin. Origin shield (regional mid-tier cache), request collapsing, and longer playlist caching for non-LL modes. Signed playback cookies prevent hotlinking. For chat on mega-streams, switch from push-all to sampled delivery or client-side polling of a rolling window so one viral comment does not fan out to 1M sockets from a single publisher path.

ABR playlist helper and ingest auth sketch

import hashlib
import hmac
import time
from dataclasses import dataclass
from typing import List


@dataclass
class Rendition:
    name: str
    bandwidth: int  # bits/sec
    path: str


def master_playlist(stream_id: str, renditions: List[Rendition]) -> str:
    lines = ["#EXTM3U", "#EXT-X-VERSION:3"]
    for r in renditions:
        lines.append(
            f'#EXT-X-STREAM-INF:BANDWIDTH={r.bandwidth},NAME="{r.name}"'
        )
        lines.append(f"/live/{stream_id}/{r.path}/index.m3u8")
    return "\n".join(lines) + "\n"


class IngestAuth:
    """Validate stream keys on RTMP connect; short-lived publish tokens."""

    def __init__(self, secret: bytes, key_store):
        self.secret = secret
        self.key_store = key_store  # stream_id → key_hash

    def publish_allowed(self, stream_id: str, stream_key: str) -> bool:
        expected = self.key_store.get(stream_id)
        if not expected:
            return False
        digest = hashlib.sha256(stream_key.encode()).hexdigest()
        return hmac.compare_digest(digest, expected)

    def sign_playback(self, stream_id: str, viewer_id: str, ttl_s: int = 3600) -> str:
        exp = int(time.time()) + ttl_s
        msg = f"{stream_id}:{viewer_id}:{exp}".encode()
        sig = hmac.new(self.secret, msg, hashlib.sha256).hexdigest()
        return f"{exp}.{sig}"

    def verify_playback(self, stream_id: str, viewer_id: str, token: str) -> bool:
        try:
            exp_s, sig = token.split(".", 1)
            exp = int(exp_s)
        except ValueError:
            return False
        if exp < time.time():
            return False
        msg = f"{stream_id}:{viewer_id}:{exp}".encode()
        expected = hmac.new(self.secret, msg, hashlib.sha256).hexdigest()
        return hmac.compare_digest(sig, expected)
use std::collections::HashMap;
use std::time::{SystemTime, UNIX_EPOCH};

struct Rendition {
    name: String,
    bandwidth: u32,
    path: String,
}

fn master_playlist(stream_id: &str, renditions: &[Rendition]) -> String {
    let mut out = String::from("#EXTM3U\n#EXT-X-VERSION:3\n");
    for r in renditions {
        out.push_str(&format!(
            "#EXT-X-STREAM-INF:BANDWIDTH={},NAME=\"{}\"\n/live/{}/{}/index.m3u8\n",
            r.bandwidth, r.name, stream_id, r.path
        ));
    }
    out
}

struct IngestAuth {
    // demo: sha256 hex of raw key; production uses a real keyed MAC crate
    keys: HashMap<String, String>,
}

impl IngestAuth {
    fn publish_allowed(&self, stream_id: &str, stream_key: &str) -> bool {
        match self.keys.get(stream_id) {
            Some(expected) => simple_hash(stream_key) == *expected,
            None => false,
        }
    }

    fn sign_playback(&self, stream_id: &str, viewer_id: &str, ttl_s: u64) -> String {
        let exp = now_secs() + ttl_s;
        let msg = format!("{}:{}:{}", stream_id, viewer_id, exp);
        format!("{}.{}", exp, simple_hash(&msg))
    }
}

fn now_secs() -> u64 {
    SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_secs()
}

fn simple_hash(s: &str) -> String {
    // Placeholder for interview board — use HMAC-SHA256 in production
    format!("{:x}", s.bytes().fold(0u64, |a, b| a.wrapping_mul(31).wrapping_add(b as u64)))
}

Request path / sequence

Trade-offs I'd say out loud

HLS vs WebRTC

HLS scales via CDN; WebRTC is lower latency but harder to fan out to millions.

Segment duration

Shorter segments lower latency, raise request rate and encode overhead.

GPU vs CPU transcode

GPU packs denser density for live ladders; CPU is simpler ops and fallback.

Exact vs approx viewers

Exact counts need global aggregation; approximate edge sampling is enough for UI.

Where it usually breaks

  • Celebrity spike without origin shield — packager CPU / disk melts on segment stampedes.
  • Publisher mobile uplink flaps — stream flaps live/offline without reconnect grace.
  • Misaligned GOPs — ABR switches cause freezes or A/V desync.
  • LL-HLS enabled globally — cache hit ratio collapses, CDN bill explodes.
  • Chat fan-out on 1M viewers treated like 1:1 messaging — gateway fleet saturates.
  • Stream key leak — unauthorized publish hijacks the live event.
