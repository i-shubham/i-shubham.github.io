Design a rate limiter

Rate limits are easy in one process and awkward across a fleet — especially when product wants different budgets per API key, IP, and user.

60-minute agenda

How I'd open the discussion

I'd start by clarifying where the rate limiter lives. If it is at the API gateway (like Kong or Envoy), it applies globally before requests reach application servers. If it is a library inside each service, it is simpler but harder to enforce consistently across a fleet. For most production systems I'd choose the gateway approach with a shared Redis backend.

The next question is granularity. Do we rate limit by IP address, authenticated user, API key, or some combination? In practice you need at least two tiers: an IP-based limit to stop brute-force attacks from unauthenticated clients, and a user/API-key limit for authenticated traffic with different tiers (free: 100 req/min, pro: 1000 req/min).

Then I'd walk through the algorithm trade-offs — token bucket for smooth traffic, sliding window counter for simplicity, and why fixed windows have the boundary burst problem.

Open questions worth asking

  • Is this a gateway-level or application-level limiter?
  • What dimensions do we limit on — IP, user ID, API key, endpoint?
  • Hard limit (reject immediately) or soft limit (queue/degrade)?
  • What response should rejected requests get — 429 with Retry-After?
  • Do we need per-endpoint limits (e.g., /login stricter than /search)?
  • What is the fleet size — how many API servers share the limit?
  • Do we need to support tiered rate plans (free, pro, enterprise)?
  • Is there a global rate limit in addition to per-client limits?
  • How should we handle Redis outages — fail open or fail closed?
  • Do we need real-time dashboard visibility into rate limit hits?

Scope I'd lock first

  • In: token bucket and sliding window counter algorithms, Redis-backed distributed state.
  • In: per-IP and per-user limits, 429 responses with Retry-After headers.
  • Out: DDoS mitigation (that is a CDN/WAF concern), adaptive ML-based throttling.
  • Defer: cost-based rate limiting (charging per request above a threshold).

Functional requirements

Check

For each incoming request, decide allow or reject based on current counter state.

Configure

Admin API to set/update rate limit rules per dimension and tier.

Headers

Return X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, Retry-After.

Monitor

Emit metrics for total requests, allowed, and rejected per rule.

Non-functional / rough numbers

Latency overhead

< 2 ms per request — the limiter must not become the bottleneck.

Accuracy

Within 1-2% of the configured limit — small overcount is acceptable.

Availability

Limiter failure should fail open (allow traffic) to avoid outages.

Consistency

Eventual — a brief burst above the limit during a Redis hiccup is acceptable.

Approach / design notes

I'd implement a sliding window counter algorithm backed by Redis. The idea is to divide time into fixed sub-windows (say, 1/60th of the full window) and maintain a counter per sub-window. To check the current rate, we sum the counters from sub-windows that overlap with the trailing window. This avoids the fixed-window boundary burst problem where a client sends the full limit at :59 and again at :00, effectively doubling throughput.

Each request triggers a Lua script on Redis that atomically increments the current sub-window counter and sums the relevant sub-windows. If the sum exceeds the limit, the script returns REJECTED with the reset timestamp. Using a Lua script ensures the read-increment-check is atomic — no race condition between two servers checking the same key.

The alternative is a token bucket: each client has a bucket with N tokens, refilled at a fixed rate. A request consumes one token. This is better for smoothing bursty traffic — a client can burst up to the bucket size and then is limited to the refill rate. I'd choose sliding window counter for simplicity at the gateway and offer token bucket as an option for specific endpoints that need burst control.

For multi-tier support, the gateway looks up the client's tier (free, pro, enterprise) from a local cache (refreshed every 30 seconds from a tier service) and selects the appropriate rule. Rules are evaluated in order: per-endpoint first, then per-user, then per-IP. The most specific matching rule wins.

If Redis is unreachable, the limiter fails open — all requests are allowed. This prevents the rate limiter from becoming a single point of failure. We'd monitor Redis availability closely and have a local in-memory fallback (per-server token bucket with conservative limits) for brief outages. The fallback is less accurate since it does not share state across servers, but it prevents total loss of rate limiting.

Deep dive (spend 15–25 minutes here)

The fixed-window boundary burst is the classic gotcha. If the window is 60 seconds and the limit is 100, a client can send 100 requests at second 59 of window N, then 100 more at second 0 of window N+1 — 200 requests in 2 seconds. The sliding window counter fixes this by weighting the previous window's count. If 70% of the previous window overlaps with the current trailing window, we compute: previous_count × 0.7 + current_count. This gives a smooth approximation with at most a ~1% error under uniform traffic.

The Redis Lua script is critical for correctness in a distributed setting. Without it, two API servers could both read the counter as 99 (limit 100), both increment to 100, and both allow the request — exceeding the limit by 1. The Lua script runs atomically on the Redis server: 1. INCR the current sub-window key 2. Sum all sub-window keys in the trailing window 3. If sum > limit, DECR back and return REJECTED 4. Otherwise return ALLOWED with remaining count This guarantees serializability per client key.

The token bucket algorithm is better understood as a state machine with two variables: tokens_remaining and last_refill_timestamp. On each request, we compute how many tokens to add based on elapsed time since last_refill, cap at bucket_size, then subtract one if tokens > 0. The beauty is that we only need to store two numbers per client in Redis, and refill is implicit (computed on demand, not via a background job). The downside is that burst size equals bucket size, which might be too permissive for some endpoints.

Multi-tier rule evaluation needs careful ordering. A single request might match an IP rule, a user rule, and an endpoint-specific rule. I'd evaluate all matching rules and reject if any rule is exceeded — this prevents a user from bypassing their per-endpoint limit by staying under the global user limit. The headers should reflect the most restrictive matching rule so the client knows which limit they are approaching.

Distributed rate limiting across multiple data centers is much harder. If each region has its own Redis, a global limit of 1000 req/min cannot be enforced by giving each region 500 — traffic patterns are uneven. Options include a single global Redis (adds cross-region latency), periodic sync between regions (allows brief overcount), or client-side estimation with server-side correction. For most systems, a single Redis cluster in a central region with < 5 ms RTT to API servers is sufficient.

Sliding window (sorted set) and token bucket implementations

import time
import redis

# Atomic sliding-window limiter implemented as a Redis Lua script.
# Uses a sorted set keyed by timestamp; stale entries are pruned each call.
SLIDING_WINDOW_LUA = """
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

redis.call("ZREMRANGEBYSCORE", key, 0, now - window)
local count = redis.call("ZCARD", key)
if count < limit then
    redis.call("ZADD", key, now, now .. ":" .. math.random(1000000))
    redis.call("EXPIRE", key, window)
    return {1, limit - count - 1}  -- allowed, remaining
end
return {0, 0}  -- rejected, 0 remaining
"""


class SlidingWindowLimiter:
    def __init__(self, redis_client: redis.Redis):
        self.r = redis_client
        self.script = self.r.register_script(SLIDING_WINDOW_LUA)

    def allow(self, client_id: str, limit: int, window_sec: int) -> dict:
        key = f"rl:{client_id}"
        now = time.time()
        result = self.script(keys=[key], args=[window_sec, limit, now])
        allowed, remaining = int(result[0]), int(result[1])
        return {
            "allowed": bool(allowed),
            "remaining": remaining,
            "reset_at": int(now) + window_sec,
        }


class TokenBucket:
    """Classic token bucket backed by a Redis hash.
    Tokens refill at a constant rate up to a max capacity."""

    def __init__(self, redis_client: redis.Redis):
        self.r = redis_client

    def allow(self, client_id: str, capacity: int, refill_rate: float) -> bool:
        key = f"tb:{client_id}"
        now = time.time()
        pipe = self.r.pipeline()
        pipe.hmget(key, "tokens", "last_refill")
        state = pipe.execute()[0]
        tokens = float(state[0] or capacity)
        last = float(state[1] or now)
        elapsed = now - last
        # Refill tokens proportional to elapsed time, capped at capacity
        tokens = min(capacity, tokens + elapsed * refill_rate)
        if tokens < 1:
            return False
        tokens -= 1
        self.r.hset(key, mapping={"tokens": tokens, "last_refill": now})
        self.r.expire(key, int(capacity / refill_rate) + 60)
        return True
use std::collections::BTreeMap;
use std::time::{Instant, Duration};

/// Sliding-window rate limiter: tracks request timestamps in a BTreeMap,
/// prunes entries outside the window on each check.
struct SlidingWindowLimiter {
    windows: std::collections::HashMap<String, BTreeMap<u128, u32>>,
}
impl SlidingWindowLimiter {
    fn new() -> Self { Self { windows: Default::default() } }

    fn allow(&mut self, client: &str, limit: usize, window: Duration) -> bool {
        let now = std::time::SystemTime::now()
            .duration_since(std::time::UNIX_EPOCH).unwrap().as_millis();
        let cutoff = now - window.as_millis();
        let entry = self.windows.entry(client.into()).or_default();
        // Remove timestamps outside the current window
        let stale: Vec<_> = entry.range(..cutoff).map(|(&k, _)| k).collect();
        for k in stale { entry.remove(&k); }
        if entry.len() < limit {
            entry.insert(now, 1);
            true
        } else {
            false // rate exceeded
        }
    }
}

/// Token bucket: tokens refill at a constant rate, consumed on each request.
struct TokenBucket {
    tokens: f64,
    capacity: f64,
    refill_rate: f64,   // tokens per second
    last_refill: Instant,
}
impl TokenBucket {
    fn new(capacity: f64, refill_rate: f64) -> Self {
        Self { tokens: capacity, capacity, refill_rate, last_refill: Instant::now() }
    }
    fn allow(&mut self) -> bool {
        let now = Instant::now();
        let elapsed = now.duration_since(self.last_refill).as_secs_f64();
        // Refill proportional to elapsed time, capped at capacity
        self.tokens = (self.tokens + elapsed * self.refill_rate).min(self.capacity);
        self.last_refill = now;
        if self.tokens >= 1.0 {
            self.tokens -= 1.0;
            true
        } else {
            false
        }
    }
}
#import <Foundation/Foundation.h>
#include <map>
#include <string>
#include <chrono>
#include <mutex>

// Sliding-window limiter: prunes old timestamps, counts recent ones
class SlidingWindowLimiter {
    std::map<double, int> _timestamps; // ts → count
    std::mutex _mu;
public:
    bool allow(int limit, double windowSec) {
        std::lock_guard<std::mutex> lock(_mu);
        double now = CFAbsoluteTimeGetCurrent();
        double cutoff = now - windowSec;
        // Prune entries outside the window
        _timestamps.erase(_timestamps.begin(), _timestamps.upper_bound(cutoff));
        int total = 0;
        for (auto &kv : _timestamps) total += kv.second;
        if (total < limit) {
            _timestamps[now]++;
            return true;
        }
        return false;
    }
};

@end

}

    if (self = [super init]) {
        _tokens = cap; _capacity = cap;
        _refillRate = rate; _lastRefill = CFAbsoluteTimeGetCurrent();
    }
    return self;
}
- (BOOL)allow {
    CFAbsoluteTime now = CFAbsoluteTimeGetCurrent();
    double elapsed = now - _lastRefill;
    // Refill proportional to elapsed time, capped at capacity
    _tokens = fmin(_capacity, _tokens + elapsed * _refillRate);
    _lastRefill = now;
    if (_tokens >= 1.0) { _tokens -= 1.0; return YES; }
    return NO;
}

Request path / sequence

Trade-offs I'd say out loud

Sliding window vs token bucket

Sliding window is precise per window; token bucket smooths bursts but is harder to reason about.

Central Redis vs local counters

Central is accurate but adds ~1 ms RTT; local is fast but inaccurate for shared limits.

Fail open vs fail closed

Fail open prevents outages but allows unlimited traffic during Redis downtime.

Lua script vs multi-step

Lua is atomic but opaque; multi-step is readable but has race conditions.

Where it usually breaks

  • Redis goes down — if fail-open, rate limiting is effectively disabled system-wide.
  • Clock drift between API servers — sub-window alignment breaks, causing under/over counting.
  • Hot API key saturates a Redis shard — one heavy client slows rate checks for all clients on that shard.
  • Lua script timeout under load — Redis blocks other operations while the script runs.
  • Rule cache stale after admin update — old limits enforced for up to 30 seconds.
