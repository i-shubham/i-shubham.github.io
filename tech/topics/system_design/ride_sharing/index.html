System Design · Hard · ~60 min

Design a ride-sharing system

Uber-style matching is geo index plus dispatch race — rush hour and GPS jitter will expose every naive nearest-driver query.

60-minute agenda

How I'd open the discussion

I'd lock geography and product. One city is a different system from a global map. I'd also ask whether drivers accept offers or the system assigns (Uber-style offer with timeout vs fully automatic dispatch). Pooling and scheduled rides change matching from "nearest idle car" to a combinatorial problem — I'd defer those unless asked.

The hot path is: drivers stream GPS, riders request a trip, a matcher finds nearby eligible drivers, an offer is exclusive for a few seconds, then the trip goes through pickup → en-route → complete → payment. Almost every bug is either stale location or two riders winning the same driver.

I'd sketch location ingest, a geo index sharded by city/cell, a matching service with leases, and a trip state machine — then deep-dive how we avoid double dispatch under retries.

Open questions worth asking

  • How many cities and peak concurrent trips?
  • Driver accept/reject, or silent assignment?
  • Vehicle types (bike, XL) and filters (accessibility)?
  • Is ride pooling (shared trips) in scope?
  • Match SLA — p50 seconds to a driver?
  • Do we show nearby cars on the map before request?
  • Payments: in-app card, cash, wallets?
  • Cancellation windows and no-show fees?
  • Cross-city trips and airport queues?
  • Safety: share trip, SOS, background checks — in or out?

Scope I'd lock first

  • In: GPS ingest, nearby-driver index, offer-based matching, trip lifecycle, basic surge.
  • In: ETA using a routing service (treat maps as a dependency).
  • Out: food delivery, micromobility IoT, full fraud ML stack.
  • Defer: pooling, scheduled rides, driver incentives marketplace.

Functional requirements

Track drivers

Idle/en-route drivers ping location every 2–4s; riders less often during a trip.

Request ride

Pickup/dropoff, product type → match or waitlist with ETA.

Dispatch

Offer to one driver at a time (or small batch) with a timeout; exclusive lock.

Trip

States: matching, assigned, arriving, in_trip, completed, cancelled.

Fare

Quote up front; settle on complete with surge and wait time.

Non-functional / rough numbers

Match latency

p95 < 5s to first offer in a dense city; degrade to waitlist, not silent fail.

Location freshness

Idle driver location < 5s old in the index; drop pings older than that.

Correctness

A driver is in at most one active trip; offers are fenced by a lease.

Availability

Matching can degrade per city; payments must still settle completed trips.

Capacity estimate (do this on the board)

Drivers online

Global 5M online drivers; a large city 50K online at peak.

GPS ingest

5M × 1 ping / 3s ≈ 1.7M pings/sec globally — shard by city, never one Kafka topic.

Ping size

~100 bytes → ~170 MB/s raw; batch and downsample when idle on a highway cell.

Trips

10M trips/day ≈ 115/sec avg, 10× peak in evening; matching QPS is bursty.

Geo index

50K drivers / city in Redis/memory on a cell grid; not a row-per-ping SQL table.

Map ETA

Cache ETAs for hot cells; do not call routing for every map tile refresh.

Approach / design notes

Partition the world by city (or metro). Each city owns a location service and a matcher. Drivers connect to the nearest edge; pings update a cell index (geohash or H3). Cells are small enough that "nearby" is k-ring lookup, not a global scan. Idle drivers are indexed; en-route drivers may stay in a lighter map for ETA to rider but are not matchable.

On request, the matcher loads candidate cells around pickup, filters by product and rating/constraints, ranks by ETA (routing service or haversine + traffic cache), and sends an exclusive offer. The driver document gets a lease: offer_id + expiry. If they accept, CAS the trip to assigned and the driver to busy. If they timeout, release and try the next candidate. Fan-out to many drivers at once increases match speed but creates more decline noise and thundering races — start with sequential or small batches of 2–3.

Trip state lives in a strongly consistent store per city (or a trip-id hash with city affinity). Location pings are eventually consistent and lossy. Payments are a separate idempotent flow on complete. Surge is computed from unmatched demand vs idle supply per cell over a short window and cached for quotes.

Deep dive (spend 15–25 minutes here)

Double-booking is the classic failure. Driver accepts two offers due to retries, or two matchers in a split-brain city. Fence with a version on the driver record: UPDATE drivers SET trip_id=?, version=version+1 WHERE id=? AND status='idle' AND version=?. Offers carry the version. Idempotency keys on accept. Matcher leadership per city (or sticky consistent hash of trip_id to a matcher worker with a lock) so two workers do not dispatch the same trip.

Stale GPS: phones sleep, tunnels, spoofing. Treat location as (point, timestamp, accuracy). Ignore pings older than T or with huge jumps (teleport). Map-match to roads if you have the cycles. For matching, slightly stale is OK; for "car arriving" you want the latest ping plus heading.

Hot downtown cells: 5K idle drivers in a few hexes. Rank with a heap of size k, not a sort of 5K ETAs. Cache traffic-aware ETA from cell centroid to pickup for a few seconds. Airport queues are a special matching mode (FIFO in a geofence) — mention it so the interviewer knows you have seen the product wart.

Failure: if the matcher dies, in-flight offers expire and a new matcher rebuilds from trip=matching plus the live index (index is reconstructible from last pings). If a city ingest partition lags, stop matching on rotten data and show longer ETAs rather than dispatching ghosts.

Geo index and exclusive offer lease

import math
import time
from dataclasses import dataclass
from typing import Dict, List, Optional, Set, Tuple

CELL = 0.01  # ~1km; production: H3 resolution 8/9


def cell_key(lat: float, lng: float) -> Tuple[int, int]:
    return (int(lat / CELL), int(lng / CELL))


def neighbors(cell: Tuple[int, int], rings: int = 1) -> List[Tuple[int, int]]:
    x, y = cell
    return [(x + dx, y + dy)
            for dx in range(-rings, rings + 1)
            for dy in range(-rings, rings + 1)]


def haversine_km(a: Tuple[float, float], b: Tuple[float, float]) -> float:
    r = 6371.0
    p1, p2 = math.radians(a[0]), math.radians(b[0])
    dphi = math.radians(b[0] - a[0])
    dl = math.radians(b[1] - a[1])
    h = math.sin(dphi / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dl / 2) ** 2
    return 2 * r * math.asin(math.sqrt(h))


@dataclass
class Driver:
    driver_id: str
    lat: float
    lng: float
    ts: float
    version: int = 0
    status: str = "idle"  # idle | offered | busy
    offer_until: float = 0.0


class CityIndex:
    def __init__(self, stale_s: float = 5.0):
        self.stale_s = stale_s
        self.drivers: Dict[str, Driver] = {}
        self.cells: Dict[Tuple[int, int], Set[str]] = {}

    def upsert_ping(self, driver_id: str, lat: float, lng: float, ts: float):
        old = self.drivers.get(driver_id)
        if old:
            prev = cell_key(old.lat, old.lng)
            self.cells.get(prev, set()).discard(driver_id)
        d = old or Driver(driver_id, lat, lng, ts)
        d.lat, d.lng, d.ts = lat, lng, ts
        self.drivers[driver_id] = d
        self.cells.setdefault(cell_key(lat, lng), set()).add(driver_id)

    def _fresh_idle(self, driver_id: str, now: float) -> Optional[Driver]:
        d = self.drivers.get(driver_id)
        if not d or d.status != "idle" or now - d.ts > self.stale_s:
            return None
        return d

    def lease_nearest(self, pickup: Tuple[float, float], now: float, ttl_s: float = 8.0) -> Optional[Driver]:
        ranked: List[Tuple[float, Driver]] = []
        for cell in neighbors(cell_key(*pickup), rings=2):
            for did in list(self.cells.get(cell, ())):
                d = self._fresh_idle(did, now)
                if d:
                    ranked.append((haversine_km(pickup, (d.lat, d.lng)), d))
        ranked.sort(key=lambda x: x[0])
        for _, d in ranked[:20]:
            if d.status != "idle":
                continue
            d.status = "offered"
            d.version += 1
            d.offer_until = now + ttl_s
            return d
        return None

    def accept(self, driver_id: str, version: int, now: float) -> bool:
        d = self.drivers.get(driver_id)
        if not d or d.version != version or d.status != "offered":
            return False
        if now > d.offer_until:
            d.status = "idle"
            return False
        d.status = "busy"
        return True

    def expire_offers(self, now: float):
        for d in self.drivers.values():
            if d.status == "offered" and now > d.offer_until:
                d.status = "idle"
use std::collections::{HashMap, HashSet};

const CELL: f64 = 0.01;
const STALE_S: f64 = 5.0;

fn cell_key(lat: f64, lng: f64) -> (i32, i32) {
    ((lat / CELL) as i32, (lng / CELL) as i32)
}

fn neighbors(cell: (i32, i32), rings: i32) -> Vec<(i32, i32)> {
    let mut out = Vec::new();
    for dx in -rings..=rings {
        for dy in -rings..=rings {
            out.push((cell.0 + dx, cell.1 + dy));
        }
    }
    out
}

fn haversine_km(a: (f64, f64), b: (f64, f64)) -> f64 {
    let r = 6371.0;
    let p1 = a.0.to_radians();
    let p2 = b.0.to_radians();
    let dphi = (b.0 - a.0).to_radians();
    let dl = (b.1 - a.1).to_radians();
    let h = (dphi / 2.0).sin().powi(2)
        + p1.cos() * p2.cos() * (dl / 2.0).sin().powi(2);
    2.0 * r * h.sqrt().asin()
}

#[derive(Clone)]
struct Driver {
    driver_id: String,
    lat: f64,
    lng: f64,
    ts: f64,
    version: u64,
    status: &'static str, // idle | offered | busy
    offer_until: f64,
}

struct CityIndex {
    drivers: HashMap<String, Driver>,
    cells: HashMap<(i32, i32), HashSet<String>>,
}

impl CityIndex {
    fn upsert_ping(&mut self, driver_id: &str, lat: f64, lng: f64, ts: f64) {
        if let Some(old) = self.drivers.get(driver_id) {
            let prev = cell_key(old.lat, old.lng);
            if let Some(set) = self.cells.get_mut(&prev) {
                set.remove(driver_id);
            }
        }
        let mut d = self.drivers.get(driver_id).cloned().unwrap_or(Driver {
            driver_id: driver_id.into(),
            lat, lng, ts, version: 0, status: "idle", offer_until: 0.0,
        });
        d.lat = lat; d.lng = lng; d.ts = ts;
        self.cells.entry(cell_key(lat, lng)).or_default().insert(driver_id.into());
        self.drivers.insert(driver_id.into(), d);
    }

    fn lease_nearest(&mut self, pickup: (f64, f64), now: f64, ttl_s: f64) -> Option<Driver> {
        let mut ranked = Vec::new();
        for cell in neighbors(cell_key(pickup.0, pickup.1), 2) {
            if let Some(ids) = self.cells.get(&cell) {
                for did in ids {
                    if let Some(d) = self.drivers.get(did) {
                        if d.status == "idle" && now - d.ts <= STALE_S {
                            ranked.push((haversine_km(pickup, (d.lat, d.lng)), did.clone()));
                        }
                    }
                }
            }
        }
        ranked.sort_by(|a, b| a.0.partial_cmp(&b.0).unwrap());
        for (_, did) in ranked.into_iter().take(20) {
            if let Some(d) = self.drivers.get_mut(&did) {
                if d.status != "idle" { continue; }
                d.status = "offered";
                d.version += 1;
                d.offer_until = now + ttl_s;
                return Some(d.clone());
            }
        }
        None
    }

    fn accept(&mut self, driver_id: &str, version: u64, now: f64) -> bool {
        let d = match self.drivers.get_mut(driver_id) {
            Some(d) => d,
            None => return false,
        };
        if d.version != version || d.status != "offered" { return false; }
        if now > d.offer_until {
            d.status = "idle";
            return false;
        }
        d.status = "busy";
        true
    }
}

Request path / sequence

Trade-offs I'd say out loud

Sequential vs batch offers

Sequential is fairer and simpler locking; batch matches faster in sparse supply.

Haversine vs routed ETA

Haversine is cheap for candidate gen; routing is required before the rider sees a number.

City shard vs global

City affinity keeps GPS local; airport metros that straddle cities need explicit overlay.

SQL geo vs memory index

SQL is durable but too slow for ping storms; rebuild memory from the last known ping stream.

Where it usually breaks

  • Two matchers dispatch the same idle driver — rider A and rider B both see "assigned."
  • Stale pings dispatch a driver who went offline in a tunnel two minutes ago.
  • Global GPS topic — one region's rush hour drowns another city's matcher.
  • Calling the routing engine for every map animation frame — ETA service melts at 6pm.
  • Offer timeout too long — supply looks busy while drivers stare at the screen.
  • Surge computed globally — a stadium event prices the whole city.

Follow-ups if time remains

  • Shared rides: inserting a second pickup onto an in-progress trip.
  • Driver incentives and guaranteed hourly vs marketplace pay.
  • Fraud: GPS spoofing, fake trips, payment chargebacks.
  • Multi-hop airport queueing and geofenced lot matching.
  • How would you add scheduled rides without starving the on-demand pool?

What "good enough" looks like in 60 minutes

Shard by city, put driver locations in a cell index, and walk exclusive offers with a versioned lease so one car cannot be booked twice. Size ping QPS and say trips are a state machine with idempotent payment. Pooling and maps internals can stay as follow-ups.
