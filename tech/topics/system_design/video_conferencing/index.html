Design a video conferencing system

Google Meet style calls are WebRTC plus an SFU — mesh graphs explode past a handful of participants.

60-minute agenda

How I'd open the discussion

I'd separate signaling from media immediately. Signaling is a small control-plane problem (who joined, SDP offer/answer, mute state). Media is the hard part: realtime audio/video with sub-second latency under lossy networks. For 1:1, a peer-to-peer WebRTC mesh with TURN fallback is fine. For 3+ participants, uplink bandwidth on each client becomes the bottleneck — each peer would otherwise upload N−1 copies of their video.

That is why production systems use an SFU (Selective Forwarding Unit): each client uploads once (often with simulcast layers), and the SFU forwards the appropriate streams to subscribers. An MCU mixes into one composite — simpler for clients, much more expensive server-side and adds latency. Google Meet–style designs are SFU-first.

I'd sketch meeting service + signaling WS, STUN/TURN, regional SFUs, then deep-dive simulcast and how we pick which layers to forward under congestion.

Latency

Mouth-to-ear < 300 ms in-region on healthy networks.

Availability

99.9% join success; media should degrade before dropping call.

Tens of millions of concurrent call participants globally (sharded by meeting).

Bandwidth

Approach / design notes

Join flow: client hits the meeting service, receives a short-lived token, signaling WebSocket URL, and ICE server list (STUN + TURN). Signaling exchanges SDP with the assigned SFU (or a signaling gateway that talks to the SFU). ICE connectivity checks establish UDP (preferred) or TURN-relayed paths. Media then flows client ↔ SFU; other participants subscribe to forwarded tracks.

Simulcast: the publisher sends multiple encodings (e.g. low/mid/high). The SFU picks layers per subscriber based on their downlink, tile size, and network feedback (REMB/TWCC). When the grid shows 16 tiny faces, forward low layers; when someone is pinned full-screen, forward high. Dominant-speaker detection (audio energy) can boost that participant's layer automatically.

Geo: pin a meeting to the SFU region closest to the majority of participants (or the host). For cross-ocean calls, cascade SFUs — each region's SFU aggregates local publishers and exchanges a smaller set of streams with the remote SFU — reducing transoceanic streams from O(N×M) to O(cascaded feeds).

Deep dive (spend 15–25 minutes here)

Why not mesh? With 10 participants at 1 Mbps video, each client would need ~9 Mbps uplink just for video. Home and mobile uplinks cannot sustain that. SFU keeps uplink constant while server egress scales with subscriptions — and egress is where data-center NICs are provisioned.

Congestion control is continuous. Clients and SFUs use transport-wide CC (TWCC) to probe available bandwidth. On loss, shift subscribers to lower simulcast layers before dropping frames harshly. Audio should be prioritized over video in packet scheduling — humans tolerate blurry video better than choppy speech.

NAT traversal: STUN discovers public bindings; when symmetric NATs or firewalls block UDP, fall back to TURN relays. Budget TURN capacity explicitly — it is expensive because media hairpins through your servers. Prefer UDP TURN; TCP/TLS TURN is last resort for locked-down networks.

SFU failover mid-call: keep meeting state in the control plane. On SFU death, signaling instructs clients to ICE-restart against a warm standby SFU in the same region, renegotiate, and resume. Brief media gap is better than ending the meeting. Recording is a special subscriber (or sidecar) that records forwarded streams — do not force every client to upload a second copy for recording unless E2E encryption requires client-side record.

Simulcast layer selection sketch

from dataclasses import dataclass
from typing import Dict, List, Optional


@dataclass
class Layer:
    name: str          # "low" | "mid" | "high"
    max_bitrate_kbps: int
    height: int


LAYERS = [
    Layer("low", 150, 180),
    Layer("mid", 500, 360),
    Layer("high", 1200, 720),
]


@dataclass
class Subscriber:
    participant_id: str
    available_kbps: int
    tile_height: int
    pinned: bool = False


def pick_layer(sub: Subscriber, layers: List[Layer] = LAYERS) -> Layer:
    """Choose the highest layer that fits bandwidth and on-screen tile size."""
    ranked = layers if sub.pinned else list(reversed(layers))
    # Prefer resolution that matches tile; never exceed estimated downlink
    candidates = [
        L for L in layers
        if L.max_bitrate_kbps <= sub.available_kbps and L.height <= max(sub.tile_height * 2, 180)
    ]
    if sub.pinned:
        candidates = [L for L in layers if L.max_bitrate_kbps <= sub.available_kbps]
    if not candidates:
        return layers[0]
    return max(candidates, key=lambda L: L.max_bitrate_kbps)


class SFURouter:
    """Maps publisher → subscribers and selected simulcast layers."""

    def __init__(self):
        self.subscriptions: Dict[str, List[str]] = {}  # publisher → subscriber ids
        self.subscribers: Dict[str, Subscriber] = {}
        self.forwarding: Dict[tuple, str] = {}         # (pub, sub) → layer name

    def subscribe(self, publisher_id: str, sub: Subscriber):
        self.subscribers[sub.participant_id] = sub
        self.subscriptions.setdefault(publisher_id, []).append(sub.participant_id)
        self._recompute(publisher_id, sub.participant_id)

    def on_bandwidth_estimate(self, subscriber_id: str, kbps: int):
        sub = self.subscribers[subscriber_id]
        sub.available_kbps = kbps
        for pub, subs in self.subscriptions.items():
            if subscriber_id in subs:
                self._recompute(pub, subscriber_id)

    def _recompute(self, publisher_id: str, subscriber_id: str):
        sub = self.subscribers[subscriber_id]
        layer = pick_layer(sub)

use std::collections::HashMap;

#[derive(Clone, Copy)]
struct Layer {
    name: &'static str,
    max_bitrate_kbps: u32,
    height: u32,
}

const LAYERS: [Layer; 3] = [
    Layer { name: "low", max_bitrate_kbps: 150, height: 180 },
    Layer { name: "mid", max_bitrate_kbps: 500, height: 360 },
    Layer { name: "high", max_bitrate_kbps: 1200, height: 720 },
];

struct Subscriber {
    participant_id: String,
    available_kbps: u32,
    tile_height: u32,
    pinned: bool,
}

fn pick_layer(sub: &Subscriber) -> Layer {
    let mut best = LAYERS[0];
    for layer in LAYERS {
        let res_ok = sub.pinned || layer.height <= sub.tile_height.saturating_mul(2).max(180);
        if layer.max_bitrate_kbps <= sub.available_kbps && res_ok {
            best = layer;
        }
    }
    best
}

struct SfuRouter {
    subscriptions: HashMap<String, Vec<String>>,
    subscribers: HashMap<String, Subscriber>,
    forwarding: HashMap<(String, String), &'static str>,
}

impl SfuRouter {
    fn subscribe(&mut self, publisher_id: &str, sub: Subscriber) {
        let sid = sub.participant_id.clone();
        self.subscribers.insert(sid.clone(), sub);
        self.subscriptions
            .entry(publisher_id.to_string())
            .or_default()
            .push(sid.clone());
        self.recompute(publisher_id, &sid);
    }

    fn on_bandwidth_estimate(&mut self, subscriber_id: &str, kbps: u32) {
        if let Some(sub) = self.subscribers.get_mut(subscriber_id) {
            sub.available_kbps = kbps;
        }
        let pubs: Vec<String> = self.subscriptions.keys().cloned().collect();
        for pub_id in pubs {
            if self.subscriptions[&pub_id].iter().any(|s| s == subscriber_id) {
                self.recompute(&pub_id, subscriber_id);
            }
        }
    }

    fn recompute(&mut self, publisher_id: &str, subscriber_id: &str) {
        let layer = pick_layer(&self.subscribers[subscriber_id]);
        self.forwarding
            .insert((publisher_id.to_string(), subscriber_id.to_string()), layer.name);
    }
}

Request path / sequence

Trade-offs I'd say out loud

Mesh vs SFU vs MCU

Mesh for 1:1; SFU for group; MCU only if you need a single mixed layout server-side.

Simulcast vs SVC

Simulcast is widely supported; SVC is more bitrate-efficient but codec/stack harder.

E2E encryption

True E2E limits server recording/moderation; insertable streams add complexity.

One SFU vs cascade

Single SFU is simpler; cascade saves intercontinental bandwidth for large geo-spread calls.

Where it usually breaks

  • Forcing mesh for 12-person calls — uplinks saturate, call becomes audio-only chaos.
  • Under-provisioned TURN — enterprise users behind symmetric NAT cannot join.
  • SFU region pinned far from participants — 400 ms+ RTT kills conversation.
  • No simulcast — everyone receives 720p and mobile downlinks collapse.
  • Signaling and media on one process — deploy restart drops in-call media.
  • Recording subscribed at full high layer × N publishers without cap — disk and CPU blow up.

Follow-ups if time remains
