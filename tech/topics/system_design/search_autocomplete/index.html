Design a search autocomplete

Autocomplete is a latency race: users notice 150ms. Prefix indexes and careful ranking matter more than a general search cluster.

60-minute agenda

How I'd open the discussion

Autocomplete is fundamentally a latency problem. Users type a character, and if suggestions take more than 100-150 ms to appear, the experience feels sluggish. That latency budget rules out hitting a general-purpose search cluster on every keystroke — we need a purpose-built index that can serve prefix lookups in single-digit milliseconds.

The classic approach is a trie where each node stores the top-K suggestions for that prefix. When the user types 'how t', we traverse to the 'how t' node and return its pre-computed top-10 suggestions, ranked by frequency. The trie is built offline from aggregated query logs and loaded into memory on serving nodes.

I'd walk through the trie structure, the offline aggregation pipeline that feeds it, and then discuss how to add personalization (blending the user's own recent queries with the global suggestions) without blowing the latency budget.

Open questions worth asking

  • How many suggestions should we return per keystroke — top 5 or top 10?
  • Do we need personalized suggestions based on user history?
  • What is the acceptable suggestion latency — p99 < 100 ms?
  • How fresh should suggestions be — real-time trending or hourly?
  • Do we need to handle typo correction or just prefix matching?
  • Should we filter offensive or NSFW suggestions?
  • Is the query language English-only or multi-language?
  • Do we need to support suggestion categories (products, queries, brands)?
  • What is the total query vocabulary size?
  • Do suggestions need to reflect real-time trending topics?

Scope I'd lock first

  • In: prefix-based suggestions from popular queries, frequency-ranked top-10.
  • In: trie index with offline build, personalization overlay.
  • Out: full-text search, typo correction / fuzzy matching, multi-language.
  • Defer: real-time trending injection, category-based suggestions.

Approach / design notes

The serving layer is a fleet of stateless nodes, each holding the full trie in memory. A load balancer distributes prefix queries across nodes. Each node loads the latest trie snapshot from object storage (S3) at startup and hot-swaps to a new version when notified by the build pipeline.

The trie is a compressed (Patricia) trie where each node stores the top-K (K=15) suggestions for that prefix, pre-ranked by a blended score of frequency, recency, and editorial boost. When a query arrives for prefix 'how t', the serving node traverses to that node in O(len(prefix)) time and returns the pre-computed list. No sorting or filtering happens at query time — it is pure lookup, which keeps latency in the 1-5 ms range on the server side.

The offline build pipeline runs hourly. It reads from the query log aggregation table, filters out blocked/offensive queries, computes frequency scores with a time decay (recent queries count more), and builds a new trie. At each trie node, it inserts all queries that pass through that prefix and keeps only the top-K by score. The resulting trie is serialized to a binary file and uploaded to S3. A notification triggers serving nodes to download and hot-swap.

Personalization adds a real-time overlay. Each user's last 20 queries are stored in a Redis sorted set (scored by timestamp). When a suggestion request includes a user_id, the serving node fetches the user's recent queries from Redis, filters to those matching the current prefix, and blends them with the global suggestions. The blending formula gives 70% weight to global and 30% to personal, with dedup so the same suggestion does not appear twice. If Redis is slow (> 20 ms), the personal overlay is skipped and only global suggestions are returned — graceful degradation.

For trending queries, I'd add a sliding-window counter (last 1 hour) in Redis for queries that spike above their historical baseline. These trending queries get an editorial boost in the next trie build. For truly real-time trending (breaking news), a small sidecar index holds the top 100 trending queries and is merged at query time.

Deep dive (spend 15–25 minutes here)

The compressed trie (Patricia trie) is critical for memory efficiency. A naive trie for 5M queries with an average of 20 characters would have ~100M nodes — each with a character, children map, and top-K list. A Patricia trie compresses chains of single-child nodes into single edges labeled with the entire substring. This reduces node count by 60-80%, bringing the trie from ~2 GB to ~500 MB. Each node stores 15 pre-ranked suggestions (just string references, not copies) and a frequency score.

The top-K pre-computation is what makes query-time performance possible. During the build phase, we insert each query into the trie with its score. At each node along the path, we maintain a min-heap of size K. If the query's score is higher than the heap's minimum, we replace it. After all queries are inserted, each node's heap contains the K highest-scoring queries that pass through that prefix. At query time, we just return this pre-computed list — no sorting needed.

Client-side debouncing is essential to avoid overwhelming the server. The client waits 50-100 ms after the last keystroke before sending the request. If the user types quickly, intermediate characters are never queried. This reduces QPS by 3-5× compared to querying on every keystroke. The client also cancels in-flight requests when a new keystroke arrives — there is no point showing suggestions for 'ho' when the user has already typed 'how'.

Offensive content filtering has two layers. The first is a blocklist checked during trie build — queries matching known offensive patterns are excluded. The second is a classifier that flags borderline content for human review. Newly popular queries (appearing in top-K for the first time) are quarantined and reviewed before being promoted to the trie. This prevents trending offensive content from appearing in suggestions.

Graceful degradation is designed in layers. If the trie server is overloaded, we return cached results from a CDN edge (suggestions for the top 1,000 prefixes are pre-cached with a 5-minute TTL). If Redis is slow, we skip personalization. If the build pipeline fails, serving nodes continue using the last successful trie — stale suggestions are better than no suggestions. The worst-case fallback is returning an empty list, which degrades the experience but does not break the search flow.

Trie with pre-computed top-K and personal blending

from __future__ import annotations
import heapq
from dataclasses import dataclass, field

TOP_K = 15  # max suggestions stored at each trie node


@dataclass
class TrieNode:
    children: dict[str, TrieNode] = field(default_factory=dict)
    top_k: list[tuple[float, str]] = field(default_factory=list)


class AutocompleteTrie:
    """Prefix trie with pre-computed top-K suggestions at every node.
    Insertions update the min-heap at each node along the path."""

    def __init__(self):
        self.root = TrieNode()

    def insert(self, query: str, score: float):
        node = self.root
        for ch in query:
            if ch not in node.children:
                node.children[ch] = TrieNode()
            node = node.children[ch]
            self._update_top_k(node, score, query)

    def _update_top_k(self, node: TrieNode, score: float, query: str):
        if len(node.top_k) < TOP_K:
            heapq.heappush(node.top_k, (score, query))
        elif score > node.top_k[0][0]:
            # Replace the lowest-scored entry if the new one is better
            heapq.heapreplace(node.top_k, (score, query))

    def suggest(self, prefix: str, limit: int = 10) -> list[str]:
        node = self.root
        for ch in prefix:
            if ch not in node.children:
                return []
            node = node.children[ch]
        ranked = sorted(node.top_k, key=lambda x: -x[0])
        return [q for _, q in ranked[:limit]]


class SuggestionService:
    """Blends global trie results with user's recent personal queries."""

    def __init__(self, trie: AutocompleteTrie, redis_client):
        self.trie = trie
        self.redis = redis_client

    def get_suggestions(
        self, prefix: str, user_id: int | None = None, limit: int = 10
    ) -> list[dict]:
        global_results = self.trie.suggest(prefix, limit=limit)
        if not user_id:
            return [{"text": q, "source": "global"} for q in global_results]
        # Fetch user's recent queries matching the prefix
        try:
            recent = self.redis.zrevrange(f"user_queries:{user_id}", 0, 19)
            personal = [q.decode() for q in recent
                        if q.decode().lower().startswith(prefix.lower())]
        except Exception:
            personal = []
        # Merge: personal results first (up to 3), then global
        seen = set()
        merged = []
        for q in personal[:3]:
            if q not in seen:
                merged.append({"text": q, "source": "personal"})
                seen.add(q)
        for q in global_results:
            if q not in seen and len(merged) < limit:
                merged.append({"text": q, "source": "global"})
                seen.add(q)
        return merged[:limit]
use std::collections::{BinaryHeap, HashMap};
use std::cmp::Reverse;

const TOP_K: usize = 15;

struct TrieNode {
    children: HashMap<char, Box<TrieNode>>,
    // Min-heap of (score, query) — keeps the K highest-scored suggestions
    top_k: BinaryHeap<Reverse<(i64, String)>>,
}
impl TrieNode {
    fn new() -> Self {
        Self { children: HashMap::new(), top_k: BinaryHeap::new() }
    }
}

/// Prefix trie with pre-computed top-K at every node.
/// Lookups are O(prefix_len) — no subtree traversal needed at query time.
struct AutocompleteTrie { root: TrieNode }

impl AutocompleteTrie {
    fn new() -> Self { Self { root: TrieNode::new() } }

    fn insert(&mut self, query: &str, score: i64) {
        let mut node = &mut self.root;
        for ch in query.chars() {
            // Ownership: entry API avoids double-borrow on the node
            node = node.children.entry(ch)
                .or_insert_with(|| Box::new(TrieNode::new()));
            Self::update_top_k(&mut node.top_k, score, query);
        }
    }

    fn update_top_k(heap: &mut BinaryHeap<Reverse<(i64, String)>>,
                    score: i64, query: &str) {
        if heap.len() < TOP_K {
            heap.push(Reverse((score, query.to_string())));
        } else if let Some(&Reverse((min_score, _))) = heap.peek() {
            if score > min_score {
                heap.pop();
                heap.push(Reverse((score, query.to_string())));
            }
        }
    }

    fn suggest(&self, prefix: &str, limit: usize) -> Vec<String> {
        let mut node = &self.root;
        for ch in prefix.chars() {
            match node.children.get(&ch) {
                Some(child) => node = child,
                None => return Vec::new(),
            }
        }
        let mut items: Vec<_> = node.top_k.iter()
            .map(|Reverse((s, q))| (*s, q.clone())).collect();
        items.sort_by(|a, b| b.0.cmp(&a.0)); // descending score
        items.into_iter().take(limit).map(|(_, q)| q).collect()
    }
}
#import <Foundation/Foundation.h>
#include <unordered_map>
#include <queue>
#include <vector>
#include <string>

static const int kTopK = 15;

struct TrieNode {
    std::unordered_map<char, TrieNode *> children;
    // Min-heap keeps the K highest-scored suggestions
    std::priority_queue<std::pair<double, std::string>,
        std::vector<std::pair<double, std::string>>,
        std::greater<>> topK;  // greater<> → min at top
};

// Prefix trie with pre-computed top-K at every node
@interface AutocompleteTrie : NSObject
- (void)insert:(NSString *)query score:(double)score;
- (NSArray<NSString *> *)suggest:(NSString *)prefix limit:(int)limit;
@end

@implementation AutocompleteTrie {
    TrieNode *_root;
}
- (instancetype)init {
    if (self = [super init]) _root = new TrieNode();
    return self;
}

- (void)_updateTopK:(TrieNode *)node score:(double)s query:(const std::string &)q {
    if ((int)node->topK.size() < kTopK) {
        node->topK.push({s, q});
    } else if (s > node->topK.top().first) {
        node->topK.pop();
        node->topK.push({s, q});
    }
}

- (void)insert:(NSString *)query score:(double)score {
    const char *cstr = query.UTF8String;
    std::string q(cstr);
    TrieNode *node = _root;
    for (char ch : q) {
        if (!node->children.count(ch))
            node->children[ch] = new TrieNode();
        node = node->children[ch];
        [self _updateTopK:node score:score query:q];
    }
}

- (NSArray<NSString *> *)suggest:(NSString *)prefix limit:(int)limit {
    TrieNode *node = _root;
    for (int i = 0; i < (int)prefix.length; i++) {
        char ch = [prefix characterAtIndex:i];
        auto it = node->children.find(ch);
        if (it == node->children.end()) return @[];
        node = it->second;
    }
    // Drain heap copy into sorted results
    auto heap = node->topK;
    std::vector<std::pair<double, std::string>> items;
    while (!heap.empty()) { items.push_back(heap.top()); heap.pop(); }
    std::sort(items.begin(), items.end(),
              [](auto &a, auto &b){ return a.first > b.first; });
    NSMutableArray *result = [NSMutableArray new];
    for (int i = 0; i < std::min((int)items.size(), limit); i++)
        [result addObject:@(items[i].second.c_str())];
    return result;
}
@end

Request path / sequence

Trade-offs I'd say out loud

Trie vs inverted index

Trie gives O(prefix) lookup with pre-computed top-K; inverted index is flexible but slower for prefix queries.

In-memory vs disk-based

In-memory is ultra-fast but limits vocabulary size; disk-based scales but adds latency.

Hourly vs real-time updates

Hourly is simpler and sufficient for most queries; real-time catches trending topics but adds complexity.

Global-only vs personalized

Global is simpler and cacheable; personalized is more relevant but adds Redis dependency.

Where it usually breaks

  • Trie build pipeline fails — serving nodes stuck on stale suggestions for hours.
  • Redis latency spike — personal suggestions add 200ms, exceeding the p99 budget.
  • Offensive query goes viral — appears in top-K before the hourly blocklist refresh.
  • Hot prefix ('how to') overloads a single trie node's top-K — but this is pre-computed so actually fine.
  • Client sends requests on every keystroke without debounce — QPS spikes 5×.
  • Trie memory exceeds node RAM after vocabulary growth — OOM kills serving process.
  • CDN caches stale suggestions — users see outdated results for 5+ minutes.
