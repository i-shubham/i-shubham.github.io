Design a collaborative document editor

Google Docs style collab is OT or CRDT plus presence — concurrent cursors will surface every race you waved away.

60-minute agenda

How I'd open the discussion

I'd clarify concurrency first: is this 2–3 editors like a personal doc, or 50+ like a shared meeting notes doc? That choice drives whether we can keep a single authoritative server (Operational Transformation) or need peer-friendly CRDTs. I'd also ask whether offline editing is in scope — offline means you must converge after arbitrary delay, which pushes hard toward CRDTs.

The product surface looks simple — a shared text buffer — but the hard problem is that every keystroke is a concurrent mutation. Two users inserting at the same cursor position must end up with a deterministic order on every client. Presence (cursors, selections) is a separate softer channel: eventually consistent is fine, and we can drop intermediate updates under load.

I'd sketch a collab server that owns the document's operation log, clients that apply ops optimistically, and a snapshot + catch-up path for reconnects — then deep-dive OT transforms or CRDT merge depending on the offline requirement.

Open questions worth asking

  • Max concurrent editors per document?
  • Is offline editing required, or always-online only?
  • Plain text, rich text, or embedded media?
  • Do we need version history / restore to past revision?
  • Comments, suggestions mode, or just direct edit?
  • Document size limits (10 KB notes vs 50 MB specs)?
  • Sharing model — link-based, org ACLs, guest access?
  • Latency target for seeing another user's keystroke?
  • Multi-region: can co-editors be continents apart?
  • Mobile clients with flaky networks?

Scope I'd lock first

  • In: realtime text sync for up to ~50 concurrent editors, presence cursors, version snapshots.
  • In: reconnect catch-up from op log, optimistic local apply.
  • Out: full comments UI, suggestion mode, OCR/import pipelines.
  • Defer: offline-first CRDT path if interviewer wants always-online OT first.

Functional requirements

Edit & sync

Keystrokes and formatting ops propagate to all editors within ~100 ms on a healthy network.

Convergence

All clients eventually show identical document content after ops settle.

Presence

Show other users' cursors and selections with low-priority updates.

History

Periodic snapshots + op log enable restore and audit.

Reconnect

Client resumes from last known revision without full re-download when possible.

Non-functional / rough numbers

Edit latency

p99 < 150 ms for op echo from collab server to peers in-region.

Consistency

Strong convergence on content; presence may be lossy.

Availability

99.9% — brief disconnects are expected; edits must not corrupt.

Throughput

10M active docs/day; hot docs ~200 ops/sec during meetings.

Capacity estimate (do this on the board)

Active sessions

10M DAU × 0.3 docs open × avg 2 editors ≈ 6M concurrent sessions peak.

Ops/sec

Typing ≈ 5 chars/sec/user → assume 2M concurrent typists × 5 = 10M ops/sec globally (shard by doc).

Op size

~100 bytes average → ~1 GB/sec ingest before batching/compression.

Hot doc

50 editors × 5 ops/sec = 250 ops/sec on one document shard.

Snapshots

Snapshot every 100 ops or 30s → keeps catch-up short.

Storage

Snapshot + truncated op log per doc; cold docs to object storage.

Approach / design notes

Each open document maps to a sticky collab server (or actor) that serializes the operation log. Clients apply local ops immediately for snappy typing, then send them to the server. The server transforms concurrent ops against the authoritative history, assigns a server revision, persists the op, and broadcasts the transformed op to peers.

Operational Transformation (OT) is the classic Google Docs approach: the server is the single source of truth, and clients transform remote ops against unacked local ops before applying. CRDTs (e.g., RGA, Yjs-style) are better when offline edits must merge without a central transformer — each character gets a unique ID and tombstones handle deletes. In a 60-minute Google interview I usually lead with OT for always-online, then mention CRDT for offline.

Documents are sharded by doc_id. One hot document never spans multiple writers for the op log — that preserves a total order. Presence rides a separate fan-out path (Redis Pub/Sub or the same WS channel with lower priority) so cursor spam cannot stall content ops. Snapshots every N revisions let reconnecting clients load snapshot + delta instead of replaying millions of keystrokes.

Deep dive (spend 15–25 minutes here)

OT insert/delete transforms are the interview meat. If A inserts at position 5 and B concurrently deletes range [3,6], the server must rewrite A's position after B's delete (or vice versa) so both sides converge. State that transformation functions T(op1, op2) must satisfy TP1/TP2 properties for correctness under arbitrary concurrency — you do not need to derive full proofs, but naming them shows you know the landmines.

Server-side serialization is what makes OT tractable: every op is transformed against the contiguous history from the client's known revision to HEAD. Clients keep a bridge of unacked local ops and transform incoming remote ops against that bridge before applying. If the WS disconnects mid-flight, the client re-joins with from_rev and either receives missed ops or a fresh snapshot if the log was compacted.

Garbage collection matters: without snapshots, op logs grow forever. Compact by writing a snapshot at rev N and deleting ops older than the oldest connected client's base revision (or a retention floor like 24 hours). Presence should be ephemeral — store in memory on the collab actor, expire on disconnect, and throttle cursor events to ~10 Hz per user.

Multi-region is painful for OT because you want one primary writer per doc. Pin the document's actor to the region of the owner or first editor; remote editors pay cross-region RTT. CRDTs allow multi-master but introduce larger metadata and more complex GC of tombstones — call that out as the offline/multi-region trade.

OT transform sketch for concurrent inserts

from dataclasses import dataclass
from typing import List, Tuple


@dataclass
class Op:
    kind: str   # "ins" | "del"
    pos: int
    text: str = ""
    length: int = 0  # for deletes


def transform(a: Op, b: Op) -> Tuple[Op, Op]:
    """Transform concurrent ops so both can apply in either order and converge.
    Simplified: insert/insert and insert/delete only — interview sketch.
    """
    a2, b2 = Op(**a.__dict__), Op(**b.__dict__)

    if a.kind == "ins" and b.kind == "ins":
        if a.pos < b.pos or (a.pos == b.pos and a.text <= b.text):
            b2.pos += len(a.text)
        else:
            a2.pos += len(b.text)
    elif a.kind == "ins" and b.kind == "del":
        if a.pos <= b.pos:
            b2.pos += len(a.text)
        elif a.pos >= b.pos + b.length:
            a2.pos -= b.length
        else:
            # insert landed inside delete range → clamp into surviving left edge
            a2.pos = b.pos
            b2.length += len(a.text)
    elif a.kind == "del" and b.kind == "ins":
        return tuple(reversed(transform(b, a)))
    # del/del omitted for brevity — similar position shifting
    return a2, b2


class DocActor:
    """Single-writer actor for one document's op log."""

    def __init__(self):
        self.rev = 0
        self.content = ""
        self.log: List[Op] = []

    def apply_client_op(self, base_rev: int, op: Op) -> Tuple[int, Op]:
        # Transform against ops the client has not seen yet
        transformed = op
        for prior in self.log[base_rev:]:
            transformed, _ = transform(transformed, prior)
        self._apply(transformed)
        self.rev += 1
        self.log.append(transformed)
        return self.rev, transformed

    def _apply(self, op: Op):
        if op.kind == "ins":
            self.content = self.content[:op.pos] + op.text + self.content[op.pos:]
        else:
            end = op.pos + op.length
            self.content = self.content[:op.pos] + self.content[end:]
#[derive(Clone, Debug)]
enum OpKind { Ins, Del }

#[derive(Clone, Debug)]
struct Op {
    kind: OpKind,
    pos: usize,
    text: String,
    length: usize,
}

fn transform(a: &Op, b: &Op) -> (Op, Op) {
    let mut a2 = a.clone();
    let mut b2 = b.clone();
    match (&a.kind, &b.kind) {
        (OpKind::Ins, OpKind::Ins) => {
            if a.pos < b.pos || (a.pos == b.pos && a.text <= b.text) {
                b2.pos += a.text.len();
            } else {
                a2.pos += b.text.len();
            }
        }
        (OpKind::Ins, OpKind::Del) => {
            if a.pos <= b.pos {
                b2.pos += a.text.len();
            } else if a.pos >= b.pos + b.length {
                a2.pos -= b.length;
            } else {
                a2.pos = b.pos;
                b2.length += a.text.len();
            }
        }
        (OpKind::Del, OpKind::Ins) => {
            let (b3, a3) = transform(b, a);
            return (a3, b3);
        }
        _ => {}
    }
    (a2, b2)
}

struct DocActor {
    rev: u64,
    content: String,
    log: Vec<Op>,
}

impl DocActor {
    fn apply_client_op(&mut self, base_rev: usize, op: Op) -> (u64, Op) {
        let mut transformed = op;
        for prior in &self.log[base_rev..] {
            let (t, _) = transform(&transformed, prior);
            transformed = t;
        }
        Self::apply_to(&mut self.content, &transformed);
        self.rev += 1;
        self.log.push(transformed.clone());
        (self.rev, transformed)
    }

    fn apply_to(content: &mut String, op: &Op) {
        match op.kind {
            OpKind::Ins => content.insert_str(op.pos, &op.text),
            OpKind::Del => { content.drain(op.pos..op.pos + op.length); }
        }
    }
}

Request path / sequence

Trade-offs I'd say out loud

OT vs CRDT

OT needs a central transformer and is proven at Docs scale; CRDT shines offline but costs metadata and GC complexity.

Sticky actor vs multi-writer

Single writer per doc simplifies ordering; multi-writer needs consensus or CRDT.

Snapshot frequency

More snapshots = faster reconnect, more storage write amplification.

Presence QoS

Dropping cursor frames is fine; dropping content ops is not — separate channels or priorities.

Where it usually breaks

  • Incorrect transform on overlapping delete/insert → permanent divergence between clients.
  • Collab actor failover without replaying unpersisted ops → lost keystrokes.
  • Op log compaction deletes revisions a slow client still needs → forced full snapshot reload storms.
  • Hot meeting doc with 50 typists saturates one shard CPU on transforms.
  • Presence fan-out at 60 Hz × N users dwarfs content bandwidth.
  • Clock-skewed client base_rev causes transform against wrong history.

Follow-ups if time remains

  • How would you support offline editing with CRDTs and tombstone GC?
  • Design suggestion mode (propose edits without mutating until accept).
  • Multi-region primary failover for a document's actor.
  • Access control: viewer vs commenter vs editor without leaking ops.
  • How do comments anchor to text that keeps moving underneath them?

What "good enough" looks like in 60 minutes

Lock scope to always-online collab, explain a sticky per-doc actor with an op log, walk an OT insert/insert transform, and show snapshot + catch-up for reconnect. Mention CRDT as the offline alternative and call out presence as a lossy side channel. Full transform proofs and rich-text schemas can stay as follow-ups.
