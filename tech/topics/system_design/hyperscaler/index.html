Design a Google-like hyperscaler

A hyperscaler is a cluster OS plus multi-tenant quota — bin packing and failure domains matter more than a prettier Kubernetes YAML.

60-minute agenda

How I'd open the discussion

I'd ask whether we are designing public IaaS (VMs, disks, VPC like GCE) or an internal cluster OS (Borg/Omega/Kubernetes: jobs, tasks, priorities). The interesting Google-shaped answer is usually both layers: a fabric of machines grouped into cells, a control plane that packs work onto those machines, and product APIs on top. I would not try to design Gmail, Search, and Cloud in one hour.

The unit of isolation is the cell: thousands to tens of thousands of machines with one scheduler. Regions contain many cells so a control-plane outage does not take a continent. Tenants get quota (CPU, RAM, disk, GPU, IP) and priorities so batch work yields to serving. Hardware dies constantly — the scheduler, not the app, is responsible for rescheduling tasks off dead nodes.

I'd draw region → cell → machine agent, then deep-dive placement (bin packing + constraints) and how the control plane stays available without becoming a global singleton.

Open questions worth asking

  • Internal Borg-like jobs, public VM/GKE APIs, or both?
  • How many machines per cell and cells per region?
  • Workloads: latency-sensitive serving vs batch vs ML training?
  • Preemption allowed for low-priority jobs?
  • GPU/TPU pools and gang scheduling (all-or-nothing workers)?
  • Network: tenant VPCs, or a flat datacenter fabric with ACLs?
  • Persistent disks and object storage in or out of scope?
  • Live migration vs kill-and-reschedule on maintenance?
  • Multi-region failover of tenant workloads — our job or theirs?
  • Who owns kernel/runtime: VMs, gVisor, or bare containers?

Scope I'd lock first

  • In: multi-tenant compute fabric, cell-based control plane, scheduler with quota and preemption.
  • In: machine agents, health, reschedule on failure, basic identity/IAM for APIs.
  • Out: designing Search ranking, a full SDN from scratch, customer billing UI.
  • Defer: global anycast load balancer product, custom TPU compiler stack.

Functional requirements

Admit work

Tenant submits a job/VM spec: image, CPU/RAM, count, constraints, priority.

Place

Scheduler packs tasks onto machines respecting capacity, affinity, and failure domains.

Run

Agent pulls image, starts isolation boundary, reports health and resource use.

Repair

Dead machine or unhealthy task → reschedule elsewhere; drain for maintenance.

Quota

Reject or queue when tenant exceeds CPU/RAM/GPU/disk in a region.

Non-functional / rough numbers

Cell size

~10K machines/cell so the scheduler's in-memory view stays tractable.

Placement latency

Serving tasks: seconds; batch can queue minutes when the cell is full.

Control plane

Cell master highly available (Paxos/Raft); no single global Borgmaster.

Utilization

Bin packing + overcommit on reclaimable batch; protect serving SLOs.

Capacity estimate (do this on the board)

Fleet

1M machines globally → 100 cells of 10K; ~20 regions × 5 cells.

Scheduling rate

10K machines × 20 tasks churn/hour ≈ 55 tasks/sec/cell peak; burst higher on deploys.

State

Per cell: machine inventory + task objects. Millions of keys, not billions — keep it in the master + watch cache.

Agent QPS

Heartbeat every 5–10s × 10K ≈ 1–2K updates/sec/cell; batch and compress.

Images

Pull-through caches per rack/row or the fabric becomes a disk storm at deploy.

Network

Clos fabric; east-west dominates. Scheduler must know ToR/row for spreading.

Approach / design notes

Physical: buildings → rows → racks → machines. Logical: region (latency/legal) → cell (scheduler blast radius) → pool (CPU vs GPU SKU). Tenants talk to a regional frontend that picks a cell with matching SKU and leftover quota, then the cell master owns placement. This is the Borg lesson: do not run one scheduler over a million machines.

The cell master holds the source of truth (replicated log). A scheduler process (can be the master or a tightly coupled replica) scores feasible machines: remaining resources, spread across racks, affinity to disks, GPU topology. It writes task→machine bindings atomically. Machine agents apply bindings, run the sandbox (VM or container), and heartbeat. If heartbeat is lost, tasks are marked unknown then rescheduled after a timeout — split-brain is avoided by fencing (power/API lock the old machine) before restarting a task that must be unique.

Priorities: serving > production batch > best-effort. Best-effort fills holes and is preempted when serving needs the capacity. Quota is admitted at submit time; bursting uses reclaimable leftover. Identity: every API call is tenant-scoped; agents get machine credentials, not tenant keys.

Deep dive (spend 15–25 minutes here)

Bin packing: first-fit decreasing is a fine interview default — sort tasks largest-first, place on the tightest machine that fits to leave contiguous holes for the next big GPU job. Scoring should penalize packing two replicas of the same serving job onto one rack (correlated power/ToR failure). GPU jobs often need gang scheduling: do not start 7 of 8 workers; hold until a full set of machines is free or timeout to a queue.

Control plane HA: 5 replicas with Paxos/Raft, leader does writes. Read-only schedulers can work off a slightly stale cache only for scoring, but binds go through the log. Upgrades: drain a fraction of agents, never "restart all kubelets." Cell too large → scheduler latency and "one bug pages 10K machines." Cell too small → stranded GPU inventory and cross-cell scheduling complexity. Quote ~5–20K machines as the working range.

Noisy neighbors: CPU hard cgroups, memory without swap for serving, disk IO tokens, network isolation (VPC overlay or hypervisor). Overcommit only memory/CPU on best-effort. Maintenance: mark machine draining, migrate or kill-and-reschedule by priority. Disk-attached VMs need the storage control plane to reattach or to have used replicated disk so the new machine can mount.

Multi-region: the hyperscaler places in a region the tenant chose. Global products (Anycast VIP, Spanner-like DBs) are separate systems that consume this fabric. Do not pretend one scheduler places a job "on Earth."

Cell scheduler: feasibility, spread, preemption

from dataclasses import dataclass, field
from typing import Dict, List, Optional, Set


@dataclass
class Machine:
    machine_id: str
    rack: str
    cpu_free: int
    mem_free: int
    gpu_free: int
    jobs_on_rack: Set[str] = field(default_factory=set)


@dataclass
class Task:
    task_id: str
    job_id: str
    cpu: int
    mem: int
    gpu: int
    priority: int  # higher wins
    avoid_racks: Set[str] = field(default_factory=set)


def score(m: Machine, t: Task) -> float:
    # Tight fit preferred (leave fewer stranded leftovers) minus rack clash.
    leftover = (m.cpu_free - t.cpu) + (m.mem_free - t.mem) * 0.01
    clash = 50.0 if t.job_id in m.jobs_on_rack else 0.0
    return leftover + clash


class CellScheduler:
    def __init__(self, machines: List[Machine]):
        self.machines: Dict[str, Machine] = {m.machine_id: m for m in machines}
        self.placement: Dict[str, str] = {}  # task → machine

    def place(self, task: Task, allow_preempt: bool = True) -> Optional[str]:
        feasible = [
            m for m in self.machines.values()
            if m.cpu_free >= task.cpu and m.mem_free >= task.mem
            and m.gpu_free >= task.gpu and m.rack not in task.avoid_racks
        ]
        if feasible:
            m = min(feasible, key=lambda x: score(x, task))
            self._bind(m, task)
            return m.machine_id
        if not allow_preempt:
            return None
        # Interview sketch: pick a machine that would fit if we dropped
        # lower-priority tasks (real Borg scores preemption cost).
        return None

    def _bind(self, m: Machine, task: Task):
        m.cpu_free -= task.cpu
        m.mem_free -= task.mem
        m.gpu_free -= task.gpu
        m.jobs_on_rack.add(task.job_id)
        self.placement[task.task_id] = m.machine_id

    def place_gang(self, tasks: List[Task]) -> bool:
        """All-or-nothing for distributed training workers."""
        snapshot = {
            mid: (m.cpu_free, m.mem_free, m.gpu_free, set(m.jobs_on_rack))
            for mid, m in self.machines.items()
        }
        bound: List[Task] = []
        for t in tasks:
            if not self.place(t, allow_preempt=False):
                for b in bound:
                    self._rollback(b, snapshot)
                return False
            bound.append(t)
        return True

    def _rollback(self, task: Task, snapshot):
        mid = self.placement.pop(task.task_id)
        m = self.machines[mid]
        m.cpu_free, m.mem_free, m.gpu_free, jobs = snapshot[mid]
        m.jobs_on_rack = set(jobs)
use std::collections::{HashMap, HashSet};

struct Machine {
    machine_id: String,
    rack: String,
    cpu_free: i32,
    mem_free: i32,
    gpu_free: i32,
    jobs_on_rack: HashSet<String>,
}

struct Task {
    task_id: String,
    job_id: String,
    cpu: i32,
    mem: i32,
    gpu: i32,
    avoid_racks: HashSet<String>,
}

fn score(m: &Machine, t: &Task) -> f64 {
    let leftover = (m.cpu_free - t.cpu) as f64 + (m.mem_free - t.mem) as f64 * 0.01;
    let clash = if m.jobs_on_rack.contains(&t.job_id) { 50.0 } else { 0.0 };
    leftover + clash
}

struct CellScheduler {
    machines: HashMap<String, Machine>,
    placement: HashMap<String, String>,
}

impl CellScheduler {
    fn place(&mut self, task: &Task) -> Option<String> {
        let mut best_id: Option<String> = None;
        let mut best_s = f64::MAX;
        for m in self.machines.values() {
            if m.cpu_free < task.cpu || m.mem_free < task.mem || m.gpu_free < task.gpu {
                continue;
            }
            if task.avoid_racks.contains(&m.rack) {
                continue;
            }
            let s = score(m, task);
            if s < best_s {
                best_s = s;
                best_id = Some(m.machine_id.clone());
            }
        }
        let mid = best_id?;
        self.bind(&mid, task);
        Some(mid)
    }

    fn bind(&mut self, machine_id: &str, task: &Task) {
        let m = self.machines.get_mut(machine_id).unwrap();
        m.cpu_free -= task.cpu;
        m.mem_free -= task.mem;
        m.gpu_free -= task.gpu;
        m.jobs_on_rack.insert(task.job_id.clone());
        self.placement.insert(task.task_id.clone(), machine_id.to_string());
    }

    fn place_gang(&mut self, tasks: &[Task]) -> bool {
        let snap: Vec<(String, i32, i32, i32, HashSet<String>)> = self
            .machines
            .values()
            .map(|m| {
                (m.machine_id.clone(), m.cpu_free, m.mem_free, m.gpu_free, m.jobs_on_rack.clone())
            })
            .collect();
        let mut bound = Vec::new();
        for t in tasks {
            if self.place(t).is_none() {
                self.rollback(&bound, &snap);
                return false;
            }
            bound.push(t.task_id.clone());
        }
        true
    }

    fn rollback(&mut self, bound: &[String], snap: &[(String, i32, i32, i32, HashSet<String>)]) {
        for tid in bound {
            self.placement.remove(tid);
        }
        for (id, cpu, mem, gpu, jobs) in snap {
            if let Some(m) = self.machines.get_mut(id) {
                m.cpu_free = *cpu;
                m.mem_free = *mem;
                m.gpu_free = *gpu;
                m.jobs_on_rack = jobs.clone();
            }
        }
    }
}

Request path / sequence

Trade-offs I'd say out loud

Cell size

Larger cells pack better and waste less GPU; smaller cells limit blast radius and scheduler lag.

VM vs container

VMs isolate noisy neighbors and custom kernels; containers pack denser for internal serving.

Preempt vs queue

Preempting batch raises serving utilization; too aggressive and ML jobs never finish.

Live migrate vs reschedule

Migration is kinder to stateful VMs; reschedule is how Borg kept serving jobs simple.

Where it usually breaks

  • One global scheduler — control-plane latency and correlated outages across the fleet.
  • All replicas of a serving job land on one rack because the scorer ignored failure domains.
  • Image pull storm after a popular deploy saturates ToR links.
  • Best-effort overcommit evicts serving tasks under memory spikes (noisy neighbor).
  • Reschedule without fencing — two copies of a stateful task both think they own the disk.
  • Quota only at VM create, not at GPU — one tenant starves the TPU cell.

Follow-ups if time remains

  • How does GKE sit on this fabric vs raw VMs?
  • Design a regional load balancer / Anycast VIP that talks to cell backends.
  • Persistent disk: attach, snapshot, live migrate with the VM.
  • Power and carbon-aware scheduling across buildings.
  • Multi-cell scheduling for jobs that cannot fit in one cell.

What "good enough" looks like in 60 minutes

Split the fleet into regional cells, put a replicated master + scheduler in each, and explain bin packing with rack spread, quota, and preemption. Show repair as fence-then-reschedule. Naming every Google product is optional; getting blast radius and placement right is not.
