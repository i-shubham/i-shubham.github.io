Design a chat messaging system

Chat is websockets plus ordering plus unread math — and group chats with 5,000 members will expose every shortcut.

60-minute agenda

How I'd open the discussion

I'd first clarify whether we are building 1:1 chat, group chat, or both. Group chats change the architecture significantly — a 5,000-member group means every message fans out to 5,000 WebSocket connections. I'd also ask about delivery guarantees: do we need sent/delivered/read receipts, and is at-least-once delivery acceptable or do we need exactly-once?

The core architecture is a WebSocket gateway that maintains persistent connections to clients. When user A sends a message to user B, it hits the gateway, the chat service persists it, and then routes it to B's gateway connection. If B is offline, it is stored and delivered when B reconnects. The tricky parts are message ordering (what happens when two messages cross in transit), presence (knowing who is online without drowning in heartbeats), and unread counts (which need to be accurate across multiple devices).

I'd sketch the gateway layer, message persistence, and then deep-dive into ordering, which is the part most candidates underestimate.

Open questions worth asking

  • 1:1 only, or groups too? What is the max group size?
  • Do we need delivery receipts (sent, delivered, read)?
  • Is message ordering strictly causal or wall-clock?
  • Do we support media messages (images, files)?
  • Multi-device — can a user be online on phone and desktop simultaneously?
  • Do we need message editing and deletion after send?
  • What is the message retention policy?
  • Is end-to-end encryption in scope?
  • Do we need typing indicators?
  • What is the target delivery latency for 1:1 messages?

Scope I'd lock first

  • In: 1:1 and group messaging, message ordering, presence, unread counts.
  • In: offline delivery via push notification, multi-device sync.
  • Out: voice/video calls, E2E encryption implementation, message search.
  • Defer: message reactions, threads/replies, file sharing pipeline.

Approach / design notes

The system has four main components: WebSocket gateways, a chat service, a message store, and a presence service.

WebSocket gateways maintain persistent connections with clients. Each gateway server handles ~100K concurrent connections. When a client connects, the gateway registers the (user_id, gateway_id) mapping in a connection registry (Redis hash). When a message needs to be delivered, the chat service looks up the recipient's gateway in the registry and forwards the message. If the user has multiple devices, they appear as multiple entries in the registry and all receive the message.

The chat service receives a message from the sender's gateway, assigns a Snowflake message_id (which embeds a timestamp for natural ordering), increments the per-conversation sequence number atomically, persists the message to the store, and then routes it to each recipient's gateway. The sender receives an ack with the server_msg_id only after the message is durably stored — this guarantees persistence before acknowledgment.

Message ordering uses per-conversation sequence numbers. Each conversation maintains an atomic counter (in Redis or the database). Every message gets the next sequence number. Clients render messages by seq_no, so even if messages arrive out of order over WebSocket, they display correctly. Gaps in seq_no indicate missing messages, prompting the client to fetch via the REST history API.

For group chats, the chat service fans out the message to all group members. For small groups (< 100), it pushes to each member's gateway connection in parallel. For large groups (> 100 members), it writes the message once to the conversation and each member's client pulls it when they next open the conversation — a hybrid push/pull model similar to the news feed celebrity problem.

Presence is a heartbeat system. Each connected client sends a heartbeat every 30 seconds. The gateway updates a Redis key with a TTL of 60 seconds: if two heartbeats are missed, the user is considered offline. Friends subscribe to presence channels — when a user goes online or offline, a presence event is published to the channel. To avoid thundering herds, presence updates are batched and slightly delayed (2-3 seconds).

Deep dive (spend 15–25 minutes here)

Message ordering is the hardest part of chat. Wall-clock timestamps are unreliable because client clocks differ and even server clocks can drift. I'd use a per-conversation atomic counter to assign sequence numbers. The counter lives in Redis (INCR is atomic and fast). If Redis is unavailable, we fall back to the Snowflake message_id, which embeds a millisecond timestamp — not perfect for causal ordering but good enough as a fallback.

Multi-device sync is where sequence numbers really pay off. When user A opens the desktop app after being on the phone, the desktop client knows its last-seen seq_no for each conversation. It requests messages with seq_no > last_seen. If there are gaps (e.g., the client has seq 40 and 42 but not 41), it explicitly fetches the missing sequence numbers. This makes the protocol resilient to dropped WebSocket frames.

Unread counts are derived, not stored as a separate counter. Each conversation member has a last_read_seq in the membership table. The unread count is max_seq - last_read_seq. When the user opens a conversation, the client sends a 'read' event with the latest seq_no they have seen, and the server updates last_read_seq. This approach avoids the race condition of incrementing/decrementing a shared counter from multiple devices.

Large group chats (1,000+ members) need special handling. Fanning out a message to 5,000 WebSocket connections per message creates a thundering-herd problem. I'd batch the fan-out: the chat service publishes the message to a group channel in Redis Pub/Sub, and only gateway servers with connected group members subscribe to that channel. A gateway with 50 group members on its server sends 50 WebSocket pushes — the fan-out is distributed across gateways rather than centralized in the chat service.

Offline delivery requires integration with push notification services (APNs, FCM). When the chat service cannot find a user in the connection registry, it enqueues a push notification with a 2-second debounce — so rapid-fire messages in a group produce one push with a count rather than 20 individual notifications. The debounce window is configurable per user in notification preferences.

Chat service with delivery routing and unread tracking

import asyncio
from dataclasses import dataclass
from collections import defaultdict


@dataclass
class Message:
    message_id: int
    conv_id: int
    sender_id: int
    content: str
    seq_no: int  # per-conversation monotonic sequence number


class ChatService:
    def __init__(self, msg_store, conn_registry, seq_counter, push_svc):
        self.msg_store = msg_store
        self.conn_registry = conn_registry  # maps user → gateway connections
        self.seq_counter = seq_counter      # atomic per-conversation counter
        self.push_svc = push_svc            # mobile push notification service

    async def send_message(
        self, sender_id: int, conv_id: int, content: str
    ) -> Message:
        # Monotonic sequence guarantees ordering even under clock skew
        seq = await self.seq_counter.incr(f"conv_seq:{conv_id}")
        msg = Message(
            message_id=self._snowflake(),
            conv_id=conv_id,
            sender_id=sender_id,
            content=content,
            seq_no=seq,
        )
        await self.msg_store.insert(msg)
        members = await self.msg_store.get_members(conv_id)
        # Fan-out delivery to all members concurrently
        await asyncio.gather(*[
            self._deliver(msg, uid)
            for uid in members if uid != sender_id
        ])
        return msg

    async def _deliver(self, msg: Message, user_id: int):
        """Route to WebSocket gateways if online, else send push notification."""
        gateways = await self.conn_registry.get_gateways(user_id)
        if gateways:
            for gw in gateways:
                await gw.push(user_id, msg)
        else:
            await self.push_svc.send_notification(
                user_id=user_id,
                title="New message in conversation",
                body=msg.content[:100],
                debounce_ms=2000,
            )

    async def mark_read(self, user_id: int, conv_id: int, up_to_seq: int):
        await self.msg_store.update_last_read(conv_id, user_id, up_to_seq)

    async def get_unread_count(self, user_id: int, conv_id: int) -> int:
        max_seq = await self.seq_counter.get(f"conv_seq:{conv_id}")
        last_read = await self.msg_store.get_last_read(conv_id, user_id)
        return max(0, max_seq - last_read)

    def _snowflake(self) -> int:
        import time
        return int(time.time() * 1000) << 22  # simplified Snowflake ID
use std::collections::HashMap;
use std::sync::{Arc, Mutex};
use std::time::{SystemTime, UNIX_EPOCH};

#[derive(Clone, Debug)]
struct Message {
    message_id: u64,
    conv_id: u64,
    sender_id: u64,
    content: String,
    seq_no: u64,  // per-conversation monotonic sequence
}

/// In-memory chat service demonstrating delivery routing and unread tracking.
/// Production version would use async I/O (tokio) and external stores.
struct ChatService {
    messages: Mutex<Vec<Message>>,
    members: Mutex<HashMap<u64, Vec<u64>>>,   // conv_id → user_ids
    sequences: Mutex<HashMap<u64, u64>>,       // conv_id → seq counter
    last_read: Mutex<HashMap<(u64, u64), u64>>, // (conv, user) → seq
}

impl ChatService {
    fn new() -> Self {
        Self {
            messages: Mutex::new(Vec::new()),
            members: Mutex::new(HashMap::new()),
            sequences: Mutex::new(HashMap::new()),
            last_read: Mutex::new(HashMap::new()),
        }
    }

    fn snowflake_id() -> u64 {
        let ms = SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_millis();
        (ms as u64) << 22 // simplified Snowflake
    }

    fn send_message(&self, sender: u64, conv: u64, content: &str) -> Message {
        let seq = {
            let mut seqs = self.sequences.lock().unwrap();
            let s = seqs.entry(conv).or_insert(0);
            *s += 1;
            *s
        };
        let msg = Message {
            message_id: Self::snowflake_id(),
            conv_id: conv, sender_id: sender,
            content: content.to_string(), seq_no: seq,
        };
        self.messages.lock().unwrap().push(msg.clone());
        // In production: fan-out to WebSocket gateways or push service
        msg
    }

    fn mark_read(&self, user: u64, conv: u64, up_to_seq: u64) {
        self.last_read.lock().unwrap().insert((conv, user), up_to_seq);
    }

    fn unread_count(&self, user: u64, conv: u64) -> u64 {
        let max_seq = *self.sequences.lock().unwrap().get(&conv).unwrap_or(&0);
        let read = *self.last_read.lock().unwrap().get(&(conv, user)).unwrap_or(&0);
        max_seq.saturating_sub(read)
    }
}

#include <unordered_map>
#include <vector>
#include <mutex>
#include <ctime>

// Message value type — plain C++ struct for efficiency
struct ChatMessage {
    uint64_t messageID, convID, senderID, seqNo;
    std::string content;
};

// Chat service with delivery routing and unread tracking
@interface ChatService : NSObject
- (ChatMessage)sendFrom:(uint64_t)sender conv:(uint64_t)conv content:(NSString *)text;
- (void)markReadUser:(uint64_t)user conv:(uint64_t)conv upTo:(uint64_t)seq;
- (uint64_t)unreadCountUser:(uint64_t)user conv:(uint64_t)conv;
@end

@implementation ChatService {
    std::vector<ChatMessage> _messages;
    std::unordered_map<uint64_t, uint64_t> _sequences;              // conv → seq
    std::unordered_map<uint64_t, std::unordered_map<uint64_t, uint64_t>> _lastRead; // conv → {user → seq}
    std::mutex _mu;
}

- (uint64_t)_snowflake {
    // Simplified Snowflake: ms-precision timestamp shifted left
    return (uint64_t)(time(NULL) * 1000) << 22;
}

- (ChatMessage)sendFrom:(uint64_t)sender conv:(uint64_t)conv content:(NSString *)text {
    std::lock_guard<std::mutex> lock(_mu);
    uint64_t seq = ++_sequences[conv]; // monotonic per-conversation counter
    ChatMessage msg{[self _snowflake], conv, sender, seq, text.UTF8String};
    _messages.push_back(msg);
    // Production: fan-out via WebSocket gateways or APNs push
    return msg;
}

- (void)markReadUser:(uint64_t)user conv:(uint64_t)conv upTo:(uint64_t)seq {
    std::lock_guard<std::mutex> lock(_mu);
    _lastRead[conv][user] = seq;
}

- (uint64_t)unreadCountUser:(uint64_t)user conv:(uint64_t)conv {
    std::lock_guard<std::mutex> lock(_mu);
    uint64_t maxSeq = _sequences.count(conv) ? _sequences[conv] : 0;
    uint64_t read = 0;
    if (_lastRead.count(conv) && _lastRead[conv].count(user))
        read = _lastRead[conv][user];
    return maxSeq > read ? maxSeq - read : 0;
}
@end

Request path / sequence

Trade-offs I'd say out loud

WebSocket vs long polling

WS gives real-time push but requires persistent connections; long poll is simpler but higher latency.

Per-conversation seq vs global timestamp

Seq numbers guarantee order within a conversation but need coordination; timestamps are decentralized but imprecise.

Push all vs pull for large groups

Push is real-time but O(members) per message; pull reduces server load but adds latency.

Derived unread vs counter

Derived (max_seq - last_read) is always consistent; a counter can drift under concurrent updates.

Where it usually breaks

  • WebSocket gateway crashes — 100K users lose connections and must reconnect, causing a thundering herd.
  • Sequence counter Redis goes down — messages cannot be ordered, delivery stalls.
  • Large group fan-out overwhelms gateway — 5K WebSocket pushes per message lag the server.
  • Offline user returns with 10K unread messages — initial sync floods the connection.
  • Push notification debounce too aggressive — user misses time-sensitive messages.
  • Multi-device read receipt race — two devices send different last_read_seq, causing inconsistent unread counts.
