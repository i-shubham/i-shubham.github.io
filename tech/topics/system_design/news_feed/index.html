Design a news feed

Feeds are a ranking problem pretending to be a storage problem — until a celebrity posts and your fan-out job melts.

60-minute agenda

How I'd open the discussion

I'd first clarify what kind of feed we are building. A social feed (like Instagram) ranks by affinity and engagement; a news feed (like Twitter) leans toward reverse-chronological with light boosting. The core architectural question is fan-out on write versus fan-out on read — and the answer is almost always a hybrid.

Fan-out on write means when a user posts, we immediately push that post ID into every follower's feed cache. This is great for fast reads but terrible when a celebrity with 50 million followers posts — the fan-out job takes minutes and creates a write storm. Fan-out on read means we compute the feed at request time by merging posts from followed users. Reads are expensive but writes are cheap. The hybrid approach fans out on write for normal users and on read for celebrities.

I'd walk through the post-creation flow, the feed-generation flow, and then drill into the ranking layer that decides which posts surface first. The ranking layer is where the product magic lives, but the infrastructure under it is what keeps it from falling over.

Open questions worth asking

  • Is this a social graph feed (friends) or a follow graph feed (asymmetric)?
  • What is the median and p99 follower count?
  • Do we rank chronologically or by engagement?
  • Are there different content types (text, image, video, link)?
  • Do we need real-time push updates or pull-on-refresh?
  • What is the feed page size and maximum depth?
  • Do we inject ads or sponsored content?
  • Should the feed include reshares/retweets?
  • What is the target feed-load latency?
  • Do we personalize per user or use a global ranking?

Scope I'd lock first

  • In: post creation, fan-out, feed retrieval with basic ranking, celebrity handling.
  • In: feed caching layer, pagination with cursor-based scrolling.
  • Out: ads injection, stories/ephemeral content, video transcoding.
  • Defer: ML-based ranking model training, A/B testing framework.

Approach / design notes

When a normal user (< 500K followers) creates a post, the post service writes it to the posts table and enqueues a fan-out job. The fan-out workers read the poster's follower list and insert the post_id into each follower's feed cache (a Redis sorted set keyed by user_id, scored by timestamp). A follower opening the app does ZREVRANGE on their feed key, fetches the top 20 post IDs, then hydrates them from the post cache. This is the push model — reads are O(1) from cache.

For celebrity accounts (> 500K followers), fan-out on write is prohibitively slow — 10M followers × 1 write = 10M Redis operations per post. Instead, we skip the fan-out. When a user loads their feed, the feed service merges the pre-built feed cache (from push) with a pull query for recent posts from any celebrities the user follows. This hybrid approach bounds fan-out cost while keeping feed latency low for most users.

Ranking happens in two phases. First, a lightweight scorer in the feed service assigns each candidate post a score based on recency, author affinity (how often the user engages with this author), and engagement velocity (likes in the first 30 minutes). This score sorts the merged list. Second, for users where we have enough signal, a server-side ML model re-ranks the top 50 candidates. The ML model is optional at launch — chronological with affinity boosting is a reasonable MVP.

Pagination uses cursor-based scrolling. The cursor is the (score, post_id) of the last item returned. On the next request, the feed service fetches items with scores below the cursor. This avoids the offset-skip problem where inserting new posts shifts pages.

The social graph is stored in a relational table sharded by follower_id so that 'who do I follow' queries are single-shard. The reverse index ('who follows me') is maintained in a separate table or a graph store for fan-out lookups.

Deep dive (spend 15–25 minutes here)

The celebrity threshold is the most nuanced parameter in this system. Set it too low (e.g., 1K followers) and too many users go through the expensive pull path at read time. Set it too high (e.g., 10M) and the fan-out service spends minutes pushing a single post. In practice, I'd start at 500K followers and tune based on fan-out worker queue depth. If the p99 fan-out time exceeds 10 seconds, either lower the threshold or add more workers.

Feed cache eviction is subtle. Each user's feed sorted set is capped at ~500 entries. When a new post is fanned out, we ZADD it and ZREMRANGEBYRANK to trim old entries. But if a user is inactive for weeks, their feed cache is stale. On their return, we detect the staleness (cache timestamp vs now) and trigger a full feed rebuild: pull recent posts from all followed users, rank, and cache the result. This rebuild is expensive (~100 ms) but only happens once per returning user.

Engagement signals for ranking create a feedback loop. Posts that rank higher get more views, which get more likes, which rank them even higher. To avoid this winner-take-all dynamic, I'd inject an exploration factor: randomly boost 5-10% of new posts from less-engaged-with authors into the top positions. This gives the ranking model fresh signal and keeps the feed from becoming an echo chamber.

Consistency matters more than people think. If user A posts and user B (a mutual friend sitting next to them) refreshes and does not see the post, it feels broken even though eventual consistency says it is fine. For mutual friends — users who follow each other — I'd add a 'read-your-writes' guarantee by checking a write-ahead notification channel. For non-mutual follows, a few seconds of delay is invisible.

Delete propagation is the other consistency concern. When a user deletes a post, we need to remove it from potentially millions of feed caches. Immediate removal is impractical. Instead, the feed service checks each post's existence at hydration time — if the post is gone (tombstone or missing), it skips it and backfills from the next candidate. A background cleanup job asynchronously removes deleted post IDs from feed caches over minutes.

Feed fan-out and hybrid merge with ranking

import heapq
from dataclasses import dataclass, field
from time import time

# Users with >= this many followers are "celebrities";
# their posts are pulled on read instead of fanned out on write.
CELEBRITY_THRESHOLD = 500_000


@dataclass(order=True)
class ScoredPost:
    score: float
    post_id: int = field(compare=False)


class FeedService:
    def __init__(self, redis, post_store, graph):
        self.redis = redis
        self.post_store = post_store
        self.graph = graph  # social graph service

    def fan_out(self, author_id: int, post_id: int):
        """Push post into each follower's precomputed feed (write path)."""
        followers = self.graph.get_followers(author_id)
        if len(followers) >= CELEBRITY_THRESHOLD:
            return  # celebrities are handled on the read path
        ts = time()
        pipe = self.redis.pipeline()
        for fid in followers:
            pipe.zadd(f"feed:{fid}", {post_id: ts})
            pipe.zremrangebyrank(f"feed:{fid}", 0, -501)  # cap at 500
        pipe.execute()

    def get_feed(self, user_id: int, limit: int = 20) -> list[int]:
        """Merge pre-computed feed with on-the-fly celebrity pull."""
        cached_ids = self.redis.zrevrange(f"feed:{user_id}", 0, limit * 2)
        celeb_ids = self._pull_celebrity_posts(user_id, limit)
        merged = self._rank_and_merge(cached_ids, celeb_ids, user_id)
        return merged[:limit]

    def _pull_celebrity_posts(self, user_id: int, limit: int) -> list[int]:
        celebs = [
            uid for uid in self.graph.get_following(user_id)
            if self.graph.follower_count(uid) >= CELEBRITY_THRESHOLD
        ]
        posts = []
        for cid in celebs:
            posts.extend(self.post_store.recent_by_author(cid, limit=5))
        return [p.post_id for p in posts]

    def _rank_and_merge(
        self, cached: list, celeb: list, user_id: int
    ) -> list[int]:
        heap: list[ScoredPost] = []
        all_ids = set(cached) | set(celeb)
        for pid in all_ids:
            post = self.post_store.get(pid)
            if post is None:
                continue
            # Time decay: recent posts score higher
            recency = 1.0 / (1 + (time() - post.created_at) / 3600)
            affinity = self.graph.affinity(user_id, post.author_id)
            # Weighted combination: 60% recency, 30% affinity, 10% engagement
            score = 0.6 * recency + 0.3 * affinity + 0.1 * post.engagement
            heapq.heappush(heap, ScoredPost(-score, pid))
        return [heapq.heappop(heap).post_id for _ in range(min(len(heap), 50))]
use std::collections::{BinaryHeap, HashSet};
use std::cmp::Reverse;
use std::time::{SystemTime, UNIX_EPOCH};

const CELEBRITY_THRESHOLD: usize = 500_000;

#[derive(PartialEq)]
struct ScoredPost { score: f64, post_id: u64 }
// Ordered by score so BinaryHeap gives max-score first
impl Eq for ScoredPost {}
impl PartialOrd for ScoredPost {
    fn partial_cmp(&self, o: &Self) -> Option<std::cmp::Ordering> {
        self.score.partial_cmp(&o.score)
    }
}
impl Ord for ScoredPost {
    fn cmp(&self, o: &Self) -> std::cmp::Ordering {
        self.partial_cmp(o).unwrap_or(std::cmp::Ordering::Equal)
    }
}

fn now_secs() -> f64 {
    SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_secs_f64()
}

/// Fan-out on write: push post_id into each follower's sorted feed.
/// Skipped for celebrities (> threshold followers) — they use pull path.
fn fan_out(author_id: u64, post_id: u64, followers: &[u64], is_celeb: bool,
           feed_store: &mut std::collections::HashMap<u64, Vec<(f64, u64)>>) {
    if is_celeb { return; }
    let ts = now_secs();
    for &fid in followers {
        let feed = feed_store.entry(fid).or_default();
        feed.push((ts, post_id));
        feed.sort_by(|a, b| b.0.partial_cmp(&a.0).unwrap());
        feed.truncate(500); // cap feed length
    }
}

/// Rank-and-merge cached + celebrity posts using a weighted score
fn rank_and_merge(cached: &[u64], celeb: &[u64], user_id: u64) -> Vec<u64> {
    let mut seen = HashSet::new();
    let mut heap = BinaryHeap::new();
    let now = now_secs();
    for &pid in cached.iter().chain(celeb.iter()) {
        if !seen.insert(pid) { continue; }
        // In production, fetch post metadata for recency/engagement
        let recency = 1.0 / (1.0 + (now - now) / 3600.0); // placeholder
        let score = 0.6 * recency + 0.3 * 0.5 + 0.1 * 0.5;
        heap.push(ScoredPost { score, post_id: pid });
    }
    let mut result = Vec::new();
    for _ in 0..heap.len().min(50) {
        result.push(heap.pop().unwrap().post_id);
    }
    result
}
#import <Foundation/Foundation.h>
#include <vector>
#include <queue>
#include <unordered_set>
#include <ctime>

static const NSUInteger kCelebrityThreshold = 500000;

struct ScoredPost {
    double score;
    uint64_t postID;
    // Max-heap: higher score = higher priority
    bool operator<(const ScoredPost &o) const { return score < o.score; }
};

// Fan-out on write: push post into followers' feeds.
// Skipped for celebrities — their posts are pulled at read time.
static void fanOut(uint64_t authorID, uint64_t postID,
                   NSArray<NSNumber *> *followers,
                   NSMutableDictionary<NSNumber *, NSMutableArray *> *feeds) {
    if (followers.count >= kCelebrityThreshold) return;
    double ts = (double)time(NULL);
    for (NSNumber *fid in followers) {
        NSMutableArray *feed = feeds[fid] ?: [NSMutableArray new];
        [feed insertObject:@(postID) atIndex:0];
        if (feed.count > 500) [feed removeLastObject]; // cap
        feeds[fid] = feed;
    }
}

// Merge cached + celebrity posts with weighted ranking
static std::vector<uint64_t> rankAndMerge(
        const std::vector<uint64_t> &cached,
        const std::vector<uint64_t> &celeb) {
    std::unordered_set<uint64_t> seen;
    std::priority_queue<ScoredPost> heap;
    double now = (double)time(NULL);
    for (auto *src : {&cached, &celeb}) {
        for (uint64_t pid : *src) {
            if (!seen.insert(pid).second) continue;
            // Weights: 60% recency, 30% affinity, 10% engagement
            double recency = 1.0 / (1.0 + (now - now) / 3600.0);
            double score = 0.6 * recency + 0.3 * 0.5 + 0.1 * 0.5;
            heap.push({score, pid});
        }
    }
    std::vector<uint64_t> result;
    size_t n = std::min(heap.size(), (size_t)50);
    for (size_t i = 0; i < n; ++i) {
        result.push_back(heap.top().postID);
        heap.pop();
    }
    return result;
}

Request path / sequence

Trade-offs I'd say out loud

Fan-out on write vs read

Write gives fast reads but O(followers) write cost; read is cheap writes but expensive reads.

Hybrid threshold

Too low means slow reads for many users; too high means fan-out storms.

Chronological vs ranked

Chrono is simpler and transparent; ranked drives more engagement but risks filter bubbles.

Sorted set vs list in Redis

Sorted set allows score-based ranking but uses 2× memory vs a simple list.

Where it usually breaks

  • Celebrity posts cause fan-out storm — 10M writes flood Redis and lag follower feeds by minutes.
  • Feed cache eviction drops old but still-relevant posts from inactive users.
  • Ranking feedback loop: highly-ranked posts get more engagement, crowding out new content.
  • Social graph partition lag: a follow takes seconds to propagate, causing missing posts.
  • Deleted post still shows in feeds until background cleanup runs.
  • Redis sorted set memory explosion when users follow thousands of active posters.
  • Clock skew across services makes timestamp-based scoring inconsistent.
