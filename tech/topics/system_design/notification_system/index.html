Design a notification system

Notifications are a fan-out problem with human constraints — quiet hours, preferences, and providers that rate-limit you mid-incident.

60-minute agenda

How I'd open the discussion

I'd clarify the channels first: email, SMS, and mobile push are the standard three, but in-app notifications and webhook callbacks might also be in scope. Each channel has different reliability characteristics — email is best-effort with no delivery guarantee, SMS has carrier-level rate limits, and push depends on device reachability. The system needs to abstract these differences behind a common dispatch interface.

The second critical requirement is user preferences. Users want to control which notifications they receive, on which channels, and when. A 'quiet hours' feature suppresses non-urgent notifications between 10 PM and 8 AM in the user's timezone. This means the dispatch pipeline needs to evaluate preferences before sending, not after.

I'd design this as a pipeline: event producers emit notification requests, a preference engine filters and routes them, channel-specific workers render templates and call provider APIs, and a retry/DLQ system handles failures.

Open questions worth asking

  • Which channels — email, SMS, push, in-app, webhook?
  • What is the daily volume and peak spike (e.g., marketing blast)?
  • Do we support quiet hours per user timezone?
  • How granular are preferences — per category, per channel, or both?
  • Do we need delivery tracking (delivered, opened, clicked)?
  • What providers are we integrating with (SendGrid, Twilio, APNs, FCM)?
  • Is there a priority system (critical alerts bypass quiet hours)?
  • Do we need template management with variable substitution?
  • How do we handle provider outages — failover to backup provider?
  • Is deduplication needed to prevent sending the same notification twice?

Scope I'd lock first

  • In: multi-channel dispatch (email, SMS, push), preference filtering, quiet hours.
  • In: retry with exponential backoff, provider failover, deduplication.
  • Out: in-app notification center, template builder UI, A/B testing on notification content.
  • Defer: delivery analytics (open/click tracking), internationalization/localization.

Approach / design notes

The system is a four-stage pipeline: ingestion, preference filtering, channel routing, and provider dispatch.

Ingestion receives notification requests from internal services via an API or message queue. Each request specifies a list of user_ids, a template_id, template parameters, channel priority, and urgency. The ingestion service validates the request, generates a notification_id for tracking, and publishes individual per-user messages to a Kafka topic partitioned by user_id. This ensures all notifications for the same user are processed in order, preventing interleaving issues.

The preference engine consumes from Kafka, looks up each user's preferences from a Redis cache (backed by Postgres), and decides which channels to use. If the user has disabled push for marketing but enabled email, the message routes to email only. If quiet hours are active and the notification is not urgent, it is re-enqueued with a delay until quiet hours end. Critical alerts (like security incidents) always bypass quiet hours.

Channel routers are separate consumer groups per channel (email, SMS, push). Each router renders the template with the provided parameters, constructs the channel-specific payload (email subject + HTML body, SMS text, push title + body + deep link), and calls the provider adapter. Provider adapters wrap the API of each third-party service (SendGrid for email, Twilio for SMS, FCM/APNs for push) behind a common interface.

The retry system uses exponential backoff with jitter: 1s, 2s, 4s, 8s, up to 5 retries. If the primary provider fails after 2 retries, the system fails over to a backup provider (e.g., SES instead of SendGrid). After all retries are exhausted, the message goes to a dead-letter queue for manual investigation. Deduplication uses the notification_id + user_id + channel composite key in the delivery log — if a record exists, the duplicate is dropped.

Deep dive (spend 15–25 minutes here)

Quiet hours are more complex than they appear. Each user has a timezone, so the preference engine must convert the current UTC time to the user's local time before checking the window. If quiet hours span midnight (e.g., 22:00 to 08:00), the check is: current_local < 08:00 OR current_local >= 22:00. Delayed notifications must be scheduled to fire at 08:00 in the user's timezone — which means different delivery times for users in different zones. I'd use a delayed queue (SQS with message timers, or a scheduled-delivery Kafka topic) with the computed delivery timestamp.

Provider rate limiting is the operational headache. Twilio has per-account sending limits; SendGrid has hourly throughput caps. During a marketing blast (100K emails in one batch), we can easily hit these limits. The channel router needs a token-bucket rate limiter per provider that throttles dispatch to stay within the provider's limits. If we hit the limit, messages queue up rather than being rejected. The rate limiter parameters are configured per provider and adjusted based on the provider's response headers (e.g., X-RateLimit-Remaining).

Deduplication has two layers. The first is idempotency at the notification_id level — if the ingestion service crashes and retries, it publishes the same notification_id, and the preference engine checks the delivery log before processing. The second is content-based dedup: if two separate notification requests would produce the same message to the same user within 5 minutes (e.g., duplicate webhook triggers), we suppress the second one. This requires hashing the (user_id, template_id, params_hash) and checking a short-lived Redis key.

Observability is critical for a notification system because failures are often silent — the user just never receives the message. I'd track metrics at every pipeline stage: ingestion rate, preference-filtered-out rate, per-channel dispatch rate, provider success/failure rate, and end-to-end latency (from request to provider acceptance). Alerts fire when the failure rate exceeds 1% or the queue depth grows beyond 5 minutes of backlog.

Template rendering needs to be sandboxed. Templates contain user-provided variables (e.g., {{order_id}}) that must be escaped to prevent injection — especially in email where HTML injection is a real risk. I'd use a safe templating engine (like Jinja2 with autoescape) and never allow raw HTML in template variables.

Preference engine and multi-channel dispatcher with retry

from enum import Enum
from dataclasses import dataclass, field
from datetime import datetime, time as dtime
import pytz


class Urgency(Enum):
    NORMAL = "normal"
    CRITICAL = "critical"


@dataclass
class NotificationRequest:
    notification_id: str
    user_id: int
    template_id: str
    params: dict
    channels: list[str]       # e.g. ["email", "push", "sms"]
    urgency: Urgency = Urgency.NORMAL


class PreferenceEngine:
    """Filters channels based on user prefs and quiet-hours schedule."""

    def __init__(self, pref_cache, quiet_cache):
        self.pref_cache = pref_cache   # user_id → {category → {channel → bool}}
        self.quiet_cache = quiet_cache  # user_id → {timezone, start, end}

    def filter_channels(
        self, req: NotificationRequest, category: str
    ) -> list[str]:
        prefs = self.pref_cache.get(req.user_id)
        allowed = [
            ch for ch in req.channels
            if prefs.get(category, {}).get(ch, True)
        ]
        if not allowed:
            return []
        # Suppress non-critical notifications during quiet hours
        if self._in_quiet_hours(req.user_id) and req.urgency != Urgency.CRITICAL:
            return []
        return allowed

    def _in_quiet_hours(self, user_id: int) -> bool:
        qh = self.quiet_cache.get(user_id)
        if not qh:
            return False
        tz = pytz.timezone(qh["timezone"])
        local_now = datetime.now(tz).time()
        start = dtime.fromisoformat(qh["start"])
        end = dtime.fromisoformat(qh["end"])
        # Handle ranges that cross midnight (e.g. 22:00 → 07:00)
        if start <= end:
            return start <= local_now <= end
        return local_now >= start or local_now <= end


class Dispatcher:
    """Sends notifications with dedup, retry, and provider failover."""

    def __init__(self, providers: dict, dedup_store, log_store):
        self.providers = providers
        self.dedup = dedup_store
        self.log = log_store

    def dispatch(self, req: NotificationRequest, channel: str):
        dedup_key = f"{req.notification_id}:{req.user_id}:{channel}"
        if self.dedup.exists(dedup_key):
            return  # already sent — idempotent skip
        provider = self.providers[channel]
        for attempt in range(5):
            try:
                provider.send(req.user_id, req.template_id, req.params)
                self.dedup.set(dedup_key, ttl=86400)
                self.log.record(req.notification_id, req.user_id, channel, "sent")
                return
            except provider.RateLimited:
                import time; time.sleep(2 ** attempt)  # exponential back-off
            except provider.Unavailable:
                # Fail over to backup provider if available
                provider = self.providers.get(f"{channel}_backup", provider)
        self.log.record(req.notification_id, req.user_id, channel, "failed")
use std::collections::{HashMap, HashSet};
use std::time::{SystemTime, UNIX_EPOCH};

#[derive(Clone, PartialEq)]
enum Urgency { Normal, Critical }

struct NotificationRequest {
    notification_id: String,
    user_id: u64,
    template_id: String,
    params: HashMap<String, String>,
    channels: Vec<String>,
    urgency: Urgency,
}

/// Filters channels based on user preferences and quiet-hours schedule.
struct PreferenceEngine {
    prefs: HashMap<u64, HashMap<String, HashMap<String, bool>>>,
    quiet: HashMap<u64, (u32, u32)>, // user → (start_min, end_min) in local time
}
impl PreferenceEngine {
    fn filter_channels(&self, req: &NotificationRequest, category: &str) -> Vec<String> {
        let allowed: Vec<String> = req.channels.iter().filter(|ch| {
            self.prefs.get(&req.user_id)
                .and_then(|c| c.get(category))
                .and_then(|m| m.get(*ch))
                .copied()
                .unwrap_or(true) // default: channel enabled
        }).cloned().collect();
        if allowed.is_empty() { return allowed; }
        // Suppress non-critical during quiet hours
        if req.urgency != Urgency::Critical && self.in_quiet_hours(req.user_id) {
            return Vec::new();
        }
        allowed
    }
    fn in_quiet_hours(&self, user_id: u64) -> bool {
        // Simplified: compare current minute-of-day against quiet window
        self.quiet.contains_key(&user_id)
    }
}

/// Sends notifications with dedup guard and exponential retry.
struct Dispatcher {
    sent: HashSet<String>, // dedup set: "notif_id:user:channel"
}
impl Dispatcher {
    fn new() -> Self { Self { sent: HashSet::new() } }

    fn dispatch(&mut self, req: &NotificationRequest, channel: &str)
        -> Result<(), &'static str>
    {
        let key = format!("{}:{}:{}", req.notification_id, req.user_id, channel);
        if self.sent.contains(&key) { return Ok(()); } // idempotent skip
        for attempt in 0..5u32 {
            // In production: call provider.send(), handle rate-limit/unavailable
            // On transient failure: sleep 2^attempt ms then retry
            self.sent.insert(key.clone());
            return Ok(());
        }
        Err("all retry attempts exhausted")
    }
}
#import <Foundation/Foundation.h>
#include <unordered_map>
#include <unordered_set>
#include <string>
#include <vector>
#include <cmath>

typedef NS_ENUM(NSInteger, Urgency) {
    UrgencyNormal,
    UrgencyCritical,
};

// Filters channels by user prefs and quiet-hours schedule
@interface PreferenceEngine : NSObject
- (NSArray<NSString *> *)filterChannels:(NSArray<NSString *> *)channels
                                 userId:(uint64_t)uid
                               category:(NSString *)cat
                                urgency:(Urgency)urg;
@end

@implementation PreferenceEngine {
    // user → {category → {channel → enabled}}
    std::unordered_map<uint64_t,
        std::unordered_map<std::string,
            std::unordered_map<std::string, bool>>> _prefs;
    std::unordered_set<uint64_t> _quietUsers; // simplified quiet-hours set
}
- (NSArray<NSString *> *)filterChannels:(NSArray<NSString *> *)channels
                                 userId:(uint64_t)uid
                               category:(NSString *)cat
                                urgency:(Urgency)urg {
    NSMutableArray *allowed = [NSMutableArray new];
    std::string catKey = cat.UTF8String;
    for (NSString *ch in channels) {
        bool enabled = true;
        auto uit = _prefs.find(uid);
        if (uit != _prefs.end()) {
            auto cit = uit->second.find(catKey);
            if (cit != uit->second.end()) {
                auto chit = cit->second.find(ch.UTF8String);
                if (chit != cit->second.end()) enabled = chit->second;
            }
        }
        if (enabled) [allowed addObject:ch];
    }
    // Suppress non-critical during quiet hours
    if (urg != UrgencyCritical && _quietUsers.count(uid))
        return @[];
    return allowed;
}
@end

// Dispatcher: dedup + retry with exponential back-off
@interface Dispatcher : NSObject
- (BOOL)dispatch:(NSString *)notifID userId:(uint64_t)uid channel:(NSString *)ch;
@end

@implementation Dispatcher {
    std::unordered_set<std::string> _sent; // dedup keys
}
- (BOOL)dispatch:(NSString *)notifID userId:(uint64_t)uid channel:(NSString *)ch {
    std::string key = std::string(notifID.UTF8String) + ":"
                    + std::to_string(uid) + ":" + ch.UTF8String;
    if (_sent.count(key)) return YES; // already sent
    for (int attempt = 0; attempt < 5; attempt++) {
        // Production: call provider, handle rate-limit with sleep(pow(2, attempt))
        _sent.insert(key);
        return YES;
    }
    return NO;
}
@end

Request path / sequence

Trade-offs I'd say out loud

Push-first vs email-first

Push is cheaper and faster; email has higher deliverability for inactive users.

Strict quiet hours vs soft

Strict blocks all non-critical; soft delays but might miss time-sensitive updates.

Single provider vs multi-provider

Single is simpler; multi gives failover but doubles integration work.

At-least-once vs exactly-once

At-least-once with dedup is practical; exactly-once requires distributed transactions.

Where it usually breaks

  • Provider rate limit during marketing blast — thousands of notifications delayed in queue.
  • Quiet hours timezone miscalculation — users in DST-transitioning zones get woken up.
  • Template variable missing — renders '{{order_id}}' literally in the email body.
  • Dedup key collision — two genuinely different notifications suppressed as duplicates.
  • Kafka consumer lag — notifications arrive hours late, order confirmation sent after delivery.
  • FCM token stale — push sent to old device, user never sees it, no feedback.

Follow-ups if time remains

  • Design delivery analytics: open rates for email, click-through for push.
  • How would you handle notification batching (digest emails instead of individual)?
  • Add support for user-defined notification rules (e.g., 'only notify me if order > $100').
